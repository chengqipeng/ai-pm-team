aPaaS 与 Agent 平台边界

Agent 平台三大独立维度（Agent 框架 · 知识库 · 提示词模板） × aPaaS 平台职责划分

一、核心定位：一句话说清楚

Agent 平台（NeoAgent）
三大独立维度协同的智能中台：Agent 框架（Tool/Plugin/Skill/记忆/反思）+ 知识库（管理/检索/业务线通用接入）+ 提示词模板（平台/开发者/流程智能）。
底层由 大模型网关平台（国内/国际模型统一接入）与 基础原子能力平台（文档解析/OCR/ASR/向量库）共同支撑。

本质：智能决策层 — 决定做什么、怎么做
aPaaS 平台（NeoPlatform）
元数据驱动的业务平台，提供业务对象建模、数据 CRUD、校验规则、工作流、权限控制。

本质：业务执行层 — 保证做得对、做得安全
关键关系：Agent 是 aPaaS 的"智能调用者"，不是"替代者"。Agent 通过 Tool 调用 aPaaS 的 API（包括 XOQL），aPaaS 的校验规则、权限、流程是硬约束，Agent 不能绕过。

三、Agent 平台的职责边界（三大独立维度）

Agent 平台对外呈现三个相互独立、可单独产品化运营的维度，三者共享推理引擎、上下文工程、安全层等底层支撑能力：

维度一 · Agent 框架
智能体核心引擎，围绕任务执行闭环组织能力
  • Tool · 原子操作
  • Plugin · 可插拔基础设施
  • Skill · 多步 SOP 编排
  • MCP · 外部工具/数据源接入
  • 记忆 · 长期/短期/向量 · 遗忘
  • 反思 · 执行评估与自我优化
维度二 · 知识库
企业级知识中台，面向 AI 与各业务线统一赋能
  • 知识库管理 · 入库/切片/向量化
  • 知识检索 · Agentic 检索 + 混合搜索
  • 业务线通用接入能力 · 客户问答 / 关联文档摘要
维度三 · 提示词模板
Prompt 中台，跨平台、开发者平台、流程智能复用
  • 平台场景 · System Prompt / 角色人设 / 输出格式
  • 开发者平台 · 自定义 Prompt / SDK / 脚本注入
  • 流程智能业务 · 工作流 / 自动流 / 业务模板

维度一：Agent 框架（智能体核心引擎）

模块定位举例与 aPaaS 的关系
Tool
LLM 的手		 一次原子操作，LLM 通过 function calling 调用 query_data / modify_data / analyze_data / query_schema / web_search / search_memories 部分封装 aPaaS API（query_data → paas-entity-service），部分完全独立（web_search）
Plugin
系统器官		 可插拔基础设施，有生命周期、有配置 llm-plugin / memory-plugin / search-plugin / document-parse-plugin / image-gen-plugin 完全独立于 aPaaS，Agent 内部消费
Skill
Agent 的 SOP		 多步业务流程编排，有判断有分支 diagnose / data_analysis / batch_data / competitive_analysis / config_entity 内部编排多个 Tool，部分 Tool 会调用 aPaaS API
MCP
外部协议接入		 标准化接入外部工具、数据源、服务能力 第三方 SaaS 工具 / 远程数据源 / 行业标准服务 / 企业内部系统 独立于 aPaaS，扩展 Agent 的可用工具集与数据源边界
记忆（Memory）
认知沉淀		 长期/短期/向量记忆统一存取 + 记忆遗忘机制 profile / preferences / agent_rules / entities / 会话短期记忆 / 过期衰减 / 冲突覆盖 / 主动遗忘 记忆是"认知"，与 aPaaS 的"事实数据"冲突时以 aPaaS 为准
反思（Reflection）
自我优化		 执行结果评估、错误识别、策略调整 Skill 执行后反思、Tool 失败重试判断、Plan 动态调整 独立于 aPaaS，仅消费 Tool 返回的 aPaaS 错误信息做决策修正

维度二：知识库（企业级知识中台）

模块定位典型能力服务对象
知识库管理
内容治理		 文档全生命周期管理 多源导入 / 文档解析 / 分段切片 / 向量化 / 版本与权限治理 / 增量更新 AI（RAG 底座）+ 业务线（文档管理 / OpenAPI）
知识检索
检索服务		 混合检索 + Agentic 多轮改写 BM25 / 向量召回 / 重排 / 查询改写 / 多轮检索评估 / 引用溯源 AI（Agent RAG）+ 业务线（搜索 API）
业务线通用接入能力
业务输出		 向各业务线开放标准化的知识消费能力 客户问答（企业内/对外 QA） / 关联文档摘要（基于业务对象聚合相关文档） / 知识卡片嵌入 / OpenAPI 对接 aPaaS 业务页面、CRM 业务线、第三方系统
关键设计：知识库不是 Agent 的附属模块，而是独立可产品化的企业级中台。它既为 Agent 提供 RAG 底座，也通过 OpenAPI/SDK 向各业务线输出客户问答、关联文档摘要等标准化接入能力。

维度三：提示词模板（Prompt 中台）

应用场景定位典型模板对接方式
平台场景
Agent 内部		 支撑 Agent 自身的对话与技能 System Prompt / 角色人设 / 输出格式约束 / 安全指令 Agent 内部加载，版本化管理
开发者平台
外部调用		 供开发者自定义调用 LLM 能力 自定义 Prompt 模板 / 工作流节点 Prompt / 自动流触发模板 / 审批建议模板 SDK / API
流程智能业务
流程节点		 嵌入 aPaaS 工作流、自动流做智能节点 自定义 Prompt 模板 / 工作流节点 Prompt / 自动流触发模板 / 审批建议模板 SDK / API
关键设计：提示词模板是统一的 Prompt 中台，同一个模板注册中心同时支撑三类场景。平台场景面向 Agent 自身，开发者平台面向二开用户，流程智能业务面向 aPaaS 流程节点，避免 Prompt 能力在多处重复建设。

三大维度共享的底层能力

  • 推理引擎 — 意图理解、任务规划、XOQL 生成等 LLM 推理链路
  • 上下文工程 — 管理 LLM 上下文窗口，四层压缩与摘要
  • 业务语义层 — aPaaS 元数据的自然语言语义描述，让 LLM 理解业务对象
  • 多模态处理 — 图片/文档/语音的理解与生成
  • 安全审查 — PII 掩码、Prompt 注入防护、输出验证、内容审查
  • HITL 风险识别 — 判断操作是否危险，决定是否暂停等待人工审批
  • AG-UI / A2UI 协议 — 与前端的流式交互和动态组件渲染
  • Multi-Agent — 子 Agent 委派与多 Agent 协作

资源点扣费层（Resource Credit Metering）

位于支撑能力层与基础设施平台之间，对所有下行调用（LLM 推理、文档解析、OCR、ASR、向量检索等）进行统一计量与扣费，实现 AI 能力的商业化闭环。

模块定位核心能力说明
用量计量
实时采集		 精确记录每次底层能力调用的资源消耗 Token 数（输入/输出分计）/ API 调用次数 / 文档解析页数 / 音频转写时长 / 向量检索次数 / 图片生成张数 所有经过大模型网关和基础原子能力平台的调用均被计量，无遗漏
资源点兑换
统一货币		 将异构资源消耗折算为统一的"资源点" 多能力统一折算规则（如 1K Token = X 资源点，1 页 PDF 解析 = Y 资源点）/ 不同模型差异化定价 / 动态调价能力 屏蔽底层能力的计费差异，上层只感知"资源点"一种货币
配额管控
三级管控		 租户 / 应用 / 用户三级配额体系 租户总额度分配 / 应用级配额隔离 / 用户级日/月限额 / 阈值预警通知 / 超额策略（拒绝/降级/审批） 防止单一租户/应用/用户过度消耗资源，保障平台整体可用性
账单中心
可视化		 资源消耗的全链路可视化与分析 实时余额查询 / 消费明细（按时间/应用/能力/用户维度）/ 趋势分析 / 账单导出 / 成本归因 支撑运营决策与客户自助查询
扣费拦截
前置卡控		 调用前校验余额，余额不足时执行降级或拒绝策略 余额预检 / 不足时拒绝并返回友好提示 / 降级策略（切换低成本模型）/ 欠费通知 / 充值引导 作为中间件嵌入调用链路，在请求到达底层平台前完成扣费判断
关键设计：资源点扣费层是支撑能力层与基础设施平台之间的"计费网关"。所有从上层（Agent 框架 / 知识库 / 提示词模板）发起的底层能力调用，必须经过此层完成余额校验 → 资源点预扣 → 实际调用 → 用量结算的完整闭环。这一层的存在使得 AI 能力的商业化计费与技术实现完全解耦。

四、两大平台职责与边界

NeoAgent 与 aPaaS 围绕"智能决策 vs 业务执行"主轴分工协作。Agent 决定"做什么、怎么做"，aPaaS 保证"做得对、做得安全"。两者通过 API / XOQL / 事件总线 / HITL 协议解耦协作。

五、未来新业务的边界定义

一句话原则：通用 AI 原子能力由 Agent 平台 负责，具体业务场景由 业务侧 实现；业务侧不自建 AI 原子能力，Agent 平台不替业务做场景。
📌 中间还有两类"可沉淀到 Agent 平台"的能力：① 通用业务实现（如百事通、知识库问答——直接交付完整产品）；② 通用场景智能组件 + 业务语义（如智能填充、智能推荐——业务侧声明即用）。平台和业务线自己的个性化 AI 场景（如元数据自动翻译、销售预测、合同审阅）归为"具体业务场景（落地）"，由各自业务团队基于上层组件实现。

5.1 归属规则

新业务类型归属边界说明
① 底层原子 AI 能力
新模型、文档解析、ASR/OCR、向量库、生图等		 Agent 平台 由"大模型网关 + 基础原子能力平台"统一提供；业务侧禁止自接 SDK、禁止自建同类能力
② 可复用的 AI 能力封装
通用 Skill/Tool、行业知识包、平台级提示词模板、MCP 适配		 Agent 平台 能被 ≥2 个业务场景复用的才沉淀到 Agent 三大维度（框架 / 知识库 / 提示词），不复用的不沉淀
③ 通用业务实现
百事通查询、知识库问答、通用分析助手、智能搜索等		 Agent 平台 业务形态稳定、跨业务线可复用的"AI 应用标品"；业务侧不重复实现，按需订阅/嵌入；数据源与权限接各租户自己的
④ 通用场景智能组件 + 业务语义
智能填充组件、智能推荐组件、业务语义理解层等（跨业务线可复用的智能零件）		 Agent 平台 把"某类智能场景的通用模式 + 对应业务语义"抽象为组件，业务侧声明即用（只填业务配置/上下文），不用重复造组件
⑤(a) 平台个性化业务实现
aPaaS 平台自身各模块的个性化 AI 场景（元数据、工作流、权限等）		 平台模块团队实现 只服务平台自身某模块的个性化 AI 场景（如元数据模块的自动翻译、Schema 变更影响分析）；由对应模块团队基于上层组件 + aPaaS 落地，不实现 AI 逻辑
⑤(b) 业务线个性化业务实现
各业务线（销售、服务、营销等）独有的 AI 场景		 业务线团队实现 只服务某一业务线、强业务语义不通用的 AI 场景（如销售预测、合同条款审阅、工单智能审阅）；由业务线团队基于上层组件 + aPaaS 落地，不实现 AI 逻辑
③ 与 ④ 与 ⑤ 的区别：
  • ③ 通用业务实现：独立的 AI 应用，用户直接打开使用（例如百事通聊天窗）；Agent 平台交付完整产品。
  • ④ 通用场景智能组件：跨业务线可复用的智能零件（如字段填充、智能推荐）；业务侧在 aPaaS 元数据/流程里声明使用即触发。
  • ⑤(a) 平台个性化：只服务 aPaaS 自身模块的个性化 AI 场景（如元数据自动翻译），由平台模块团队自己落地。
  • ⑤(b) 业务线个性化：只服务某一业务线的 AI 场景（如销售预测、合同审阅），由业务线团队自己落地。
边界铁律：Agent 不直连 aPaaS 数据库；业务数据一律经 aPaaS API / XOQL；模型调用一律经大模型网关；原子能力（OCR/ASR/解析/向量）一律经基础原子能力平台；所有底层能力调用一律经资源点扣费层计量；破坏性操作一律 HITL。
