# 验证场景 2: 修复技能工具调用错误

> 模拟 update_skill 处理"技能执行报错"的修复请求，验证最小化修改原则。

---

## 用户输入

```
"商机赢率评估技能报错了，说 entity_api_key 'opportunities' 不存在，应该是 'opportunity'"
```

---

## 预期执行流程

### Step 1: 加载现有技能定义

```
manage_skill(action="list")
→ 找到 opportunity_win_rate 技能

query_data(entity_api_key="ai_skill", filters={api_key: "opportunity_win_rate"})
→ 获取完整定义，发现 Prompt 中有:
  query_data(entity_api_key="opportunities", ...)  ← 错误！应为 "opportunity"
```

### Step 2: 理解更新意图

```
判断结果：
- 更新场景: A（修复问题）
- 修改范围: 仅 Prompt 中的 entity_api_key 拼写
- 修改原因: entity_api_key 拼写错误导致查询失败
- 影响评估: 最小修改，不影响其他逻辑
```

### Step 3: 设计修改方案

**最小化修改原则：**
- 只修改 Prompt 中所有 `entity_api_key="opportunities"` → `entity_api_key="opportunity"`
- 不动其他任何逻辑

**验证修复正确性：**
```
query_schema(query_type="list_entities")
→ 确认 "opportunity" 存在于系统中
```

### Step 5: 生成修改后的定义

```json
{
  "api_key": "opportunity_win_rate",
  "prompt": "（仅修改了 entity_api_key 拼写，其余完全不变）"
}
```

### Step 7: 变更对比

```
## 技能更新方案

**目标技能**: opportunity_win_rate — 商机赢率评估
**更新类型**: 场景 A（修复问题）
**更新原因**: entity_api_key 拼写错误导致查询失败

### 变更摘要

| 字段 | 修改前 | 修改后 |
|------|--------|--------|
| prompt | ...entity_api_key="opportunities"... | ...entity_api_key="opportunity"... |

### Prompt 变更说明
- 修改: 将所有 `entity_api_key="opportunities"` 修正为 `entity_api_key="opportunity"`
- 影响位置: 步骤 1.1、步骤 1.5、步骤 5.2（共 3 处）

### 影响评估
- 向后兼容: ✅（arguments 未变）
- 风险等级: 低（修复拼写错误，逻辑不变）
```

### Step 8: 执行更新

```
manage_skill(
  action="update",
  api_key="opportunity_win_rate",
  skill_definition={...修复后的完整定义...}
)
```

### Step 9: 建议验证

```
ask_user(
  interrupt_type="confirm",
  title="是否需要测试验证？",
  message="技能已修复。是否需要用一个商机 ID 测试一下？"
)
```

---

## 质量自检

| 检查项 | 结果 |
|--------|------|
| 最小化修改？ | ✅ 仅修改了拼写错误，未动其他逻辑 |
| 修复是否正确？ | ✅ query_schema 确认 "opportunity" 存在 |
| 是否引入新问题？ | ✅ 无（仅拼写修正） |
| api_key 保持不变？ | ✅ opportunity_win_rate |
| arguments 未变？ | ✅ |

---

## 关键验证点

此场景验证 update_skill 的**最小化修改原则**：
1. 不会因为修复一个拼写错误而顺便重构整个 Prompt
2. 不会在修复过程中添加用户没有要求的新功能
3. 变更对比清晰展示了"只改了什么"
4. 修复前通过 query_schema 验证了正确值
