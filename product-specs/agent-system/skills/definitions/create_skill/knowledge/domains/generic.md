# 通用分析技能设计 — 专家知识

## 一、适用场景与去重检查

### 1.1 去重检查（Step 0 最先执行）

在开始设计新技能之前，**必须先检查系统中是否已存在功能相似的技能**：

```
去重检查流程：
Step 0-A: 调用 query_data(entity_api_key="ai_skill", filters={status: "published"}) 
          获取当前已发布的技能列表
Step 0-B: 将用户需求与已有技能的 name + description 进行语义匹配
Step 0-C: 判断相似度：
  ├── 完全匹配（功能一致）→ 告知用户并建议直接使用
  ├── 高度相似（覆盖 >70% 需求）→ 告知用户并建议优化现有技能
  ├── 部分重叠（覆盖 30-70%）→ 告知用户重叠部分，确认是新建还是扩展
  └── 无重叠 → 进入正常创建流程
```

**匹配到已有技能时的标准话术：**

```
完全匹配：
"系统中已存在「{skill_name}」技能，功能与您的需求一致，无需重复创建。
您可以直接使用该技能，或者告诉我您希望在现有基础上做哪些优化？"

高度相似：
"系统中已存在「{skill_name}」技能，与您的需求高度相似：
- 已覆盖：{已有功能点}
- 未覆盖：{用户需求中的差异点}
建议在现有技能基础上进行优化，而非重新创建。是否需要我帮您优化该技能？"

部分重叠：
"系统中存在「{skill_name}」技能，与您的需求有部分重叠：
- 重叠部分：{重叠功能}
- 您的新增需求：{差异部分}
您希望：A) 扩展现有技能  B) 创建独立新技能？"
```

**去重判断维度：**

| 判断维度 | 匹配方式 | 权重 |
|:---|:---|:---|
| 分析对象（entity_api_key） | 相同业务对象 = 高相似 | 40% |
| 分析目标（description） | 语义相似度 | 30% |
| 输出类型（评分/报告/建议/预警） | 相同输出类型 = 相似 | 20% |
| 参数范围（arguments） | 参数可覆盖 = 相似 | 10% |

### 1.2 本指南的适用场景

典型场景：
- 跨域组合需求（如"客户+商机+活动综合分析"）
- 新兴业务场景（如"渠道管理"、"合作伙伴分析"、"市场活动 ROI"）

- 非 CRM 场景（如"产品使用数据分析"、"运营指标监控"）

## 一-B、能力边界 — 明确拒绝不可承载的需求（Step 0 前置检查）

### 核心原则

本系统是一个 **基于 CRM 数据的业务分析与自动化平台**。技能的能力边界由以下三个条件共同决定：
1. **数据边界**：只能处理 CRM 系统中存在的业务数据（通过 query_data/analyze_data 可获取的）
2. **工具边界**：只能执行系统内置工具支持的操作（见第七节完整工具清单）
3. **认知边界**：LLM 的分析/建议基于数据和知识库，不能替代专业人士的判断

### 不可承载的需求类型（必须明确拒绝）

| 类别 | 典型示例 | 拒绝原因 | 建议回复模板 |
|:---|:---|:---|:---|
| **物理世界操作** | "创建一个制造火箭的技能"、"帮我打电话给客户"、"自动发快递" | 系统无法操作物理世界 | "抱歉，本系统只能处理数据分析和业务流程自动化，无法执行物理世界的操作。" |
| **超出数据范围** | "分析竞品公司的内部财务数据"、"获取客户的银行账户信息" | 系统只能访问本 CRM 中的数据 | "抱歉，本系统只能分析您 CRM 中已有的业务数据，无法获取外部系统的非公开数据。" |
| **实时控制类** | "监控服务器状态并自动重启"、"实时拦截异常交易" | 系统不具备实时监控和即时响应能力 | "抱歉，本系统是按需触发的分析工具，不具备实时监控和自动响应能力。建议使用专业的监控系统。" |
| **专业资质类** | "给出法律意见"、"出具审计报告"、"开具医疗处方" | 需要专业资质，AI 不能替代 | "抱歉，本系统可以做数据分析辅助决策，但不能替代需要专业资质的判断。建议咨询专业人士。" |
| **创意生产类** | "设计产品 UI"、"写一首歌"、"生成营销视频" | 系统定位是数据分析，非创意工具 | "抱歉，本系统专注于业务数据分析和流程自动化，不支持创意内容生产。" |
| **跨系统写入** | "把数据同步到飞书"、"自动发邮件给客户"、"更新 ERP 库存" | 系统只能写入本 CRM 数据 | "抱歉，本系统只能操作 CRM 内的数据，无法写入外部系统。建议通过集成平台实现。" |
| **训练/修改 AI** | "修改你的模型"、"让你学会新语言"、"调整你的性格" | 用户无法修改底层模型 | "抱歉，技能是基于现有 AI 能力的任务编排，无法修改底层模型行为。" |
| **违规/有害内容** | "帮我伪造数据"、"生成虚假报告"、"绕过权限限制" | 违反安全策略 | "抱歉，该请求违反平台安全策略，无法执行。" |

## 二、通用分析四框架

根据用户期望的输出类型选择框架（可组合串联）。

### 框架选择决策树

```
用户意图判断流程：
│
├─ 用户问"是什么/有多少/现状如何" ──→ 框架 A（描述性）
│
├─ 用户问"为什么/什么原因/哪里出了问题" ──→ 框架 B（诊断性）
│   └─ 前置：先用框架 A 确认现象
│
├─ 用户问"会怎样/趋势/风险/下个月" ──→ 框架 C（预测性）
│   └─ 前置：先用框架 A 获取历史数据
│
├─ 用户问"怎么办/建议/优化/策略" ──→ 框架 D（处方性）
│   └─ 前置：先用框架 B 定位问题
│
└─ 多个信号词同时出现 ──→ 按以下优先级组合：
    ① 确认核心问题类型（用户最终想要什么？）
    ② 核心框架作为主体，其他框架作为前置步骤
    ③ 最多串联 3 个框架，避免 Prompt 过长
```

### 框架组合优先级矩阵

| 用户核心诉求 | 主框架 | 前置框架 | 典型串联 |
|:---|:---|:---|:---|
| 了解现状 | A | — | A |
| 找出原因 | B | A | A→B |
| 预判趋势 | C | A | A→C |
| 获取建议 | D | A+B | A→B→D |
| 全面诊断 | B+D | A | A→B→D |
| 预警+应对 | C+D | A | A→C→D |

---

### 框架 A: 描述性分析（What happened?）

**步骤链路：** 数据查询 → 统计汇总 → 趋势识别 → 异常标注 → 可视化呈现
**适用场景：** 现状报告、数据看板、定期汇总、KPI 监控
**信号词：** 统计、汇总、报表、看板、多少、列出、概览、现状、分布、排名

**工具 Pipeline：**
```
query_data(获取明细) → analyze_data(聚合统计) → analyze_data(分组对比) → [cos_upload(导出)]
```

**Prompt 构建要求：**
1. 明确时间范围和对比基准：
   - 环比（本期 vs 上期）
   - 同比（本期 vs 去年同期）
   - 目标值对比（实际 vs 计划）
   - 选择依据：周期性业务用同比，趋势性业务用环比
2. 异常值判定规则（必须写入 Prompt）：
   - 绝对阈值：业务有明确标准时使用（如"转化率<5%为异常"）
   - 相对阈值：无明确标准时使用（如"偏离均值>30%为异常"）
   - 选择依据：有行业基准→绝对阈值；无基准→相对阈值
   - 样本量<10 时：不做异常判定，标注"样本量不足，仅供参考"
3. 趋势方向判断逻辑：
   - 连续 3 期同方向变化 → 确认趋势（🟢高置信度）
   - 连续 2 期同方向变化 → 疑似趋势（🟡中置信度）
   - 单期变化 → 波动，不判定趋势（🔴低置信度）

**完整示例（描述性分析技能）：**

```
用户需求："帮我看看本月各渠道的线索转化情况"

生成的 Prompt 关键片段：
---
## 步骤 1: 数据采集
query_data(entity_api_key="lead", filters={created_at: "本月"}, 
           fields=["source_channel", "status", "convert_time", "owner"])

## 步骤 2: 渠道转化率分析
analyze_data(entity_api_key="lead", 
             metrics=[{field:"id", function:"count"}, {field:"convert_time", function:"count"}],
             group_by=["source_channel"], filters={created_at: "本月"})
- 各渠道线索总量 [来源:analyze_data]
- 各渠道转化率 = 已转化数/总量 [来源:计算]
- 环比变化 = (本月转化率 - 上月转化率) / 上月转化率 [来源:计算]
- 异常判定：转化率偏离整体均值 >30% 标注为异常渠道

## 步骤 3: 趋势与异常
- 连续 3 月下降的渠道 → 标注"持续下降趋势" 🟢高置信度
- 单月突变的渠道 → 标注"需关注，暂不判定趋势" 🔴低置信度
---
```

### 框架 B: 诊断性分析（Why did it happen?）

**步骤链路：** 现象描述 → 维度拆解 → 对比分析 → 归因定位 → 根因验证
**适用场景：** 问题排查、下降原因分析、异常诊断、差距分析
**信号词：** 为什么、原因、下降、异常、问题、差距、对比、诊断、根因

**工具 Pipeline：**
```
analyze_data(确认现象) → analyze_data(分组下钻) → query_data(明细验证) → [web_search(外部因素)]
```

**Prompt 构建要求：**
1. 维度拆解策略（逐层下钻，每层选最大偏差维度）：
   - 第一层：时间维度（哪个时段开始异常？）
   - 第二层：组织维度（哪个团队/区域？）
   - 第三层：人员维度（哪些个体？）
   - 第四层：行为维度（哪个环节/动作？）
   - 下钻规则：每层选偏差最大的分组继续下钻，最多 3 层
2. 对比基准选择逻辑：
   - 与自身历史对比 → 识别"变差了"
   - 与同行/团队均值对比 → 识别"本来就差"
   - 与目标值对比 → 识别"差距有多大"
   - 三种对比得出不同结论，Prompt 中必须明确用哪种
3. 归因置信度标注：
   - 单因素归因（仅一个维度异常）→ 🟢高置信度
   - 多因素交叉（2-3 个维度同时异常）→ 🟡中置信度，列出各因素贡献度
   - 无法定位（各维度均匀下降）→ 🔴低置信度，建议"可能是外部因素，需人工确认"

**完整示例（诊断性分析技能）：**

```
用户需求："本月商机转化率为什么下降了？"

生成的 Prompt 关键片段：
---
## 步骤 1: 确认现象
analyze_data(entity_api_key="opportunity", metrics=[{field:"id", function:"count"}],
             group_by=["stage"], filters={close_date: "本月"})
- 确认整体转化率数值及下降幅度 [来源:analyze_data]
- 对比上月同期数据 [来源:analyze_data]

## 步骤 2: 时间维度下钻
analyze_data(...group_by=["close_date_week"])
- 定位从哪一周开始下降 [来源:analyze_data]

## 步骤 3: 组织维度下钻
analyze_data(...group_by=["owner_department"], filters={close_date: "异常周"})
- 定位哪个团队贡献了最大降幅 [来源:analyze_data]
- 偏差最大的团队继续下钻到人员维度

## 步骤 4: 归因判断
- 如果单一团队贡献 >60% 降幅 → "主因：XX团队转化异常" 🟢高置信度
- 如果多团队均匀下降 → "可能是市场/产品外部因素" 🔴低置信度，建议人工确认
- 每个归因结论标注 [来源:xxx] 和置信度
---
```

### 框架 C: 预测性分析（What will happen?）

**步骤链路：** 历史模式提取 → 特征识别 → 趋势外推 → 置信度标注 → 风险预警
**适用场景：** 趋势预测、风险预警、目标预判、容量规划
**信号词：** 预测、趋势、预警、风险、下个月、未来、可能、预判、达成率

**工具 Pipeline：**
```
query_data(历史数据) → analyze_data(趋势统计) → execute_code(建模计算) → [web_search(外部信号)]
```

**Prompt 构建要求：**
1. 预测方法选择（根据数据量和复杂度）：
   - 数据 <6 期：简单外推（最近 3 期均值），标注 🔴低置信度
   - 数据 6-12 期：加权移动平均（近期权重更高），标注 🟡中置信度
   - 数据 >12 期：线性回归/季节性分解（execute_code），标注 🟢高置信度
   - 选择依据必须写入 Prompt，让 LLM 根据实际数据量动态选择
2. 置信区间操作定义：
   - 🟢高置信度：历史数据充足（>12期）+ 趋势稳定（波动率<15%）+ 无重大外部变化
   - 🟡中置信度：数据量中等（6-12期）或 趋势有波动（波动率 15-30%）
   - 🔴低置信度：数据不足（<6期）或 趋势剧烈波动（波动率>30%）或 存在已知外部干扰
3. 风险预警规则：
   - 预测值 vs 目标值差距 >20% → 红色预警
   - 预测值 vs 目标值差距 10-20% → 黄色预警
   - 预测值 vs 目标值差距 <10% → 绿色（正常）
4. 关键假设声明（必须包含）：
   - "本预测基于以下假设：{假设1}、{假设2}"
   - "如果 {风险因素} 发生，预测结果可能偏差 ±X%"
   - 明确标注"预测≠事实"，所有预测数据标注 [来源:推算]

**完整示例（预测性分析技能）：**

```
用户需求："预测下个季度的营收达成情况"

生成的 Prompt 关键片段：
---
## 步骤 1: 历史数据采集
query_data(entity_api_key="opportunity", 
           filters={close_date: "过去12个月", stage: "won"},
           fields=["amount", "close_date", "owner_department"])
- 获取过去 12 个月的成交数据 [来源:query_data]

## 步骤 2: 趋势建模
execute_code(language="python", code="""
import numpy as np
# 加权移动平均 + 季节性因子
monthly_revenue = [...]  # 从步骤1获取

### 框架 D: 处方性分析（What should we do?）

**步骤链路：** 目标定义 → 现状评估 → 差距识别 → 方案生成 → 优先级排序 → 行动计划
**适用场景：** 行动建议、策略推荐、资源优化、改进方案
**信号词：** 建议、怎么做、优化、改进、策略、方案、行动、下一步、提升

**工具 Pipeline：**
```
query_data(现状) → analyze_data(差距量化) → knowledge_search(最佳实践) → [web_search(行业方案)] → ask_user(确认优先级)
```

**Prompt 构建要求：**
1. 建议生成规则（每条建议必须包含 4 要素）：
   - 依据：基于哪个数据/差距得出（标注 [来源:xxx]）
   - 行动：具体做什么（可执行，非空泛建议）
   - 预期效果：量化估算（如"预计提升 X%"，标注 [来源:推算]）
   - 时间线：本周/2 周内/1 个月内/下季度
2. 优先级排序标准（2×2 矩阵）：
   - 影响大 + 实施易 → P0（立即执行）
   - 影响大 + 实施难 → P1（规划执行）
   - 影响小 + 实施易 → P2（顺手做）
   - 影响小 + 实施难 → P3（暂缓/放弃）
   - 影响大小判断：对核心 KPI 的贡献度
   - 实施难易判断：所需资源/时间/跨部门协调程度
3. 建议数量控制：
   - P0 建议：最多 3 条（聚焦）
   - P1 建议：最多 3 条
   - P2/P3：可选，最多各 2 条
   - 总计不超过 8 条建议，避免信息过载

**完整示例（处方性分析技能）：**

```
用户需求："我的团队转化率低于平均水平，给我改进建议"

生成的 Prompt 关键片段：

knowledge_search(query="提升销售转化率最佳实践")

## 三、分析维度选择方法论

当需要为技能选择 3-4 个核心分析维度时，使用以下方法：

### 维度选择决策流程

```
Step 1: 列出所有可能的分析维度（通常 6-10 个）
Step 2: 用以下 3 个标准打分（每项 1-3 分）：
  - 数据可得性：CRM 中是否有对应字段？（3=直接可查, 2=需计算, 1=无数据）
  - 决策影响力：对用户决策的帮助程度？（3=直接影响行动, 2=辅助判断, 1=仅供了解）
  - 差异化价值：是否提供非显而易见的洞察？（3=深度洞察, 2=常规分析, 1=简单统计）
Step 3: 总分排序，选 Top 3-4 个维度
Step 4: 验证选中维度之间有逻辑关联（能形成分析链路）
```

### 维度选择反模式（禁止）

| 反模式 | 问题 | 正确做法 |
|:---|:---|:---|
| 选 8-10 个维度浅尝 | LLM 注意力分散，每个维度只有 1-2 句 | 选 3-4 个维度深入 |
| 选无数据支撑的维度 | 导致幻觉或空洞分析 | 先 query_schema 确认字段存在 |
| 选相互独立的维度 | 无法形成洞察链路 | 确保维度间有因果/关联关系 |
| 选用户自己能看到的维度 | 无增量价值 | 选需要计算/对比/推断的维度 |

## 四、跨域组合指导

当用户需求涉及多个业务域时：

### 跨域组合规则

1. **识别主域和辅域**：
   - 主域 = 用户最关心的核心问题（分配 60-70% 分析深度）
   - 辅域 = 支撑主域判断的补充信息（分配 30-40% 分析深度）
   - 判断依据：用户语句中的主语/动词指向哪个域

2. **主域使用完整分析体系**（加载对应域文件），辅域只取关键指标

3. **在 Prompt 中明确标注**哪些维度来自主域、哪些来自辅域

4. **辅域数据作为"补充证据"**而非"独立分析"

### 跨域组合示例

| 用户需求 | 主域 | 辅域 | 组合方式 |
|:---|:---|:---|:---|
| "客户扩展机会分析" | account.md（客户画像） | opportunity（只取赢率+渗透度） | 客户 360 + 商机渗透率 |
| "团队 Pipeline 健康度" | team.md（绩效矩阵） | forecast（只取覆盖率） | 人员绩效 + Pipeline 指标 |
| "活动对商机的影响" | activity.md（效能模型） | opportunity（只取阶段推进） | 活动量 → 商机推进关联 |
| "客户+商机+活动综合" | generic.md（本文件） | 各域取 1-2 个核心指标 | 通用框架 + 多域关键指标 |

### 跨域数据关联方法

```
关联路径（通过 entity_link 或共同字段）：
- 客户 → 商机：account_api_key 关联
- 商机 → 活动：opportunity_api_key 关联
- 客户 → 活动：account_api_key 关联
- 人员 → 商机/活动：owner 字段关联
- 团队 → 人员：department 字段关联

Prompt 中必须明确关联路径，禁止假设关联关系存在。
先用 query_schema(query_type="entity_links") 确认关联关系。
```

## 五、非分析类技能设计指导

### 5.1 数据导出类

**设计要点：**
- 明确导出格式（Markdown 表格 / JSON / CSV）
- 明确字段选择逻辑（全量 or 用户指定，通过 arguments 参数化）
- 明确筛选条件参数化（{时间范围}、{筛选条件}）
- 大数据量处理策略：
  - 记录数 <100：直接展示 Markdown 表格
  - 记录数 100-1000：cos_upload 生成 CSV 下载链接
  - 记录数 >1000：分页查询 + cos_upload，提示用户"数据量较大，已生成文件"
- 输出方式选择：直接展示（小量）/ cos_upload 文件下载（大量）

**工具选择：** `query_data` + `cos_upload`（大数据量时）+ `ask_user`（确认导出范围）

**Prompt 骨架：**
```
## 步骤 1: 确认导出范围
- 如果 {筛选条件} 不明确 → ask_clarification 追问
## 步骤 2: 查询数据
- query_data(entity_api_key="{对象}", filters={...}, fields=[...])
- 先 count 确认数据量
## 步骤 3: 格式化输出
- <100 条：Markdown 表格直接展示
- ≥100 条：write_file → cos_upload → 返回下载链接
## 步骤 4: 数据完整性声明
- "共导出 X 条记录，时间范围：{range}，筛选条件：{filters}"
```

### 5.2 报告生成类

**设计要点：**
- 明确报告结构（章节划分、每章数据源）
- 明确受众（给谁看决定详略和术语）：
  - 给高管：结论先行，数据精简，重点是趋势和决策建议
  - 给经理：数据详实，含对比分析，重点是团队表现和行动项
  - 给一线：操作导向，含具体客户/商机列表，重点是下一步动作
- 明确时间范围参数化（{报告周期}）
- 报告结构模板：
  - 📊 摘要（3-5 句话概括核心发现）
  - 📈 数据部分（表格/指标，每个数据标注来源）
  - 🔍 分析部分（趋势/异常/对比）
  - 💡 建议部分（可行动的下一步）
  - ⚠️ 局限性声明（数据范围/缺失/假设）

**工具选择：** `query_data` + `analyze_data` + `knowledge_search`（模板/历史报告）+ `cos_upload`（长报告）

**Prompt 骨架：**
```
## 步骤 1: 数据采集（按章节分别查询）
## 步骤 2: 各章节分析
- 每章遵循"数据→指标→判断"链路
- 每个数据点标注 [来源:query_data/analyze_data/计算]
## 步骤 3: 综合摘要（最后写，基于各章结论）
## 步骤 4: 格式化输出
- 按受众调整详略
- 末尾附数据局限性声明
```

### 5.3 流程自动化类

**设计要点：**
- 明确触发条件（参数化）
- 明确执行步骤（有序、每步可验证）
- 涉及写操作必须配合 ask_user 确认
- 明确异常处理策略：
  - 查询失败 → 重试一次，仍失败则中止并告知用户
  - 数据校验失败 → 中止，列出校验失败项，ask_user 确认是否继续
  - 写入失败 → 中止，不做部分写入，告知用户失败原因
- 明确幂等性（重复执行不产生副作用）：
  - 写入前先查询是否已存在
  - 更新操作使用条件更新（where 条件包含预期旧值）

**工具选择：** `query_data`（查询现状）+ `modify_data`（写入）+ `ask_user`（确认，必须）+ `ask_clarification`（参数不全时）

**Prompt 骨架：**
```
## 步骤 1: 参数校验
- 检查所有必要参数是否完整
- 不完整 → ask_clarification
## 步骤 2: 前置检查
- query_data 确认目标数据存在
- 检查是否已执行过（幂等性）
## 步骤 3: 执行预览
- 列出将要执行的操作（不执行）
- ask_user(interrupt_type="confirm") 确认
## 步骤 4: 执行
- modify_data 逐条执行
- 每步记录结果
## 步骤 5: 结果汇报
- 成功/失败数量
- 失败项明细
```

- 成功/失败数量
- 失败项明细
```

| 金额分布 | opportunity.amount | 客户结构 | 大/中/小单占比 |
| 周期分析 | opportunity.created_at → close_date | 效率评估 | 平均/中位数销售周期 |
| 流失阶段 | opportunity.lost_stage + lost_reason | 瓶颈定位 | 各阶段流失率 + Top 丢单原因 |
| 竞争格局 | opportunity.competitor | 竞品威胁 | 竞品出现频率 + 对应赢率 |
| 来源渠道 | opportunity.source | 渠道 ROI | 各渠道贡献量/赢率/均单 |

#### 客户分析维度池

| 维度 | 数据来源 | 分析价值 | 常用指标 |
|:---|:---|:---|:---|
| 行业分布 | account.industry | 市场聚焦度 | 行业集中度/渗透率 |
| 规模分层 | account.employee_count / revenue | 客户结构 | 大/中/小客户占比 |
| 生命周期阶段 | account.lifecycle_stage | 成熟度分布 | 各阶段客户数/收入占比 |
| 活跃度 | 最近活动/登录/工单 | 健康度信号 | 30/60/90 天活跃率 |
| 钱包份额 | account.revenue / 预估总预算 | 扩展空间 | 渗透率 + 扩展潜力 |
| 决策链完整度 | contact.role 覆盖 | 关系深度 | EB/UB/TB/Coach 覆盖率 |

#### 活动分析维度池

| 维度 | 数据来源 | 分析价值 | 常用指标 |
|:---|:---|:---|:---|
| 活动量 | activity.count by type | 投入度 | 日/周均活动量 |
| 活动类型分布 | activity.type | 行为模式 | 电话/邮件/拜访/会议占比 |
| 活动→商机关联 | activity → opportunity 推进 | 效能评估 | 活动转化率 |
| 活动节奏 | activity.date 间隔 | 跟进连续性 | 平均跟进间隔/断档天数 |
| 活动质量 | activity.duration + outcome | 深度评估 | 有效活动占比 |

### 5B.4 专业性注入规则

```
规则 1: 方法论匹配
  当技能涉及以下关键词时，必须注入对应方法论到 Prompt 中：
  - "赢率/评估/资质" → MEDDIC 或 BANT
  - "漏斗/转化/阶段" → 销售漏斗理论
  - "健康度/流失/续约" → Health Score 模型
  - "预测/Pipeline/覆盖" → Pipeline Coverage + Forecast 三档
  - "绩效/辅导/团队" → 绩效九宫格 + Activity-Based Coaching
  - "效率/速度/周期" → Sales Velocity

规则 2: 基准数据注入
  当 Prompt 中有"判断"或"评估"步骤时：
  - 优先指导 LLM 用客户历史数据作为基准
  - 无历史数据时，注入行业基准值 + 标注 [来源:行业基准]
  - 必须在 Prompt 中写明："如果客户有自定义基准，以客户基准为准"

规则 3: 维度选择优先级
  从维度池中选择时，优先选择：
  - 有明确行业方法论支撑的维度（如 MEDDIC 六维度）
  - 有行业基准可对比的维度（如赢率、续约率）
  - 能形成"数据→指标→基准→判断→行动"完整链路的维度

规则 4: 专业术语使用
  生成的 Prompt 中应使用 CRM 行业标准术语：
  - Pipeline（而非"销售管道"）
  - Quota（而非"销售目标"）
  - ACV/ARR（而非"年度合同额"）
  - MQL/SQL（而非"营销线索/销售线索"）
  - Churn Rate（而非"流失率"，或中英并用）
  - NRR/GRR（而非"净收入留存"，或中英并用）
  但必须在 Prompt 的角色定义中注明："输出时使用中文为主，关键指标保留英文缩写并附中文解释"

规则 5: 分析深度保障
  每个分析维度必须达到以下深度（不能停留在"统计数字"层面）：
  - Level 1 统计：是什么数字？（描述性）
  - Level 2 对比：比基准好还是差？差多少？（诊断性）
  - Level 3 归因：为什么好/差？哪个因素贡献最大？（归因性）
  - Level 4 行动：应该做什么？优先级如何？（处方性）
  最低要求：达到 Level 2（有对比有判断）
  专业要求：达到 Level 3-4（有归因有建议）
```

### 5B.5 专业性自检清单

生成技能 Prompt 后，用以下清单验证专业性：

```
□ 是否引用了至少 1 个行业方法论？（非自创框架）
□ 是否有明确的判断基准？（行业基准或历史基准，非拍脑袋）
□ 分析维度是否来自维度池？（非随意发明的维度）
□ 每个维度是否达到 Level 2+ 深度？（有对比有判断，非纯统计）
□ 是否使用了 CRM 行业标准术语？（Pipeline/Quota/NRR 等）
□ 建议是否具体可执行？（"优化跟进节奏，将间隔从7天缩短到3天" vs "加强跟进"）
□ 是否标注了基准来源？（[来源:行业基准] 或 [来源:历史数据]）
□ 是否考虑了数据局限性？（哪些维度可能无数据）
```

## 六、通用 Prompt 骨架

当无法套用预定义域方法论时，使用以下骨架构建技能 Prompt。

### 骨架使用说明

```
使用前必须完成：
1. 第一节的去重检查（确认需要新建）
2. 第一-B节的能力边界检查（确认可承载）
3. 第二节的框架选择（确定用哪个/哪几个框架）
4. 第三节的维度选择（确定 3-4 个核心维度）

骨架中的占位符填充规则：
- {领域}：用户业务所在领域，如"销售管理"、"渠道运营"、"客户服务"
- {具体方向}：技能聚焦的细分方向，如"转化率优化"、"ROI 分析"、"流失预警"
- {对象}：CRM 中的 entity_api_key，必须通过 query_schema 确认存在
- {核心分析维度 N}：从第三节维度选择方法论中选出的 Top 3-4 维度
- {报告周期}/{时间范围}：参数化，由用户运行时传入

步骤数动态调整：
- 🟢简单技能（单数据源、1-2 步分析）：3-4 步（采集 + 分析 + 核验）
- 🟡中等技能（多数据源、需框架指导）：5-6 步（采集 + 2-3 维度分析 + 综合 + 核验）
- 🔴复杂技能（计算模型、跨域组合）：6-8 步（采集 + 3-4 维度分析 + 建模 + 综合 + 核验）
```

```markdown

│ Pipeline E: 数据写入流程                                                  │
│ query_data(查现状) → ask_user(确认) → modify_data(执行) → query_data(验证)│
│ 适用：批量更新、数据清洗、流程自动化                                        │
│ allowed_tools: ["query_data", "modify_data", "ask_user"]                │
│ ⚠️ modify_data 必须与 ask_user 配对，写前必须确认                          │
├─────────────────────────────────────────────────────────────────────────┤
│ Pipeline F: 报告导出                                                     │
│ query_data → analyze_data → write_file(生成) → cos_upload(上传) → 输出   │
│ 适用：周报/月报生成、数据导出、文件下载                                     │
│ allowed_tools: ["query_data", "analyze_data", "write_file", "cos_upload"]│
│ 可选追加: "execute_code"（复杂格式处理）                                   │
├─────────────────────────────────────────────────────────────────────────┤
│ Pipeline G: 脚本驱动分析                                                  │
│ terminal(安装依赖) → write_file(写脚本) → execute_code(执行) → read_file  │
│ 适用：复杂统计模型、可视化图表、自定义算法                                   │
│ allowed_tools: ["terminal", "execute_code", "write_file", "read_file",  │
│                 "query_data", "cos_upload"]                              │
└─────────────────────────────────────────────────────────────────────────┘
```

### 工具选择原则

```
核心原则：工具越少越精确，LLM 越不容易走偏。

选择规则：
1. 只读分析类 → query_data + analyze_data（基础，几乎必选）
2. 需要外部信息 → 追加 web_search
3. 需要行业知识/最佳实践 → 追加 knowledge_search
4. 需要域专家知识 → 追加 read_skill_resource
5. 需要复杂计算/建模 → 追加 execute_code（+ write_file + read_file）
6. 需要安装依赖/运行脚本 → 追加 terminal
7. 涉及数据写入 → 追加 modify_data + ask_user（必须配对）
8. 需要导出文件 → 追加 cos_upload（+ write_file）
9. 参数可能不完整 → 追加 ask_clarification
10. 需要用户决策/确认 → 追加 ask_user

禁止组合：
- ❌ modify_data 不配 ask_user → 写操作必须有确认
- ❌ browse_metamodel/query_metadata 加到业务分析技能 → 那是元数据管理专用
- ❌ manage_skill 加到普通技能 → 那是 create_skill 专用
- ❌ 无脑全选所有工具 → 增加 LLM 决策负担，降低输出质量
- ❌ execute_code 不配 query_data → 没有数据输入的计算无意义

推荐数量：
- 简单技能：2-3 个工具
- 中等技能：3-5 个工具
- 复杂技能：5-8 个工具
- 超过 8 个工具 → 考虑拆分为多个技能
```

## 八、置信度标注操作规范

### 置信度等级定义

| 等级 | 符号 | 判定条件（满足全部） | 典型场景 |
|:---|:---|:---|:---|
| 高 | 🟢 | 数据覆盖率>90% + 样本量>30 + 数据源一致 + 结论方向明确 | 基于完整数据的统计结论 |
| 中 | 🟡 | 覆盖率60-90% 或 样本量10-30 或 多源基本一致 或 需要推算 | 基于部分数据的分析判断 |
| 低 | 🔴 | 覆盖率<60% 或 样本量<10 或 数据源矛盾 或 纯推算 | 预测、外推、假设性结论 |

### 置信度标注规则

```
规则 1: 每个核心结论必须标注置信度（非核心的辅助说明可省略）
规则 2: 标注格式统一为 "[来源:xxx] 🟢/🟡/🔴"
规则 3: 如果一个结论依赖多个数据源，取最低置信度
规则 4: 推算/预测类结论最高为 🟡（除非有 >12 期历史数据验证）
规则 5: 外部数据（web_search）最高为 🟡（无法验证准确性）
规则 6: 置信度为 🔴 的结论必须附加"建议人工确认"
```

### 防止置信度膨胀（Anti-pattern）

```
❌ 错误：所有结论都标 🟢（讨好用户倾向）
✅ 正确：严格按条件判定，宁可标低不标高

❌ 错误：只标注高置信度的结论，低置信度的不标
✅ 正确：所有核心结论都标注，低置信度更需要标注

❌ 错误：置信度标注但不解释原因
✅ 正确：🔴低置信度时附加原因（如"样本量仅 5 条"）
```

## 九、异常处理完整规范

### 异常分类与处理策略

| 异常类型 | 识别方式 | 处理策略 | Prompt 中的表述 |
|:---|:---|:---|:---|
| 数据缺失 | query_data 返回空/字段为 null | 跳过该维度，标注"无数据" | "该维度无数据，无法分析" |
| 查询失败 | query_data 返回错误 | 重试 1 次，仍失败则跳过 | "查询异常，该部分暂无法分析" |
| 数据过期 | 最后更新时间 >7 天 | 继续分析但标注时效性 | "数据最后更新于 {date}，可能不是最新" |
| 权限不足 | 返回 403/permission denied | 中止该部分，告知用户 | "无权访问该数据，请联系管理员" |
| 数据量过大 | 单次返回 >1000 条 | 分页处理或缩小范围 | 自动分页，不需要告知用户 |
| 结果矛盾 | 两个数据源数值冲突 | 列出两方数据，标注冲突 | "数据矛盾：A 显示 X，B 显示 Y，需人工确认" |
| 样本量不足 | 记录数 <10 | 降级分析，标注局限性 | "样本量仅 {n} 条，结论仅供参考 🔴" |
| 超出能力边界 | 需求涉及系统不支持的功能 | 明确告知，建议替代方案 | "当前不支持 {xxx}，建议 {替代方案}" |
| 参数歧义 | 用户输入可多种理解 | ask_clarification 追问 | 中断追问，不猜测 |
| 计算溢出 | execute_code 超时/报错 | 简化计算逻辑，重试 | "计算复杂度过高，已简化处理" |

### 降级策略

```
完整分析（理想状态）
  ↓ 数据部分缺失
有限分析（标注缺失维度，其余正常分析）
  ↓ 数据严重缺失（>50% 维度无数据）
最小分析（只分析有数据的维度，明确告知局限性）
  ↓ 完全无数据
中止分析（告知用户"数据不足，无法完成分析"，建议数据补充方向）
```

## 十、端到端完整示例

### 示例 1: 跨域组合分析技能

**用户需求：** "创建一个渠道 ROI 分析技能"

**分析过程：**
- 场景判断：非预定义域（渠道管理），使用 generic.md
- 框架选择：描述性（现状）+ 诊断性（哪个渠道好/差）+ 处方性（优化建议）= A→B→D
- 维度选择：
  - 渠道投入产出比（数据可得 3 + 决策影响 3 + 差异化 2 = 8）✅
  - 渠道转化漏斗（数据可得 3 + 决策影响 3 + 差异化 2 = 8）✅
  - 渠道质量评分（数据可得 2 + 决策影响 3 + 差异化 3 = 8）✅
