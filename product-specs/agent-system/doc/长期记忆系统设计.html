一、设计背景与技术选型

1.1 基于 OpenViking 范式的设计

本系统以 OpenViking 的文件系统范式为架构基础，完整实现了其核心设计理念：

继承的 OpenViking 核心能力：

能力 OpenViking 原始设计 本系统实现
虚拟文件系统 VikingFS（URI 路径 + 目录树） ✅ 完整实现 viking_fs.py，支持 ls/tree/read/find/rm
L0/L1/L2 三层信息模型 目录聚合 L0/L1 + 叶子 L2 ✅ 完整实现，目录节点 LLM 聚合 + 叶子节点按需加载
目录递归检索 优先队列 + 分数传播 + 收敛检测 ✅ 完整实现，α=0.5 分数传播 + Top-K 连续 3 轮不变停止
语义去重 + LLM 合并 向量预筛 + LLM 精判（skip/create/merge/delete） ✅ 完整实现 _dedup_create()
分层加载 检索返回 L0 摘要，Agent 按需加载 L1/L2 ✅ 完整实现 memory_read 工具
会话结束反思 post_session_reflection ✅ 完整实现 reflect_on_session()
定期全局反思 weekly_global_reflection ✅ 完整实现 reflect_global()
记忆遗忘 TTL + 热度驱动 ✅ 完整实现三阶段淡化 + 复活机制

针对 CRM toB 场景的领域适配：

维度 OpenViking 通用设计 本系统 CRM 适配
分类体系 9 类通用分类 精简为 4 类（profile/preferences/agent_rules/entities），聚焦 CRM 核心场景
提取架构 单路 LLM 提取 + 后分类 4 路并行 LLM 提取，每路独立提示词 + 边界规则
存储后端 通用向量库 腾讯向量库 tcvectordb（支持 BM25 稀疏向量 + filter index）+ PG 双存储
检索策略 纯向量语义检索 BM25 0.7 + 向量 0.3 混合检索（CRM 场景客户名精确匹配优先）
系统数据一致性 无（通用场景无此问题） 提取时排除 CRM 系统已有字段 + biz_id 锚定 + source_type 标记
预过滤 无 规则预过滤（寒暄/确认/工具失败跳过），节省 ~30% LLM 调用

1.2 最终选型

架构范式: OpenViking（VikingFS 虚拟文件系统 + L0/L1/L2 三层 + 目录递归检索 + 反思修正）
提取层:   4 路并行 LLM 提取 + 规则预过滤（CRM 领域适配）
存储层:   腾讯向量库（tcvectordb SDK 直连，BM25 稀疏向量 + filter index）
          + PG（profile/agent_rules 权威存储 + 全量记忆生命周期管理）
检索层:   BM25 混合检索（0.7 关键词 + 0.3 向量）+ 目录递归展开 + 分层加载
组织层:   VikingFS 虚拟文件系统（viking:// URI + ls/tree/read/find/rm）

2.2 分类决策逻辑（四路并行提取）

代码实现：src/memory/extraction/prompts.py + src/memory/extraction/extractor.py

当前实现为 4 路并行 LLM 提取，每路独立判断、互不依赖：

用户发言 → 4 路并行 LLM 调用:
  ├── Profile:      用户是谁？（稳定身份属性）
  ├── Preferences:  用户偏好什么？（个人喜好/习惯/标准）
  ├── Agent Rules:  Agent 应该怎么做？（持久行为约束）
  └── Entities:     第三方有什么事实？（客户/联系人/竞品）

各路核心判别原则：

类别 核心问题 判别标准
profile 用户是谁？ 该信息在下一个新会话里对 Agent 理解"这个用户是谁"是否仍有帮助
preferences 用户偏好什么？ 该信息脱离当前上下文后，在下一个新会话里对理解"这个用户"是否仍有价值
agent_rules Agent 应该怎么做？ 该规则在下一次类似请求中 Agent 是否应继续遵守
entities 第三方有什么事实？ 关于第三方的可复用事实（角色关系/业务/偏好/竞争情报）

跨维度边界规则（每路提示词中明确定义）：

Profile 不属于:
  - 我的喜好/习惯/厌恶 → preferences
  - 对 Agent 的持久指令 → agent_rules
  - 第三方事实 → entities
  - 单次操作、孤立数值 → 不提取

Preferences 不属于:
  - 纯指向 Agent 行为的规则式指令 → agent_rules
  - 描述身份或组织 → profile
  - 描述第三方偏好/事实 → entities
  - 单次反馈/操作 → 不提取

Agent Rules 不属于:
  - 描述用户本人（个人习惯、性格、喜好）→ preferences
  - 纯身份或组织描述 → profile
  - 对第三方事实的纯陈述 → entities
  - 单次调整、评价、感叹 → 不提取

Entities 不属于:
  - 用户履历、团队或公司特征 → profile
  - 用户自己的偏好 → preferences
  - 命令 Agent 的持久指令 → agent_rules
  - 疑问句/纯查询/操作指令 → 不提取

多维度混合处理：同句含多维度时，各路独立判断、各自提取属于自己的部分。

2.3 各类别存储形式详解

每个类别的 abstract（L0）、overview（L1）、content（L2）的存储位置、是否参与检索和打分各不相同：

profile — 用户身份

存储与检索特性：

层级 字段 存储位置 参与检索 参与打分 用途
— content PG ❌ ❌ LLM 合并后的完整画像，注入提取提示词
— abstract PG ❌ ❌ 前端展示用摘要

profile 不存储在向量库，不参与语义检索。通过 get_profile() 从 PG 读取，注入提取提示词的 {existing_profile} 避免重复提取。

场景示例：

━━━ 对话场景 ━━━
[用户] 我是华东区的销售总监，管着15个人，主要跑互联网行业大客户。我们公司刚从Salesforce迁到纷享销客。

━━━ 提取 & 存储 ━━━
category:  profile
merge_key: "profile"

PG 存储:
{
  "category": "profile",
  "merge_key": "profile",
  "abstract": "用户身份: 华东区销售总监，管理15人团队，负责互联网大客户，使用纷享销客",
  "content": "用户是华东区销售总监，管理15人团队，主要负责互联网行业大客户。公司近期从Salesforce迁移到纷享销客CRM。",
  "status": "active"
}

━━━ 使用方式（不参与检索） ━━━
注入到 PROFILE_EXTRACT_PROMPT 的 {existing_profile} 占位符，避免重复提取。
不写入向量库，不参与 hybrid_search，不参与打分。

preferences — 用户偏好

存储与检索特性：

层级 字段 存储位置 参与检索 参与打分 用途
L0 abstract 向量库 ✅ embed → cosine + BM25 ✅ 0.7×BM25 + 0.3×cosine 检索匹配 + 注入 Agent 上下文
L1 overview 向量库 ❌ ❌ Agent 调用 memory_read(level="L1") 按需加载
L2 content 向量库 ❌ ❌ Agent 调用 memory_read(level="L2") 按需加载

场景示例：

━━━ 对话场景 ━━━
[用户] 以后数据展示都用表格，金额用万为单位不要小数点

━━━ 提取 & 存储 ━━━
category:      preferences
slug:          "data_display"
merge_key:     "preferences/data_display"

向量库存储（叶子节点）:
{
  "id": "mem_d4e5f6a7",
  "vector": embed("数据展示偏好: 表格格式，金额万为单位，不要小数"),       ← L0 向量化，参与检索
  "sparse_vector": BM25("数据展示偏好: 表格格式，金额万为单位，不要小数"), ← L0 稀疏向量，参与检索
  "abstract": "数据展示偏好: 表格格式，金额万为单位，不要小数",            ← L0（返回给 Agent）
  "overview": "## 偏好\n- 表格格式\n- 金额万为单位\n- 不要小数",           ← L1（按需加载）
  "content": "用户偏好表格展示数据，金额统一用万为单位且不要小数点。",      ← L2（按需加载）
  "category": "preferences",
  "merge_key": "preferences/data_display",
  "is_leaf": "true",
  "status": "active"
}

━━━ 检索时打分示例 ━━━
用户问 "用什么格式展示数据" →
  BM25("数据""展示"精确命中 abstract) → bm25_score = 0.75
  cosine(查询向量 vs abstract向量)    → cosine_score = 0.82
  final_score = 0.7 × 0.75 + 0.3 × 0.82 = 0.771 → 命中，返回 L0 摘要
  Agent 按需调用 memory_read(level="L2") 获取完整偏好

agent_rules — Agent 行为准则

存储与检索特性：

层级 字段 存储位置 参与检索 参与打分 用途
— content PG ❌ ❌ 每轮对话前作为 SystemMessage 全量注入
— abstract PG ❌ ❌ 前端展示用摘要

agent_rules 不存储在向量库，不参与语义检索。每轮对话开始时通过 get_agent_rules_text() 从 PG/缓存读取，作为 SystemMessage 注入，Agent 从第一轮就遵守。

场景示例：

entities — 第三方事实

存储与检索特性：

层级 字段 存储位置 参与检索 参与打分 用途

L2 content 向量库 ❌ ❌ Agent 调用 memory_read(level="L2") 按需加载

三、L0/L1/L2 三层信息模型

对齐 apps-agent（OpenViking）：L0/L1 属于目录，L2 属于叶子。

3.1 三层定义（对齐 apps-agent）

层级 归属 生成方式 Token 量 用途
L0 目录节点 系统 LLM 聚合（从所有叶子 content 压缩为一句话） ~30-100 向量检索匹配 + 注入 Agent 上下文

1. 目录节点（is_leaf=false）

5.1 完整流程

用户查询

  ├── 过滤条件: tenant_id = "{tenant_id}" AND user_id = "{uid}" AND status != "archived"

  │     匹配方式: 查询向量 vs 每条记忆 abstract 的向量 → cosine 相似度

  │     匹配方式: 查询的 BM25 稀疏向量 vs 每条记忆 abstract 的稀疏向量 → 关键词精确匹配

  │     │
  │     ├── 搜索子节点:
  │     │     过滤条件: user_id = "{uid}" AND parent_uri = "{当前目录URI}"
  │     │     检索方式: 纯向量搜索（query_vec vs 子节点的 vector 字段）
  │     │     返回: 该目录下的直接子节点（可能是叶子，也可能是子目录）
  │     │
  │     ├── 分数传播（α = 0.5）:
  │     │     child_final_score = 0.5 × child_own_score + 0.5 × parent_dir_score
  │     │     含义: 子节点的最终分数 = 自身与查询的相关度 + 父目录的相关度加成
  │     │     效果: 高分目录下的子节点即使自身分数一般，也能获得父目录的分数加成

  │           每轮递归后检查当前 Top-K 结果是否变化
  │           连续 3 轮 Top-K 不变 → 停止递归（结果已收敛）

  └── 递归终止条件: 优先队列为空 OR 连续 3 轮收敛
  │
  ▼

5.3 目录递归展开详解

为什么需要递归展开：

向量库中的记忆按目录树组织。用户问"华为的情况"时，全局检索可能命中"华为科技"目录节点（L0 聚合摘要与查询相关），但目录本身只是摘要，真正有价值的是其下的叶子节点。递归展开就是从命中的目录出发，逐层下钻找到具体的叶子记忆。

递归展开示例：

向量库中的目录结构:
  viking://user/memories/entities/华为科技/          ← 目录节点（is_leaf=false）
    ├── viking://user/memories/entities/华为科技/张伟  ← 叶子（is_leaf=true）
    ├── viking://user/memories/entities/华为科技/ERP升级 ← 叶子（is_leaf=true）
    └── viking://user/memories/entities/华为科技/审批流程 ← 叶子（is_leaf=true）

用户查询: "华为那边的情况"

Step 1 全局检索命中:
  - 目录 "华为科技: 张伟直接，ERP有分歧，审批3周" → score=0.88 → 入优先队列
  - 叶子 "华为科技/张伟: 说话直接，汇报用PPT"    → score=0.72 → 直接收集

Step 3 递归展开目录 "华为科技/":
  搜索 parent_uri="viking://user/memories/entities/华为科技/" 的子节点:
    - 华为科技/ERP升级 → own_score=0.65
      final_score = 0.5 × 0.65 + 0.5 × 0.88 = 0.765 → 收集
    - 华为科技/审批流程 → own_score=0.45
      final_score = 0.5 × 0.45 + 0.5 × 0.88 = 0.665 → 收集
    - 华为科技/张伟 → 已在 seen_ids 中，跳过

最终 Top-K（按 final_score 排序）:
  1. [DIR] 华为科技 → 0.88（目录本身也可返回）
  2. [ID]  华为科技/ERP升级 → 0.765（递归展开发现）
  3. [ID]  华为科技/张伟 → 0.72（全局直接命中）
  4. [ID]  华为科技/审批流程 → 0.665（递归展开发现）

分数传播的意义：

不用分数传播时:
  华为科技/审批流程 own_score=0.45（与"华为那边的情况"语义关联弱）→ 可能被过滤

用分数传播后:
  华为科技/审批流程 final_score = 0.5×0.45 + 0.5×0.88 = 0.665
  → 因为父目录"华为科技"高度相关，子节点获得加成，不会被遗漏
  → 效果：问"华为的情况"时，华为下的所有子记忆都能被召回

两路检索各自返回 Top-K 结果后，通过 WeightedRerank 融合：

  final_score = sparse_weight × BM25_score + dense_weight × vector_score
              = 0.7 × BM25_score + 0.3 × vector_score

权重设计原因：
  BM25 权重 0.7（高）：CRM 场景中客户名、联系人名是精确匹配需求
    "华为科技" 必须精确命中包含"华为科技"的记忆，不能被语义相近的"中兴通讯"替代
  向量权重 0.3（低）：语义补充，捕获同义词和隐含关系
    "商机情况" 可以匹配到"ERP项目有分歧"（语义相关但无关键词重叠）

即使腾讯的 vector_score 较高（语义上"商机"相关），BM25 的高权重确保了客户名精确匹配优先。

5.5 检索匹配字段 vs 存储字段

向量库中每个文档有多个字段，但只有 abstract 的向量化结果参与检索匹配，其他字段只是存储：

向量库中有 3 个文档：

1. 目录节点（华为科技/）
   vector = embed("华为科技: 张伟直接，ERP有分歧，审批3周")  ← 参与检索（cosine）

   content = ""                                             ← 目录没有 content

2. 叶子节点（华为科技/ERP项目）
   vector = embed("华为科技/ERP项目: 张伟和李娜有分歧")      ← 参与检索

   abstract = "华为科技/ERP项目: 张伟和李娜有分歧"           ← 向量化的源文本

   abstract = "华为科技/张伟: 说话直接，汇报用PPT"           ← 向量化的源文本
   content = "张伟说话直接不绕弯子，汇报用PPT带数据..."       ← 不参与检索（按需加载）

总结：

字段 是否参与检索匹配 用途
vector（embed(abstract)） ✅ cosine similarity 语义匹配
sparse_vector（BM25(abstract)） ✅ 关键词精确匹配
abstract ❌（是向量化的源文本） 检索返回给 Agent 的 L0 摘要
overview（L1） ❌ Agent 调用 memory_read(level="L1") 时返回
content（L2） ❌ Agent 调用 memory_read(level="L2") 时返回

5.6 分层加载

检索默认返回 L0 摘要（~30 tokens/条），Agent 按需加载 L1/L2：

  L0 够用 → Agent 直接回答（不调用 memory_read）
  需要目录结构 → memory_read(id=DIR_ID, level="L1") → 返回结构化 Markdown
  需要叶子详情 → memory_read(id=LEAF_ID, level="L2") → 返回完整记忆内容

Token 开销对比：
  5 条 L0 注入: 5 × 30 = 150 tokens
  按需加载 2 条 L2: 2 × 200 = 400 tokens
  总计: 550 tokens（vs 直接返回 5 条 L2 = 1000 tokens）

6.2 语义去重流程（entities 无 merge_key 时）

当 entities 类记忆没有明确的 merge_key 时（LLM 未能生成结构化的实体路径），通过语义去重避免重复存储：

候选记忆（无 merge_key 的 entities）
  │
  ▼
向量预筛: 搜索已有同类别记忆，取 Top-3
  │
  ├── 最高相似度 < 0.9 → 直接 create（新信息，独立存储）
  │
  └── 最高相似度 >= 0.9 → 调 LLM 精判（DEDUP_PROMPT）
        │

        ├── merge:  同主题的信息更新 → LLM 生成合并内容，替换旧记忆

6.3 合并/去重后 active_count 继承策略

active_count 是记忆的检索热度指标，直接影响遗忘策略（active_count >= 3 的记忆享有高热度豁免）。合并或去重操作会删除旧记忆并创建新记忆，必须正确继承热度，否则高价值记忆可能因合并后热度归零而被错误遗忘。

6.3.1 各场景继承规则

操作场景旧记忆数继承规则设计依据
_merge_by_key 写入时合并1 条旧 → 1 条新新 active_count = 旧 active_count信息演进，热度延续
_merge_profile profile 追加1 条旧 → 1 条新新 active_count = 旧 active_countprofile 每次检索都命中，热度必须延续
_merge_agent_rules 规则融合1 条旧 → 1 条新新 active_count = 旧 active_count同 profile
_dedup_create 去重 merge1 条旧 → 1 条新新 active_count = 旧 active_count合并内容是旧记忆的演进
_dedup_create 去重 delete1 条旧 → 1 条新新 active_count = 0旧记忆完全失效，不继承
reflect_global 碎片合并N 条旧 → 1 条新新 active_count = sum(各碎片)各碎片被命中总次数即实际使用频率
reflect_on_session update_old1 条旧 → 1 条新新 active_count = 旧 + 1被更新说明仍有价值，热度 +1

6.3.2 为什么碎片合并用 sum 而非 max

碎片 A: active_count = 5, 碎片 B: active_count = 3, 碎片 C: active_count = 1

sum = 9 → 各碎片是同一 merge_key 的不同侧面，命中任一条都是"用这组信息"
         合并后 1 条承载原 N 条的检索负载，sum 准确反映实际使用频率

1对1 合并不用 sum: 始终只有 1 条记忆的演进，直接继承即可

七、记忆遗忘策略

遗忘机制判断粒度判断条件处理方式执行时机
逐条遗忘（7.2）单条记忆age > 180d + active_count < 3三阶段淡化: active → stale → archived → deleted每日定时
高热度豁免（7.2）单条记忆age > 180d + active_count >= 3保留为 active，不进入淡化每日定时
实体级沉寂（7.3）parent_entity 整体60d 无写入 + 60d 无检索渐进式: dormant → stale → archived每日定时

遗忘策略由 decay_memories() 统一执行，纯规则判断，0 LLM 消耗。profile / preferences / agent_rules 永不遗忘。

为什么需要记忆遗忘：

记忆系统不是无限增长的数据库，而是模拟人类记忆的"有选择性保留"机制。没有遗忘的记忆系统会面临三个核心问题：

  1. 检索噪声：记忆越多，检索时无关结果越多。半年前"张伟下周出差"的记忆如果仍然 active，会干扰当前检索结果的相关性排序，导致 Agent 回答质量下降。

  2. 信息过时：CRM 场景中第三方事实有天然时效性。商机阶段会推进、联系人会变动、项目会结束。过时的记忆不仅无用，还可能误导 Agent 给出错误信息。

  3. 存储成本：向量库按存储量计费，无限增长的记忆会带来不必要的成本。单用户 500 条记忆是合理上限，超出需要淘汰低价值记忆。

设计原则：

  • 分类差异化：不同类别的记忆有不同的时效性特征，不能一刀切
  • 热度豁免：频繁被检索命中的记忆即使过期也有价值，不应被遗忘
  • 渐进淡化：不直接删除，而是通过三阶段（stale→archived→deleted）逐步降低影响，给予复活机会
  • 全量清理兜底：租户注销/用户离职时需要彻底清除，满足数据合规要求

7.1 各类别遗忘策略

类别 保留天数 遗忘策略 设计逻辑
profile 永不遗忘 不进入淡化流程 用户身份是 Agent 个性化的基础锚点。"华东区销售总监"这类信息不会因时间推移而失效，且每用户只有 1 条，存储成本可忽略。即使用户调岗，新信息会通过 LLM 合并覆盖旧内容，而非删除。
preferences 永不遗忘 不进入淡化流程 用户偏好是 Agent 输出质量的关键。"表格展示""金额用万"等偏好一旦建立就长期有效，用户不会每次重复说明。偏好变更时通过同维度合并覆盖（新值替换旧值），不需要遗忘机制。
agent_rules 永不遗忘 不进入淡化流程 Agent 行为准则是用户对 Agent 的持久约束，每轮对话都需要注入。"回复不超过100字"这类规则除非用户主动修改，否则永远生效。矛盾时通过 LLM 融合以新为准，不需要遗忘。

  → 示例: "华为科技/张伟: 说话直接" 虽然是半年前提取的，但每次问华为相关问题都命中，说明仍有参考价值

  → 永不进入遗忘流程，不受 age_days 影响

8.1 失败驱动反思 reflect_on_failure()

触发: Agent 任务失败后
流程:
  1. 检索本轮对话中被使用的记忆
  2. LLM 分析失败原因是否与某条记忆有关
  3. 如果有 → 删除错误记忆

8.2 用户反馈反思 reflect_on_correction()

触发: 用户说"不对"/"错了"/"改一下"
流程:
  1. 检索与纠正内容相关的记忆
  2. LLM 判断哪些记忆需要修正或删除
  3. 执行修正

8.3 会话结束反思 reflect_on_session()

参考 OpenViking 的 post_session_reflection 设计。在每次 extract_and_update 完成后异步调用。

触发: extract_and_update 完成后（异步，不阻塞主流程）
输入: 本次提取的新记忆列表 + user_id

流程:
  1. 对每条新记忆，检索已有的相似记忆（排除本次写入的）
  2. 过滤高相似度候选（score > 0.7）
  3. LLM 判断关系类型:
     - no_conflict: 无矛盾，信息互补 → 不处理
     - contradiction: 直接矛盾（偏好改变、事实更正）→ 需要解决
     - evolution: 信息演进（旧信息过时但不矛盾）→ 需要解决
     - duplicate: 重复信息 → 需要解决
  4. 对每个冲突，LLM 决定解决方案:
     - update_old: 用合并内容更新旧记忆
     - archive_old: 归档旧记忆，保留新记忆
     - keep_both: 两者都保留
     - discard_new: 丢弃新记忆

返回: {"checked": N, "conflicts": N, "resolved": N, "actions": [...]}

示例:
  新记忆: "华为ERP项目金额800万，谈判阶段"
  已有记忆: "华为ERP项目金额500万，谈判阶段"
  → 关系: evolution（金额从500万调整为800万）
  → 解决: update_old（用800万更新旧记忆）

8.4 定期全局反思 reflect_global()

每日凌晨定时执行，单次遍历完成全部反思工作。通过场景判断决定每个实体需要做哪些分析，避免固定分频带来的复杂度。

8.4.1 设计原则

1. 单次执行，场景驱动
   不按"碎片/质量/一致性/洞察"分阶段分频，而是一次遍历所有 entities，
   按每个 parent_entity 的数据状态匹配场景，命中什么就处理什么。

2. LLM 按需调用
   场景指标全部是数据库统计（0 LLM 开销），只在需要合并或判断矛盾时调用 LLM。
   设置单次执行 LLM 调用上限（20 次），超出则记录跳过项，下次优先处理。

3. 与 session 反思互补
   session 反思处理"刚写入的单条新记忆"与存量的矛盾（增量、实时）。
   global 反思处理"存量整体"的健康状态（批量、每日）。
   global 的场景 C 兜底 session 可能遗漏的矛盾。

8.4.2 执行流程

触发: 每日凌晨定时任务（或手动调用）
输入: user_id
范围: entities 类别全量 + profile + preferences

Step 0: 数据加载
  ├── 从向量库拉取 user_id 下所有 entities 记忆
  ├── 从 PG 获取 profile + preferences
  ├── 按 parent_entity 分组
  └── 计算每组的场景指标

Step 1: 逐实体场景判断 + 对应处理
  对每个 parent_entity:
    1. 计算场景指标（纯数据统计，0 LLM）
    2. 匹配场景，一个实体可命中多个:
       A(碎片堆积) / B(内部矛盾) / C(高活跃稀疏)
    3. 按优先级 A > B > C 依次执行处理逻辑
    4. 检查 LLM 预算，超出则跳过并记录

Step 2: 遗忘 + 全局级检查
  ├── decay_memories(): 逐条遗忘 + 实体级沉寂检测（7.2/7.3）
  └── profile ↔ preferences 一致性检查（仅 profile 有变更时执行）

Step 3: 输出反思报告

8.4.3 场景指标定义

对每个 parent_entity 计算以下指标（纯数据库统计，不消耗 LLM）：

指标来源说明
fragment_count向量库 group by merge_key having count > 1同 merge_key 碎片组数
total_count向量库 count该实体下记忆总条数
max_similarity向量库 pairwise cosine（抽样 top-5 对）不同 merge_key 间最高相似度
recent_write_7dPG created_at > now-7d近 7 天新增记忆条数
recent_access_7dPG last_accessed_at > now-7d近 7 天被检索命中次数
days_since_last_writePG max(created_at)最后写入距今天数
days_since_last_accessPG max(last_accessed_at)最后检索距今天数
avg_age_daysPG avg(now - created_at)平均存活天数

8.4.4 场景 A: 碎片堆积

业务背景：CRM 销售场景中，用户多次提及同一项目/联系人的不同侧面信息，session 反思只处理"矛盾"关系，互补信息（no_conflict）会被跳过，导致同一 merge_key 下碎片积累。

业务示例:
  周一: "华为ERP金额从500调到800万" → merge_key="华为科技/ERP项目"
  周三: "华为ERP明天开评审会"         → merge_key="华为科技/ERP项目"
  周五: "华为评审通过了，下周签合同"   → merge_key="华为科技/ERP项目"
  → session 反思: 三条互补不矛盾，全部 no_conflict 跳过
  → 结果: 同 key 3 条碎片，应合并为 1 条完整项目时间线

判断条件: fragment_count >= 1

处理逻辑:
  1. 按 updated_at 排序（最新在前）
  2. LLM 合并（1 次调用/组）
  3. 质量校验: 合并后 content 长度 ≥ 原始最长条目的 50%
  4. 继承碎片中最高的 active_count
  5. 原子操作: 写入新条目 → 删除旧碎片

合并后示例:
  abstract: "华为科技/ERP项目: 金额800万，评审已通过，下周签合同"
  content: "华为ERP项目。金额800万（2026-03从500万调整）。
            2026-04-28评审通过。预计下周签合同。决策人: 张总(CTO)。"
  key_changes: ["2026-03 金额500→800万", "2026-04-28 评审通过"]

LLM 消耗: 每组 1 次。典型日 1-2 组，极端日 8-10 组。

8.4.5 场景 B: 内部矛盾（session 反思兜底）

业务背景：session 反思遗漏矛盾的三种情况：网络异常、merge_key 不一致、间接矛盾（关联失效）。

判断条件: max_similarity > 0.85 AND fragment_count == 0

处理逻辑:
  Step 1: 找出相似度 > 0.85 的记忆对（跨 merge_key）
  Step 2: LLM 判断关系（复用 _classify_relation，1 次/对）:
    identical → archive 热度低的
    evolution → 保留新的，archive 旧的
    contradiction → 记录异常日志，不自动处理
    unrelated → 跳过
  Step 3: 间接矛盾检测（P1 实现）
    包含状态变更关键词（离职/调岗/取消）→ 级联检查关联记忆 → 标记"待确认"

LLM 消耗: 每对 1 次。通常 0-2 对/天。

8.4.6 场景 C: 高活跃但稀疏

业务背景：用户密集问某客户问题，但该客户记忆很薄，Agent 只能给出泛泛回答。

判断条件: recent_access_7d >= 3 AND total_count <= 2

处理逻辑（不消耗 LLM）:
  不做自动修改。输出建议:
  recommendations += {"entity": "阿里巴巴", "type": "coverage_gap",
                      "message": "近7天被检索3次但仅有1条记忆"}

后续利用:
  方式1: 下次对话注入提示"你对该客户记忆较少，可主动追问补充"
  方式2: 管理后台可视化展示"记忆覆盖度预警"

十、记忆与系统数据边界

10.1 核心原则

记忆系统只记录增量认知，不记录 CRM 系统已有的结构化数据。

CRM 系统中已有的数据（客户行业、商机金额、联系人电话、活动状态等）可以通过工具实时查询获取，不需要记忆系统做镜像。记忆系统的价值在于记录系统中没有的信息——用户在对话中透露的主观判断、沟通技巧、关系洞察、隐性知识。

10.2 提取边界

✅ 记忆应该记录的（增量认知，CRM 系统中没有）:
  - 沟通风格: "张伟说话直接，开会不要绕弯子"
  - 关系洞察: "张伟和李娜有分歧，建议分别沟通"
  - 内部流程: "华为审批至少3-4周，需要过采购委员会"
  - 主观判断: "ERP项目希望最大"
  - 竞争情报: "对手报价比我们低20%"
  - 口头承诺: "丁总口头同意了报价方案"

❌ 记忆不应该记录的（系统数据，可实时查询）:
  - 客户字段: 行业、城市、员工数、营收、评分
  - 商机字段: 金额、阶段、概率、关闭日期、来源
  - 联系人字段: 职位、电话、邮箱
  - 活动字段: 类型、主题、日期、状态

10.3 提取提示词中的排除规则

在 ENTITIES_EXTRACT_PROMPT 中明确告知 LLM 不提取系统数据：

以下字段值不要作为记忆的主体内容（CRM 系统已有，可实时查询）:
- 客户: 行业、城市、员工数、营收、评分
- 商机: 金额、阶段、概率、关闭日期、来源
- 联系人: 职位、电话、邮箱
- 活动: 类型、主题、日期、状态

但客户名和人名必须保留在 merge_key / parent_entity / abstract 中作为定位锚点。

10.4 检索时的防御性设计

即使提取时偶尔混入了系统数据，Agent 也不会直接引用：

  • CRM_SYSTEM_PROMPT 中的行为约束："记忆是参考不是数据源：记忆中的客户/商机信息可能已过时，涉及具体数据（金额、阶段、电话等）时必须用工具实时查询确认"
  • source_type="system_data" 的记忆在检索结果中附加提示：[建议用工具实时查询确认最新数据]

十一、子Agent记忆提取限制

11.1 设计原则

核心规则：子Agent（Sub-Agent）不具备记忆提取能力，不能触发记忆写入流水线。

记忆提取仅在主Agent（顶层Agent）的对话上下文中触发。子Agent 作为主Agent 分派的任务执行单元，其对话内容不进入记忆系统的提取链路。

设计依据：记忆系统记录的是用户与 Agent 之间的直接交互中产生的长期认知。子Agent 的执行过程是主Agent 内部的"工作过程"，不代表用户意图的直接表达，也不包含需要跨会话复用的增量认知。

11.2 为什么子Agent不能提取记忆

维度 问题 说明
信息来源不可靠 子Agent 的输出是中间推理产物，非用户直接表达 用户说"帮我分析华为的情况"，子Agent 可能生成大量分析文本，但这些是 Agent 的推理结果而非用户透露的增量认知。将其作为记忆提取源会引入大量噪声。
上下文污染 子Agent 的对话历史混入会导致提取提示词语义漂移 记忆提取依赖 {existing_profile}、{existing_preferences} 等已有状态注入。子Agent 的执行上下文不包含这些状态，盲目提取会导致重复记忆或分类错误。
合并冲突 子Agent 产出的"事实"可能与用户实际表达矛盾 子Agent 可能基于工具返回数据做推断（如"华为ERP项目应该已签约"），但用户后续可能纠正。如果子Agent 的推断已被提取为记忆，会造成合并冲突和记忆污染。
LLM 成本膨胀 子Agent 执行频率远高于主Agent 对话轮次 一次用户请求可能触发多个子Agent 并行执行，每个子Agent 可能有多轮内部对话。如果每轮都触发 4 路并行 LLM 提取，成本将不可控。
权限边界 子Agent 是受限执行环境，不应拥有持久化写入能力 子Agent 的设计原则是"执行完即销毁"，不保留状态。赋予其记忆写入能力违背了最小权限原则。

11.3 实现机制

11.3.1 MemoryMiddleware 调用方身份识别

MemoryMiddleware.aafter_agent() 记忆提取入口:

  def aafter_agent(self, context: AgentContext):
      # 子Agent 直接跳过记忆提取
      if context.agent_type == "sub_agent":
          logger.debug(f"跳过子Agent记忆提取: agent_id={context.agent_id}")
          return

      # 只有主Agent（顶层Agent）才进入提取流水线
      if context.agent_type != "main_agent":
          return

      # 正常提取流程...
      await self._extract_and_update(context)

11.3.2 Agent 类型标识传递

Agent 类型在创建时确定，通过 context 传递:

主Agent 创建:
  context.agent_type = "main_agent"
  context.parent_agent_id = None

子Agent 创建（由主Agent 分派）:
  context.agent_type = "sub_agent"
  context.parent_agent_id = main_agent.agent_id

判断链路:
  用户消息 → 主Agent → MemoryMiddleware.aafter_agent() → ✅ 触发提取
  主Agent → 分派子Agent → 子Agent执行完毕 → MemoryMiddleware.aafter_agent() → ❌ 跳过提取

11.3.3 记忆读取权限（子Agent可读不可写）

子Agent 的记忆访问权限:

  ┌──────────────┬──────────┬──────────┐
  │ 操作          │ 主Agent  │ 子Agent  │
  ├──────────────┼──────────┼──────────┤
  │ 记忆检索注入  │ ✅        │ ✅*      │
  │ memory_read  │ ✅        │ ✅*      │
  │ 记忆提取写入  │ ✅        │ ❌       │
  │ 记忆合并      │ ✅        │ ❌       │
  │ 记忆删除      │ ✅        │ ❌       │
  └──────────────┴──────────┴──────────┘

  * 子Agent 可以读取记忆（继承主Agent 的 user_id/tenant_id），
    但读取结果不会触发 active_count 更新（避免子Agent 高频执行导致热度指标失真）。

设计理由:
  - 允许读取: 子Agent 执行任务时可能需要参考用户的偏好或历史信息
    （如"帮我写邮件"的子Agent 需要知道用户偏好的邮件风格）
  - 禁止写入: 子Agent 的执行产物不应污染用户的长期记忆
  - 不更新热度: 子Agent 一次任务可能触发数十次检索，如果每次都更新
    active_count，会导致热度指标失去"用户真实使用频率"的含义

11.4 边界场景处理

场景 处理方式 说明
子Agent 执行中用户发了新消息 新消息由主Agent 处理，正常触发提取 用户直接交互始终走主Agent 链路
子Agent 返回结果后主Agent 继续对话 主Agent 的 aafter_agent 正常触发提取 主Agent 整合子Agent 结果后回复用户，该轮对话正常进入提取
子Agent 调用工具获得了用户相关的新信息 不提取，由主Agent 回复时体现 子Agent 工具返回的信息会传回主Agent，主Agent 如果将其体现在回复中，用户确认后的对话才会触发提取
子Agent 嵌套调用子Agent（多层级） 所有非顶层 Agent 一律不提取 无论嵌套深度如何，只有 agent_type == "main_agent" 才触发提取
Skill 执行（类子Agent） Skill 执行过程不触发记忆提取 Skill 作为 Agent 的工具调用，其内部执行过程等同子Agent，不具备记忆写入能力

  └── EVOLUTION_MERGE_PROMPT（evolution 时 1 次）

12.2 提取阶段提示词（4 次 LLM）

四路提示词共享统一章节结构：识别原则 → 排除规则 → 边界判定 → 输出格式。
设计原则：语义规则驱动，不枚举具体句式，避免过拟合。

① PROFILE_EXTRACT_PROMPT — 用户画像提取

触发场景：每轮对话 after_agent 时并行调用，从用户发言中提取稳定身份属性。

从用户发言中提取【稳定、长期有效】的身份背景，合并到已有画像后输出完整版本。

## 识别原则
用户对【我 / 我们团队 / 我们公司】的稳定属性描述：
- 职位 / 履历 / 所在区域 / 长期可量化指标（KPI、预算、团队或客户规模）
- 职场状态（新入职 / 在熟悉业务 / 调岗等当前身份阶段）
- 所属组织的业务、规模、文化、工具、覆盖行业
- 允许省略主语；从语义可判为用户自述即可

判别：该信息在下一个新会话里对 Agent 理解"这个用户是谁"是否仍有帮助。

## 排除规则
以下内容不属于本路，即使句中出现"我"字：
- 个人喜好、习惯、厌恶（态度动词：喜欢/讨厌/习惯/在意）→ preferences
- 对 Agent 行为的持久指令（动作指向 Agent 产物）→ agent_rules
- 第三方事实（核心主语是第三方，含"客户反馈我们…"）→ entities
- 单次操作、临时状态、孤立数值 → 不提取

## 边界判定
- profile vs preferences：集体属性（"我们部门/团队/公司"的文化、制度、工具）→ profile；个人态度（"我个人喜欢/习惯/在意"）→ preferences
- profile vs entities：主语是"我/我们"描述自身特征 → profile；主语是第三方或描述第三方事实 → entities
- 提取 vs 不提取：稳定身份信息（跨会话仍有效）→ 提取；临时状态 → 不提取

## 输出格式
- 有新增：{"profile": {"content": "<合并后完整画像>"}}
- 无新增：{"profile": {}}

② PREFERENCES_EXTRACT_PROMPT — 用户偏好提取

触发场景：每轮对话 after_agent 时并行调用，从用户发言中提取个人喜好、习惯、标准。

从用户发言中提取【用户自己】的喜好、习惯、厌恶或个人标准。

## 识别原则
提取"描述用户本人是什么样的人"的可复用信息：
- 个人喜好与厌恶（喜欢/讨厌/受不了/偏好/倾向）
- 稳定的行为习惯（频率 / 条件 / 时间模式）
- 个人要求的品质标准（在意/要求/觉得应该）

判别：该信息脱离当前上下文后，在下一个新会话里对理解"这个用户"是否仍有价值。

## 排除规则
以下内容不属于本路，本路返空：
- 动作指向 Agent 产物的持久指令 → agent_rules。判定标准：如果去掉这句话 Agent 的输出行为会改变，则属于 agent_rules 而非 preferences。
- 描述组织/团队的集体属性 → profile
- 描述第三方的偏好或事实 → entities
- 单次反馈或操作指令（"这次 X"、"帮我 X"）→ 不提取

## 边界判定
- preferences vs agent_rules：核心主语是"我"且表达个人态度（无行为约束意图）→ preferences；句子的效果是约束 Agent 未来输出行为 → agent_rules。同时含两者时仅提取个人态度部分。
- preferences vs profile："我个人"的态度/习惯/风格 → preferences；"我们部门/团队/公司"的集体属性 → profile
- 提取 vs 不提取：可跨会话复用的稳定偏好 → 提取；单次场景的临时调整 → 不提取

## 输出格式
{"preferences": [{"slug": "<英文下划线>", "abstract": "<1句>", "overview": "<Markdown>", "content": "<完整叙述>"}]}
无偏好返回 {"preferences": []}。

③ AGENT_RULES_EXTRACT_PROMPT — Agent 行为准则提取

触发场景：每轮对话 after_agent 时并行调用，从用户发言中提取对 Agent 未来行为的持久约束。

从用户发言中提取【对 Agent 未来行为的持久约束】，合并到已有规则后输出完整版本。

## 识别原则
两个条件同时满足：
1. 行为指向 Agent：约束 Agent 的输出、沟通、流程、角色或禁止事项。标志：主语或隐含主语是 Agent / 报告 / 回复 / 邮件 / 分析等 Agent 产物。
2. 持久性：规则可复用到未来同类场景，不是"这次/刚才"的单次调整。

判别：该规则在下一次类似请求中 Agent 是否应继续遵守。

## 排除规则
以下内容不属于本路，本路返空：
- 句子整体描述用户本人的态度/习惯/性格（主语是"我"，谓语是态度动词）→ preferences
- 纯身份或组织描述 → profile
- 对第三方事实的纯陈述（动作未指向 Agent，而是描述第三方的要求/特点/状态）→ entities。判定标准：句子是在"告知 Agent 一个事实"还是"命令 Agent 做某事"？前者是 entities，后者是 agent_rules。
- 单次调整（"这次 X"）、评价（"感觉你像 X"）、感叹 → 不提取

## 边界判定
- agent_rules vs preferences：句中存在泛化的 Agent 行为约束（格式/长度/频率/渠道/流程）→ agent_rules；仅表达个人态度无 Agent 行为约束 → preferences。同时含两者时各路独立提取。
- agent_rules vs entities：动作指向 Agent → agent_rules；纯陈述第三方要求 → entities
- 提取 vs 不提取：持久性（"以后/每次/所有"等泛化标志）→ 提取；单次性（"这次/刚才/算了"）→ 不提取

## 输出格式
- 有新指令：{"agent_rules": {"content": "<合并后完整规则>"}}
- 无新指令：{"agent_rules": {}}

④ ENTITIES_EXTRACT_PROMPT — 第三方事实提取

触发场景：每轮对话 after_agent 时并行调用，从对话中提取关于第三方的客观事实。只提取增量认知，排除 CRM 系统已有字段。

从对话中提取关于【第三方】的客观事实。第三方指非用户本人、非用户所在组织、非 Agent 的对象。

## 识别原则
任何关于第三方的可复用事实：
- 角色关系 / 业务与规模 / 偏好与风格
- 第三方的要求或规则（陈述式）
- 对用户方的反馈、评价、承诺
- 竞争情报、时效性信息
- 用户对第三方的判断（主语"我"但内容描述的是第三方）

第三方主体识别：具名公司/人名/品牌、可锁定的代词、关系动词的宾语。

## 排除规则
以下内容不属于本路，本路返空：
- 用户自身的履历/团队/公司特征（无关系动词串联到第三方当前事实）→ profile
- 用户自己的偏好 → preferences
- 命令 Agent 行为的持久指令（动作指向 Agent）→ agent_rules
- 疑问句 / 纯查询 / 操作指令 → 不提取
- CRM 系统已有的结构化字段值（金额/阶段/电话/邮箱）→ 不提取

## 边界判定
- entities vs profile：主语是第三方或描述第三方事实 → entities；主语是"我/我们"描述自身特征 → profile。纯履历提到公司名但无关系动词 → profile；履历+关系动词串联到第三方当前事实 → entities
- entities vs agent_rules：纯陈述第三方的要求/特点 → entities；命令 Agent 针对该实体采取行动 → agent_rules
- 提取 vs 不提取：增量认知（系统中查不到的洞察）→ 提取；系统数据字段值 → 不提取

## 输出格式
{"entities": [{"abstract": "<1句>", "overview": "<Markdown>", "content": "<完整叙述>", "merge_key": "<公司/项目>", "parent_entity": "<父实体>"}]}
无有效实体返回 {"entities": []}。

⑤ _COMMON_OUTPUT_RULES — 共享输出规则（附加在每个提取提示词末尾）

## 输出规则
- abstract ≤50 字；overview 为 Markdown ≤200 字；content 完整叙述
- 文本使用 {output_language}（auto 则跟随对话主要语言）
- 多维度混合：同句含多维度时，各维度独立判断，各自提取属于自己的部分
- 只输出 JSON，不写其他说明

12.3 合并阶段提示词（0~2 次 LLM）

⑥ PROFILE_MERGE_PROMPT — 用户画像合并

触发场景：提取到新 profile 内容时，与 PG 中已有画像 LLM 合并为一条。每用户始终只保留 1 条 profile。

将以下用户身份信息整合为一段连贯的用户画像描述。

已有用户画像:
{existing_profile}

新增信息:
{new_info}

要求:
1. 合并已有画像和新增信息，保留所有有效的身份信息
2. 如果新增信息和已有画像矛盾，以新增为准（如职位变更）
3. 用第三人称描述（"用户是..."）
4. 控制在 200 字以内

直接输出合并后的用户画像文本，不要其他内容。

⑦ AGENT_RULES_MERGE_PROMPT — Agent 规则融合

触发场景：提取到新 agent_rules 内容时，与 PG 中已有规则 LLM 融合为一条。每用户始终只保留 1 条 agent_rules。

将以下用户对 Agent 的角色定义和行为准则整合为一段连贯的描述。

已有行为准则:
{existing_rules}

新增定义:
{new_definitions}

要求:
1. 合并已有准则和新增定义，保留所有有效的角色定义和行为准则
2. 如果新增定义和已有准则矛盾，以新增为准
3. 用第二人称描述（"你是..."、"你要..."）
4. 控制在 300 字以内

直接输出合并后的行为准则文本，不要其他内容。

⑧ DEDUP_PROMPT — 语义去重决策

触发场景：preferences 同 slug 合并时 / entities 有 merge_key 合并时 / entities 无 merge_key 且向量相似度 >0.9 时调用。LLM 判断 4 种决策。

判断如何更新长期记忆。

候选记忆:
  摘要: {candidate_abstract}
  内容: {candidate_content}

已有相似记忆:
{existing_memories}

## 候选级别决策
- skip: 候选冗余（重复/改写/过于模糊），不存储，不修改已有记忆
- create: 候选是有效的新信息，独立存储
- merge: 候选和某条已有记忆是同一主题，应合并（提供合并后的内容）
- delete: 候选使某条已有记忆完全失效

## 关键删除边界（非破坏性优先）
- 部分冲突（某些陈述冲突，其他仍有效）→ 用 merge，不要 delete
- 仅在整个已有记忆完全过时/失效时才 delete
- 绝不能因为主题/方面不匹配而删除（不同方面的记忆互不影响）
- 不确定时选择 skip 或 merge，而非 delete

## 决策优先级
1. 候选冗余 → skip
2. 同主题更新/部分矛盾 → merge（生成合并后内容）
3. 明显独立的新信息 → create
4. 已有记忆完全失效 → delete（极少使用）

返回 JSON:
{"decision":"skip|create|merge|delete","target_id":"目标ID（merge/delete时必填）",
 "reason":"原因","merged_abstract":"合并后摘要（merge时必填）",
 "merged_overview":"合并后概览（merge时必填）",
 "merged_content":"合并后完整内容（merge时必填，保留旧记忆中仍有效的信息+候选的新信息）"}

⑨ REFINE_PROMPT — 超长内容压缩

触发场景：profile 合并后超过 200 字 / agent_rules 合并后超过 300 字时自动触发，压缩到阈值以内。

压缩以下{type_name}到{max_chars}字以内。
保留所有关键信息（身份、职责、约束、流程、禁止），去掉冗余修饰语。
用简洁短句，不要套话。

原文:
{content}

直接输出压缩后的文本。

⑩ AGGREGATE_L1_PROMPT — 目录 L1 结构化聚合

触发场景：叶子节点写入后，异步触发该叶子所属目录（parent_entity）的重新聚合。收集目录下所有叶子的 content，LLM 生成结构化 Markdown 导航。

将以下多条记忆聚合为一个结构化 Markdown 目录。

目录路径: {directory_path}
记忆条目:
{l2_list}

要求:
1. 用 ## 标题分组，相关信息归到同一标题下
2. 用 - 列表列出具体信息
3. 保留所有有效信息，不要遗漏
4. 如果有矛盾信息，保留最新的

直接输出 Markdown，不要包裹在代码块中。

⑪ AGGREGATE_L0_PROMPT — 目录 L0 一句话压缩

触发场景：L1 生成后，进一步压缩为一句话摘要。该摘要会被向量化后参与检索匹配（embed(L0) → 目录节点的 vector 字段）。

将以下结构化目录压缩为一句话摘要（不超过100字）。

目录路径: {directory_path}
目录内容:
{l1_content}

直接输出一句话摘要，不要其他内容。

12.6 反思阶段提示词（0~2 次 LLM）

⑫ REFLECTION_RELATION_PROMPT — 关系判断（4 选 1）

触发场景：会话结束反思时，新提取的 entities 记忆与已有记忆向量相似度 >0.7 时调用。极简分类任务，只返回一个词。后续 action 由规则映射决定（不靠 LLM）。

判断新记忆与已有记忆的关系。

新记忆: {new}
已有记忆: {old}

关系类型只有 4 种：
- identical: 完全相同的信息（字面重复）
- contradiction: 直接矛盾（相同主体，不同结论，如"张伟是对接人" vs "李娜是对接人"）
- evolution: 信息演进（旧信息过时或被新信息补充，但不完全矛盾，如"方案阶段" → "谈判阶段"）
- unrelated: 不相关（检索召回有误，不是同一主题）

只返回一个词（identical/contradiction/evolution/unrelated），不要解释。

规则映射（Step 2，不消耗 LLM）：

identical     → discard_new（丢弃新记忆）
contradiction → archive_old（归档旧记忆）
evolution     → update_old（调用 EVOLUTION_MERGE_PROMPT 合并）
unrelated     → keep_both（不操作）

⑬ EVOLUTION_MERGE_PROMPT — 演进合并

触发场景：反思判定关系为 evolution 时调用，将新旧记忆合并为最新状态描述。

将旧记忆和新记忆合并为一条完整的最新状态描述。

旧记忆: {old_content}
新记忆: {new_content}

要求：
1. 保留旧记忆中仍然有效的信息
2. 用新记忆的信息覆盖已变化的部分
3. 不超过 200 字

直接输出合并后的完整内容。
