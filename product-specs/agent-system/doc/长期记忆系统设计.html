VikingMemoryEngine — 长期记忆系统设计文档

基于 OpenViking 范式设计，直连腾讯向量库（tcvectordb SDK），不依赖 mem0。
对齐 apps-agent（OpenViking）的核心能力，针对 CRM toB 场景做领域适配。

整体架构设计图

数据流概览：

阶段 流向 关键操作
写入 对话 → 提取 → 合并 → 存储 4路并行LLM提取 → 语义去重 → PG/向量库写入 → 目录聚合 → 异步反思
读取 查询 → 检索 → 注入 → Agent 查询改写 → hybrid_search → 目录递归展开 → 返回L0摘要 → Agent按需加载L1/L2
遗忘 定时任务 → 状态转换 → 清理 每日检测过期 → 三阶段淡化（stale→archived→deleted）→ 高热度豁免
反思 信号检测 → 冲突判断 → 修正 失败/纠正/会话结束 → 检索相关记忆 → LLM判断关系 → 归档/合并/删除

一、设计背景与技术选型

1.1 基于 OpenViking 范式的设计

本系统以 OpenViking 的文件系统范式为架构基础，完整实现了其核心设计理念：

继承的 OpenViking 核心能力：

能力 OpenViking 原始设计 本系统实现
虚拟文件系统 VikingFS（URI 路径 + 目录树） ✅ 完整实现 viking_fs.py，支持 ls/tree/read/find/rm
L0/L1/L2 三层信息模型 目录聚合 L0/L1 + 叶子 L2 ✅ 完整实现，目录节点 LLM 聚合 + 叶子节点按需加载
目录递归检索 优先队列 + 分数传播 + 收敛检测 ✅ 完整实现，α=0.5 分数传播 + Top-K 连续 3 轮不变停止
语义去重 + LLM 合并 向量预筛 + LLM 精判（skip/create/merge/delete） ✅ 完整实现 _dedup_create()
分层加载 检索返回 L0 摘要，Agent 按需加载 L1/L2 ✅ 完整实现 memory_read 工具
会话结束反思 post_session_reflection ✅ 完整实现 reflect_on_session()
定期全局反思 weekly_global_reflection ✅ 完整实现 reflect_global()
记忆遗忘 TTL + 热度驱动 ✅ 完整实现三阶段淡化 + 复活机制

针对 CRM toB 场景的领域适配：

维度 OpenViking 通用设计 本系统 CRM 适配
分类体系 9 类通用分类 精简为 4 类（profile/preferences/agent_rules/entities），聚焦 CRM 核心场景
提取架构 单路 LLM 提取 + 后分类 4 路并行 LLM 提取，每路独立提示词 + 边界规则
存储后端 通用向量库 腾讯向量库 tcvectordb（支持 BM25 稀疏向量 + filter index）+ PG 双存储
检索策略 纯向量语义检索 BM25 0.7 + 向量 0.3 混合检索（CRM 场景客户名精确匹配优先）
系统数据一致性 无（通用场景无此问题） 提取时排除 CRM 系统已有字段 + biz_id 锚定 + source_type 标记
预过滤 无 规则预过滤（寒暄/确认/工具失败跳过），节省 ~30% LLM 调用

不直接使用 OpenViking SDK 的原因：

OpenViking SDK 面向通用场景，我们需要在其范式基础上做深度定制：
1. 存储层需要直连腾讯向量库（tcvectordb SDK），利用其原生 BM25 稀疏向量和 filter index 能力
2. 提取层需要 CRM 领域专用的 4 路并行提取架构，而非通用的单路提取
3. 检索层需要 BM25 高权重混合检索，确保客户名/联系人名精确匹配优先
4. 需要与 CRM 系统数据的一致性机制（biz_id 锚定、source_type 区分、系统数据排除）

1.2 最终选型

架构范式: OpenViking（VikingFS 虚拟文件系统 + L0/L1/L2 三层 + 目录递归检索 + 反思修正）
提取层:   4 路并行 LLM 提取 + 规则预过滤（CRM 领域适配）
存储层:   腾讯向量库（tcvectordb SDK 直连，BM25 稀疏向量 + filter index）
          + PG（profile/agent_rules 权威存储 + 全量记忆生命周期管理）
检索层:   BM25 混合检索（0.7 关键词 + 0.3 向量）+ 目录递归展开 + 分层加载
组织层:   VikingFS 虚拟文件系统（viking:// URI + ls/tree/read/find/rm）

2.2 分类决策逻辑（四路并行提取）

代码实现：src/memory/extraction/prompts.py + src/memory/extraction/extractor.py

当前实现为 4 路并行 LLM 提取，每路独立判断、互不依赖：

用户发言 → 4 路并行 LLM 调用:
  ├── Profile:      用户是谁？（稳定身份属性）
  ├── Preferences:  用户偏好什么？（个人喜好/习惯/标准）
  ├── Agent Rules:  Agent 应该怎么做？（持久行为约束）
  └── Entities:     第三方有什么事实？（客户/联系人/竞品）

各路核心判别原则：

类别 核心问题 判别标准
profile 用户是谁？ 该信息在下一个新会话里对 Agent 理解"这个用户是谁"是否仍有帮助
preferences 用户偏好什么？ 该信息脱离当前上下文后，在下一个新会话里对理解"这个用户"是否仍有价值
agent_rules Agent 应该怎么做？ 该规则在下一次类似请求中 Agent 是否应继续遵守
entities 第三方有什么事实？ 关于第三方的可复用事实（角色关系/业务/偏好/竞争情报）

跨维度边界规则（每路提示词中明确定义）：

Profile 不属于:
  - 我的喜好/习惯/厌恶 → preferences
  - 对 Agent 的持久指令 → agent_rules
  - 第三方事实 → entities
  - 单次操作、孤立数值 → 不提取

Preferences 不属于:
  - 纯指向 Agent 行为的规则式指令 → agent_rules
  - 描述身份或组织 → profile
  - 描述第三方偏好/事实 → entities
  - 单次反馈/操作 → 不提取

Agent Rules 不属于:
  - 描述用户本人（个人习惯、性格、喜好）→ preferences
  - 纯身份或组织描述 → profile
  - 对第三方事实的纯陈述 → entities
  - 单次调整、评价、感叹 → 不提取

Entities 不属于:
  - 用户履历、团队或公司特征 → profile
  - 用户自己的偏好 → preferences
  - 命令 Agent 的持久指令 → agent_rules
  - 疑问句/纯查询/操作指令 → 不提取

多维度混合处理：同句含多维度时，各路独立判断、各自提取属于自己的部分。

2.3 各类别存储形式详解

每个类别的 abstract（L0）、overview（L1）、content（L2）的存储位置、是否参与检索和打分各不相同：

profile — 用户身份

存储与检索特性：

层级 字段 存储位置 参与检索 参与打分 用途
— content PG ❌ ❌ LLM 合并后的完整画像，注入提取提示词
— abstract PG ❌ ❌ 前端展示用摘要

profile 不存储在向量库，不参与语义检索。通过 get_profile() 从 PG 读取，注入提取提示词的 {existing_profile} 避免重复提取。

场景示例：

━━━ 对话场景 ━━━
[用户] 我是华东区的销售总监，管着15个人，主要跑互联网行业大客户。我们公司刚从Salesforce迁到纷享销客。

━━━ 提取 & 存储 ━━━
category:  profile
merge_key: "profile"

PG 存储:
{
  "category": "profile",
  "merge_key": "profile",
  "abstract": "用户身份: 华东区销售总监，管理15人团队，负责互联网大客户，使用纷享销客",
  "content": "用户是华东区销售总监，管理15人团队，主要负责互联网行业大客户。公司近期从Salesforce迁移到纷享销客CRM。",
  "status": "active"
}

━━━ 使用方式（不参与检索） ━━━
注入到 PROFILE_EXTRACT_PROMPT 的 {existing_profile} 占位符，避免重复提取。
不写入向量库，不参与 hybrid_search，不参与打分。

preferences — 用户偏好

存储与检索特性：

层级 字段 存储位置 参与检索 参与打分 用途
L0 abstract 向量库 ✅ embed → cosine + BM25 ✅ 0.7×BM25 + 0.3×cosine 检索匹配 + 注入 Agent 上下文
L1 overview 向量库 ❌ ❌ Agent 调用 memory_read(level="L1") 按需加载
L2 content 向量库 ❌ ❌ Agent 调用 memory_read(level="L2") 按需加载

场景示例：

━━━ 对话场景 ━━━
[用户] 以后数据展示都用表格，金额用万为单位不要小数点

━━━ 提取 & 存储 ━━━
category:      preferences
slug:          "data_display"
merge_key:     "preferences/data_display"

向量库存储（叶子节点）:
{
  "id": "mem_d4e5f6a7",
  "vector": embed("数据展示偏好: 表格格式，金额万为单位，不要小数"),       ← L0 向量化，参与检索
  "sparse_vector": BM25("数据展示偏好: 表格格式，金额万为单位，不要小数"), ← L0 稀疏向量，参与检索
  "abstract": "数据展示偏好: 表格格式，金额万为单位，不要小数",            ← L0（返回给 Agent）
  "overview": "## 偏好\n- 表格格式\n- 金额万为单位\n- 不要小数",           ← L1（按需加载）
  "content": "用户偏好表格展示数据，金额统一用万为单位且不要小数点。",      ← L2（按需加载）
  "category": "preferences",
  "merge_key": "preferences/data_display",
  "is_leaf": "true",
  "status": "active"
}

━━━ 检索时打分示例 ━━━
用户问 "用什么格式展示数据" →
  BM25("数据""展示"精确命中 abstract) → bm25_score = 0.75
  cosine(查询向量 vs abstract向量)    → cosine_score = 0.82
  final_score = 0.7 × 0.75 + 0.3 × 0.82 = 0.771 → 命中，返回 L0 摘要
  Agent 按需调用 memory_read(level="L2") 获取完整偏好

agent_rules — Agent 行为准则

存储与检索特性：

层级 字段 存储位置 参与检索 参与打分 用途
— content PG ❌ ❌ 每轮对话前作为 SystemMessage 全量注入
— abstract PG ❌ ❌ 前端展示用摘要

agent_rules 不存储在向量库，不参与语义检索。每轮对话开始时通过 get_agent_rules_text() 从 PG/缓存读取，作为 SystemMessage 注入，Agent 从第一轮就遵守。

场景示例：

第 20 次: [用户] 回复100字以内就行（与"回复不要太长"矛盾，以新为准）

merge_key: "agent_rules"

{
  "category": "agent_rules",
  "merge_key": "agent_rules",
  "abstract": "Agent行为准则: 数据分析助理，回复≤100字，华为沟通用正式语气",

━━━ 使用方式（不参与检索，全量注入） ━━━
每轮对话开始时注入 system prompt:

  │   ...                            │

entities — 第三方事实

存储与检索特性：

层级 字段 存储位置 参与检索 参与打分 用途
L0 abstract 向量库 ✅ embed → cosine + BM25 ✅ 0.7×BM25 + 0.3×cosine 检索匹配 + 注入 Agent 上下文
L1 overview 向量库 ❌ ❌ Agent 调用 memory_read(level="L1") 按需加载
L2 content 向量库 ❌ ❌ Agent 调用 memory_read(level="L2") 按需加载

entities 同时存在叶子节点和目录节点。目录节点的 L0/L1 由系统 LLM 从子叶子聚合生成，也参与检索打分。

三、L0/L1/L2 三层信息模型

对齐 apps-agent（OpenViking）：L0/L1 属于目录，L2 属于叶子。

3.1 三层定义（对齐 apps-agent）

层级 归属 生成方式 Token 量 用途
L0 目录节点 系统 LLM 聚合（从所有叶子 content 压缩为一句话） ~30-100 向量检索匹配 + 注入 Agent 上下文

3.2 目录节点 vs 叶子节点

1. 目录节点（is_leaf=false）

5.3 目录递归展开详解

为什么需要递归展开：

向量库中的记忆按目录树组织。用户问"华为的情况"时，全局检索可能命中"华为科技"目录节点（L0 聚合摘要与查询相关），但目录本身只是摘要，真正有价值的是其下的叶子节点。递归展开就是从命中的目录出发，逐层下钻找到具体的叶子记忆。

递归展开示例：

向量库中的目录结构:
  viking://user/memories/entities/华为科技/          ← 目录节点（is_leaf=false）
    ├── viking://user/memories/entities/华为科技/张伟  ← 叶子（is_leaf=true）
    ├── viking://user/memories/entities/华为科技/ERP升级 ← 叶子（is_leaf=true）
    └── viking://user/memories/entities/华为科技/审批流程 ← 叶子（is_leaf=true）

用户查询: "华为那边的情况"

Step 1 全局检索命中:
  - 目录 "华为科技: 张伟直接，ERP有分歧，审批3周" → score=0.88 → 入优先队列
  - 叶子 "华为科技/张伟: 说话直接，汇报用PPT"    → score=0.72 → 直接收集

Step 3 递归展开目录 "华为科技/":
  搜索 parent_uri="viking://user/memories/entities/华为科技/" 的子节点:
    - 华为科技/ERP升级 → own_score=0.65
      final_score = 0.5 × 0.65 + 0.5 × 0.88 = 0.765 → 收集
    - 华为科技/审批流程 → own_score=0.45
      final_score = 0.5 × 0.45 + 0.5 × 0.88 = 0.665 → 收集
    - 华为科技/张伟 → 已在 seen_ids 中，跳过

最终 Top-K（按 final_score 排序）:
  1. [DIR] 华为科技 → 0.88（目录本身也可返回）
  2. [ID]  华为科技/ERP升级 → 0.765（递归展开发现）
  3. [ID]  华为科技/张伟 → 0.72（全局直接命中）
  4. [ID]  华为科技/审批流程 → 0.665（递归展开发现）

分数传播的意义：

不用分数传播时:
  华为科技/审批流程 own_score=0.45（与"华为那边的情况"语义关联弱）→ 可能被过滤

用分数传播后:
  华为科技/审批流程 final_score = 0.5×0.45 + 0.5×0.88 = 0.665
  → 因为父目录"华为科技"高度相关，子节点获得加成，不会被遗漏
  → 效果：问"华为的情况"时，华为下的所有子记忆都能被召回

两路检索各自返回 Top-K 结果后，通过 WeightedRerank 融合：

  final_score = sparse_weight × BM25_score + dense_weight × vector_score
              = 0.7 × BM25_score + 0.3 × vector_score

权重设计原因：
  BM25 权重 0.7（高）：CRM 场景中客户名、联系人名是精确匹配需求
    "华为科技" 必须精确命中包含"华为科技"的记忆，不能被语义相近的"中兴通讯"替代
  向量权重 0.3（低）：语义补充，捕获同义词和隐含关系
    "商机情况" 可以匹配到"ERP项目有分歧"（语义相关但无关键词重叠）

向量库中有 3 个文档：

1. 目录节点（华为科技/）
   vector = embed("华为科技: 张伟直接，ERP有分歧，审批3周")  ← 参与检索（cosine）
   sparse_vector = BM25("华为科技: 张伟直接，ERP有分歧...")  ← 参与检索（关键词）
   abstract = "华为科技: 张伟直接，ERP有分歧，审批3周"       ← 向量化的源文本
   overview = "## 联系人\n- 张伟...\n## 商机\n- ERP..."     ← 不参与检索（按需加载）
   content = ""                                             ← 目录没有 content

2. 叶子节点（华为科技/ERP项目）
   vector = embed("华为科技/ERP项目: 张伟和李娜有分歧")      ← 参与检索
   sparse_vector = BM25("华为科技/ERP项目: 张伟和李娜...")   ← 参与检索
   abstract = "华为科技/ERP项目: 张伟和李娜有分歧"           ← 向量化的源文本
   content = "ERP项目张伟和李娜意见有分歧，建议分别沟通..."   ← 不参与检索（按需加载）

3. 叶子节点（华为科技/张伟）
   vector = embed("华为科技/张伟: 说话直接，汇报用PPT")      ← 参与检索
   sparse_vector = BM25("华为科技/张伟: 说话直接...")        ← 参与检索
   abstract = "华为科技/张伟: 说话直接，汇报用PPT"           ← 向量化的源文本
   content = "张伟说话直接不绕弯子，汇报用PPT带数据..."       ← 不参与检索（按需加载）

总结：

字段 是否参与检索匹配 用途
vector（embed(abstract)） ✅ cosine similarity 语义匹配
sparse_vector（BM25(abstract)） ✅ 关键词精确匹配
abstract ❌（是向量化的源文本） 检索返回给 Agent 的 L0 摘要
overview（L1） ❌ Agent 调用 memory_read(level="L1") 时返回
content（L2） ❌ Agent 调用 memory_read(level="L2") 时返回

5.6 分层加载

检索默认返回 L0 摘要（~30 tokens/条），Agent 按需加载 L1/L2：

  L0 够用 → Agent 直接回答（不调用 memory_read）
  需要目录结构 → memory_read(id=DIR_ID, level="L1") → 返回结构化 Markdown
  需要叶子详情 → memory_read(id=LEAF_ID, level="L2") → 返回完整记忆内容

Token 开销对比：
  5 条 L0 注入: 5 × 30 = 150 tokens
  按需加载 2 条 L2: 2 × 200 = 400 tokens
  总计: 550 tokens（vs 直接返回 5 条 L2 = 1000 tokens）

六、记忆合并策略

6.1 按类别差异化

类别 合并方式 触发条件 实现方法
profile 始终合并（追加） 每次 profile 记忆写入 _merge_profile(): 搜索已有 → 内容追加 → 删旧写新
preferences 同 aspect 替换 merge_key 相同且相似度 > 0.8 _merge_by_key(): 按 merge_key 搜索 → 替换（向量库）
entities 同实体替换 merge_key 相同且相似度 > 0.8 _merge_by_key(): 按 merge_key 搜索 → 替换
events 不合并 相似度 > 0.9 时 LLM 判断 _dedup_create(): 向量预筛 + LLM 精判
cases 不合并 相似度 > 0.9 时 LLM 判断 _dedup_create(): 向量预筛 + LLM 精判
patterns 同流程合并 merge_key 相同 _merge_by_key()
tools 同工具合并 merge_key = 工具名 _merge_by_key()
skills 同技能合并 merge_key = 技能名 _merge_by_key()

6.2 语义去重流程（entities 无 merge_key 时）

当 entities 类记忆没有明确的 merge_key 时（LLM 未能生成结构化的实体路径），通过语义去重避免重复存储：

候选记忆（无 merge_key 的 entities）
  │
  ▼
向量预筛: 搜索已有同类别记忆，取 Top-3
  │
  ├── 最高相似度 < 0.9 → 直接 create（新信息，独立存储）
  │
  └── 最高相似度 >= 0.9 → 调 LLM 精判（DEDUP_PROMPT）
        │
        ├── skip:   候选与已有记忆重复/改写 → 不存储，不修改已有
        ├── create:  虽然相似但确实是新信息 → 独立存储
        ├── merge:  同主题的信息更新 → LLM 生成合并内容，替换旧记忆
        └── delete: 已有记忆完全失效 → 删除旧记忆，存储新记忆（极少使用）

场景示例：

━━━ 场景 1: skip（重复信息，不存储）━━━

已有记忆:
  abstract: "华为科技/ERP项目: 内部张伟和李娜有分歧，建议分别沟通"

新提取候选:
  abstract: "华为ERP项目张伟和李娜意见不一致，需要分开沟通"

向量预筛: 相似度 = 0.94（> 0.9）→ 调 LLM 精判
LLM 判断: skip（语义重复，只是换了说法）
结果: 不存储候选，已有记忆不变


━━━ 场景 2: merge（信息演进，合并更新）━━━

已有记忆:
  abstract: "华为科技/ERP项目: 内部张伟和李娜有分歧，建议分别沟通"
  content:  "华为ERP项目内部张伟和李娜有分歧，建议分别沟通。"

新提取候选:
  abstract: "华为科技/ERP项目: 分歧已解决，张伟方案获批"
  content:  "华为ERP项目内部分歧已解决，最终采用张伟的方案，李娜也同意了。"

向量预筛: 相似度 = 0.91（> 0.9）→ 调 LLM 精判
LLM 判断: merge（同主题信息更新，旧信息部分过时）
LLM 生成合并内容: "华为ERP项目此前张伟和李娜有分歧，现已解决，最终采用张伟方案。"
结果: 删除旧记忆 → 写入合并后的新记忆


━━━ 场景 3: create（相似但不同主题）━━━

已有记忆:
  abstract: "华为科技/张伟: 说话直接，汇报用PPT，开会控制30分钟"

新提取候选:
  abstract: "华为科技/张伟: 下周出差两周，期间找李娜对接"

向量预筛: 相似度 = 0.92（> 0.9，因为都是"华为科技/张伟"）→ 调 LLM 精判
LLM 判断: create（虽然主体相同，但是全新的时效性信息，不是对旧信息的更新）
结果: 独立存储为新记忆

注: 如果该候选有 merge_key="华为科技/张伟"，则走 _merge_by_key 逻辑直接合并，
    不会进入语义去重流程。语义去重只处理无 merge_key 的情况。

七、记忆遗忘策略

7.1 各类别遗忘策略

类别 保留天数 遗忘策略 设计逻辑
profile 永不遗忘 不进入淡化流程 用户身份是 Agent 个性化的基础锚点。"华东区销售总监"这类信息不会因时间推移而失效，且每用户只有 1 条，存储成本可忽略。即使用户调岗，新信息会通过 LLM 合并覆盖旧内容，而非删除。
preferences 永不遗忘 不进入淡化流程 用户偏好是 Agent 输出质量的关键。"表格展示""金额用万"等偏好一旦建立就长期有效，用户不会每次重复说明。偏好变更时通过同维度合并覆盖（新值替换旧值），不需要遗忘机制。
agent_rules 永不遗忘 不进入淡化流程 Agent 行为准则是用户对 Agent 的持久约束，每轮对话都需要注入。"回复不超过100字"这类规则除非用户主动修改，否则永远生效。矛盾时通过 LLM 融合以新为准，不需要遗忘。
entities 180 天 三阶段淡化（active → stale → archived → deleted） 第三方事实有时效性。"张伟下周出差"半年后已无意义；"华为ERP项目谈判阶段"可能早已签约或丢单。180 天是 CRM 销售周期的经验值（大客户商机平均 3-6 个月关闭）。但高热度记忆（active_count ≥ 3）即使过期也保留——频繁被检索说明仍有价值。

7.2 遗忘条件

遗忘判断（仅 entities 类别，每日凌晨定时任务执行）:

过期 AND 低热度:
  age_days > 180 AND active_count < 3
  → 进入三阶段淡化

过期 BUT 高热度:
  age_days > 180 AND active_count >= 3
  → 保留为 active（频繁被检索到的记忆即使过期也有价值）
  → 示例: "华为科技/张伟: 说话直接" 虽然是半年前提取的，但每次问华为相关问题都命中，说明仍有参考价值

profile / preferences / agent_rules:
  → 永不进入遗忘流程，不受 age_days 影响

7.3 全量清理策略

不受 _RETENTION_DAYS 限制，直接物理删除：

触发场景 清理范围 触发方式 操作
租户过期/注销 该 tenant_id 下所有用户的全部记忆 平台管理接口 / 定时任务检测租户状态 PG 物理删除 + 向量库按 tenant_id filter 批量删除
用户离职/停用 该 user_id 下的全部记忆（所有类别） HR 系统 Webhook / 管理后台手动触发 PG 物理删除 + 向量库按 user_id filter 批量删除

八、反思修正机制

8.1 失败驱动反思 reflect_on_failure()

触发: Agent 任务失败后
流程:
  1. 检索本轮对话中被使用的记忆
  2. LLM 分析失败原因是否与某条记忆有关
  3. 如果有 → 删除错误记忆

8.2 用户反馈反思 reflect_on_correction()

触发: 用户说"不对"/"错了"/"改一下"
流程:
  1. 检索与纠正内容相关的记忆
  2. LLM 判断哪些记忆需要修正或删除
  3. 执行修正

8.3 会话结束反思 reflect_on_session()

参考 OpenViking 的 post_session_reflection 设计。在每次 extract_and_update 完成后异步调用。

触发: extract_and_update 完成后（异步，不阻塞主流程）
输入: 本次提取的新记忆列表 + user_id

流程:
  1. 对每条新记忆，检索已有的相似记忆（排除本次写入的）
  2. 过滤高相似度候选（score > 0.7）
  3. LLM 判断关系类型:
     - no_conflict: 无矛盾，信息互补 → 不处理
     - contradiction: 直接矛盾（偏好改变、事实更正）→ 需要解决
     - evolution: 信息演进（旧信息过时但不矛盾）→ 需要解决
     - duplicate: 重复信息 → 需要解决
  4. 对每个冲突，LLM 决定解决方案:
     - update_old: 用合并内容更新旧记忆
     - archive_old: 归档旧记忆，保留新记忆
     - keep_both: 两者都保留
     - discard_new: 丢弃新记忆

返回: {"checked": N, "conflicts": N, "resolved": N, "actions": [...]}

示例:
  新记忆: "华为ERP项目金额800万，谈判阶段"
  已有记忆: "华为ERP项目金额500万，谈判阶段"
  → 关系: evolution（金额从500万调整为800万）
  → 解决: update_old（用800万更新旧记忆）

8.4 定期全局反思 reflect_global()

参考 OpenViking 的 weekly_global_reflection 设计。建议每天或每周执行一次。

触发: 定时任务（每天/每周）或手动调用

Step 1: 碎片化检测与合并
  ├── 遍历向量库中所有类别（entities/events/cases/patterns）
  ├── 按 merge_key 分组
  ├── 同 merge_key 超过 1 条 → LLM 合并为 1 条
  └── 删除旧碎片，写入合并后的新条目

Step 2: 一致性检查（profile vs preferences）
  ├── 从 PG 获取 profile 和 preferences
  ├── LLM 检查两者是否矛盾
  └── 记录不一致项（不自动修复，留给人工确认）

Step 3: 过时检测
  └── 调用 cleanup_expired() 清理过期 + 低热度记忆

返回: {"merged": N, "inconsistencies": N, "stale_marked": N}

八-C、记忆与系统数据一致性

9C.1 问题分析

当前 entities 类记忆用客户名称做 merge_key 和 parent_entity，存在两个根本性问题：

问题 1：系统数据变更 → 记忆过时

时间线:
  T1: 对话中提取记忆 → "华为科技/ERP升级: 金额500万，谈判阶段"
  T2: 销售在 CRM 系统中修改了商机金额 → 800万
  T3: 用户问 "华为ERP项目多少钱" → Agent 检索到记忆 → 回答 "500万"（错误！）

根因: 记忆存的是对话时刻的数据快照，不是系统数据的引用

问题 2：实体重命名 → 记忆孤儿

时间线:
  T1: 记忆中有 5 条 parent_entity="华为科技" 的记忆
  T2: 管理员在 CRM 中把客户名改为 "深圳华为科技"
  T3: 用户问 "深圳华为科技的商机" → 向量库 filter parent_entity="深圳华为科技" → 0 条命中
      用户问 "华为科技的商机" → 命中 5 条，但客户名已经不对了

根因: merge_key 和 parent_entity 用的是名称字符串，不是系统 ID

9C.2 记忆应该记什么 vs 不应该记什么

这是核心设计决策。entities 类记忆不应该做系统数据的镜像，而应该记录对话中产生的增量认知：

❌ 不应该记的（系统已有的结构化数据）:
  "华为科技/ERP升级: 金额500万，谈判阶段"
  → 这些数据在 CRM 系统中已经存在，Agent 可以实时查询
  → 存成记忆 = 存了一份会过时的快照

✅ 应该记的（对话中产生的、系统中没有的增量认知）:
  "华为科技/ERP升级: 张总倾向选方案B，对价格敏感，建议不要主动提折扣"
  "华为科技/张总: 喜欢先看数据再讨论，不喜欢PPT，每次会议控制在30分钟内"
  "华为科技: 内部审批流程复杂，至少需要3周，建议提前准备材料"
  → 这些是销售在对话中透露的主观判断、沟通技巧、隐性知识
  → CRM 系统中没有这些字段，只有记忆系统能存

9C.3 解决方案：双锚点 + 分层存储

方案核心:
  1. entities 记忆绑定系统 record_id（不依赖名称字符串）
  2. 区分"系统数据摘要"和"增量认知"两种记忆类型
  3. 系统数据变更时通过 Webhook 级联更新记忆

方案 A：record_id 锚定（推荐）

在 entities 记忆中增加 biz_id 字段，绑定 CRM 系统的 record_id：

当前存储:
  merge_key:     "华为科技/ERP升级"      ← 名称字符串，会过时
  parent_entity: "华为科技"              ← 名称字符串，会过时

改进后存储:
  merge_key:     "华为科技/ERP升级"      ← 仍然保留（用于人类可读的目录展示）
  parent_entity: "华为科技"              ← 仍然保留（用于目录展示）
  biz_id:        "opp_12345"            ← 新增：CRM 系统的 record_id（不变的锚点）
  biz_parent_id: "acc_67890"            ← 新增：父实体的 record_id
  biz_type:      "opportunity"          ← 新增：业务实体类型

检索时:
  优先用 biz_id filter（精确匹配，不受改名影响）
  fallback 到 merge_key / parent_entity（兼容无 biz_id 的旧记忆）

方案 B：增量认知 vs 数据摘要分离

entities 记忆拆成两个子类型:

  entities_summary（数据摘要）:
    来源: 工具返回的结构化数据
    特点: 会过时，需要定期刷新或标记 TTL
    示例: "华为科技/ERP升级: 金额500万，谈判阶段"
    TTL:  24小时（过期后下次检索时实时查询系统数据替代）

  entities_insight（增量认知）:
    来源: 对话中的主观判断、隐性知识
    特点: 不会因系统数据变更而失效
    示例: "华为科技/ERP升级: 张总倾向方案B，对价格敏感"
    TTL:  180天（正常遗忘策略）

检索时:
  entities_summary → 检查 TTL，过期则标记为 stale，提示 Agent 实时查询
  entities_insight → 正常返回，不受系统数据变更影响

方案 C：实体重命名级联更新

CRM 系统 Webhook → 记忆系统:

  事件: 客户名称变更（华为科技 → 深圳华为科技）
  │
  ▼
  记忆系统收到 rename 事件:
    1. 查询所有 biz_parent_id = "acc_67890" 的记忆
    2. 批量更新:
       parent_entity: "华为科技" → "深圳华为科技"
       merge_key: "华为科技/ERP升级" → "深圳华为科技/ERP升级"
       abstract: 替换文本中的 "华为科技" → "深圳华为科技"
       重新 embed(abstract) → 更新 vector
    3. 记录一条 events 记忆:
       "2026-04-28 客户华为科技更名为深圳华为科技"

9C.4 推荐实施路径

Phase 1（短期，改提取逻辑）:
  ├── 修改 EXTRACTION_PROMPT，要求 LLM 区分"数据摘要"和"增量认知"
  ├── 数据摘要类记忆标记 source_type="system_data"，设置短 TTL
  ├── 增量认知类记忆标记 source_type="insight"，正常 TTL
  └── 检索时对 stale 的数据摘要标记 [可能已过时]

Phase 2（中期，加 biz_id 锚定）:
  ├── 提取时从 ToolMessage 中解析 record_id
  │   （工具返回的数据通常包含 id 字段）
  ├── 存储时写入 biz_id / biz_parent_id / biz_type
  ├── 检索时优先用 biz_id filter
  └── 向量库 collection 增加 biz_id filter index

Phase 3（长期，Webhook 级联）:
  ├── CRM 系统数据变更时发送 Webhook
  ├── 记忆系统接收 Webhook，级联更新相关记忆
  ├── 实体重命名时批量更新 merge_key / parent_entity / abstract
  └── 重新 embed 更新后的 abstract

9C.5 提取提示词改进

当前 EXTRACTION_PROMPT 的问题:
  LLM 会把工具返回的结构化数据（金额、阶段、电话）原样提取为记忆
  这些数据在 CRM 系统中已经存在，存成记忆是冗余且会过时的

改进方向:
  1. 明确告诉 LLM: 不要提取系统中已有的结构化字段值
  2. 重点提取: 用户的主观判断、沟通策略、隐性知识、关系洞察
  3. 对于必须提取的数据摘要，标记 source_type

改进后的提取规则（增加到 EXTRACTION_PROMPT）:

  ## 提取优先级
  - 高优先级（必须提取）:
    用户的主观判断: "张总对价格很敏感"
    沟通策略: "建议先展示ROI再谈价格"
    关系洞察: "张总和李经理有分歧，需要分别沟通"
    隐性知识: "华为内部审批至少3周"
    用户偏好: "喜欢表格展示"

  - 低优先级（可选提取，标记 source_type="system_data"）:
    实体属性快照: "ERP项目金额500万"
    联系人信息: "张总电话139-xxxx"
    → 这些数据系统中已有，提取时标记为数据摘要

  - 不提取:
    工具返回的原始数据（"查到5条记录..."）
    操作描述（"用户请求查询..."）
    通用知识

9C.6 各场景处理方式

场景 当前行为 改进后行为
商机金额变更 记忆过时，Agent 回答旧数据 数据摘要 TTL 过期 → Agent 实时查询系统
客户名称变更 记忆孤儿，检索不到 biz_id 锚定 → 不受改名影响；Webhook 级联更新名称
联系人离职 记忆中仍有旧联系人 数据摘要 TTL 过期 → 不再返回；insight 类记忆保留（"张总喜欢先看数据"仍有参考价值）
商机关闭 记忆中仍显示"谈判阶段" 数据摘要 TTL 过期；events 记忆记录"商机已关闭"
新增商机 需要对话才能产生记忆 数据摘要可选同步；insight 仍需对话产生

十一、成本估算

单次对话的记忆成本:

  预过滤: 0（纯代码规则）
  LLM 提取: ~800 tokens input + ~300 tokens output = ~$0.0002
  工具统计: 0（纯 Python）
  语义去重: ~500 tokens（仅 events/cases 触发）= ~$0.0001
  Embedding: ~100 tokens × 3 条 = ~$0.00003
  向量库写入: 免费（腾讯向量库按存储计费）

  单次对话总成本: ~$0.0003

月均成本（100 个销售用户，每人每天 30 次对话）:
  100 × 30 × 30 × $0.0003 = $27/月

SOUL 蒸馏（额外）:
  100 × 30 × $0.0003 = $0.9/月

总计: ~$28/月（可忽略）
