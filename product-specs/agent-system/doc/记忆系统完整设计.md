# 记忆系统完整设计 — 提取·检索·遗忘·反思·一致性

> 本文档整合了记忆提取与检索、记忆遗忘与反思、记忆与系统数据一致性三份设计方案。
> 所有设计逻辑与代码实现完全对齐（代码入口：`src/memory/extraction/`、`src/memory/viking_engine.py`、`src/middleware/memory.py`）。

## 一、架构总览

### 1.1 四路并行提取架构

代码实现：`src/memory/extraction/extractor.py` → `MemoryExtractor.extract_all()`

```
用户消息 → MemoryMiddleware.aafter_agent()
  │
  ▼
预过滤（_should_extract: 最少 1 轮 + 50 tokens）
  │
  ▼
四路并行提取（MemoryExtractor）:
  ├── profile:      用户画像（PG 存储，LLM 合并）
  ├── preferences:  用户偏好（向量库，按 slug 合并）
  ├── agent_rules:  Agent 行为准则（PG 存储，LLM 融合）
  └── entities:     第三方事实（向量库，按 merge_key 合并）
  │
  ▼
语义去重 + 分类合并（_dedup_and_store）
  │
  ▼
会话反思（reflect_on_session，仅 entities）
```

### 1.2 记忆分类体系

| 类别 | 存储位置 | 合并策略 | 遗忘策略 |
|:---|:---:|:---|:---|
| profile | PG | 每用户 1 条，LLM 合并（PROFILE_MERGE_PROMPT） | 不遗忘，超 200 字精炼 |
| preferences | 向量库 | 按 slug 合并（同 slug 覆盖） | 不遗忘，同 slug 覆盖 |
| agent_rules | PG | 每用户 1 条，LLM 合并（AGENT_RULES_MERGE_PROMPT） | 不遗忘，超 300 字精炼 |
| entities | 向量库 | 按 merge_key 合并（LLM 生成合并内容） | 三阶段淡化（180 天） |

### 1.3 L0/L1/L2 三层结构

每条记忆存储三层信息：

```
向量库中每条记忆:
  {
    abstract: "华为科技/ERP项目: 张总倾向方案B",     ← L0（摘要，用于向量检索）
    overview: "## 洞察\n- 倾向方案B\n## 建议...",    ← L1（结构化 Markdown）
    content:  "华为科技ERP项目关键决策人张总...",     ← L2（完整内容）
  }
```

目录级聚合按需生成（`aggregate_directory()`），不持久化：
- 查询某目录下所有 L2 → LLM 聚合生成目录级 L1 → LLM 压缩生成目录级 L0
- 用于 VikingFS.tree() 展示、前端类别概览

## 二、提取设计

### 2.1 设计原则

1. **来源区分**：`[工具:xxx]` 返回的是系统数据，`[用户]`/`[助手]` 说的才可能有增量认知
2. **排除法**：列出不提取的（系统字段），剩下的都提取
3. **不过拟合**：不枚举"应该提取什么"，让 LLM 自己判断
4. **紧凑**：每个提示词 ≤ 1500 chars

### 2.2 四路提取提示词设计

代码位置：`src/memory/extraction/prompts.py`

#### Profile（用户画像）

识别原则：用户对"我/我们团队/我们公司"的稳定属性描述。

核心边界：
- 主语是"我" + 描述身份/背景 → profile
- 主语是第三方 → entities
- 主语是 Agent 产物 → agent_rules
- 个人喜好/习惯 → preferences

#### Preferences（用户偏好）

识别原则：描述"用户本人是什么样的人"的可复用信息。

核心边界：
- 个人喜好与厌恶、稳定行为习惯、个人品质标准 → preferences
- 纯指向 Agent 行为的规则式指令 → agent_rules
- 描述身份或组织 → profile
- 第三方偏好/事实 → entities

#### Agent Rules（行为准则）

识别原则：两个条件同时满足 — 行为指向 Agent + 持久性（可复用到未来同类场景）。

核心边界：
- "以后分析要深入一些" → agent_rules（持久反馈式规则）
- "这次分析深入一些" → 不提取（单次）
- "跟 <实体> 沟通要用正式语气" → agent_rules（命令 Agent）
- "<实体> 那边要求正式语气" → entities（陈述事实）
- "我喜欢 X"（无 Agent 行为约束） → preferences

#### Entities（第三方事实）

识别原则：任何关于第三方的可复用事实。

核心边界：
- 第三方角色关系/业务/偏好/风格 → entities
- 用户对第三方的判断（主语"我"但内容描述第三方） → entities
- 用户履历/团队/公司特征 → profile
- 命令 Agent 的持久指令 → agent_rules
- 疑问句/纯查询/操作指令 → 不提取

### 2.3 系统数据排除规则

**核心原则：记忆系统只记录 CRM 系统中不存在的增量认知，不做系统数据的镜像。**

判断标准：这条信息能通过 query_data 工具实时查到吗？能 → 不提取；不能 → 提取。

排除法（在 entities 提取中生效）：

```
以下字段值不要作为记忆的主体内容（CRM 系统已有，可实时查询）:
- 客户: 行业、城市、员工数、营收、评分
- 商机: 金额、阶段、概率、关闭日期、来源
- 联系人: 职位、电话、邮箱
- 活动: 类型、主题、日期、状态
- 线索: 公司、电话、来源、状态、评分

但客户名和人名必须保留在 merge_key / parent_entity / abstract 中作为定位锚点。
```

正确示例：
- ✅ "华为科技/张伟: 喜欢PPT汇报，开会不要绕弯子"（增量认知）
- ❌ "华为科技/张伟: 职位IT总监，电话138xxx"（系统数据快照，会过时）

### 2.4 多维度混合处理

一句话同时含多维度时，各维度独立判断、各自提取属于自己的部分：
- "我喜欢简洁，你回复不超过 3 句" → preferences 取"偏好简洁"，agent_rules 取"回复不超过 3 句"
- "你是我的CRM顾问，我们用的是纷享销客" → agent_rules 取"角色: CRM顾问"，profile 取"使用纷享销客"

### 2.5 预过滤

代码位置：`src/memory/viking_engine.py` → `_should_extract()`

```python
_SKIP_PATTERNS = frozenset(
    "你好 您好 hi hello hey 在吗 好的 ok 是的 对 嗯 收到 明白 了解 "
    "谢谢 感谢 thanks 再见 拜拜 bye".split()
)
```

跳过条件：消息轮次 < 1 或 tokens < 50 或纯寒暄。

## 三、检索设计

### 3.1 检索流程

代码位置：`src/memory/viking_engine.py` → `retrieve()`

```
查询 → embed → 全局向量搜索（hybrid_search）
  │
  ▼
分离目录节点和叶子节点
  │
  ├── 目录节点 → 入优先队列，递归展开子节点
  └── 叶子节点 → 直接收集
  │
  ▼
递归展开（分数传播: α × 自身分数 + (1-α) × 父目录分数）
  │
  ▼
收敛检测（Top-K 连续 3 轮不变则停止）
  │
  ▼
后处理:
  - stale 状态记忆: 分数 ×0.5，标注 [可能过时]
  - archived 状态: 不返回（filter 过滤）
  - source_type="system_data": 附加提示 "[建议用工具实时查询确认最新数据]"
  │
  ▼
异步更新 PG（last_accessed_at + active_count + 复活逻辑）
```

### 3.2 检索结果格式

```
<memory_context>
以下是与当前问题相关的记忆摘要（L0）。
- [DIR:xxx] 是目录摘要，调用 memory_read(memory_id=xxx, level='L1') 获取结构化概览
- [ID:xxx] 是记忆摘要，调用 memory_read(memory_id=xxx, level='L2') 获取完整内容

  - [DIR:mem_001] [entities] 华为科技: 3个商机，张伟为主要对接人
  - [ID:mem_002] [entities] 华为科技/ERP升级: 张总倾向方案B，对价格敏感
  - [ID:mem_003] [preferences] 数据展示偏好: 表格格式，金额用万为单位
</memory_context>
```

### 3.3 Agent Rules 注入

代码位置：`src/middleware/memory.py` → `abefore_agent()`

Agent Rules 作为 SystemMessage 在每轮对话前注入，让 Agent 从第一轮就知道行为准则。

### 3.4 状态过滤与降权

| 状态 | 检索行为 |
|:---|:---|
| active | 正常返回，正常排序 |
| stale | 返回但分数 ×0.5，标注 [可能过时] |
| archived | 不返回（向量库 filter 过滤） |
| deleted | 物理删除，不存在 |

### 3.5 复活机制

检索命中 stale/archived 状态的记忆时，异步更新 PG：
- last_accessed_at = now
- active_count += 1
- 状态恢复为 active（由定时任务在下次 decay 时判断）

代码位置：`_update_access_batch()`

## 四、合并策略

### 4.1 各类别合并逻辑

代码位置：`src/memory/viking_engine.py` → `_dedup_and_store()`

| 类别 | 路由 | 合并方式 |
|:---|:---|:---|
| profile | PG | `_merge_single_record()` → LLM 合并（PROFILE_MERGE_PROMPT），每用户 1 条 |
| agent_rules | PG | `_merge_single_record()` → LLM 合并（AGENT_RULES_MERGE_PROMPT），每用户 1 条 |
| preferences | 向量库 | `_merge_by_key()` → 同 slug 时 LLM 合并（DEDUP_PROMPT），保留旧记忆中仍有效的信息 |
| entities（有 merge_key） | 向量库 | `_merge_by_key()` → 同 merge_key 时 LLM 合并（DEDUP_PROMPT） |
| entities（无 merge_key） | 向量库 | `_dedup_create()` → 语义去重（>0.9 时 LLM 判断 skip/create/merge/delete） |

### 4.2 去重决策（DEDUP_PROMPT）

LLM 返回 4 种决策：

| 决策 | 含义 | 操作 |
|:---|:---|:---|
| skip | 候选冗余 | 不存储，不修改已有 |
| create | 有效新信息 | 独立存储 |
| merge | 同主题更新 | LLM 生成合并内容，替换旧记忆 |
| delete | 已有完全失效 | 删除旧记忆（极少使用） |

决策优先级：skip > merge > create > delete

关键删除边界：
- 部分冲突 → merge，不要 delete
- 仅在整个已有记忆完全过时/失效时才 delete
- 不确定时选择 skip 或 merge

### 4.3 向量库写入字段

```python
{
    "id": record_id,
    "vector": vec,
    "text": abstract,           # 用于 BM25
    "abstract": abstract,       # L0
    "overview": overview,       # L1
    "content": content,         # L2
    "category": category,
    "merge_key": merge_key,
    "parent_entity": parent_entity,
    "user_id": user_id,
    "uri": leaf_uri,            # 虚拟文件系统路径
    "parent_uri": parent_uri,
    "is_leaf": "true",
    "thread_id": thread_id,
    "source_type": source_type, # "insight" / "system_data"
    "status": "active",
    "created_at": now,
    "updated_at": now,
}
```

## 五、遗忘机制

### 5.1 设计原则

1. **检索链路只走向量库**，PG 不参与检索关键路径
2. **向量库只读不写**（检索时），所有更新通过异步任务或定时任务完成
3. **向量库只存 status**（FilterIndex），last_accessed_at 和 active_count 只存 PG
4. **status 变更通过定时任务批量同步到向量库**，不是每次检索都同步

### 5.2 三阶段淡化

代码位置：`src/memory/viking_engine.py` → `decay_memories()`

状态转换：

```
active ──过期+30天无检索──→ stale ──30天无检索──→ archived ──30天无检索──→ deleted
  ▲                          │                      │
  │         被检索命中         │       被检索命中       │
  └──────────────────────────┘                      │
  └─────────────────────────────────────────────────┘
```

各类别生命周期：

| 类别 | active 期 | + stale | + archived | 总生命周期 |
|:---|:---:|:---:|:---:|:---:|
| entities | 180 天 | 30 天 | 30 天 | 240 天 |
| patterns（未来扩展） | 365 天 | 30 天 | 30 天 | 425 天 |

### 5.3 数据存储分工

```
向量库存：status（FilterIndex，检索时过滤用）
PG 存：  status + last_accessed_at + active_count（生命周期管理用）

检索时（实时，只读向量库）：
  用户查询 → hybrid_search(filter: status != "archived") → 代码中 stale 降权 → 返回

检索后（异步，写 PG）：
  UPDATE ai_agent_memory SET last_accessed_at=now, active_count+=1 WHERE vector_id IN (...)

每日凌晨（定时任务）：
  从 PG 读 last_accessed_at → 判断状态转换 → 更新 PG + 批量同步向量库 status
```

### 5.4 profile / agent_rules 精炼

代码位置：`_refine_if_needed()`

每次 LLM 合并后检查长度，超限自动压缩：
- agent_rules 超过 300 字 → LLM 压缩（REFINE_PROMPT）
- profile 超过 200 字 → LLM 压缩（REFINE_PROMPT）

### 5.5 配置常量

```python
_RETENTION_DAYS = {
    "profile": 9999, "preferences": 9999, "agent_rules": 9999,  # 不遗忘
    "entities": 180,
}
_STALE_GRACE_DAYS = 30
_ARCHIVE_GRACE_DAYS = 30
_AGENT_RULES_MAX_CHARS = 300
_PROFILE_MAX_CHARS = 200
_TOOL_DECAY_FACTOR = 0.7
```

## 六、反思机制

### 6.1 为什么需要反思

merge 只能处理同 merge_key 的更新。跨 merge_key 的语义矛盾需要反思兜底：

| 场景 | merge 能处理 | 需要反思 |
|:---|:---:|:---:|
| 华为/ERP: 方案→谈判（同 key 更新） | ✅ | ❌ |
| 华为/张伟→华为/李娜（换人） | ❌ | ✅ |
| 重复事件（同一会议记两次） | ❌ | ✅ |
| 跨层级策略矛盾 | ❌ | ✅ |
| 偏好更新（同 key 覆盖） | ✅ | ❌ |

### 6.2 三种反思机制

代码位置：`src/memory/viking_engine.py` + `src/middleware/memory.py`

| 反思类型 | 触发来源 | 触发时机 | 覆盖范围 |
|:---|:---|:---|:---|
| 会话结束反思 | extract_and_update 完成后 | 实时（只对 entities） | 新记忆 vs 已有记忆的跨 key 矛盾 |
| 失败驱动反思 | AI 报错 / Tool 失败 | 实时（middleware 自动检测） | 错误记忆导致的执行失败 |
| 用户反馈反思 | 用户说"不对"/"错了" | 实时（middleware 自动检测） | 用户主动纠正的记忆 |

全局反思（`reflect_global()`）：碎片合并 + 一致性检查，建议每周执行。

### 6.3 触发优先级

单轮对话最多触发 1 种反思（middleware 中按优先级判断）：

```
P0: 用户反馈反思（强信号：消息前 30 字包含"不对"/"错了"等）
P1: 失败驱动反思（AI 回复报错 / Tool status=error）
P2: 会话结束反思（提取到 entities 新记忆）
```

### 6.4 信号检测

代码位置：`src/middleware/memory.py`

失败信号（`_detect_ai_failure`）：
```python
_AI_ERROR_PATTERNS = (
    "查询失败", "调用失败", "执行失败", "报错",
    "未找到", "查不到", "没有找到", "返回为空", "空结果",
    "无法", "error", "failed", "not found", "exception",
)
```

用户纠正强信号（`_detect_correction_signal`）：
```python
_STRONG_CORRECTION_KEYWORDS = (
    "不对", "错了", "搞错了", "说错了",
    "改一下", "更正", "修正一下",
    "你错了", "你记错了", "不是这样",
)
```

### 6.5 冷却机制

代码位置：`ReflectionCooldown` 类

| 反思类型 | 冷却时间 | 冷却 key |
|:---|:---:|:---|
| session | 5 秒 | thread_id |
| failure | 60 秒 | thread_id |
| correction | 30 秒 | thread_id |
| global | 6 小时 | user_id |

### 6.6 会话反思：两步法冲突检测

代码位置：`reflect_on_session()` + `_classify_relation()` + `_apply_reflection_action()`

**Step 1：LLM 判断关系类型（REFLECTION_RELATION_PROMPT，4 选 1）**

```
- identical: 完全相同（字面重复）
- contradiction: 直接矛盾（同一角色/主体，不同结论）
- evolution: 信息演进（旧信息过时，新信息补充）
- unrelated: 不相关
```

**Step 2：规则映射到 action（不靠 LLM）**

```python
_RELATION_TO_ACTION = {
    "identical":     "discard_new",    # 丢弃新记忆
    "contradiction": "archive_old",    # 归档旧记忆
    "evolution":     "update_old",     # LLM 合并新旧内容覆盖旧记忆
    "unrelated":     "keep_both",      # 不操作
}
```

相似度阈值：`_REFLECTION_SIMILARITY_THRESHOLD = 0.7`

只对 entities 类别触发：`_REFLECTION_CATEGORIES = {"entities"}`

### 6.7 反思不超出记忆提取的边界

反思不做独立边界校验，信任记忆提取的结果。边界规则的单一数据源是提取提示词。

## 七、系统数据一致性

### 7.1 问题定义

三个问题场景：

**场景 A：系统数据字段变更** — 记忆中存了"500万谈判阶段"，CRM 中已改为"800万closing"

**场景 B：实体名称变更** — 记忆中 parent_entity="华为科技"，CRM 中改为"深圳华为科技有限公司"

**场景 C：实体被删除/合并** — 记忆指向不存在的客户

根因：记忆系统把"工具返回的结构化数据"和"对话中的增量认知"混在一起存储。

### 7.2 解决方案

#### 场景 A：提取时排除系统数据（已实现）

策略：提取时 LLM 优先提取增量认知，系统数据不记。

```
对话:
  [用户] 查一下华为的商机
  [工具] 返回 ERP升级500万谈判阶段
  [助手] 华为ERP升级项目500万，谈判阶段。张总说他倾向方案B。

提取结果:
  ✅ "华为科技/ERP升级: 张总倾向方案B，对价格敏感"  (source_type=insight)
  ❌ "华为科技/ERP升级: 金额500万，谈判阶段"       (系统数据，不记)
```

纯查询对话（无增量认知）→ 提取结果为空，这是正确行为。

#### 场景 B：biz_id 锚定 + rename_entity()

代码位置：`rename_entity()`

记忆存储时绑定业务 ID：
```
merge_key:     "华为科技/ERP升级"      ← 人类可读（用于展示）
parent_entity: "华为科技"              ← 人类可读（用于展示）
biz_id:        "opp_001"              ← 系统锚点（不变）
biz_parent_id: "acc_001"              ← 父实体锚点（不变）
```

biz_id 来源：从 ToolMessage 中解析 record_id。无法获取时退化为名称字符串匹配。

rename_entity() 级联更新：
1. 查询所有 biz_parent_id = target_id 的记忆
2. 批量替换 merge_key / parent_entity / abstract 中的旧名称
3. 重新 embed(abstract) 更新向量

#### 场景 C：实体删除/合并

- 删除：标记相关记忆为 archived，或依赖遗忘策略自然过期
- 合并：调 rename_entity() + reflect_global() 碎片合并

### 7.3 检索时的防御性设计

即使记忆中存了过时的系统数据，Agent 也不会直接引用：

CRM_SYSTEM_PROMPT 中的行为约束：
> "记忆是参考不是数据源：记忆中的客户/商机信息可能已过时，涉及具体数据（金额、阶段、电话等）时必须用工具实时查询确认"

source_type="system_data" 的记忆在检索结果中附加提示：`[建议用工具实时查询确认最新数据]`

## 八、完整数据流

### 8.1 写入流程

```
用户消息 → MemoryMiddleware.aafter_agent()
  │
  ├── 预过滤（_should_extract）
  │     └── 不满足条件 → 跳过
  │
  ├── 四路并行提取（MemoryExtractor.extract_all）
  │     ├── profile → PROFILE_EXTRACT_PROMPT → 已有画像 + 新增 → LLM 合并
  │     ├── preferences → PREFERENCES_EXTRACT_PROMPT → 按 slug 分条
  │     ├── agent_rules → AGENT_RULES_EXTRACT_PROMPT → 已有规则 + 新增 → LLM 合并
  │     └── entities → ENTITIES_EXTRACT_PROMPT → 排除系统数据 → 按 merge_key 分条
  │
  ├── 分类路由（_dedup_and_store）
  │     ├── profile/agent_rules → PG（_store_to_pg → _merge_single_record）
  │     ├── preferences（有 slug） → 向量库（_merge_by_key）
  │     ├── entities（有 merge_key） → 向量库（_merge_by_key）
  │     └── entities（无 merge_key） → 向量库（_dedup_create）
  │
  ├── PG 同步（_sync_to_pg，异步，用于前端展示）
  │
  ├── 会话反思（_safe_reflect_on_session，异步，仅 entities）
  │
  └── Agent Rules 更新（_update_agent_rules，如有变更）
```

### 8.2 读取流程

```
用户消息 → MemoryMiddleware.abefore_agent()
  │
  ├── 获取当前查询（_get_current_query）
  │
  ├── 查询改写（rewrite_query，多轮上下文时）
  │
  ├── 向量检索（retrieve）
  │     ├── embed → hybrid_search（全局）
  │     ├── 目录递归展开（分数传播 + 收敛检测）
  │     ├── stale 降权 / archived 过滤
  │     └── 异步更新 PG（last_accessed_at + active_count）
  │
  ├── 格式化（_format_memory → <memory_context>）
  │
  ├── Agent Rules 注入（get_agent_rules_text → SystemMessage）
  │
  └── 注入到 Agent 上下文（SystemMessage）
```

### 8.3 反思触发流程

```
MemoryMiddleware.aafter_agent()
  │
  ├── P0: 检测用户纠正信号（_detect_correction_signal）
  │     └── 强信号 + 冷却通过 → reflect_on_correction()
  │           └── 向量搜索相关记忆 → LLM 判断矛盾 → 删除错误记忆
  │
  ├── P1: 检测失败信号（_detect_ai_failure / _detect_tool_failure）
  │     └── 有失败 + 冷却通过 → reflect_on_failure()
  │           └── 向量搜索相关记忆 → LLM 判断是否因错误记忆导致 → 删除
  │
  └── P2: 会话反思（在 extract_and_update 内部触发）
        └── 新提取的 entities → reflect_on_session()
              └── 向量搜索已有记忆 → 两步法（关系判断 + action 映射）
```

## 十二、风险与权衡

### 12.1 不记系统数据的风险

**风险：Agent 失去"上次查到什么"的上下文**

缓解：
- 同一会话内：上下文在 messages 列表中，不需要记忆
- 跨会话时：Agent 可以重新调 query_data 查询
- 纯查询对话提取不到任何记忆 → 这不是问题，数据在系统中，下次查还是一样

**风险：混合对话中增量认知和系统数据交织**

处理：
- 提示词要求只保留增量认知部分
- 可以接受："华为科技/ERP升级: 张总倾向方案B"（merge_key 中包含商机名是定位用的）
- 不可以接受："华为科技/ERP升级: 金额500万，谈判阶段，张总倾向方案B"

### 12.2 biz_id 不可用的降级

用户口头提到客户（没有调工具查询）→ biz_id 为空 → 退化为名称字符串匹配。
这种记忆通常是 insight 类，即使客户改名，内容本身仍然有价值。

### 12.3 提取质量的依赖

LLM 可能仍然提取系统数据。缓解：
1. 提取提示词中明确列出"不提取"的字段类型
2. 后处理中自动检测纯结构化字段 → 标记为 system_data 或丢弃
3. 定期 reflect_global() 清理纯系统数据类记忆
4. CRM_SYSTEM_PROMPT 中的防御性约束：涉及具体数据时必须用工具实时查询确认
