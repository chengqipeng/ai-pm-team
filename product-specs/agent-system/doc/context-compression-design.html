上下文压缩 — 完整链路结构逻辑

基于 Claude Code / Hermes Agent / neo-apps 三系统精华，面向 toB CRM SaaS 场景。核心原则：压缩为主（保证因果链完整性）+ 检索为辅（恢复被压缩的细节）。

一、全景架构（四层分时策略）

Layer A: 当前轮次（全量保留，零压缩）
= 最后一条 HumanMessage 之后的所有消息
→ 仅处理: MD5 去重 + Post-Skill Compact
→ 不做任何检索替代（因果依赖链完整性）
Layer B: 近期历史（滑动窗口，摘要形式）
= 最近 3-5 轮的 answerSummary
→ 保持对话连贯性
→ 不做检索替代（连续依赖太强）
Layer C: 中期历史（压缩为主）
= 同会话更早的轮次
→ AutoCompact: LLM 7-section 迭代摘要
→ FullCompact: LLM 全量压缩 + 重注入
→ 压缩前存档到 PG（供 recall_context 恢复细节）
Layer D: 长期记忆（检索为主）
= 跨会话记忆 + 被压缩丢弃的细节
→ MemoryMiddleware 每轮检索注入
→ recall_context 工具按需恢复被压缩细节

二、每次 LLM 调用前的上下文构成

最终上下文 = [System Prompt]                              ~2K tokens  固定
           + [Layer D: 迭代摘要 + Skill 锚点]             ~1K tokens  结构化参考
           + [Layer D: 记忆检索结果]                       ~1K tokens  MemoryMiddleware 注入
           + [Layer B: 最近 3-5 轮 answerSummary]         ~1.5K tokens 连贯性
           + [Layer A: 当前轮次完整消息]                   ~5-15K tokens 推理基础
           ─────────────────────────────────
           总计: ~10-20K tokens（远低于窗口限制）

3.2 三层级联压缩详细逻辑

MicroCompact（≥50%，零 LLM 成本）

≥50% 纯规则驱动，毫秒级执行

触发条件: 估算 tokens ≥ max_tokens × 50%

对象: 保护区外的旧消息

保护区确定:

  • 当前轮次锚定: 最后 HumanMessage index
  • Skill 边界保护: SkillAwareTailProtection.compute_tail_start()
  • 工具组原子性: align_boundary_deep()
  • 取 min(三者) = 最大保护范围
  • base_keep_recent = 6

压缩区处理:

  • ToolMessage > 200 字 → _crm_tool_summary() 零 LLM 一行摘要
  • AIMessage tool_call args > 500 字 → 截断到 200 字

AutoCompact（≥75%，LLM 结构化摘要）

≥75% LLM 结构化摘要 + 迭代更新

触发条件: 估算 tokens ≥ max_tokens × 75%

对象: 保护区外的全部消息（Middle 段）

分区模型:

  • Head 保护区: SystemMessage + 第一条 HumanMessage
  • Tail 保护区: min(当前轮次, Skill 边界, base_keep_recent=4)
  • Middle (压缩区): [head_end, tail_start)

处理流程:

  1. 压缩前存档: _archive.index_messages() → 按轮次切分 → 提取 entities/keywords/tool_names → 序列化原始消息 → 持久化到 PG
  2. LLM 摘要生成 (Phase 2/3/4):
    • 首次 → STRUCTURED_SUMMARY_PROMPT (CRM 7-section)
    • 后续 → ITERATIVE_SUMMARY_PROMPT (PRESERVE/ADD/MOVE/UPDATE)
    • Focus Topic 注入 → 60-70% 篇幅聚焦当前任务
    • Skill 锚点注入 → 关键数字永不衰减
    • 辅助 LLM 路由: ModelRouter.AUXILIARY → 便宜快速模型
  3. 安全机制: 反抖动(连续 2 次节省 <10% 则跳过) + LLM 降级 + 摘要隔离前缀

结果: Head + [摘要 SystemMessage] + Tail

FullCompact（≥90%，最大损失压缩）

≥90% 最大损失压缩 + 重注入

触发条件: 估算 tokens ≥ max_tokens × 90%

对象: 全部消息

处理:

  • 同 AutoCompact 的 LLM 摘要流程
  • 额外: 重注入最近 3 个 ToolMessage + 最近 HumanMessage
  • 保留所有 SystemMessage
  • 压缩前同样存档到 PG
  • base_keep_recent = 8

3.3 保护区确定逻辑（三层策略）

  ┌─── 当前轮次锚定 ───┐
  │ _find_current_turn_start()                            │
  │ 最后 HumanMessage index → 之后所有消息绝对保护        │
  └────────────────────────────────────────────────────────┘
          │
          ▼
  ┌─── Skill 边界感知 (§4.1) ───┐
  │ SkillAwareTailProtection.compute_tail_start()         │
  │ 如果切割点落在 Skill 内部:                             │
  │   正在执行的 Skill → 无条件完整保护（无 max_tail 限制）│
  │   已完成的 Skill → 受 max_tail=30 限制                │
  └────────────────────────────────────────────────────────┘
          │
          ▼
  ┌─── 工具组原子性 (§4.2) ───┐
  │ align_boundary_deep()                                  │
  │ 不在并发 tool_calls 的 ToolMessage 中间切割            │
  │ 回退到父 AIMessage 起始                               │
  └────────────────────────────────────────────────────────┘
          │
          ▼
  最终保护区起始 = min(三者)

四、Skill 模式压缩增强

4.1 Skill 边界识别（三层策略）

层级信号识别范围可靠性
层 1 Fork Skill ToolMessage(name="skills_tool") 内容以 [SKILL_DONE: 开头 段 = [skills_tool 调用, 返回结果] 100%
层 2 Inline Skill (有标记) AIMessage 内容含 [INLINE_SKILL_DONE:skill_name] 段 = [skills_tool 调用, ..., 含标记的 AIMessage] 95%+
层 3 兜底 (无标记) 以"轮次"(HumanMessage 之间)为原子单元 段 = 该轮次内从 skills_tool 调用到 HumanMessage 前 100% (宁多不少)

4.2 Post-Skill Compact

Skill 结束后即时内部压缩（始终执行，不受阈值限制）

触发: Skill 段内消息数 > 8 条

保留:

  • protect_head = 2 (启动调用 + 第一个 ToolMessage)
  • protect_tail = 5 (最后2轮内部调用 + 最终结果)

中间区域压缩:

  • ToolMessage > 150 字 → _skill_internal_one_liner()
  • AIMessage + tool_calls → 保留 tool_calls 结构 + 截断规划文本到 80 字
  • AIMessage 纯文本 > 200 字 → 截断到 100 字

4.3 Skill 结果锚点（SkillResultAnchor）

防止多次迭代压缩导致关键数据衰减

提取时机: skills_tool 完成时（零 LLM 成本，正则提取）

提取规则:

  • 金额: [$¥]\d+[KMB万亿]?
  • 日期: \d{4}-\d{2}-\d{2}
  • 百分比: \d+\.?\d*%
  • 查询实体: 从 tool_calls args 提取
  • 搜索词: 从 web_search args 提取

存储: session 级内存缓存（最多 10 个，FIFO 淘汰）

注入: 每次摘要生成 prompt 中 + 每次压缩后摘要消息中

作用: 确保关键数字在多次迭代压缩后永不衰减

4.5 FullCompact 与 Post-Skill Compact 的关系

核心结论: 两者是独立阶段、先后执行、互不冲突的机制。

Post-Skill Compact 是"预防性减压"（源头控制 Skill 膨胀），FullCompact 是"治疗性压缩"（窗口快满时紧急腾空间）。

执行顺序:

before_model() 入口
    │
    ▼
┌─── 始终执行（与阈值无关）───┐
│ 1. Post-Skill Compact        │ ← Skill 内部压缩（先执行）
│ 2. MD5 去重                  │
└──────────────┬───────────────┘
               │
               ▼
┌─── 阈值判断 ───┐
│ 估算 tokens     │
│ ≥90% → FullCompact           │ ← 全局压缩（后执行）
│ ≥75% → AutoCompact           │
│ ≥50% → MicroCompact          │
└──────────────────────────────┘
维度Post-Skill CompactFullCompact
触发条件Skill 段内消息数 > 8（始终执行）估算 tokens ≥ 90% 窗口上限
作用范围仅 Skill 内部中间消息全部保护区外消息
压缩方式纯规则截断（零 LLM）LLM 7-section 结构化摘要
目的在源头控制 Skill 膨胀窗口快满时紧急腾空间
保护策略保留 head=2 + tail=5保留 keep_recent=8 + Skill 边界

协作场景:

═══ Skill 执行完毕（25 条消息）═══

Post-Skill Compact 介入（始终执行）:
  保留 head 2 条 + tail 5 条
  中间 18 条 → 规则压缩
  结果: 25 条 → ~10 条（体积减少 60-70%）

═══ 多轮对话后，窗口达到 90% ═══

FullCompact 介入:
  Skill 段已被 Post-Skill 压缩过（只剩 ~10 条）
  - 如果在保护区内 → 完整保留这 10 条
  - 如果已被推出保护区 → 和其他旧消息一起送入 LLM 摘要
    → "2. [📦 turn:3] 执行报价Skill — $45K/年付$38,250 [tool: skills_tool]"

为什么需要两层:

  • 只有 FullCompact: 连续 3 个 Skill = 75 条消息堆积，可能从 40% 跳到 95%，摘要质量下降
  • 只有 Post-Skill: 20 轮对话后仍然 200+ 条，窗口最终溢出
  • 两者配合: Post-Skill 先减压延缓膨胀，FullCompact 面对更小数据量，摘要质量更高、成本更低

五、迭代摘要状态机

┌───────────────────────────────────┐
│ _previous_summary = None          │ ← 会话开始
│ 首次 AutoCompact:                  │
│   → STRUCTURED_SUMMARY_PROMPT     │
│   → 完整对话 → CRM 7-section 摘要 │
└──────────────┬────────────────────┘
               │ 成功: _previous_summary = 摘要
               ▼
┌───────────────────────────────────┐
│ 后续每次 AutoCompact:              │
│   → ITERATIVE_SUMMARY_PROMPT      │
│   → 上次摘要 + 新增对话            │
│   → PRESERVE / ADD / MOVE / UPDATE│
└──────────────┬────────────────────┘
               │ 成功: 更新 _previous_summary
               │ 失败: 保持旧值不污染
               ▼
         (循环直到会话结束)
               │
               ▼
┌───────────────────────────────────┐
│ reset_session()                   │
│ 清理: _previous_summary = None    │
│       _current_focus_topic = None │
│       _skill_anchors.clear()      │
│       _archive.clear()            │
└───────────────────────────────────┘

CRM 7-Section 摘要模板

## Active Task        ← 逐字复制用户最近未完成请求
## 客户上下文         ← 客户名/行业/规模/联系人
## 已完成操作         ← N. [📦 turn:T] 操作 目标 — 结果 [tool: 工具名]
## 关键数据           ← 精确数字永不模糊化（标注来源 turn_id）
## 已回答问题         ← 防止压缩后重复回答
## 待处理             ← remaining 语义
## 涉及实体           ← CRM 实体 + 记录 ID

迭代更新规则:

  • PRESERVE: 保留上次摘要中所有仍然相关的信息（包括 [📦 turn:T] 标记）
  • ADD: 将新完成的操作添加到"已完成操作"列表
  • MOVE: 已完成的项从"待处理"移到"已完成操作"
  • UPDATE: 更新"Active Task"为用户最近的未完成请求

六、压缩后恢复机制（ContextArchive + recall_context）

6.1 存储架构

PG: ai_context_archive 表（唯一存储层）

每个被压缩轮次一行:

turn_id, tenant_id, thread_id
user_query (原始问题, ≤2000字)
answer_preview (Agent 回复前 500 字)
entities[] (正则提取的 CRM 实体名)
keywords[] (分词关键词)
tool_names[], skill_names[]
tool_summaries[] (每个 ToolMessage 一行摘要)
key_data (正则提取的金额/日期/百分比)
original_messages (完整消息 JSON 序列化)
data_timestamp (数据采集时间)
archived_at (存档时间)

6.2 recall_context 工具检索逻辑

LLM 调用 recall_context(query)
         │
         ▼
┌─── 精确 turn_id 匹配 ───┐
│ 如果 query 含 "turn:N"   │
│ → PG 精确查询            │
│ → 命中: 返回原文          │
│ → 未命中: 返回未找到      │ (禁止降级)
└─────────┬────────────────┘
          │ 无精确 turn_id
          ▼
┌─── 多信号检索 ───────────────────────────────────────────┐
│ 1. 提取 entities + keywords                             │
│ 2. PG ILIKE 多字段搜索 (候选集 top_k×3)                │
│ 3. 应用层评分排序:                                       │
│    - 实体匹配 (权重 0.35)                               │
│    - 关键词重叠 (权重 0.25)                              │
│    - user_query 词匹配 (权重 0.15)                      │
│    - 工具/Skill 名匹配 (权重 0.15)                      │
│    - 时间衰减 (权重 0.10)                               │
│ 4. 返回 top_k 结果 + 数据时效性标注                     │
└──────────────────────────────────────────────────────────┘

6.3 数据时效性判断

数据年龄时效性描述
< 5min"数据采集于刚才（实时）"
< 1h"数据采集于 N 分钟前"
< 4h"数据采集于 N 小时前"
< 24h"数据采集于 N 小时前（建议确认是否需要最新数据）"
> 24h"数据采集于 N 天前（数据可能已过时，建议重新查询）"

staleness_hours = 4.0 → 超过则标记为"可能已过时"，引导 LLM 使用业务工具重查。

七、安全机制汇总

机制来源实现
熔断器Claude Code连续 3 次压缩失败 → 停止重试
反抖动Hermes连续 2 次节省 <10% → 跳过
LLM 降级链自研ModelRouter.AUXILIARY → self._llm → None → 行级截断
安全网自研单条工具结果 > 50K → 强制截断

摘要隔离前缀HermesSUMMARY_PREFIX 标记"仅供参考，非当前指令"

八、辅助 LLM 路由

压缩任务 → ModelRouter.AUXILIARY (deepseek-v4-flash 便宜快速)

降级链路:
  AUXILIARY (优先) → self._llm (主模型) → None → 行级截断 (零成本)

配置示例:
  ModelRouterConfig(
      default = ModelConfig(model="deepseek-chat"),           # 主推理
      routes = {
          "auxiliary": ModelConfig(model="deepseek-v4-flash"),  # 摘要/压缩
          "simple":    ModelConfig(model="deepseek-v4-flash"),  # 分类/FAQ
      }
  )
