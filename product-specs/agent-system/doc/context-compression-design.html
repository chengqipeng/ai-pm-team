🗜️ Agent 上下文压缩链路

四层级联压缩 + Skill 边界感知 + VDB 存档恢复  |  基于 Hermes Agent + Claude Code 最佳实践

为什么需要这套机制
上下文压缩
模型窗口有限，多轮对话后上下文溢出导致 Agent 无法继续工作
Token 预算
上下文信息过多时 LLM 注意力分散，遗漏关键业务约束做出错误判断
recall_context
压缩后用户追问明细时，避免重新查询导致数据快照不一致（前后矛盾）
压缩让 Agent 能持续工作，预算让 Agent 保持专注，recall 让 Agent 前后一致。
一、设计哲学
核心矛盾：
  业务需要完整数据 → LLM 才能做出准确判断
  窗口有限 (100K tokens) → 放不下所有数据
  用户要快 → 不能每次都调 LLM 做压缩

解法：不是"砍数据"，而是"分层管控 + 按需恢复"

原则 ①
不到阈值不压缩
窗口没压力时完整保留一切，不做任何预防性裁剪
原则 ②
当前轮次绝对保护
LLM 正在推理的因果链不可破坏，任何压缩只作用于历史
原则 ③
压缩不等于丢弃
被压缩的原文存入 VDB，用户追问或 LLM 需要时随时恢复

压缩执行链路（before_model 阶段，每次 LLM 调用前）
Stage 0 · 安全网截断 wrap_tool_call · 极端防御 始终检查 · 几乎不触发
纯防御性机制 — 正常工具返回（500~5000 字符）完整保留，仅对极端异常（工具 bug 返回未分页全量数据、爬虫拉回整页 HTML 等）做紧急截断。生产环境触发概率 < 1%。
触发条件：单条 ToolMessage > 20,000 字符（从 token 预算推导: 保护区预算 20K tokens × 50% × 2 字符/token）

按数据类型分发处理 ▸
数据类型检测方式处理策略保留信息
JSON 对象 内容以 { 开头 提取关键字段（name/id/industry/amount/stage/status）拼接为一行摘要 记录身份 + 核心业务状态
JSON 数组 内容以 [ 开头 提取记录数 + 前 5 条的 name/title + 金额汇总 + 阶段分布 数据规模 + 代表性样本 + 聚合统计
Markdown / 长文本 含换行符、非 JSON 格式 提取前 3 行有意义文本（20~200字符的行）作为摘要预览 文档结构骨架 + 关键结论
HTML / 富文本 含 <html> 或 <div> 标签 同 Markdown 策略：提取有意义的纯文本行 页面核心内容（去标签噪音）
兜底（未知格式） 上述规则均未命中 保留前 SAFETY_CAP / 10（约 5K）字符 + 原始长度标注 内容前缀 + 元信息（便于 LLM 判断是否需要重查）
跳过工具（不做安全网截断） ▸
工具跳过原因
skills_tool由 SkillExecutor 自行管理内部消息，Post-Skill Compact 负责压缩
agent_tool子 Agent 调用结果由子 Agent 内部处理完毕后返回摘要
ask_user用户交互消息不可截断（保证对话完整性）
read_skill_resource知识文件/资源文件内容，Skill 执行依赖完整原文不可截断
设计意图：安全网阈值从 token 预算体系推导（非硬编码），公式: tail_token_budget × 50% × 2。含义: 单条工具结果最多占用保护区预算的一半。窗口越大阈值越宽松，窗口越小阈值越严格。如果此阶段频繁触发，说明上游工具需要增加分页/限流逻辑。
Stage 1 · Post-Skill Compact Skill 增强 始终执行
已完成的 Skill 执行段满足触发条件时，即时压缩中间工具调用过程。
触发条件（任一满足即触发）：
  条件 A：Skill 内部消息数 > 8 条（多轮调用场景）
  条件 B：Skill 内部估算 token > 4000（少轮但单条结果巨大，如 web_search 返回 8K+ 字符）
  两条件均不满足 → 不压缩（Skill 够短且内容量小）

边界识别（三层策略）：
  层 1：Fork Skill → [SKILL_DONE:] 前缀精确终止（100% 可靠）
  层 2：Inline Skill → [INLINE_SKILL_DONE:xxx] 标记（95%+）
  层 3：兜底 → 以 HumanMessage / 下一个 skills_tool 为终止

保护策略：
  protect_head = 2（skills_tool 调用 + prompt/启动确认）
  protect_tail = 5（最后 2 轮内部调用 + 最终结果）
  中间区：ToolMessage > 150字 → 一行摘要 | AIMessage 规划文本 → 截断到 80字
Stage 2 · MD5 去重 始终执行
从末尾向前遍历，相同内容的 ToolMessage 只保留最新一份。
算法：MD5 前 12 位作为 key，content < 100 字符 跳过
替换内容："[重复结果 — 与最近一次相同查询结果一致]"
典型场景：LLM 重复调用 query_schema / query_data 同一实体
Stage 3 · 阈值触发压缩 条件触发
估算当前 token 用量，按阈值触发三级压缩（优先使用 LLM 真实 usage 回填值）。
级别触发条件处理方式LLM 成本
MicroCompact ≥ 50% 窗口 保护区外旧 ToolMessage → CRM 一行摘要 + tool_call args > 500字截断到 200字 零
AutoCompact ≥ 75% 窗口 压缩区 → LLM 7-section 结构化摘要（迭代更新） + Skill 锚点注入 1 次辅助模型
FullCompact ≥ 90% 窗口 全量 LLM 摘要 + 重注入最近 3 个 ToolMessage + 最近 HumanMessage 1 次辅助模型
安全机制： 熔断器（连续 3 次失败 → 停止重试）| 反抖动（连续 2 次节省 <10% → 跳过）| LLM 降级链（AUXILIARY → 主模型 → 行级截断）
保护区划定（决定哪些消息不被压缩）
Head 保护区 SystemMessage + 第一条 HumanMessage
压缩区（送入 LLM 摘要 / 规则裁剪） head_end ... tail_start 之间的全部消息
Tail 保护区（绝对保护） 当前轮次 + Skill 边界 + 工具组原子性
Tail 计算规则（取最大保护范围）：

tail_start = min(current_turn_start, skill_boundary_start)
tail_start = align_boundary_deep(messages, tail_start)

① 当前轮次锚定：最后一条 HumanMessage 之后 → 全部保护
② Token 预算：尾部保护区最多占 max_tokens × 20%（soft_ceiling = 1.5×）
③ Skill 边界感知：切割点在 Skill 内部 → 推进到 Skill 起始位置
    • 正在执行的 Skill → 无条件完整保护（不受 max_tail 限制）
    • 已完成的 Skill → 受 max_tail=30 条限制
④ 工具组原子性：切割点在并发 ToolMessage 中间 → 回退到父 AIMessage

LLM 结构化摘要（AutoCompact / FullCompact 核心）
CRM 7-Section 模板：

## Active Task — 逐字复制用户最近未完成请求（最重要字段）
## 客户上下文 — 客户名称 / 行业 / 规模 / 关键联系人
## 已完成操作 — N. 操作 目标 — 结果摘要 [tool: 工具名]
## 关键数据 — 精确数字永不模糊化（$45,000 ≠ "约4.5万"）
## 已回答问题 — 防止压缩后重复回答
## 待处理 — 未完成请求（remaining 语义，非指令）
## 涉及实体 — CRM 实体 + 记录 ID

迭代更新策略（Phase 3）：
首次 → STRUCTURED_SUMMARY_PROMPT（完整对话 → 7-section）
后续 → ITERATIVE_SUMMARY_PROMPT（上次摘要 + 新增 → PRESERVE / ADD / MOVE / UPDATE）
超长驱逐 → 摘要 >1200字时："已回答问题"只保留最近 3 条

关键设计决策
Skill 内部执行逻辑是否保留？
查询类 Skill → 不保留（中间工具调用无因果依赖）
决策类 Skill → 由 VDB 存档兜底恢复
为什么不做源头压缩？
对齐 Hermes：当前轮次工具结果 LLM 必须完整看到（因果链完整性 > 空间节省）
迭代摘要 vs 全量重生成？
迭代更新（PRESERVE/ADD）防止多次压缩导致早期信息衰减
辅助 LLM 为什么独立路由？
ModelRouter.AUXILIARY → 便宜快速模型，摘要失败不阻塞主推理链路
正在执行的 Skill 为何无条件保护？
Skill 执行中被部分压缩 → LLM 丢失已完成工具结果 → 后续工具选择和参数失败
为什么用 MD5 而非字符串比较？
工具结果可达数十 KB，逐字符比较 O(n²) 太慢；MD5 前 12 位碰撞概率 ≈ 1/281 万亿

Post-Skill Compact — 压缩细节设计
定位：Skill 执行完成后的即时内部压缩。不等全局阈值触发，Skill 一完成就将内部工具调用过程收缩，从源头控制上下文膨胀。
时机：每次 LLM 调用前的 before_model 阶段，在 MD5 去重和全局阈值检查之前执行。
成本：零 LLM 调用，纯规则处理，毫秒级完成。
触发条件（OR 关系，任一满足即触发）
条件 A · 消息条数
> 8 条
多轮工具调用场景
（竞品调研 10+ 步、多实体关联查询）
OR
条件 B · Token 总量
> 4,000
少轮但单条结果巨大
（web_search 返回 8K+、query_data 50条商机）
两个条件均不满足 → 不压缩（Skill 够短且内容量小，完整保留）
两种压缩模式（根据消息数自动选择）
模式 A · 删除中间条目
适用：消息数 ≥ protect_head + protect_tail (7条)
■ protect_head = 2
  ① skills_tool 调用 AIMessage
  ② Skill prompt/启动确认 ToolMessage

■ 中间区 → 规则压缩
  ToolMessage > 150字 → 一行摘要
  AIMessage(tool_calls) → 规划文本截断到 80字
  AIMessage(纯文本) > 200字 → 截断到 100字

■ protect_tail = 5
  最后 2 轮内部工具调用 + 最终结果
模式 B · 就地压缩大内容
适用：消息数 < 7 但 token > 4000（少轮大内容）
■ 保留第一条和最后一条完整
  第一条: skills_tool 调用
  最后一条: Skill 最终结果

■ 中间每条就地压缩
  ToolMessage > 500字 → 一行摘要替换
  AIMessage(tool_calls) > 150字 → 截断保留 tool_calls
  AIMessage(纯文本) > 300字 → 截断到 150字

■ 不删除任何条目
  消息结构完整，只是每条内容变短
一行摘要生成策略（_skill_internal_one_liner）
核心原则: 关键数字不丢失 — 即使截断了原文，金额/百分比/日期通过正则/结构提取保留在摘要中。

与其他压缩机制的协作
阶段Post-Skill Compact 的角色
Skill 完成时 立即执行，将内部 12K tokens 压到 ~3K。后续 LLM 调用看到的已经是压缩后的 Skill 段
全局 MicroCompact 压缩后的 Skill 段如果在保护区外，ToolMessage 被进一步压缩为 CRM 一行摘要。但因为已经很短（~3K），额外收益有限
全局 AutoCompact 压缩后的 Skill 段和其他历史消息一起被 LLM 摘要为 7-section 结构。此时 Skill 的关键数据由 SkillResultAnchor 锚点保护
用户追问细节 被压缩的中间步骤原文已在 Skill 完成前由 ContextArchive 存档到 VDB。recall_context 可恢复完整工具过程
关键保障：SkillResultAnchor
Skill 完成时，正则提取关键数字（金额/日期/百分比/实体名/搜索词）存入 session 级缓存。
后续所有压缩（Post-Skill / AutoCompact / FullCompact）的摘要生成 prompt 中都会注入这些锚点，
确保关键数字在多次迭代压缩后永不衰减。
MicroCompact 与 Post-Skill Compact 的关系
结论：时序互补，非功能重叠。两者通过阈值天然互斥——Post-Skill Compact 压缩后的摘要通常 60-150 字符，低于 MicroCompact 的 200 字符触发阈值，不会被二次处理。

唯一会被 MicroCompact 处理的情况：
Post-Skill Compact 的 protect_tail 保护了 Skill 最后 5 条消息的完整原文（如 ToolMessage 3000字）。
这些消息后来随着对话推进被推出保护区 → 此时 MicroCompact 会将它们压缩。
这是预期行为: 当时需要完整内容做推理，推出保护区说明已不再是当前任务的直接依赖。

双路向量化策略
Dense Embedding（权重 0.6）
输入：user_query + answer_preview + 实体名 + 工具名
截断：800 字符
模型：text-embedding-3-small
优势：语义相似度，覆盖"用不同词表达同一意思"
例: 写入"生成报价" → 追问"价格怎么算的" ✓
BM25 Sparse（权重 0.4）
输入：user_query + answer_preview（纯原文）
截断：800 字符
编码：VDB 内置 BM25 自动编码
优势：精确词匹配，覆盖"用原词追问"
例: 写入含"付款条件" → 追问"付款条件" ✓
为什么 Dense 和 BM25 用不同的源文本：
Dense 追加实体名+工具名 → 扩展语义空间，提升跨表达召回
BM25 只用纯原文 → 避免辅助词稀释词频，保证精确匹配的区分度
检索匹配逻辑（hybrid_search）
用户追问: "之前报价的付款条件怎么写的"

① query → embedding → query_vector
② query → BM25 自动编码
③ VDB hybrid_search(
    vector=query_vector,
    query_text=query,
    dense_weight=0.6, sparse_weight=0.4,
    filter='thread_id="当前会话"',
    top_k=15
  )
④ score ≥ 0.35 → 返回 content 字段（原始 JSON）
⑤ 反序列化 → 格式化为可读文本 → 注入上下文
AutoCompact vs FullCompact — 为什么需要两级而非一级
核心原因：压缩力度和信息损失是 trade-off。窗口压力不同时需要不同的压缩策略——压力中等时保守压缩（保留更多上下文连贯性），压力紧急时激进压缩（确保不溢出）。如果只有一级，要么过早丢信息，要么来不及释放空间。
维度 AutoCompact (≥75%) FullCompact (≥90%)
压力程度 中等 — 还有 25% 空间，不紧急 紧急 — 只剩 10%，下一轮可能溢出
Tail 保护条数 base_keep = 4（保守，保留更多近期上下文） base_keep = 8（更大保护区，但压缩区更广）
压缩区范围 head_end → tail_start（部分历史） head_end → tail_start（全部历史，Tail 更靠后）
压缩后重注入 无 — 摘要 + Tail 保护区已够用 重注入最近 3 个 ToolMessage + 最近 HumanMessage
（摘要替换了全部历史，需要补回最近交互的具体数据）
摘要策略 可能是首次生成（STRUCTURED_SUMMARY_PROMPT） 强制迭代更新（基于上次 _previous_summary）
典型节省 75K → 15-20K（节省 70-80%） 90K → 12-18K（节省 80-85%）
信息损失程度 低 — Tail 保护 4 条 + 摘要完整 中 — 压缩区更大，但重注入弥补关键数据
触发频率 较高（10-15 轮对话后常见） 较低（20+ 轮或多 Skill 连续执行才触发）
为什么不合并为一个？
如果只有 AutoCompact（75% 触发）
窗口从 75% 压到 20% 后继续对话，再次涨到 90%+ 时：
• _previous_summary 已存在，可以迭代更新 ✓
• 但没有"重注入"机制 → 摘要替换了全部历史后，LLM 看不到最近的具体工具结果
• 问题：LLM 只有摘要没有原始数据，回复"根据之前分析"却说不出具体数字
如果只有 FullCompact（90% 触发）
窗口涨到 75-89% 时没有任何压缩介入：
• 用户在 80% 时提问，LLM 推理用 80K tokens 的 input → 延迟高 + 成本高
• 如果这轮 LLM 又调了工具，可能直接从 85% 跳到 95% → FullCompact 被迫紧急压缩
• 问题：没有渐进降压，直接从"满载"跳到"紧急全压" → 信息损失更大
两级的协作逻辑：
75% 时 AutoCompact 做一次温和压缩（降到 ~20%）→ 用户继续对话 → 再次涨到 90% → FullCompact 做紧急压缩 + 重注入关键数据。
类比：内存管理中的 soft limit (GC) + hard limit (OOM kill)。AutoCompact = GC，FullCompact = OOM 前的最后一次全量 GC + 数据抢救。
FullCompact 独有：重注入机制
FullCompact 压缩区覆盖几乎全部历史，摘要替换后 LLM 只剩抽象描述。重注入确保 LLM 仍能看到"最近发生了什么"的具体数据。
FullCompact 后的最终 messages 结构:

[1] SystemMessage: Agent 身份 + 工具说明
[2] HumanMessage: 第一条用户消息（全局指令）
[3] SystemMessage: [CONTEXT COMPACTION] + 7-section 摘要 + 锚点
[4] AIMessage: tool_calls=[tc1, tc2, tc3] (占位，对应重注入的3个TM)
[5] ToolMessage: 最近第3个工具结果（完整原文）
[6] ToolMessage: 最近第2个工具结果（完整原文）
[7] ToolMessage: 最近第1个工具结果（完整原文）
[8] HumanMessage: 用户最近的问题
[9+] Tail 保护区: 当前轮次完整消息...
