# 真实用户场景未覆盖分析 — 数据查询未准确返回问题

> 基于真实使用反馈，深度分析 5 个查询场景为何无法准确返回数据
>
> 生成日期：2026-07-06

---

## 一、问题场景逐一分析

### 场景 1：「搜索我的商机并分析商机对应的具体问题，输出一个报告」

**问题本质：复合多意图 + 跨 Skill 协作**

| 意图拆解 | 涉及能力 | 现状 |
|---------|---------|------|
| ① 搜索我的商机 | crm-query（查商机列表） | 支持 ✅ |
| ② 分析商机的具体问题 | opp-analysis（商机分析）或 opp-health（健康评估） | 支持 ✅ |
| ③ 输出报告 | answer_by_data(mode=answer) + `<long_text>` 标签 | 部分支持 ⚠️ |
| **组合 ①②③ 为一句话** | task_planner → 多 Skill 串行协作 | ❌ 未有效覆盖 |

**失败原因分析：**
1. **task_planner 被触发但规划失败** — 用户请求同时包含"查询 + 分析 + 输出报告"3个步骤，理应触发 task_planner，但规划器需要正确识别出"先查商机 → 拿结果 → 对每个商机做分析 → 汇总输出报告"的链路
2. **跨 Skill 数据传递断裂** — crm-query 返回的商机列表结果无法自动作为 opp-analysis 的输入，中间缺少数据桥接机制
3. **"输出报告"触发了什么？** — 系统可能不理解"报告"应该用 `<long_text>` 格式输出，而是误入其他分支

**测试用例覆盖：❌ 完全为空**
- promptfoo-test 中零条"查询 + 分析 + 报告"三合一场景
- cross_skill_combo 目录存在但缺少此类场景

---

### 场景 2：「我的记忆有哪些，这些记忆能帮我做什么」

**问题本质：元能力查询（查询系统内部状态）**

| 意图 | 涉及工具 | 现状 |
|------|---------|------|
| 查看我的记忆内容 | memory_search(dimension="all") | 工具存在 ✅ |
| 解释记忆能帮做什么 | LLM 直接回答（能力引导） | 需 LLM 自主判断 ⚠️ |

**失败原因分析：**
1. **意图识别不准** — "我的记忆有哪些"不是标准的 CRM 业务查询，可能被误路由到 crm-query 或直接当成闲聊
2. **memory_search 的触发条件** — 工具描述是"当需要回忆用户之前提到的事实、偏好或历史信息时调用"，但用户问的是"列出我的所有记忆"这种全量查询，与工具设计的"检索特定信息"模式不匹配
3. **没有"列出全部记忆"的标准流程** — manage_memory 只支持 add/delete，memory_search 需要具体 query 文本做向量检索，没有"全量列出"的能力
4. **"帮我做什么"需要能力引导** — 这是纯 LLM 回答场景，需要系统理解记忆系统的使用场景并解释

**系统设计缺陷：**
- memory_search 必须传 query（检索向量），没有"全量导出"接口
- profile 和 soul 维度可以通过 URI 精确查询（MySQL），但 preference/entities 走向量检索必须有查询文本

**测试用例覆盖：❌ 完全为空**

### 场景 3：「今天有哪些日程」

**问题本质：相对时间 + 简单单实体查询**

| 意图 | 涉及 Skill | 现状 |
|------|-----------|------|
| 查询今天的日程 | crm-query → 查 schedule 实体 | 理论支持 ✅ |

**失败原因分析：**
1. **"今天"的时间解析** — 现有日程测试用例全部用固定时间（"25年9月"、"名称包含XX"），从未测试过"今天/明天/本周"这类相对时间表达
2. **XOQL 生成能力** — generate_xoql 需要正确将"今天"解析为 `startTime >= '2026-07-06 00:00:00' AND startTime < '2026-07-07 00:00:00'`，但这个逻辑依赖 LLM 的时间理解能力，如果 system_prompt 中没有注入当前时间，LLM 不知道"今天"是哪天
3. **"我的"范围限定** — 需要正确识别为"当前用户的日程"（owner = 当前用户），这个隐含条件是否被正确处理？

**真实验证情况：**
- 日程测试用例 10 条，全部使用 `/query-crm-data` 前缀强制路由 + 固定条件
- 无一条测试"今天的日程"、"明天的日程"、"本周的日程"

**测试用例覆盖：❌ 相对时间场景完全为空**

---

### 场景 4：「查询我逾期的任务」

**问题本质：概念歧义 — "任务"在系统中指什么？**

| 可能含义 | CRM 实体映射 | 支持情况 |
|---------|-------------|---------|
| CRM 待办任务（Task） | 可能映射为自定义对象或标准 Task 实体 | ⚠️ 不确定是否有此实体 |
| 商机推进任务（阶段目标） | opportunity 的阶段/deadline | 间接支持 |
| 日程中的逾期项 | schedule（过了结束时间未完成） | 需 XOQL 条件拼接 |
| Agent 自主执行任务 | autonomous task | 非查询能力 |
| 用户认知的"我的待办" | ❌ 系统明确不支持 | ❌ |

**失败原因分析：**
1. **"我的待办"被系统明确拦截** — query-crm-data Agent 的 system_prompt 明确规定：`查询我的待办（如用户仅输入"查我的待办"）` 属于不支持的查询，直接返回"暂不支持"
2. **"逾期的任务"是否等同于"待办"？** — 这取决于用户是否有 Task 实体。如果系统中有 Task 对象且含 dueDate 字段，理论上 crm-query 可以查询"dueDate < 今天 AND status != 完成"的记录
3. **实体识别可能失败** — 如果用户租户中没有名为"任务"/"Task"的标准实体，extract_entity 会找不到对应实体返回 checkFail

**核心矛盾：** 系统设计者认为"查我的待办"是不支持的（因为 CRM 的待办系统是独立的，不走 XOQL），但用户自然地把"逾期的任务"当成一个合理的 CRM 查询。

**测试用例覆盖：❌ 完全为空**

### 场景 5：「我的任务有哪些」

**问题本质：与场景 4 相同的概念歧义**

- 即使不被拦截，"任务"实体是否存在、字段结构如何，都是未知的

## 二、根因归类

将 5 个场景的失败归纳为 4 类根因：

| 根因类型 | 影响场景 | 严重程度 |
|---------|---------|---------|
| **R1. 多意图/跨 Skill 协作失效** | 场景1 | 🔴 高 |
| **R2. 相对时间解析能力缺失** | 场景3 | 🔴 高 |
| **R3. 系统能力边界与用户预期不匹配** | 场景2、4、5 | 🟡 中 |
| **R4. "优雅拒绝"用户体验差** | 场景4、5 | 🟡 中 |

### R1. 多意图/跨 Skill 协作失效

**现象：** 用户一句话包含"查询 + 分析 + 输出"多个步骤，系统无法正确拆解和串行执行

**技术原因：**
- task_planner 存在但不保证被正确触发（LLM 判断"是否需要规划"）
- 即使规划成功，跨 Skill 的数据传递（A 的输出作为 B 的输入）机制不健全
- 缺乏"批量分析"能力 — opp-analysis 是针对单个商机设计的，无法批量处理列表

**代码证据：**
```yaml
# default agent 的 tools 列表：
tools: ["skills_tool", "task_planner", ...]
# task_planner 描述中：复杂的多步骤任务/多个任务时使用
# 但实际效果取决于 planner LLM 的规划质量
```

### R2. 相对时间解析能力缺失

**现象：** "今天的日程"无法正确查询

**技术原因：**
- crm_query_simple 调用 salescloud-ai 时，后端 LLM 生成 XOQL 需要知道"今天"的具体日期
- answer_by_data 的 prompt 中注入了 `现在时间:{current_time}`，但 generate_xoql 是否注入当前时间？
- 测试用例从未覆盖相对时间，说明此场景可能确实存在系统性缺陷

### R3. 系统能力边界与用户预期不匹配

**现象：** 用户期望系统能做的事情，系统设计上不支持

| 用户预期 | 系统现实 |
|---------|---------|
| "列出我的所有记忆" | memory_search 需要具体 query 做向量检索，无全量导出 |
| "查我的任务" | "待办"被明确列为不支持的查询 |
| "逾期任务" | Task 实体可能不存在或不标准 |

### R4. "优雅拒绝"用户体验差

**现象：** 不支持时的回复不够友好，且没有引导用户替代方案

**期望的拒绝方式：**
```
抱歉，我暂不支持直接查询待办任务。您可以：
1. 查询您今天的日程：「今天有哪些日程」
2. 查询商机中已过期的：「查询预计结单日期已过期的商机」
3. 查询您负责的活动记录：「最近7天的活动记录」
```

## 五、总结

你遇到的这 5 个场景，暴露了 AI Agent 系统的一个核心矛盾：

> **系统按"技能/工具"原子化设计，但用户按"自然意图"整体表达**

具体体现为：
1. **时间理解** — 系统测试全用固定日期，但用户自然地说"今天/最近/逾期"
2. **概念映射** — 系统用 "schedule/task/activity" 区分实体，但用户说"日程/任务/待办"可能指同一件事
3. **能力组合** — 系统的 Skill 各自独立运行，但用户期望"查+分析+报告"一句话搞定
4. **元认知** — 系统有记忆能力但没有暴露"查看我有什么记忆"的用户入口

这些都是测试用例体系中 **完全为空（0条）** 的区域，说明测试设计时过于聚焦"工具是否按预期工作"，而忽略了"用户实际会怎么说话"。

## 六、数据完整性验证的核心缺陷 — 无法对比真实数据差异

### 6.1 问题描述

> **数据库中有 3 条数据，Agent 实际只返回了 2 条** — 这类"数据丢失"问题，现有测试体系完全无法发现。

这是当前测试框架的 **最大结构性缺陷**：所有断言都是"Agent 回复中是否包含某些关键词"，而不是"Agent 返回的数据是否与数据库真实数据一致"。

### 6.2 现有断言机制的本质局限

| 断言方式 | 做了什么 | 没做什么 |
|---------|---------|---------|
| `contains` | 检查回复中是否含"重庆三峡" | ❌ 不检查是否遗漏了其他客户 |
| `contains-any` | 检查回复中是否含列表中任一项 | ❌ 不检查完整性 |
| `llm-rubric` | LLM 语义评判回复合理性 | ❌ 无法验证数据库级别的精确度 |
| `dynamic: true + xoql` | **仅是标注元数据** | ❌ 运行时完全不执行 XOQL 验证 |

**关键发现：** JSON 用例中的 `"dynamic": true` 和 `"xoql": "select ..."` 字段，在 `generate_tests.js` 中 **被完全忽略**。它们只是写用例的人留的注释，说明"我当时是通过这条 XOQL 查到了这些预期值"，但测试框架从不在运行时去真正执行这条 XOQL 做实时对比。

```javascript
// generate_tests.js 中处理 conditions 的逻辑：
// 只读取 type 和 value，entity/keyword/fields/xoql/dynamic 全部被丢弃
for (let i = 0; i < _conditions.length; i++) {
    let condition_obj = JSON.parse(JSON.stringify(_conditions[i]));
    let _type = condition_obj.type;
    // ... 只处理 type 和 value
}
```

### 6.3 这导致了什么问题

#### 场景举例

**用户查询：** "查询本月新增的客户"

**数据库真实情况：** 本月有 `客户A`、`客户B`、`客户C` 共 3 条

**Agent 返回：** "为您找到 2 条数据" — 只返回了 `客户A`、`客户B`

**测试结果：** ✅ PASS（因为断言只是 `contains: ["客户A"]`，只要包含一个就通过）

**实际质量：** ❌ FAIL — 丢失了 `客户C`

#### 这类问题的常见原因

| 原因 | 说明 |
|------|------|
| XOQL 条件生成不完整 | 漏掉了某个筛选条件导致过滤过多 |
| 时间边界计算错误 | "本月"起止时间差1天 |
| 权限过滤多余 | 不该过滤的数据被权限规则删掉了 |
| 分页截断 | limit 参数太小 |
| 字段映射错误 | 用错了字段名导致部分数据被排除 |
| 元数据缓存过期 | Redis 缓存的实体/字段信息过期 |

### 6.4 理想的测试验证模式

应当引入 **"预言机"（Oracle）模式** — 测试运行时独立执行 XOQL 获取真实数据，再与 Agent 返回对比：

```
┌─────────────────────────────────────────────────────┐
│  Test Runner                                         │
│                                                     │
│  ① 发送查询给 Agent → 获得 Agent 回复               │
│                                                     │
│  ② 独立执行 XOQL（预言机） → 获得数据库真实结果      │
│     SELECT * FROM account                            │
│     WHERE createdAt >= '2026-07-01'                  │
│     AND owner = '当前用户'                           │
│                                                     │
│  ③ 对比:                                            │
│     • Agent 返回的记录数 == XOQL 真实记录数？         │
│     • Agent 返回的每条记录 ID 都在真实结果中？        │
│     • 没有多余或遗漏的记录？                         │
│     • 字段值是否一致？                               │
└─────────────────────────────────────────────────────┘
```

### 6.5 具体实现方案

#### 方案 A：在测试框架中增加 XOQL 预查询断言（推荐）

```json
{
    "metadata": {
        "business_scenario": "查CRM数据：数据完整性验证-本月新增客户"
    },

                "match_mode": "count_exact",
                "tolerance": 0
            }

    }
}
```

**需要新增的断言类型：**

| 断言类型 | 含义 | 参数 |
|---------|------|------|
| `data-integrity` | 完整性对比 | oracle_xoql + match_mode |
| `count_exact` | 数量精确匹配 | Agent 返回条数 == XOQL 查询条数 |
| `count_gte` | 数量不少于 | Agent 返回条数 >= XOQL 查询条数 |
| `records_contain` | 记录包含 | Agent 返回的每条记录都在 XOQL 结果中 |
| `records_exact` | 记录精确一致 | 双向包含（无多余无遗漏） |

#### 方案 C：后置 XOQL 校验 Provider（最小改动）

在现有 `agent_copilotkit_api.js` Provider 中增加后处理逻辑：

```javascript
// 伪代码：在 Provider 返回结果前，执行 oracle 查询做对比
async function postValidate(agentResponse, conditions) {
    for (const cond of conditions) {
        if (cond.type === 'data-integrity' && cond.oracle_xoql) {
            // 1. 执行 oracle_xoql 获取真实数据
            const oracleResult = await executeCrmXoql(cond.oracle_xoql);
            const oracleCount = oracleResult.total_count;
            
            // 2. 从 Agent 响应中提取返回的记录数
            const agentCount = extractRecordCount(agentResponse);
            
            // 3. 对比
            if (cond.match_mode === 'count_exact' && agentCount !== oracleCount) {
                return {
                    pass: false,
                    reason: `数据不完整：数据库有 ${oracleCount} 条，Agent 只返回了 ${agentCount} 条`
                };
            }
        }
    }
    return { pass: true };
}
```

### 6.6 短期折中方案

在实现完整 oracle 机制之前，可以先做以下改进：

| 改进 | 成本 | 效果 |
|------|------|------|
| 将 `dynamic: true` 的 xoql 真正执行（每次运行时刷新预期值） | 中 | 解决数据变化后断言过期问题 |
| 增加 `contains-count` 断言：验证"X 条"中的数字 | 低 | 至少验证数量是否匹配预期 |
| 在 Agent 返回的事件流中提取 `total_count` 做断言 | 低 | 验证 Agent 自报的数量 |
| 对关键场景增加"全量枚举"断言（contains 列出所有预期记录名） | 低 | 确保每条都返回了 |

## 七、最终总结

你指出的这个问题 — **"数据库有3条，实际只查到2条"** — 是整个测试体系最核心的短板：

1. **现有断言只做"是否包含关键词"的弱验证**，不做"返回数据是否与数据库一致"的强验证
2. **`dynamic: true` + `xoql` 字段只是死注释**，运行时从不执行
3. **所有预期值都是"写用例时的快照"**，数据变化后断言就过期了
4. **没有"预言机"机制**来独立验证 Agent 输出的数据完整性和正确性

这意味着即使现有 416 条用例全部 PASS，也无法保证 Agent 返回的数据是 **完整的、准确的、没有遗漏的**。

**最优先的改进：** 激活 `dynamic: true` 的 XOQL 字段，让测试框架在运行时真正执行这些 XOQL 作为 oracle，对比 Agent 返回的记录数和记录内容。这个改动成本可控（改 generate_tests.js + 增加一个 XOQL 执行 HTTP 客户端），但能将数据查询场景的验证从"弱断言"升级为"强断言"。
