# 长期记忆系统设计文档

> 基于 OpenViking 文件系统范式设计，采用 L0/L1/L2 三层信息模型 + 目录递归检索 + BM25 混合检索架构。
> 直连腾讯向量库（tcvectordb SDK）实现语义检索，结合 PostgreSQL 实现精确查询与生命周期管理，针对 CRM toB 场景做领域适配。

## 一、设计背景与技术选型

### 1.1 基于 OpenViking 范式的设计

本系统以 OpenViking 的文件系统范式为架构基础，完整实现了其核心设计理念：

**继承的 OpenViking 核心能力：**

| 能力 | OpenViking 原始设计 | 本系统实现 |
|:---|:---|:---|
| 虚拟文件系统 | VikingFS（URI 路径 + 目录树） | ✅ 完整实现 `viking_fs.py`，支持 ls/tree/read/find/rm |
| L0/L1/L2 三层信息模型 | 目录聚合 L0/L1 + 叶子 L2 | ✅ 完整实现，目录节点 LLM 聚合 + 叶子节点按需加载 |
| 目录递归检索 | 优先队列 + 分数传播 + 收敛检测 | ✅ 完整实现，α=0.5 分数传播 + Top-K 连续 3 轮不变停止 |
| 语义去重 + LLM 合并 | 向量预筛 + LLM 精判（skip/create/merge/delete） | ✅ 完整实现 `_dedup_create()` |
| 分层加载 | 检索返回 L0 摘要，Agent 按需加载 L1/L2 | ✅ 完整实现 `memory_read` 工具 |
| 会话结束反思 | post_session_reflection | ✅ 完整实现 `reflect_on_session()` |
| 定期全局反思 | weekly_global_reflection | ✅ 完整实现 `reflect_global()` |
| 记忆遗忘 | TTL + 热度驱动 | ✅ 完整实现三阶段淡化 + 复活机制 |

**针对 CRM toB 场景的领域适配：**

| 维度 | OpenViking 通用设计 | 本系统 CRM 适配 |
|:---|:---|:---|
| 分类体系 | 9 类通用分类 | 精简为 4 类（profile/preferences/agent_rules/entities），聚焦 CRM 核心场景 |
| 提取架构 | 单路 LLM 提取 + 后分类 | 4 路并行 LLM 提取，每路独立提示词 + 边界规则 |
| 存储后端 | 通用向量库 | 腾讯向量库 tcvectordb（支持 BM25 稀疏向量 + filter index）+ PG 双存储 |
| 检索策略 | 纯向量语义检索 | BM25 0.7 + 向量 0.3 混合检索（CRM 场景客户名精确匹配优先） |
| 系统数据一致性 | 无（通用场景无此问题） | 提取时排除 CRM 系统已有字段 + biz_id 锚定 + source_type 标记 |
| 预过滤 | 无 | 规则预过滤（寒暄/确认/工具失败跳过），节省 ~30% LLM 调用 |



### 1.2 最终选型

```
架构范式: OpenViking（VikingFS 虚拟文件系统 + L0/L1/L2 三层 + 目录递归检索 + 反思修正）
提取层:   4 路并行 LLM 提取 + 规则预过滤（CRM 领域适配）
存储层:   腾讯向量库（tcvectordb SDK 直连，BM25 稀疏向量 + filter index）
          + PG（profile/agent_rules 权威存储 + 全量记忆生命周期管理）
检索层:   BM25 混合检索（0.7 关键词 + 0.3 向量）+ 目录递归展开 + 分层加载
组织层:   VikingFS 虚拟文件系统（viking:// URI + ls/tree/read/find/rm）
```

### 2.1 4 类分类体系

代码实现：`src/memory/viking_engine.py` → `MemoryCategory` 枚举

| 类别 | 存储位置 | 说明 | 合并策略 | CRM 场景示例 | 存储格式示例 |
|:---|:---:|:---|:---|:---|:---|
| profile | PG | 用户对"我/我们团队/我们公司"的**稳定属性描述**：职位、履历、所在区域、团队规模、所属组织的业务与文化、使用的工具。判别标准：该信息在下一个新会话里对 Agent 理解"这个用户是谁"是否仍有帮助。 | 每用户 1 条，LLM 合并 | ① "我是华东区销售总监，管理15人团队"<br>② "我们公司用的是纷享销客CRM" | `merge_key: "profile"`<br>`content: "华东区销售总监，管理15人团队，负责互联网大客户。公司使用纷享销客CRM。"` |

> 实际实现精简为 4 类。原 soul 类合并到 agent_rules；events/cases/patterns/tools/skills 未实现独立提取，
> 相关信息视语义归入 entities 或不提取。

### 2.2 分类决策逻辑（四路并行提取）

代码实现：`src/memory/extraction/prompts.py` + `src/memory/extraction/extractor.py`

当前实现为 **4 路并行 LLM 提取**，每路独立判断、互不依赖：

```
用户发言 → 4 路并行 LLM 调用:
  ├── Profile:      用户是谁？（稳定身份属性）
  ├── Preferences:  用户偏好什么？（个人喜好/习惯/标准）
  ├── Agent Rules:  Agent 应该怎么做？（持久行为约束）
  └── Entities:     第三方有什么事实？（客户/联系人/竞品）
```

各路核心判别原则：

| 类别 | 核心问题 | 判别标准 |
|:---|:---|:---|
| profile | 用户是谁？ | 该信息在下一个新会话里对 Agent 理解"这个用户是谁"是否仍有帮助 |
| preferences | 用户偏好什么？ | 该信息脱离当前上下文后，在下一个新会话里对理解"这个用户"是否仍有价值 |
| agent_rules | Agent 应该怎么做？ | 该规则在下一次类似请求中 Agent 是否应继续遵守 |
| entities | 第三方有什么事实？ | 关于第三方的可复用事实（角色关系/业务/偏好/竞争情报） |

跨维度边界规则（每路提示词中明确定义）：

```
Profile 不属于:
  - 我的喜好/习惯/厌恶 → preferences
  - 对 Agent 的持久指令 → agent_rules
  - 第三方事实 → entities
  - 单次操作、孤立数值 → 不提取

Preferences 不属于:
  - 纯指向 Agent 行为的规则式指令 → agent_rules
  - 描述身份或组织 → profile
  - 描述第三方偏好/事实 → entities
  - 单次反馈/操作 → 不提取

Agent Rules 不属于:
  - 描述用户本人（个人习惯、性格、喜好）→ preferences
  - 纯身份或组织描述 → profile
  - 对第三方事实的纯陈述 → entities
  - 单次调整、评价、感叹 → 不提取

Entities 不属于:
  - 用户履历、团队或公司特征 → profile
  - 用户自己的偏好 → preferences
  - 命令 Agent 的持久指令 → agent_rules
  - 疑问句/纯查询/操作指令 → 不提取
```

多维度混合处理：同句含多维度时，各路独立判断、各自提取属于自己的部分。

### 2.3 各类别存储形式详解

每个类别的 abstract（L0）、overview（L1）、content（L2）的存储位置、是否参与检索和打分各不相同：

#### profile — 用户身份

**存储与检索特性：**

| 层级 | 字段 | 存储位置 | 参与检索 | 参与打分 | 用途 |
|:---|:---|:---:|:---:|:---:|:---|
| — | content | PG | ❌ | ❌ | LLM 合并后的完整画像，注入提取提示词 |
| — | abstract | PG | ❌ | ❌ | 前端展示用摘要 |

> profile 不存储在向量库，不参与语义检索。通过 `get_profile()` 从 PG 读取，注入提取提示词的 `{existing_profile}` 避免重复提取。

**场景示例：**

```
━━━ 对话场景 ━━━
[用户] 我是华东区的销售总监，管着15个人，主要跑互联网行业大客户。我们公司刚从Salesforce迁到纷享销客。

━━━ 提取 & 存储 ━━━
category:  profile
merge_key: "profile"

PG 存储:
{
  "category": "profile",
  "merge_key": "profile",
  "abstract": "用户身份: 华东区销售总监，管理15人团队，负责互联网大客户，使用纷享销客",
  "content": "用户是华东区销售总监，管理15人团队，主要负责互联网行业大客户。公司近期从Salesforce迁移到纷享销客CRM。",
  "status": "active"
}

━━━ 使用方式（不参与检索） ━━━
注入到 PROFILE_EXTRACT_PROMPT 的 {existing_profile} 占位符，避免重复提取。
不写入向量库，不参与 hybrid_search，不参与打分。
```

#### preferences — 用户偏好

**存储与检索特性：**

| 层级 | 字段 | 存储位置 | 参与检索 | 参与打分 | 用途 |
|:---|:---|:---:|:---:|:---:|:---|
| L0 | abstract | 向量库 | ✅ embed → cosine + BM25 | ✅ 0.7×BM25 + 0.3×cosine | 检索匹配 + 注入 Agent 上下文 |
| L1 | overview | 向量库 | ❌ | ❌ | Agent 调用 memory_read(level="L1") 按需加载 |
| L2 | content | 向量库 | ❌ | ❌ | Agent 调用 memory_read(level="L2") 按需加载 |

**场景示例：**

```
━━━ 对话场景 ━━━
[用户] 以后数据展示都用表格，金额用万为单位不要小数点

━━━ 提取 & 存储 ━━━
category:      preferences
slug:          "data_display"
merge_key:     "preferences/data_display"

向量库存储（叶子节点）:
{
  "id": "mem_d4e5f6a7",
  "vector": embed("数据展示偏好: 表格格式，金额万为单位，不要小数"),       ← L0 向量化，参与检索
  "sparse_vector": BM25("数据展示偏好: 表格格式，金额万为单位，不要小数"), ← L0 稀疏向量，参与检索
  "abstract": "数据展示偏好: 表格格式，金额万为单位，不要小数",            ← L0（返回给 Agent）
  "overview": "## 偏好\n- 表格格式\n- 金额万为单位\n- 不要小数",           ← L1（按需加载）
  "content": "用户偏好表格展示数据，金额统一用万为单位且不要小数点。",      ← L2（按需加载）
  "category": "preferences",
  "merge_key": "preferences/data_display",
  "is_leaf": "true",
  "status": "active"
}

━━━ 检索时打分示例 ━━━
用户问 "用什么格式展示数据" →
  BM25("数据""展示"精确命中 abstract) → bm25_score = 0.75
  cosine(查询向量 vs abstract向量)    → cosine_score = 0.82
  final_score = 0.7 × 0.75 + 0.3 × 0.82 = 0.771 → 命中，返回 L0 摘要
  Agent 按需调用 memory_read(level="L2") 获取完整偏好
```

#### agent_rules — Agent 行为准则

**存储与检索特性：**

| 层级 | 字段 | 存储位置 | 参与检索 | 参与打分 | 用途 |
|:---|:---|:---:|:---:|:---:|:---|
| — | content | PG | ❌ | ❌ | 每轮对话前作为 SystemMessage 全量注入 |
| — | abstract | PG | ❌ | ❌ | 前端展示用摘要 |

> agent_rules 不存储在向量库，不参与语义检索。每轮对话开始时通过 `get_agent_rules_text()` 从 PG/缓存读取，作为 SystemMessage 注入，Agent 从第一轮就遵守。

**场景示例：**

```
━━━ 对话场景（多轮累积） ━━━
第 1 次: [用户] 你是我的数据分析助理，回复不要太长
第 12 次: [用户] 跟华为那边沟通的邮件要用正式语气
第 20 次: [用户] 回复100字以内就行（与"回复不要太长"矛盾，以新为准）

━━━ LLM 融合后存储 ━━━
category:  agent_rules
merge_key: "agent_rules"

PG 存储:
{
  "category": "agent_rules",
  "merge_key": "agent_rules",
  "abstract": "Agent行为准则: 数据分析助理，回复≤100字，华为沟通用正式语气",
  "content": "角色为用户的数据分析助理。回复不超过100字。跟华为沟通的邮件使用正式语气。",
  "status": "active"
}

━━━ 使用方式（不参与检索，全量注入） ━━━
每轮对话开始时注入 system prompt:
  ┌─────────────────────────────────┐
  │ CRM_SYSTEM_PROMPT（通用规范）     │
  ├─────────────────────────────────┤
  │ <agent_rules>                    │  ← 全量注入
  │   角色为用户的数据分析助理...      │
  │ </agent_rules>                   │
  ├─────────────────────────────────┤
  │ <memory_context>                 │  ← 本轮检索记忆
  │   ...                            │
  │ </memory_context>                │
  └─────────────────────────────────┘
不参与 hybrid_search，不参与打分。
```

#### entities — 第三方事实

**存储与检索特性：**

| 层级 | 字段 | 存储位置 | 参与检索 | 参与打分 | 用途 |
|:---|:---|:---:|:---:|:---:|:---|
| L0 | abstract | 向量库 | ✅ embed → cosine + BM25 | ✅ 0.7×BM25 + 0.3×cosine | 检索匹配 + 注入 Agent 上下文 |
| L1 | overview | 向量库 | ❌ | ❌ | Agent 调用 memory_read(level="L1") 按需加载 |
| L2 | content | 向量库 | ❌ | ❌ | Agent 调用 memory_read(level="L2") 按需加载 |

> entities 同时存在叶子节点和目录节点。目录节点的 L0/L1 由系统 LLM 从子叶子聚合生成，也参与检索打分。

**场景示例：**

```
━━━ 对话场景 ━━━
[用户] 查一下华为的联系人
[工具:query_data] {"records":[{"name":"张伟","title":"CTO","phone":"139-0001-0001"}]}
[助手] 华为联系人张伟，CTO，电话139-0001-0001。
[用户] 张伟这个人说话很直接，开会不要绕弯子，每次控制在30分钟内。汇报用PPT带数据。

━━━ 提取 & 存储 ━━━
category:      entities
merge_key:     "华为科技/张伟"
parent_entity: "华为科技"

✅ 提取（增量认知）: "说话直接，开会控制30分钟，汇报用PPT带数据"
❌ 不提取（系统数据）: "CTO，电话139-0001-0001"

向量库存储 — 叶子节点（is_leaf=true）:
{
  "id": "mem_e8f9a0b1",
  "vector": embed("华为科技/张伟: 说话直接，汇报用PPT，开会控制30分钟"),       ← L0 向量化，参与检索
  "sparse_vector": BM25("华为科技/张伟: 说话直接，汇报用PPT，开会控制30分钟"), ← L0 稀疏向量，参与检索
  "abstract": "华为科技/张伟: 说话直接，汇报用PPT，开会控制30分钟",            ← L0（返回给 Agent）
  "overview": "## 沟通风格\n- 直接不绕弯子\n- 汇报用PPT\n## 会议\n- 控制30分钟", ← L1（按需加载）
  "content": "张伟说话直接不绕弯子，汇报用PPT带数据，开会控制30分钟。",         ← L2（按需加载）
  "category": "entities",
  "merge_key": "华为科技/张伟",
  "parent_entity": "华为科技",
  "uri": "viking://user/memories/entities/华为科技/张伟",
  "is_leaf": "true",
  "status": "active"
}

向量库存储 — 目录节点（is_leaf=false，系统 LLM 聚合生成）:
{
  "id": "dir_华为科技",
  "vector": embed("华为科技: 张伟直接喜欢PPT，ERP有分歧，审批3周"),       ← 目录 L0 向量化，参与检索
  "sparse_vector": BM25("华为科技: 张伟直接喜欢PPT，ERP有分歧，审批3周"), ← 参与检索
  "abstract": "华为科技: 张伟直接喜欢PPT，ERP有分歧，审批3周",            ← 目录 L0（聚合摘要）
  "overview": "## 联系人\n- 张伟: 直接，PPT\n## 商机\n- ERP: 有分歧",     ← 目录 L1（聚合导航）
  "content": "",                                                          ← 目录无 L2
  "category": "entities",
  "merge_key": "华为科技",
  "parent_entity": "",
  "uri": "viking://user/memories/entities/华为科技/",
  "is_leaf": "false",
  "status": "active"
}

━━━ 检索时打分示例 ━━━
用户问 "华为那边张伟是什么风格" →
  叶子: BM25=0.91("华为""张伟"命中) cosine=0.89 → final = 0.7×0.91 + 0.3×0.89 = 0.904
  目录: BM25=0.85("华为"命中)       cosine=0.78 → final = 0.7×0.85 + 0.3×0.78 = 0.829

返回给 Agent:
  <memory_context>
  - [DIR:dir_华为科技] [entities] 华为科技: 张伟直接喜欢PPT，ERP有分歧，审批3周
  - [ID:mem_e8f9a0b1] [entities] 华为科技/张伟: 说话直接，汇报用PPT，开会控制30分钟

  memory_read(id="mem_e8f9a0b1", level="L2") → "张伟说话直接不绕弯子，汇报用PPT带数据，开会控制30分钟。"
```

### 2.5 各类别存储形式汇总

| 类别 | merge_key 含义 | parent_entity 含义 | 存储位置 | 合并行为 | 记忆数量 |
|:---|:---|:---|:---:|:---|:---|
| profile | 固定 "profile" | 空 | PG | LLM 合并，全局 1 条 | 每用户 1 条 |
| preferences | slug（如 "data_display"） | 空 | 向量库 | 同 slug 合并覆盖 | 每用户 5-15 条 |
| agent_rules | 固定 "agent_rules" | 空 | PG | LLM 融合，全局 1 条 | 每用户 1 条 |
| entities | 实体路径（如"华为科技/张伟"） | 父实体名（如"华为科技"） | 向量库 | 同 key 合并覆盖 | 每客户 3-10 条 |

## 三、L0/L1/L2 三层信息模型

> 对齐 apps-agent（OpenViking）：L0/L1 属于目录，L2 属于叶子。

### 3.1 三层定义（对齐 apps-agent）

| 层级 | 归属 | 生成方式 | Token 量 | 用途 |
|:---|:---|:---|:---|:---|
| L0 | 目录节点 | 系统 LLM 聚合（从所有叶子 content 压缩为一句话） | ~30-100 | 向量检索匹配 + 注入 Agent 上下文 |
| L1 | 目录节点 | 系统 LLM 聚合（从所有叶子 content 生成结构化 Markdown） | ~200-500 | Agent 按需加载（了解目录结构） |
| L2 | 叶子节点 | LLM 提取时直接输出 | 无限制 | Agent 按需加载（获取完整记忆内容） |

### 3.2 目录节点 vs 叶子节点

```
向量库中的文档分两种：

1. 目录节点（is_leaf=false）
   abstract:  L0 聚合摘要（系统 LLM 生成）
   overview:  L1 结构化导航（系统 LLM 生成）
   content:   空
   vector:    embed(L0)
   示例:
     abstract = "华为科技: 张伟说话直接喜欢PPT，ERP项目内部有分歧需分别沟通，审批流程复杂至少3-4周"
     overview = "## 联系人洞察\n- 张伟: 说话直接，汇报用PPT\n## 商机洞察\n- ERP项目: 内部有分歧\n## 内部流程\n- 审批: 至少3-4周"

2. 叶子节点（is_leaf=true）
   abstract:  叶子的一句话摘要（LLM 提取时输出）
   overview:  空（不需要，由目录 L1 替代）
   content:   完整记忆内容（LLM 提取时输出）
   vector:    embed(abstract)
   示例:
     abstract = "华为科技/张伟: 说话直接，汇报用PPT，开会控制30分钟"
     content  = "张伟说话直接不绕弯子，汇报用PPT带数据，开会控制30分钟。建议和他沟通时直接说重点。"
```

### 3.3 目录 L0/L1 的生成逻辑

**触发时机**：每次叶子节点写入或更新后，异步触发该叶子所属目录的重新聚合。

```
LLM 提取叶子 → 写入向量库 → 看到 parent_entity="华为科技"
  → asyncio.create_task(_ensure_directory_node("entities", "华为科技", user_id))
  → 收集华为科技下所有叶子的 content
  → LLM 生成 L1（结构化 Markdown）
  → LLM 从 L1 压缩生成 L0（一句话摘要）
  → 写入/更新目录节点（abstract=L0, overview=L1）
```

**LLM 不提取目录**。目录的存在完全由叶子的 `parent_entity` 字段驱动。

**L0 生成 prompt**：
```
将以下结构化目录压缩为一句话摘要（不超过100字）。
目录路径: entities/华为科技
目录内容: {L1 内容}
直接输出一句话摘要。
```

**L1 生成 prompt**：
```
将以下多条记忆聚合为一个结构化 Markdown 目录。
目录路径: entities/华为科技
记忆条目:
- 张伟说话直接不绕弯子，汇报用PPT带数据，开会控制30分钟
- ERP项目张伟和李娜意见有分歧，建议分别沟通
- 华为内部审批流程复杂，IT部门后还需采购委员会，至少3-4周
用 ## 标题分组，- 列表列出具体信息。
```

### 3.4 检索时的分层加载

```
检索流程:
  1. 用户查询 → embedding → hybrid_search（匹配目录 L0 向量 + 叶子 abstract 向量）
  2. 返回 Top-K 结果，区分目录节点和叶子节点
  3. 注入 Agent 上下文:
     - 目录节点 → 注入 L0 摘要，标记 [DIR:xxx]
     - 叶子节点 → 注入 abstract（L0 摘要），标记 [ID:xxx]
  4. Agent 按需加载:
     - 需要目录结构 → memory_read(id=目录ID, level="L1") → 返回 overview
     - 需要叶子详情 → memory_read(id=叶子ID, level="L2") → 返回 content

注入格式:
  <memory_context>
  - [DIR:dir_001] [entities] 华为科技: 张伟直接，审批3周，ERP有分歧
  - [ID:mem_001] [entities] 华为/张伟: 说话直接，汇报用PPT，开会控制30分钟
  - [ID:mem_002] [entities] 华为/ERP项目: 张伟和李娜有分歧，建议分别沟通
  </memory_context>
```

### 4.1 存储路由

```
LLM 提取出一条记忆
  │

  │   → PG 存储（_merge_single_record）
  │   → 每用户各一条，LLM 合并
  │   → 不写入向量库（不需要语义检索）
  │
  └── category = preferences / entities
      → 向量库存储（_merge_by_key 或 _dedup_create）
      → 同时异步写 PG（_sync_to_pg，前端展示 + 生命周期管理）

```

### 4.2 完整流程

```
对话消息
  │
  ▼
第一层: 预过滤 _should_extract()（代码规则，0 LLM 成本）
  ├── 跳过: 寒暄/确认/感谢
  ├── 跳过: AI 回复太短
  ├── 跳过: 工具全部失败
  └── 通过: 有实质内容的对话
  │
  ▼
第二层: LLM 结构化提取（注入已有 profile/agent_rules/preferences 状态避免重复）
  ├── 输入: EXTRACTION_PROMPT + 已有状态上下文 + 对话文本
  ├── 输出: JSON {"memories": [{category, abstract, content, merge_key, parent_entity}]}
  ├── 注意: LLM 只输出 abstract + content，不输出 overview（由目录聚合生成）
  └── profile/agent_rules 的 merge_key 固定为 "profile"/"agent_rules"
  │
  ▼
第三层: 语义去重 + 分类合并 _dedup_and_store()
  │
  ├── profile / agent_rules → _merge_single_record()
  │     读 PG 已有 → LLM 合并 → 写回 PG 一条
  │     超长自动精炼（profile≤200字，agent_rules≤300字）
  │
  ├── preferences / entities → _merge_by_key()
  │     向量搜索同 merge_key → 同 key 且相似度>0.8 → LLM 合并覆盖
  │     不同 key → 独立存储
  │
  └── 无 merge_key 的 entities → _dedup_create()
        向量预筛（相似度>0.9）→ LLM 精判（skip/create/merge/delete）
  │
  ▼
第四层: 写入向量库（叶子节点）
  │
  ▼
第五层: 异步触发目录聚合 _ensure_directory_node()
  ├── 条件: parent_entity 非空
  ├── 收集该目录下所有叶子的 content
  ├── LLM 生成 L1（结构化 Markdown 导航）
  ├── LLM 从 L1 压缩生成 L0（一句话摘要）
  └── 写入/更新目录节点（abstract=L0, overview=L1, is_leaf=false）
  │
  ▼
第六层: 异步同步 PG（ai_agent_memory 表，前端展示 + 生命周期管理）
  │
  ▼
第七层: 异步触发会话反思（只对 entities 类别）
```

## 五、记忆检索流水线

### 5.1 完整流程

```
用户查询
  │
  ▼
Step 0: 查询改写（多轮对话时 LLM 解析代词）
  "那个项目怎么样" → "华为ERP项目的状态"
  │
  ▼
Step 1: 全局 hybrid_search
  │
  ├── 检索范围: 向量库中该租户该用户的所有文档（目录节点 + 叶子节点）
  ├── 过滤条件: tenant_id = "{tenant_id}" AND user_id = "{uid}" AND status != "archived"
  │
  ├── 稠密向量路（cosine similarity）:
  │     检索字段: vector（= embed(abstract)，即 L0 摘要的向量化结果）
  │     匹配方式: 查询向量 vs 每条记忆 abstract 的向量 → cosine 相似度
  │
  ├── 稀疏向量路（BM25 关键词匹配）:
  │     检索字段: sparse_vector（= BM25(abstract)，即 L0 摘要的 BM25 稀疏向量）
  │     匹配方式: 查询的 BM25 稀疏向量 vs 每条记忆 abstract 的稀疏向量 → 关键词精确匹配
  │
  ├── 融合打分: final_score = 0.7 × BM25_score + 0.3 × cosine_score
  │
  └── 返回 Top-10 结果（目录节点和叶子节点混合）
  │
  ▼
Step 2: 分离目录节点和叶子节点
  │
  ├── 判断依据: is_leaf 字段
  │     is_leaf = "true"  → 叶子节点 → 直接收集到结果集，score 作为 _final_score
  │     is_leaf = "false" → 目录节点 → 入优先队列（按 -score 排序），等待递归展开
  │
  └── 目录节点本身不直接返回给 Agent，而是通过递归展开找到其下的叶子节点
  │
  ▼
Step 3: 递归展开目录（优先队列 + 分数传播 + 收敛检测）
  │
  ├── 循环: 从优先队列中取出分数最高的目录
  │     │
  │     ├── 搜索子节点:
  │     │     过滤条件: user_id = "{uid}" AND parent_uri = "{当前目录URI}"
  │     │     检索方式: 纯向量搜索（query_vec vs 子节点的 vector 字段）
  │     │     返回: 该目录下的直接子节点（可能是叶子，也可能是子目录）
  │     │
  │     ├── 分数传播（α = 0.5）:
  │     │     child_final_score = 0.5 × child_own_score + 0.5 × parent_dir_score
  │     │     含义: 子节点的最终分数 = 自身与查询的相关度 + 父目录的相关度加成
  │     │     效果: 高分目录下的子节点即使自身分数一般，也能获得父目录的分数加成
  │     │
  │     ├── 子节点分流:
  │     │     子目录（is_leaf=false）且 final_score > 0.3 → 入优先队列继续递归
  │     │     叶子节点（is_leaf=true）→ 收集到结果集
  │     │
  │     └── 收敛检测:
  │           每轮递归后检查当前 Top-K 结果是否变化
  │           连续 3 轮 Top-K 不变 → 停止递归（结果已收敛）
  │
  └── 递归终止条件: 优先队列为空 OR 连续 3 轮收敛
  │
  ▼
Step 4: 后处理 & 构建返回结果
  │
  ├── 按 _final_score 降序排列所有收集到的叶子节点
  ├── 取 Top-K（默认 5 条）
  ├── stale 状态记忆: 分数 ×0.5，标注 [可能过时]
  ├── archived 状态: 已在 Step 1 的 filter 中排除
  └── 返回每条记忆的 abstract（L0 摘要），标记节点类型:
        目录节点 → [DIR:xxx]（有 L1 可加载）
        叶子节点 → [ID:xxx]（有 L2 可加载）
  │
  ▼
Step 5: 注入 Agent 上下文
  <memory_context>
  - [DIR:dir_001] [entities] 华为科技: 张伟直接，审批3周，ERP有分歧
  - [ID:mem_001] [entities] 华为/张伟: 说话直接，汇报用PPT
  - [ID:mem_002] [entities] 华为/ERP项目: 张伟和李娜有分歧
  </memory_context>
  │
  ▼
Step 6: Agent 按需加载（memory_read 工具）
  memory_read(id=目录ID, level="L1") → 返回目录 overview（结构化导航）
  memory_read(id=叶子ID, level="L2") → 返回叶子 content（完整记忆）
  │
  ▼
Step 7: 异步更新 PG（不阻塞检索）
  UPDATE ai_agent_memory SET last_accessed_at=now, active_count+=1
  stale/archived 被命中 → 复活为 active
```

### 5.2 检索字段详解

**核心规则：只有 abstract（L0）的向量化结果参与检索匹配，其他字段只是存储。**

| 向量库字段 | 来源 | 参与检索 | 匹配方式 | 说明 |
|:---|:---|:---:|:---|:---|
| vector | embed(abstract) | ✅ | cosine similarity（稠密向量） | L0 摘要的语义向量，捕获同义词和隐含关系 |
| sparse_vector | BM25(abstract) | ✅ | 关键词精确匹配（稀疏向量） | L0 摘要的 BM25 向量，确保客户名/人名精确命中 |
| abstract（L0） | LLM 提取 / 系统聚合 | ❌（是向量化源文本） | — | 检索命中后返回给 Agent 的摘要 |
| overview（L1） | 系统 LLM 聚合（目录）| ❌ | — | Agent 调用 memory_read(level="L1") 按需加载 |
| content（L2） | LLM 提取（叶子） | ❌ | — | Agent 调用 memory_read(level="L2") 按需加载 |

### 5.3 目录递归展开详解

**为什么需要递归展开：**

向量库中的记忆按目录树组织。用户问"华为的情况"时，全局检索可能命中"华为科技"目录节点（L0 聚合摘要与查询相关），但目录本身只是摘要，真正有价值的是其下的叶子节点。递归展开就是从命中的目录出发，逐层下钻找到具体的叶子记忆。

**递归展开示例：**

```
向量库中的目录结构:
  viking://user/memories/entities/华为科技/          ← 目录节点（is_leaf=false）
    ├── viking://user/memories/entities/华为科技/张伟  ← 叶子（is_leaf=true）
    ├── viking://user/memories/entities/华为科技/ERP升级 ← 叶子（is_leaf=true）
    └── viking://user/memories/entities/华为科技/审批流程 ← 叶子（is_leaf=true）

用户查询: "华为那边的情况"

Step 1 全局检索命中:
  - 目录 "华为科技: 张伟直接，ERP有分歧，审批3周" → score=0.88 → 入优先队列
  - 叶子 "华为科技/张伟: 说话直接，汇报用PPT"    → score=0.72 → 直接收集

Step 3 递归展开目录 "华为科技/":
  搜索 parent_uri="viking://user/memories/entities/华为科技/" 的子节点:
    - 华为科技/ERP升级 → own_score=0.65
      final_score = 0.5 × 0.65 + 0.5 × 0.88 = 0.765 → 收集
    - 华为科技/审批流程 → own_score=0.45
      final_score = 0.5 × 0.45 + 0.5 × 0.88 = 0.665 → 收集
    - 华为科技/张伟 → 已在 seen_ids 中，跳过

最终 Top-K（按 final_score 排序）:
  1. [DIR] 华为科技 → 0.88（目录本身也可返回）
  2. [ID]  华为科技/ERP升级 → 0.765（递归展开发现）
  3. [ID]  华为科技/张伟 → 0.72（全局直接命中）
  4. [ID]  华为科技/审批流程 → 0.665（递归展开发现）
```

**分数传播的意义：**

```
不用分数传播时:
  华为科技/审批流程 own_score=0.45（与"华为那边的情况"语义关联弱）→ 可能被过滤

用分数传播后:
  华为科技/审批流程 final_score = 0.5×0.45 + 0.5×0.88 = 0.665
  → 因为父目录"华为科技"高度相关，子节点获得加成，不会被遗漏
  → 效果：问"华为的情况"时，华为下的所有子记忆都能被召回
```

```
两路检索各自返回 Top-K 结果后，通过 WeightedRerank 融合：

  final_score = sparse_weight × BM25_score + dense_weight × vector_score
              = 0.7 × BM25_score + 0.3 × vector_score

权重设计原因：
  BM25 权重 0.7（高）：CRM 场景中客户名、联系人名是精确匹配需求
    "华为科技" 必须精确命中包含"华为科技"的记忆，不能被语义相近的"中兴通讯"替代
  向量权重 0.3（低）：语义补充，捕获同义词和隐含关系
    "商机情况" 可以匹配到"ERP项目有分歧"（语义相关但无关键词重叠）
```

### 5.4 融合打分公式与排序示例

```
查询: "华为科技的商机情况"

候选记忆                              BM25_score  vector_score  final_score
─────────────────────────────────────────────────────────────────────────
[DIR] 华为科技: 张伟直接，ERP有分歧     0.95        0.88         0.7×0.95 + 0.3×0.88 = 0.929
[ID]  华为科技/ERP项目: 有分歧          0.90        0.82         0.7×0.90 + 0.3×0.82 = 0.876
[ID]  华为科技/张伟: 说话直接            0.85        0.75         0.7×0.85 + 0.3×0.75 = 0.820
[ID]  腾讯/云项目: 方案阶段             0.20        0.70         0.7×0.20 + 0.3×0.70 = 0.350
─────────────────────────────────────────────────────────────────────────

结果：华为相关记忆排在前面（BM25 精确匹配"华为科技"），腾讯被压到最后（BM25 不匹配）。
即使腾讯的 vector_score 较高（语义上"商机"相关），BM25 的高权重确保了客户名精确匹配优先。
```

### 5.5 检索匹配字段 vs 存储字段

向量库中每个文档有多个字段，但**只有 abstract 的向量化结果参与检索匹配**，其他字段只是存储：

```
向量库中有 3 个文档：

1. 目录节点（华为科技/）
   vector = embed("华为科技: 张伟直接，ERP有分歧，审批3周")  ← 参与检索（cosine）
   sparse_vector = BM25("华为科技: 张伟直接，ERP有分歧...")  ← 参与检索（关键词）
   abstract = "华为科技: 张伟直接，ERP有分歧，审批3周"       ← 向量化的源文本
   overview = "## 联系人\n- 张伟...\n## 商机\n- ERP..."     ← 不参与检索（按需加载）
   content = ""                                             ← 目录没有 content

2. 叶子节点（华为科技/ERP项目）
   vector = embed("华为科技/ERP项目: 张伟和李娜有分歧")      ← 参与检索
   sparse_vector = BM25("华为科技/ERP项目: 张伟和李娜...")   ← 参与检索
   abstract = "华为科技/ERP项目: 张伟和李娜有分歧"           ← 向量化的源文本
   content = "ERP项目张伟和李娜意见有分歧，建议分别沟通..."   ← 不参与检索（按需加载）

3. 叶子节点（华为科技/张伟）
   vector = embed("华为科技/张伟: 说话直接，汇报用PPT")      ← 参与检索
   sparse_vector = BM25("华为科技/张伟: 说话直接...")        ← 参与检索
   abstract = "华为科技/张伟: 说话直接，汇报用PPT"           ← 向量化的源文本
   content = "张伟说话直接不绕弯子，汇报用PPT带数据..."       ← 不参与检索（按需加载）
```

**总结**：

| 字段 | 是否参与检索匹配 | 用途 |
|------|:--------------:|------|
| vector（embed(abstract)） | ✅ | cosine similarity 语义匹配 |
| sparse_vector（BM25(abstract)） | ✅ | 关键词精确匹配 |
| abstract | ❌（是向量化的源文本） | 检索返回给 Agent 的 L0 摘要 |
| overview（L1） | ❌ | Agent 调用 memory_read(level="L1") 时返回 |
| content（L2） | ❌ | Agent 调用 memory_read(level="L2") 时返回 |

### 5.6 分层加载

```
检索默认返回 L0 摘要（~30 tokens/条），Agent 按需加载 L1/L2：

  L0 够用 → Agent 直接回答（不调用 memory_read）
  需要目录结构 → memory_read(id=DIR_ID, level="L1") → 返回结构化 Markdown
  需要叶子详情 → memory_read(id=LEAF_ID, level="L2") → 返回完整记忆内容

Token 开销对比：
  5 条 L0 注入: 5 × 30 = 150 tokens
  按需加载 2 条 L2: 2 × 200 = 400 tokens
  总计: 550 tokens（vs 直接返回 5 条 L2 = 1000 tokens）
```

## 六、记忆合并策略

### 6.1 按类别差异化

| 类别 | 合并方式 | 触发条件 | 实现方法 |
|:---|:---|:---|:---|
| profile | 始终合并（追加） | 每次 profile 记忆写入 | `_merge_profile()`: 搜索已有 → 内容追加 → 删旧写新 |
| preferences | 同 aspect 替换 | merge_key 相同且相似度 > 0.8 | `_merge_by_key()`: 按 merge_key 搜索 → 替换（向量库） |
| entities | 同实体替换 | merge_key 相同且相似度 > 0.8 | `_merge_by_key()`: 按 merge_key 搜索 → 替换 |
| agent_rules | 始终合并（融合） | 每次 agent_rules 记忆写入 | `_merge_agent_rules()`: 搜索已有 → LLM 融合新旧 → 删旧写新 |

### 6.2 语义去重流程（entities 无 merge_key 时）

当 entities 类记忆没有明确的 merge_key 时（LLM 未能生成结构化的实体路径），通过语义去重避免重复存储：

```
候选记忆（无 merge_key 的 entities）
  │
  ▼
向量预筛: 搜索已有同类别记忆，取 Top-3
  │
  ├── 最高相似度 < 0.9 → 直接 create（新信息，独立存储）
  │
  └── 最高相似度 >= 0.9 → 调 LLM 精判（DEDUP_PROMPT）
        │
        ├── skip:   候选与已有记忆重复/改写 → 不存储，不修改已有
        ├── create:  虽然相似但确实是新信息 → 独立存储
        ├── merge:  同主题的信息更新 → LLM 生成合并内容，替换旧记忆
        └── delete: 已有记忆完全失效 → 删除旧记忆，存储新记忆（极少使用）
```

**场景示例：**

```
━━━ 场景 1: skip（重复信息，不存储）━━━

已有记忆:
  abstract: "华为科技/ERP项目: 内部张伟和李娜有分歧，建议分别沟通"

新提取候选:
  abstract: "华为ERP项目张伟和李娜意见不一致，需要分开沟通"

向量预筛: 相似度 = 0.94（> 0.9）→ 调 LLM 精判
LLM 判断: skip（语义重复，只是换了说法）
结果: 不存储候选，已有记忆不变


━━━ 场景 2: merge（信息演进，合并更新）━━━

已有记忆:
  abstract: "华为科技/ERP项目: 内部张伟和李娜有分歧，建议分别沟通"
  content:  "华为ERP项目内部张伟和李娜有分歧，建议分别沟通。"

新提取候选:
  abstract: "华为科技/ERP项目: 分歧已解决，张伟方案获批"
  content:  "华为ERP项目内部分歧已解决，最终采用张伟的方案，李娜也同意了。"

向量预筛: 相似度 = 0.91（> 0.9）→ 调 LLM 精判
LLM 判断: merge（同主题信息更新，旧信息部分过时）
LLM 生成合并内容: "华为ERP项目此前张伟和李娜有分歧，现已解决，最终采用张伟方案。"
结果: 删除旧记忆 → 写入合并后的新记忆


━━━ 场景 3: create（相似但不同主题）━━━

已有记忆:
  abstract: "华为科技/张伟: 说话直接，汇报用PPT，开会控制30分钟"

新提取候选:
  abstract: "华为科技/张伟: 下周出差两周，期间找李娜对接"

向量预筛: 相似度 = 0.92（> 0.9，因为都是"华为科技/张伟"）→ 调 LLM 精判
LLM 判断: create（虽然主体相同，但是全新的时效性信息，不是对旧信息的更新）
结果: 独立存储为新记忆

注: 如果该候选有 merge_key="华为科技/张伟"，则走 _merge_by_key 逻辑直接合并，
    不会进入语义去重流程。语义去重只处理无 merge_key 的情况。
```

### 6.3 合并/去重后 active_count 继承策略

`active_count` 是记忆的检索热度指标，直接影响遗忘策略（active_count >= 3 的记忆享有高热度豁免）。合并或去重操作会删除旧记忆并创建新记忆，必须正确继承热度，否则高价值记忆可能因合并后热度归零而被错误遗忘。

#### 6.3.1 各场景继承规则

| 操作场景 | 旧记忆数 | 继承规则 | 设计依据 |
|:---|:---|:---|:---|
| `_merge_by_key` 写入时合并 | 1 条旧 → 1 条新 | 新记忆 active_count = 旧记忆 active_count | 信息演进，热度应延续 |
| `_merge_profile` profile 追加 | 1 条旧 → 1 条新 | 新记忆 active_count = 旧记忆 active_count | profile 每次检索都命中，热度必须延续 |
| `_merge_agent_rules` 规则融合 | 1 条旧 → 1 条新 | 新记忆 active_count = 旧记忆 active_count | 同 profile |
| `_dedup_create` 语义去重 merge | 1 条旧 → 1 条新 | 新记忆 active_count = 旧记忆 active_count | 合并内容是旧记忆的演进 |
| `_dedup_create` 语义去重 delete | 1 条旧 → 1 条新 | 新记忆 active_count = 0 | 旧记忆已完全失效，不继承 |
| `reflect_global` 碎片合并 | N 条旧 → 1 条新 | 新记忆 active_count = sum(各碎片 active_count) | 各碎片被命中的总次数即为该组信息的实际使用频率 |
| `reflect_on_session` archive_old | 不创建新记忆 | 无需继承（旧记忆保留原值，状态变为 archived） | — |
| `reflect_on_session` update_old | 1 条旧 → 1 条新 | 新记忆 active_count = 旧记忆 active_count + 1 | 被更新说明仍有价值，热度 +1 |

#### 6.3.2 实现要点

```
写入时合并（_merge_by_key / _merge_profile / _merge_agent_rules）:
  1. 搜索到旧记忆时，读取 old_active_count = e.get("active_count", 0)
  2. 删除旧记忆
  3. 创建新记忆时写入 active_count = old_active_count
  4. 同步更新 PG: active_count = old_active_count

全局反思碎片合并（reflect_global 场景 A）:
  1. 收集碎片组所有记忆的 active_count
  2. total_count = sum(m.get("active_count", 0) for m in items)
  3. 新合并记忆写入 active_count = total_count
  4. 同步更新 PG

向量库字段:
  active_count 作为向量库文档的标量字段存储（int64），
  合并写入时通过 upsert 设置初始值。

PG 字段:
  ai_agent_memory.active_count（INTEGER DEFAULT 0），
  合并后通过 INSERT 或 UPDATE 设置继承值。
```

#### 6.3.3 为什么碎片合并用累加（sum）

```
碎片合并场景:
  碎片 A: active_count = 5（"金额800万" 被检索命中 5 次）
  碎片 B: active_count = 3（"评审通过" 被检索命中 3 次）
  碎片 C: active_count = 1（"下周签合同" 被检索命中 1 次）

合并后 active_count = 5 + 3 + 1 = 9

为什么用 sum 而非 max:
  - 这些碎片是同一 merge_key（同一项目/联系人）的不同侧面
  - 合并前检索命中碎片 A 或碎片 B，本质上都是在"用这组信息"
  - 合并后 1 条记忆承载原来 N 条的检索负载，sum 准确反映实际使用频率
  - 遗忘阈值是 3，sum=9 明确应该豁免；如果用 max=5 也能豁免，但丢失了使用次数的准确性

为什么 1对1 合并（_merge_by_key）不用 sum:
  - 1对1 是"新信息替换旧信息"，始终只有 1 条记忆
  - 旧记忆被命中 N 次 → 新记忆继承 N 次，因为是同一条的演进
  - 不存在"多条分别被命中"的情况
```

## 七、记忆遗忘策略

| 遗忘机制 | 判断粒度 | 判断条件 | 处理方式 | 执行时机 |
|:---|:---|:---|:---|:---|
| 逐条遗忘（7.2） | 单条记忆 | age > 180d + active_count < 3 | 三阶段淡化: active → stale → archived → deleted | 每日定时 |
| 高热度豁免（7.2） | 单条记忆 | age > 180d + active_count >= 3 | 保留为 active，不进入淡化 | 每日定时 |
| 实体级沉寂（7.3） | parent_entity 整体 | 60d 无写入 + 60d 无检索 | 渐进式: dormant → stale → archived | 每日定时 |
| 全量清理（7.4） | 用户/租户级 | 租户注销或用户离职 | 物理删除全部记忆（PG + 向量库） | 事件驱动 |

> 遗忘策略由 `decay_memories()` 统一执行，纯规则判断，0 LLM 消耗。
> profile / preferences / agent_rules 永不遗忘。

---

**为什么需要记忆遗忘：**

记忆系统不是无限增长的数据库，而是模拟人类记忆的"有选择性保留"机制。没有遗忘的记忆系统会面临三个核心问题：

1. **检索噪声**：记忆越多，检索时无关结果越多。半年前"张伟下周出差"的记忆如果仍然 active，会干扰当前检索结果的相关性排序，导致 Agent 回答质量下降。

2. **信息过时**：CRM 场景中第三方事实有天然时效性。商机阶段会推进、联系人会变动、项目会结束。过时的记忆不仅无用，还可能误导 Agent 给出错误信息。

3. **存储成本**：向量库按存储量计费，无限增长的记忆会带来不必要的成本。单用户 500 条记忆是合理上限，超出需要淘汰低价值记忆。

**设计原则：**

- **分类差异化**：不同类别的记忆有不同的时效性特征，不能一刀切
- **热度豁免**：频繁被检索命中的记忆即使过期也有价值，不应被遗忘
- **渐进淡化**：不直接删除，而是通过三阶段（stale→archived→deleted）逐步降低影响，给予复活机会
- **全量清理兜底**：租户注销/用户离职时需要彻底清除，满足数据合规要求

### 7.1 各类别遗忘策略

| 类别 | 保留天数 | 遗忘策略 | 设计逻辑 |
|:---|:---:|:---|:---|
| profile | 永不遗忘 | 不进入淡化流程 | 用户身份是 Agent 个性化的基础锚点。"华东区销售总监"这类信息不会因时间推移而失效，且每用户只有 1 条，存储成本可忽略。即使用户调岗，新信息会通过 LLM 合并覆盖旧内容，而非删除。 |
| preferences | 永不遗忘 | 不进入淡化流程 | 用户偏好是 Agent 输出质量的关键。"表格展示""金额用万"等偏好一旦建立就长期有效，用户不会每次重复说明。偏好变更时通过同维度合并覆盖（新值替换旧值），不需要遗忘机制。 |
| agent_rules | 永不遗忘 | 不进入淡化流程 | Agent 行为准则是用户对 Agent 的持久约束，每轮对话都需要注入。"回复不超过100字"这类规则除非用户主动修改，否则永远生效。矛盾时通过 LLM 融合以新为准，不需要遗忘。 |
| entities | 180 天 | 三阶段淡化（active → stale → archived → deleted） | 第三方事实有时效性。"张伟下周出差"半年后已无意义；"华为ERP项目谈判阶段"可能早已签约或丢单。180 天是 CRM 销售周期的经验值（大客户商机平均 3-6 个月关闭）。但高热度记忆（active_count ≥ 3）即使过期也保留——频繁被检索说明仍有价值。 |

### 7.2 遗忘条件

```
遗忘判断（仅 entities 类别，每日凌晨定时任务执行）:

过期 AND 低热度:
  age_days > 180 AND active_count < 3
  → 进入三阶段淡化

过期 BUT 高热度:
  age_days > 180 AND active_count >= 3
  → 保留为 active（频繁被检索到的记忆即使过期也有价值）
  → 示例: "华为科技/张伟: 说话直接" 虽然是半年前提取的，但每次问华为相关问题都命中，说明仍有参考价值

profile / preferences / agent_rules:
  → 永不进入遗忘流程，不受 age_days 影响
```

### 7.3 实体级沉寂检测

除了 7.2 的逐条遗忘判断外，还需要从 **parent_entity 整体活跃度**维度判断——当整个客户实体长期无活动时，批量降权比逐条等待过期更高效。

**业务背景：**

```
情况1: 丢单
  竞标失败，用户不再关注该客户 → 记忆应逐步退出检索范围，避免干扰

情况2: 转交
  客户转给团队其他人跟进 → 记忆对当前用户无价值

情况3: 暂时搁置
  客户预算冻结，项目推迟到下半年 → 现在沉寂但未来可能恢复
```

> 因为情况 3 的存在，沉寂 ≠ 无用，不能直接删除。采用渐进式策略。

**判断条件：**

```
按 parent_entity 分组统计:
  days_since_last_write > 60 AND days_since_last_access > 60
  （整个实体 60 天无新增也无检索）
```

> 阈值说明: 60 天（2 个月）无写入也无检索，覆盖了正常项目"暂停后恢复"的观察窗口。
> 与 7.2 逐条遗忘的区别: 7.2 按单条记忆的 age 判断，7.3 按整个实体的活跃度判断。

**处理逻辑（渐进式）：**

```
第 1 次命中沉寂:
  → 标记 dormant_count = 1（仅记录，不改变状态）

连续 7 次命中（即连续 7 天都判定为沉寂，实际 67 天无活动）:
  → 整组记忆进入 stale
  → 效果: 检索时权重降低（仍可命中，但排序靠后）

进入 stale 后 30 天仍无活动:
  → 由 decay_memories 处理: stale → archived（不再出现在检索结果中）

任何时候用户重新提及该客户:
  → active_count +1，自动恢复为 active
  → dormant_count 重置为 0
```

> 时间线: 60天沉寂 + 7天确认 + 30天stale = 97天才archived。
> 对于 CRM 项目周期（3-6 月），足够区分"暂时搁置"和"确实不再关注"。

**执行时机：** 由 `decay_memories()` 每日定时任务统一执行（与逐条遗忘判断在同一任务中）。

### 7.4 全量清理策略

不受 `_RETENTION_DAYS` 限制，直接物理删除：

| 触发场景 | 清理范围 | 触发方式 | 操作 |
|:---|:---|:---|:---|
| 租户过期/注销 | 该 tenant_id 下所有用户的全部记忆 | 平台管理接口 / 定时任务检测租户状态 | PG 物理删除 + 向量库按 tenant_id filter 批量删除 |
| 用户离职/停用 | 该 user_id 下的全部记忆（所有类别） | HR 系统 Webhook / 管理后台手动触发 | PG 物理删除 + 向量库按 user_id filter 批量删除 |

## 八、反思修正机制

| 反思类型 | 函数 | 触发时机 | 处理对象 | LLM 消耗 | 频率 |
|:---|:---|:---|:---|:---|:---|
| 失败驱动反思 | `reflect_on_failure()` | Agent 任务失败后 | 本轮使用的记忆 | 1 次 | 事件驱动 |
| 用户反馈反思 | `reflect_on_correction()` | 用户说"不对/错了" | 与纠正相关的记忆 | 1-2 次 | 事件驱动 |
| 会话结束反思 | `reflect_on_session()` | extract_and_update 完成后（异步） | 本次提取的新记忆 vs 存量 | 每条 1 次 | 每次写入 |
| 定期全局反思 | `reflect_global()` | 每日凌晨定时任务 | entities 全量存量 | 0-20 次（预算控制） | 每日 |

**职责划分：**
- 8.1 ~ 8.3 为**实时反思**（事件驱动，处理"刚发生的"）
- 8.4 为**定期反思**（批量执行，处理"积累的"）
- 遗忘策略（第七章）负责时间驱动的状态转换，不属于反思

### 8.1 失败驱动反思 `reflect_on_failure()`

```
触发: Agent 任务失败后
流程:
  1. 检索本轮对话中被使用的记忆
  2. LLM 分析失败原因是否与某条记忆有关
  3. 如果有 → 删除错误记忆
```

### 8.2 用户反馈反思 `reflect_on_correction()`

```
触发: 用户说"不对"/"错了"/"改一下"
流程:
  1. 检索与纠正内容相关的记忆
  2. LLM 判断哪些记忆需要修正或删除
  3. 执行修正
```

### 8.3 会话结束反思 `reflect_on_session()`

参考 OpenViking 的 `post_session_reflection` 设计。在每次 `extract_and_update` 完成后异步调用。

```
触发: extract_and_update 完成后（异步，不阻塞主流程）
输入: 本次提取的新记忆列表 + user_id

流程:
  1. 对每条新记忆，检索已有的相似记忆（排除本次写入的）
  2. 过滤高相似度候选（score > 0.7）
  3. LLM 判断关系类型:
     - no_conflict: 无矛盾，信息互补 → 不处理
     - contradiction: 直接矛盾（偏好改变、事实更正）→ 需要解决
     - evolution: 信息演进（旧信息过时但不矛盾）→ 需要解决
     - duplicate: 重复信息 → 需要解决
  4. 对每个冲突，LLM 决定解决方案:
     - update_old: 用合并内容更新旧记忆
     - archive_old: 归档旧记忆，保留新记忆
     - keep_both: 两者都保留
     - discard_new: 丢弃新记忆

返回: {"checked": N, "conflicts": N, "resolved": N, "actions": [...]}

示例:
  新记忆: "华为ERP项目金额800万，谈判阶段"
  已有记忆: "华为ERP项目金额500万，谈判阶段"
  → 关系: evolution（金额从500万调整为800万）
  → 解决: update_old（用800万更新旧记忆）
```


### 8.4 定期全局反思 `reflect_global()`

每日凌晨定时执行，单次遍历完成全部反思工作。通过**场景判断**决定每个实体需要做哪些分析，避免固定分频带来的复杂度。

#### 8.4.1 设计原则

```
1. 单次执行，场景驱动
   不按"碎片/质量/一致性/洞察"分阶段分频，而是一次遍历所有 entities，
   按每个 parent_entity 的数据状态匹配场景，命中什么就处理什么。

2. LLM 按需调用
   场景指标全部是数据库统计（0 LLM 开销），只在需要合并或判断矛盾时调用 LLM。
   设置单次执行 LLM 调用上限（20 次），超出则记录跳过项，下次优先处理。

3. 与 session 反思互补
   session 反思处理"刚写入的单条新记忆"与存量的矛盾（增量、实时）。
   global 反思处理"存量整体"的健康状态（批量、每日）。
   global 的场景 C 兜底 session 可能遗漏的矛盾。
```

#### 8.4.2 执行流程

```
触发: 每日凌晨定时任务（或手动调用）
输入: user_id
范围: entities 类别全量 + profile + preferences

┌─────────────────────────────────────────────────────────┐
│ Step 0: 数据加载                                         │
│  ├── 从向量库拉取 user_id 下所有 entities 记忆           │
│  ├── 从 PG 获取 profile + preferences                   │
│  ├── 按 parent_entity 分组                               │
│  └── 计算每组的场景指标                                  │
└─────────────────────────────────────────────────────────┘
          │
          ▼
┌─────────────────────────────────────────────────────────┐
│ Step 1: 逐实体场景判断 + 对应处理                        │
│                                                          │
│  对每个 parent_entity:                                   │
│    1. 计算场景指标（纯数据统计，0 LLM）                  │
│    2. 匹配场景，一个实体可命中多个:                       │
│       A(碎片堆积) / B(内部矛盾) / C(高活跃稀疏)          │
│    3. 按优先级 A > B > C 依次执行处理逻辑                │
│    4. 检查 LLM 预算，超出则跳过并记录                    │
└─────────────────────────────────────────────────────────┘
          │
          ▼
┌─────────────────────────────────────────────────────────┐
│ Step 2: 遗忘 + 全局检查                                  │
│  ├── decay_memories(): 逐条遗忘 + 实体级沉寂检测（7.2/7.3）│
│  └── profile ↔ preferences 一致性检查（仅 profile 有变   │
│      更时执行，通过 updated_at 判断）                    │
└─────────────────────────────────────────────────────────┘
          │
          ▼
┌─────────────────────────────────────────────────────────┐
│ Step 3: 输出反思报告                                     │
└─────────────────────────────────────────────────────────┘
```

#### 8.4.3 场景指标定义

对每个 parent_entity 计算以下指标（纯数据库统计，不消耗 LLM）：

| 指标 | 来源 | 说明 |
|:---|:---|:---|
| `fragment_count` | 向量库 group by merge_key having count > 1 | 同 merge_key 碎片组数 |
| `total_count` | 向量库 count | 该实体下记忆总条数 |
| `max_similarity` | 向量库 pairwise cosine（抽样 top-5 对） | 不同 merge_key 间最高相似度 |
| `recent_access_7d` | PG last_accessed_at > now-7d | 近 7 天被检索命中次数 |

#### 8.4.4 场景 A: 碎片堆积

**业务背景：**

CRM 销售场景中，用户多次提及同一项目/联系人的不同侧面信息（金额变化、阶段推进、评审结果），session 反思只处理"矛盾"关系，互补信息（`no_conflict`）会被跳过，导致同一 merge_key 下碎片积累。

```
业务示例:
  周一: "华为ERP金额从500调到800万" → merge_key="华为科技/ERP项目"
  周三: "华为ERP明天开评审会"         → merge_key="华为科技/ERP项目"
  周五: "华为评审通过了，下周签合同"   → merge_key="华为科技/ERP项目"
  → session 反思: 三条互补不矛盾，全部 no_conflict 跳过
  → 结果: 同 key 3 条碎片，应合并为 1 条完整项目时间线
```

**判断条件：**

```
fragment_count >= 1（存在同 merge_key 多条记忆）
```

> 阈值说明: CRM 场景下同一项目/联系人的信息应该是一条完整记忆，2 条就是碎片。

**处理逻辑：**

```
对每个碎片组（同 merge_key 记录数 > 1）:
  1. 按 updated_at 排序（最新在前）
  2. LLM 合并（1 次调用/组）
  3. 质量校验: 合并后 content 长度 ≥ 原始最长条目的 50%（防信息丢失）
  4. 继承碎片中最高的 active_count（保留热度信号）
  5. 原子操作: 写入新条目 → 删除旧碎片
```

**合并 Prompt：**

```
以下是关于 '{merge_key}' 的 {N} 条记忆，按时间从新到旧排列：

{记忆列表，每条标注 [时间] 内容}

请合并为 1 条完整记忆，规则：
1. 时间冲突时以最新信息为准（如金额、阶段等变化）
2. 非冲突信息全部保留（如联系方式、偏好、关系）
3. 标注关键变化时间点（如 "2026-03 金额从500万调为800万"）
4. 保持 CRM 场景所需的可操作性（人名、数字、状态要精确）

返回 JSON: {"abstract":"一句话摘要","content":"完整合并内容","key_changes":["变化1","变化2"]}
```

**合并后示例：**

```
合并前（3 条碎片）:
  ① [2026-03-15] "华为ERP项目金额800万（从500万调整）"
  ② [2026-04-27] "华为ERP明天评审会"
  ③ [2026-04-29] "华为ERP评审通过，下周签合同"

合并后（1 条）:
  abstract: "华为科技/ERP项目: 金额800万，评审已通过，下周签合同"
  content: "华为ERP项目。金额800万（2026-03从500万调整）。
            2026-04-28评审通过。预计下周签合同。决策人: 张总(CTO)。"
  key_changes: ["2026-03 金额500→800万", "2026-04-28 评审通过"]
```

**LLM 消耗：** 每个碎片组 1 次调用。典型日 1-2 组，极端日（月初汇报）8-10 组。

#### 8.4.5 场景 B: 内部矛盾（session 反思兜底）

**业务背景：**

session 反思可能遗漏矛盾的三种情况：

```
情况1: 网络异常
  extract_and_update 写入成功，但 reflect_on_session 异步执行时网络超时失败
  → 旧记忆"800万"和新记忆"1000万"并存，无人处理

情况2: merge_key 不一致
  旧: merge_key="华为科技/ERP项目"
  新: merge_key="华为科技/ERP升级项目"（LLM 提取时命名略有差异）
  → session 反思的向量检索可能因表述差异导致相似度低于 0.7 阈值，未触发

情况3: 间接矛盾（关联失效）
  记忆A: "华为张总是CTO"
  记忆B: "华为张总已离职"（一个月后用户提及，session 反思处理了 A→archive）
  记忆C: "华为张总偏好PPT汇报"（C 和 B 不矛盾，session 不处理）
  → 但逻辑上 C 已失效（人都走了，沟通偏好无意义）
```

**判断条件：**

```
max_similarity > 0.85 AND fragment_count == 0
```

> 阈值说明:
> - max_similarity > 0.85: 比 session 反思的 0.7 阈值高，只兜底真正高风险的
> - fragment_count == 0: 先排除碎片问题（碎片由场景 A 处理），这里处理的是"不同 merge_key 但实际有冲突"

**处理逻辑：**

```
Step 1: 找出相似度 > 0.85 的记忆对（跨 merge_key）

Step 2: LLM 判断关系（复用 _classify_relation，1 次调用/对）:
  ├── identical（完全重复）→ archive 热度低的那条
  ├── evolution（信息演进）→ 保留新的，archive 旧的
  ├── contradiction（直接矛盾）→ 记录到异常日志，不自动处理（需人工确认）
  └── unrelated（语义相近但不矛盾）→ 跳过
      示例: "华为/ERP评审通过" vs "华为/云迁移方案阶段"
      → 高相似度（都是华为项目）但不矛盾，属于不同项目

Step 3: 间接矛盾检测（P1 阶段实现）
  如果记忆中包含状态变更关键词（离职/调岗/取消/作废/终止）:
  → 级联检查同 parent_entity 下引用该主体的其他记忆
  → 标记为"待确认"（不自动删除——万一人回来了呢）
  → 输出到 recommendations
```

**LLM 消耗：** 每对 1 次调用。通常 0-2 对/天（矛盾是偶发事件）。

#### 8.4.6 场景 C: 高活跃但稀疏

**业务背景：**

用户本周密集问某客户相关问题，但该客户记忆很薄——检索虽然命中了，但 Agent 只能给出泛泛回答，无法提供深度上下文。

```
业务示例:
  用户本周 3 次问"阿里那个项目怎么样了"
  entities 中关于阿里的记忆只有 1 条: "阿里巴巴/蚂蚁项目: 在谈"
  → 每次检索都命中这条，但信息太薄
  → Agent 无法回答"什么阶段""谁负责""金额多少"

可能原因:
  - 用户对话偏口语（"帮我查下阿里那边"），无增量认知可提取
  - 信息都在 CRM 系统中（工具可查），对话中只口头提及
  - 是新客户，刚开始跟进，信息积累还不够
```

**判断条件：**

```
recent_access_7d >= 3 AND total_count <= 2
```

> 阈值说明:
> - 一周被检索 3 次说明用户确实在密集关注
> - 2 条以下属于"极度稀疏"，正常活跃客户通常有 5-10 条记忆

**处理逻辑（不消耗 LLM）：**

```
不做自动修改（没有数据来源可补充）。输出建议:

recommendations += [{
    "entity": "阿里巴巴",
    "type": "coverage_gap",
    "message": "近7天被检索3次但仅有1条记忆，信息覆盖不足",
    "suggestion": "下次对话涉及该客户时，可主动追问补充"
}]

后续利用（由上层决定）:
  方式1: 下次 Agent 对话涉及该客户时，在 system prompt 注入提示:
         "你对阿里巴巴的记忆较少，可以主动追问细节以补充认知"
  方式2: 纯记录，管理后台可视化展示"记忆覆盖度预警"
```

**LLM 消耗：** 0

#### 8.4.7 场景优先级与 LLM 预算控制

```
同一实体命中多场景时，按优先级顺序执行:
  A（碎片堆积） > B（内部矛盾） > C（高活跃稀疏）

优先级依据:
  - A 最高: 碎片直接影响检索质量（多条碎片 vs 1条完整 → 检索精度不同）
  - B 次高: 矛盾记忆可能导致 Agent 给出错误回答（正确性 > 效率）
  - C 最低: 不影响正确性，只影响覆盖度（且无自动操作，仅输出建议）
```

**LLM 预算控制：**

```
单次全局反思 LLM 调用上限: 20 次
分配:
  ├── 碎片合并（场景A）: 每组 1 次，优先消耗预算
  ├── 矛盾检测（场景B）: 每对 1 次
  └── 一致性检查（Step 2）: 1 次（仅 profile 有变更时）

超出预算时:
  ├── 记录跳过项到 pending_reflection 队列（PG 持久化）
  └── 下次执行时优先处理 pending 队列中的项（FIFO）
```

**典型日 vs 极端日 LLM 调用估算：**

| 情况 | 场景 A | 场景 B | 一致性 | 合计 |
|:---|:---|:---|:---|:---|
| 典型日（日常 3-5 轮对话） | 1-2 次 | 0 | 0 | **1-2 次** |
| 活跃日（汇报日，更新 5 客户） | 4-5 次 | 0-1 | 0 | **4-6 次** |
| 极端日（月初批量汇报 10+ 客户） | 8-10 次 | 2-3 | 1 | **11-14 次** |

#### 8.4.8 遗忘 + 全局级检查（Step 2）

**遗忘（由 decay_memories 统一执行）：**

```
逐条遗忘（7.2）:
  active → stale:    age > 180d + active_count < 3 + 30天无检索
  stale → archived:  持续 30 天无检索
  archived → deleted: 持续 30 天无检索（物理删除向量库 + PG）

实体级沉寂检测（7.3）:
  整个 parent_entity 60天无写入+无检索 → 渐进式降权（dormant → stale → archived）
```

**profile ↔ preferences 一致性检查：**

```
触发条件: profile 的 updated_at 在上次反思之后有变更（增量触发，非每日都执行）

流程:
  ├── 从 PG 获取 profile
  ├── 从向量库获取 preferences（最多 50 条）
  ├── 1 次 LLM 判断是否矛盾
  └── 记录不一致项（不自动修复，留给人工确认）

示例:
  不矛盾: profile="技术总监" vs preference="回复请简洁"
    → 技术人员也可能偏好简洁表达，不矛盾
  可能矛盾: profile="销售总监，管理15人" vs preference="请详细解释每个技术细节"
    → 管理者通常要结论不要细节 → 记录
```

#### 8.4.9 自适应触发（写入时即时检查）

除每日定时执行外，在 `extract_and_update` 写入后即时检查：

```
触发点: extract_and_update 完成写入后
检查: 该 merge_key 下碎片数 >= 3
操作: 异步触发单 key 级碎片合并（场景 A 的子集，只处理该 key）
约束: 不阻塞主流程，不影响 session 反思的执行

为什么阈值是 3（而非日常反思的 2）:
  - 2 条碎片: 可能是"正在进行的对话"（用户分两次说完一件事），等每日反思合并即可
  - 3 条碎片: 明确的堆积信号，应立即处理（避免检索时命中多条碎片降低体验）
```

#### 8.4.10 输出格式

```python
返回: {
    # 碎片合并统计
    "merged": N,
    # 矛盾解决统计
    "conflicts_resolved": N,
    # 一致性问题
    "inconsistencies": N,
    # 建议项（不自动执行，供上层决策）
    "recommendations": [
        {"entity": "阿里巴巴", "type": "coverage_gap",
         "message": "近7天被检索3次但仅有1条记忆"},
        {"entity": "华为科技/张伟", "type": "cascading_invalidation",
         "message": "张伟已离职，关联记忆'偏好PPT汇报'可能失效"}
    ],
    # 各实体场景命中（可观测性）
    "entity_scenes": {
        "华为科技": ["A:合并2组碎片"],
        "阿里巴巴": ["C:高活跃稀疏"],
        "中兴": ["B:解决1对evolution"]
    },
    # 淡化统计（由 decay_memories 产出，含实体级沉寂检测）
    "decay": {"to_stale": N, "to_archived": N, "deleted": N,
              "dormant_entities": ["腾讯", "字节跳动"]},
    # 预算使用情况
    "llm_budget": {"used": 5, "limit": 20, "pending": 0}
}
```

#### 8.4.11 与实时反思的职责边界

```
用户对话产出新记忆
        │
        ▼
   session 反思（实时，异步）
   ├── 职责: 新记忆 vs 存量的矛盾检测
   ├── 处理: contradiction/evolution/duplicate → archive/update/discard
   ├── 不处理: no_conflict（互补信息）→ 留给 global 的场景 A 合并
   └── 可能遗漏: 网络异常、merge_key 不一致、间接矛盾
        │
        │ 碎片积累 / 遗漏矛盾
        ▼
   全局反思（每日定时，批量）— 只做"反思"（分析+修正）
   ├── 场景 A: 合并 session 判定为 no_conflict 的互补碎片
   ├── 场景 B: 兜底 session 遗漏的跨 key 矛盾
   └── 场景 C: 检测检索暴露的覆盖度不足（输出建议）

   遗忘策略（每日定时，由 decay_memories 统一执行）— 只做"遗忘"（时间驱动状态转换）
   ├── 逐条遗忘: age > 180d + 低热度 → stale → archived → deleted（7.2）
   └── 实体级沉寂: 整个 parent_entity 60d 无活动 → 渐进式降权（7.3）

职责边界:
  - 反思 = 分析记忆内容质量并修正（需要 LLM 或语义计算）
  - 遗忘 = 基于时间和热度的状态转换（纯规则，0 LLM）
  - 两者在同一每日任务中顺序执行: 先反思，再遗忘
```

## 十、记忆与系统数据边界

### 10.1 核心原则

**记忆系统只记录增量认知，不记录 CRM 系统已有的结构化数据。**

CRM 系统中已有的数据（客户行业、商机金额、联系人电话、活动状态等）可以通过工具实时查询获取，不需要记忆系统做镜像。记忆系统的价值在于记录系统中**没有的**信息——用户在对话中透露的主观判断、沟通技巧、关系洞察、隐性知识。

### 10.2 提取边界

```
✅ 记忆应该记录的（增量认知，CRM 系统中没有）:
  - 沟通风格: "张伟说话直接，开会不要绕弯子"
  - 关系洞察: "张伟和李娜有分歧，建议分别沟通"
  - 内部流程: "华为审批至少3-4周，需要过采购委员会"
  - 主观判断: "ERP项目希望最大"
  - 竞争情报: "对手报价比我们低20%"
  - 口头承诺: "丁总口头同意了报价方案"

❌ 记忆不应该记录的（系统数据，可实时查询）:
  - 客户字段: 行业、城市、员工数、营收、评分
  - 商机字段: 金额、阶段、概率、关闭日期、来源
  - 联系人字段: 职位、电话、邮箱
  - 活动字段: 类型、主题、日期、状态
```

### 10.3 提取提示词中的排除规则

在 ENTITIES_EXTRACT_PROMPT 中明确告知 LLM 不提取系统数据：

```
以下字段值不要作为记忆的主体内容（CRM 系统已有，可实时查询）:
- 客户: 行业、城市、员工数、营收、评分
- 商机: 金额、阶段、概率、关闭日期、来源
- 联系人: 职位、电话、邮箱
- 活动: 类型、主题、日期、状态

但客户名和人名必须保留在 merge_key / parent_entity / abstract 中作为定位锚点。
```

### 10.4 检索时的防御性设计

即使提取时偶尔混入了系统数据，Agent 也不会直接引用：

- CRM_SYSTEM_PROMPT 中的行为约束：*"记忆是参考不是数据源：记忆中的客户/商机信息可能已过时，涉及具体数据（金额、阶段、电话等）时必须用工具实时查询确认"*
- source_type="system_data" 的记忆在检索结果中附加提示：`[建议用工具实时查询确认最新数据]`
