# 记忆遗忘与反思 — 设计方案

> 本文档整合了记忆遗忘（三阶段淡化 + 精炼 + 统计衰减）和记忆反思（会话反思 + 失败反思 + 用户纠正反思 + 全局反思）的完整技术方案。

---

## 一、设计原则

1. **检索链路只走向量库**，PG 不参与检索关键路径
2. **向量库只读不写**（检索时），所有更新通过异步任务或定时任务完成
3. **向量库只存 status**（FilterIndex），last_accessed_at 和 active_count 只存 PG
4. **status 变更通过定时任务批量同步到向量库**，不是每次检索都同步
5. **反思不能超出记忆提取的边界**，不用正则硬编码，信任 EXTRACTION_PROMPT 的判断
6. **反思是记忆的质量保障层**，不是必须的，但长期运行必须有

---

## 二、遗忘与反思的关系

| 维度 | 遗忘 | 反思 |
|------|------|------|
| 解决什么问题 | 记忆膨胀、过时信息占用存储 | 跨 merge_key 的语义矛盾 |
| 处理对象 | 所有向量库类别（entities/events/cases/patterns） | 只处理 entities/events |
| 触发方式 | 定时任务（每天/每月） | 实时（每轮对话后）+ 定时（每周） |
| 判断方式 | 规则（TTL + last_accessed_at） | LLM（关系判断） |
| 操作 | 状态转换（active→stale→archived→deleted） | 归档/删除/合并旧记忆 |
| 可恢复性 | stale/archived 被检索命中可复活 | archive_old 可复活，delete 不可恢复 |

## 三、9 类记忆的遗忘策略

| 类别 | 存储 | 遗忘方式 | 说明 |
|------|:----:|---------|------|
| soul | PG | 不遗忘，定期精炼 | 每用户 1 条，超 300 字 LLM 压缩 |
| profile | PG | 不遗忘，定期精炼 | 每用户 1 条，超 200 字 LLM 压缩 |
| preferences | 向量库 | 不遗忘，同 merge_key 覆盖 | 用户说"我现在喜欢图表"覆盖旧的"表格" |
| entities | 向量库 | 三阶段淡化（180 天） | active → stale → archived → deleted |
| events | 向量库 | 三阶段淡化（90 天） | 时效性最强 |
| cases | 向量库 | 三阶段淡化（180 天） | 问题解决方案 |
| patterns | 向量库 | 三阶段淡化（365 天） | 工作模式，保留最久 |
| tools | PG | 统计衰减（每月 ×0.7） | 长期不用降权 |
| skills | PG | 统计衰减（每月 ×0.7） | 同 tools |

## 四、三阶段淡化

### 4.1 状态转换

```
active ──过期+30天无检索──→ stale ──30天无检索──→ archived ──30天无检索──→ deleted
  ▲                          │                      │
  │         被检索命中         │       被检索命中       │
  └──────────────────────────┘                      │
  └─────────────────────────────────────────────────┘
```

### 4.2 状态定义

| 状态 | 检索行为 | 进入条件 | 退出条件 |
|------|---------|---------|---------|
| active | 正常返回，正常排序 | 新写入 / 复活 | 过期 + 30 天无检索 → stale |
| stale | 返回但分数 ×0.5，标注 [可能过时] | active 过期且 30 天无检索 | 被命中 → active；30 天无检索 → archived |
| archived | 不返回（向量库 filter 过滤） | stale 持续 30 天无检索 | 被精确搜索命中 → active；30 天无检索 → deleted |
| deleted | 物理删除 | archived 持续 30 天无检索 | 不可恢复 |

### 4.3 各类别生命周期

| 类别 | active 期 | + stale | + archived | 总生命周期 |
|------|:---------:|:------:|:----------:|:---------:|
| events | 90 天 | 30 天 | 30 天 | 150 天 |
| entities / cases | 180 天 | 30 天 | 30 天 | 240 天 |
| patterns | 365 天 | 30 天 | 30 天 | 425 天 |

### 4.4 数据存储分工

```
向量库存：status（FilterIndex，检索时过滤用）
PG 存：  status + last_accessed_at + active_count（生命周期管理用）

检索时（实时，只读向量库）：
  用户查询 → hybrid_search(filter: status != "archived") → 代码中 stale 降权 → 返回

检索后（异步，写 PG）：
  UPDATE ai_agent_memory SET last_accessed_at=now, active_count+=1 WHERE vector_id IN (...)

每日凌晨（定时任务）：
  从 PG 读 last_accessed_at → 判断状态转换 → 更新 PG + 批量同步向量库 status
```

## 五、soul / profile 精炼

每次 LLM 合并后检查长度，超限自动压缩：

```
soul 超过 300 字 → LLM 压缩，保留关键信息去掉冗余
profile 超过 200 字 → LLM 压缩，保留关键信息去掉冗余
```

## 六、tools / skills 统计衰减

```
每月 1 号执行：active_count = active_count × 0.7
衰减后 active_count = 0 → 标记 stale
```

## 七、反思机制

### 7.1 为什么需要反思

merge 只能处理同 merge_key 的更新。跨 merge_key 的语义矛盾需要反思兜底：

| 场景 | merge 能处理 | 需要反思 |
|------|:----------:|:-------:|
| 华为/ERP: 方案→谈判（同 key 更新） | ✅ | ❌ |
| 华为/张伟→华为/李娜（换人） | ❌ | ✅ |
| 重复事件（同一会议记两次） | ❌ | ✅ |
| 跨层级策略矛盾 | ❌ | ✅ |
| 偏好更新（同 key 覆盖） | ✅ | ❌ |

### 7.2 四种反思机制

| 反思类型 | 触发来源 | 触发时机 | 覆盖范围 |
|---------|---------|---------|---------|
| 会话结束反思 | extract_and_update 完成后 | 实时（只对 entities/events） | 新记忆 vs 已有记忆的跨 key 矛盾 |
| 失败驱动反思 | AI 报错 / Tool 失败 | 实时（middleware 自动检测） | 错误记忆导致的执行失败 |
| 用户反馈反思 | 用户说"不对"/"错了" | 实时（middleware 自动检测） | 用户主动纠正的记忆 |
| 全局反思 | 定时任务 | 每周 | 碎片合并 + 一致性检查 + 淡化 |

### 7.3 触发优先级

单轮对话最多触发 1 种反思：

```
P0: 用户反馈反思（强信号：消息前 30 字包含"不对"/"错了"等）
P1: 失败驱动反思（AI 回复报错 / Tool status=error）
P2: 会话结束反思（提取到 entities/events 新记忆）
```

### 7.4 冷却机制

| 反思类型 | 冷却时间 | 冷却 key |
|---------|:-------:|---------|
| session | 5 秒 | thread_id |
| failure | 60 秒 | thread_id |
| correction | 30 秒 | thread_id |
| global | 6 小时 | user_id |

### 7.5 两步法冲突检测

**Step 1：LLM 判断关系类型（4 选 1 简单分类）**

```
- identical: 完全相同（字面重复）
- contradiction: 直接矛盾（同一角色/主体，不同结论）
- evolution: 信息演进（旧信息过时，新信息补充）
- unrelated: 不相关
```

**Step 2：规则映射到 action（不靠 LLM）**

```
identical     → discard_new（丢弃新记忆）
contradiction → archive_old（归档旧记忆）
evolution     → update_old（LLM 合并新旧内容覆盖旧记忆）
unrelated     → keep_both（不操作）
```

### 7.6 反思与记忆边界的一致性

反思不做独立边界校验，信任记忆提取的结果。边界规则的单一数据源是 `EXTRACTION_PROMPT`。
