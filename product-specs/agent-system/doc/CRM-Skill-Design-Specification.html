设计哲学
核心原则：Agent 做判断，脚本做计算

将 LLM 的语义理解优势与代码的精确计算优势严格分离，消除 LLM 数字幻觉对报告质量的影响。

角色负责禁止
Agent（LLM） 理解用户意图、搜索信息、定性判断、撰写报告/建议 数学计算 操作大数据集 编造统计数据
Scripts（代码） 聚合统计、评分模型、阈值检测、数据校验 主观判断 创造性分析 上下文理解

LLM 在 CRM 场景中的已知幻觉模式

🔢 数值编造
编造客户营收/续约率、把5个商机金额加错、Q1增速和Q2增速搞混
🎯 自信推断
没有活动记录支撑就判断"关系良好"、编造竞品使用情况
💭 模糊建议
"建议关注""值得期待"替代具体行动、缺少 WHO/WHAT/WHEN
📊 虚假评分
凭直觉给健康度评分、自行打概率分数、伪造加权计算过程

3
SKILL.md 规范结构

每个 CRM Skill 的 SKILL.md 必须包含以下章节，顺序固定：

---
name: <skill-api-key>                       # camelCase，全局唯一
description: <一句话描述，含核心价值>
whenToUse: <触发关键词，'|' 分隔>
version: "<major>.<minor>.<patch>"
standalone: true | false
agentCapabilities:
  - query_data
  - analyze_data
  - search_web | knowledge_search | ...
providedOutputs:
  - path: output/<动态文件名>.md
    type: markdown
    description: 唯一交付物
---

# <Skill 中文名>

## 启动命令
## 完整流程（严格按顺序，不可跳步）
## ⛔ 禁止直接调用的命令
## 遇到报错时
## 核心原则（最高优先级）
  ### 流程红线（N条）
  ### 章节写作指导
## 分析方法论参考框架
## 数据获取原则（⚠️ 最高优先级）
  ### 文件路径结构
  ### 获取数据的正确方式
  ### ⛔ 绝对禁止的操作
## 决策收敛规则
## 任务完成标志
## 报告模板
## 报告自检（N条）
⚠️ Front Matter 字段说明

whenToUse：'|' 分隔的触发关键词，Agent 路由时做意图匹配
standalone：true = 独立运行（含 vendor），false = 依赖平台工具注册
providedOutputs：声明唯一交付物路径模式，运行时动态替换变量

模式 2：一键聚合命令

原则

暴露给 Agent ≤ 5 条命令。Agent 不该知道内部有 10+ 个子脚本。每个用户可见命令背后可以是任意复杂的编排，但接口极简。

# Agent 能执行的全部命令
python3 run_skill.py init --account-id <ID>
python3 run_skill.py post_analysis --account-id <ID>
python3 run_skill.py recommend --account-id <ID>
python3 run_skill.py calc_metrics --account-id <ID>
python3 run_skill.py status --account-id <ID>
python3 run_skill.py validate --account-id <ID>

模式 3：Agent-Script 数据契约

Agent 数据获取结果 → fsWrite → analysis_input.json
                              → market_context.json
                              → relationship_map.json

Scripts 读取 JSON → 计算/评分 → scored_result.json
                               → risk_signals.json
                               → recommendation.json

Agent 读取脚本产出 → 撰写交付物

脚本端必须实现自动修复逻辑：Agent 写错类型自动转换、漏填字段自动补全、校验失败给精确诊断。

模式 4：禁止清单 > 允许清单

⛔ CRM Skill 通用禁止清单（最高优先级）
  1. 禁止编造客户营收/利润/融资数据 — 搜不到标"信息空白"
  2. 禁止自行计算转化率/增长率/加权评分 — 用 calc_metrics 脚本
  3. 禁止猜测决策链角色 — 未确认的标 [推断]
  4. 禁止用"建议关注""值得期待"等模糊措辞 — 每条建议含 WHO/WHAT/WHEN
  5. 禁止一次 query_data 查全量 — 分页查询，单次≤100条
  6. 禁止直接读取大 JSON 中间文件 — 用 extract_summary 命令
  7. 禁止把推测当事实 — 标注 [事实]/[推断]/[估算]/[信息空白]
  8. 禁止跳过矛盾解释 — 数据矛盾处必须给出解释
  9. 禁止产出多个文件 — 唯一交付物
  10. 禁止暴露内部字段名/评分公式/调试信息

决策收敛规则（CRM 版）

CRM 矛盾检测（6项）

#检测项对比维度矛盾含义
1活动 vs 进展活动频繁 × 商机阶段不推进 关系好但没找到痛点/决策人
2NPS vs 续约NPS 高分 × 续约风险信号 使用者满意但决策者有其他考量
3规模 vs 价值客户规模大 × 贡献金额小 钱包份额低，有扩展空间或有竞品
4赢率 vs 资源历史赢率低 × 投入资源多 可能是错误的客户或策略有问题
5增长 vs 健康客户业务增长 × 我方份额不增 竞品在蚕食或产品不满足新需求
6承诺 vs 行为客户口头承诺 × 行为不匹配 Champion 影响力不足或预算受阻

最终建议映射

维度组合建议等级行动方向
高价值 + 高健康 + 低风险 🟢 扩展 Cross-sell / Up-sell
高价值 + 低健康 + 高风险 🔴 紧急救援 Executive engagement + 价值重申
低价值 + 高健康 🟡 培育 自动化服务 + 观察增长信号
低价值 + 低健康 ⚪ 最小投入 降级服务等级
矛盾冲突 ⚠️ 需确认 标注矛盾 + 建议数据核实

报告模板设计原则
⛔ 格式锁定规则

以下结构所有分析目标格式完全一致，差异只体现在内容中。禁止改名/合并/拆分/调序。

## 一、结论先行           ← ⛔格式锁定：固定表格（评级+核心判断+首要行动）
---
## 二、关键数据           ← 固定多维数据表（计算结果引用，非心算）
## 三、深度分析           ← 按场景拆解的分析章节
## 四、风险与矛盾         ← 风险矩阵 + 矛盾检测结果
## 五、行动计划           ← P0/P1/P2 优先级 + WHO/WHAT/WHEN
## 六、跟踪指标           ← 下次复查时的观察点
<small>附录：数据来源 + 置信度说明</small>

"一、结论先行"格式硬约束

  • 综合评级行：⭐星级 + 评级词 + 评分/100 + ≤30字核心判断
  • 首要行动：恰好 1-2 句，含具体角色和时间
  • 禁止在表格前后插入自由文字段落
  • 所有目标无论行业/规模/场景，格式完全相同

数据获取原则

获取数据的正确方式

需要的数据正确做法禁止做法
客户基本信息 query_data(action="get", entity="account", record_id=X) 从记忆中回忆
商机统计（金额/转化） python3 run_skill.py calc_metrics --account-id X Agent 自行加总/算转化率
活动频次趋势 analyze_data(entity="activity", group_by="month") Agent 数活动条数

竞品信息 search_web("客户名+竞品关键词") + 标注来源 编造竞品使用情况

流失概率 脚本评分模型输出 Agent 凭直觉给概率

⛔ 绝对禁止的操作

  1. 禁止一次 query_data 查 >100 条记录（分页或用 analyze_data 聚合）
  2. 禁止直接读取 baseline.json / scored_result.json 完整内容（用 extract_summary）
  3. 禁止用 python -c 执行任何数据处理（用 run_skill.py 命令）
  4. 禁止编造客户未公开的财务数据
  5. 禁止在没有活动记录支撑的情况下判断"关系良好"

自检质量保证
设计原则

每条自检对应一个历史上出过的质量问题。任何一项硬门槛未通过则报告不得产出。

CRM 通用自检模板（10项）

  • 数据完整性：所有必查实体的数据已获取，缺失标注"信息空白"
  • 计算正确性：所有数值型结论来自 calc_metrics 脚本输出，非 Agent 心算
  • 证据链完整：每条结论有数据支撑，标注来源（CRM/搜索/知识库/推断）
  • 行动可执行：每条建议含 WHO（角色）/ WHAT（动作）/ WHEN（时间）
  • 格式合规：报告严格遵循模板结构，章节名称/顺序/表格格式未被修改
  • 无幻觉标记：所有不确定信息标注 [推断] / [估算] / [信息空白]
  • 矛盾已处理：数据矛盾处有解释（即使是"数据不一致，需人工确认"）
  • 无内部泄露：报告中无系统字段名、评分公式、调试信息
  • 时效性标注：外部搜索数据标注获取日期，≥90天标注"可能过时"
  • 唯一交付物：只产出了 1 个文件

场景专属自检追加项（示例）

场景追加自检项
续约风险流失概率来自评分模型（非直觉）、包含竞品替换成本分析、有≥2种防御策略
商机推进MEDDIC 6维逐项评估、有竞争态势判断、风险信号≥3条来源

版本演进策略
核心规律

每个版本的核心改进都来自"Agent 在生产中反复犯的同一个错"。Skill 的质量通过"运行→发现问题→加规则/加校验/加自动修复"不断螺旋上升。

错误模式修复方式版本号变更
Agent 算错转化率加 calc_metrics 脚本 + 禁止心算规则minor
Agent 忽略竞品信息搜索计划强制包含竞品查询 + 自检增加patch
Agent 产出格式不一致格式锁定 + 模板硬约束minor
Agent 给模糊建议禁止清单 + WHO/WHAT/WHEN 自检patch
Agent 自信编造数据[推断]/[信息空白] 强制标注 + 校验minor
流程中断后恢复困难增加 status 命令 + 前置条件检查major

版本号规约

  • major（X.0.0）：流程架构变更（新增/删除步骤、产出格式重构）
  • minor（X.Y.0）：新增脚本能力、新增禁止规则、新增自检项
  • patch（X.Y.Z）：修复已知 Agent 错误模式、优化提示词

Skill 设计 Checklist（通用）
✅ 设计任何高质量 Skill 时逐项检查
  • [流程定义] 完整流水线，每步有前置条件检查和状态查询命令
  • [职责分离] Agent做判断+搜索，脚本做计算+评分+校验
  • [接口极简] 暴露给Agent的命令≤5个，内部复杂度封装在脚本中
  • [数据契约] Agent↔脚本通过标准化JSON交换，有schema+自动修复+诊断
  • [禁止清单] 每条禁止对应一个已知的LLM幻觉或错误模式
  • [方法论嵌入] 领域专家SOP结构化写入SKILL.md，Agent执行时参考
  • [数据策略] 不靠Agent即兴查询，由引擎生成结构化数据获取计划
  • [交叉验证] 多源结论必须交叉验证，发现矛盾必须解释
  • [输出模板] 唯一交付物+格式锁定+自检门槛
  • [错误恢复] status命令+精确诊断+自动修复，Agent遇错不卡死
  • [独立部署] vendor化所有依赖，一个目录可完整运行
  • [版本演进] 每次修复一个"Agent反复犯的错"就升级一条规则
💡 一句话总结

把 Agent 当成一个"会犯错的聪明实习生"来设计——给他清晰的SOP、明确的禁止清单、精确的工具、自动的校验，然后让他发挥判断力做那些只有人能做的事。
