# 记忆提取与检索 — 提示词 + L0/L1/L2 + 对比验证

## 第一章：提取提示词

# EXTRACTION_PROMPT 最终版

## 设计原则

1. **来源区分**：`[工具:xxx]` 返回的是系统数据，`[用户]`/`[助手]` 说的才可能有增量认知
2. **排除法**：列出不提取的（系统字段），剩下的都提取
3. **不过拟合**：不枚举"应该提取什么"，让 LLM 自己判断
4. **紧凑**：整个提示词控制在 ~700 tokens

## 最终提示词

> 最终版提示词已直接维护在代码中：`src/memory/viking_engine.py` 的 `EXTRACTION_PROMPT` 变量。
> 以下为关键设计决策的说明文档。

### 核心变更（v2 → v3）

| 变更点 | v2 版本 | v3 最终版 |
|:---|:---|:---|
| 分类数 | 8 类 | 9 类（新增 soul） |
| soul 定义 | 无 | 用户对 Agent 的角色定义和行为准则 |
| 短回复处理 | LLM 可能判断"无值得记忆" | 显式规则：SOUL/profile/preferences 即使回复短也必须提取 |
| soul vs patterns | 无区分 | 用户定义的流程 → soul，经验归纳 → patterns |
| soul 更新 | 无 | "之前让你XX现在改成XX" → soul（更新覆盖） |
| profile 边界 | 仅"我是XX" | 扩展到"我们公司是XX"、"我们的竞争对手是XX" |
| entities 边界 | 宽泛 | 明确：客户/联系人信息 → entities，用户/公司信息 → profile |

### 9 类分类体系

```
soul         — 用户对 Agent 的角色定义和行为准则（主语是"你"）
profile      — 用户描述自己的身份信息（主语是"我"，描述身份/背景）
preferences  — 用户表达自己的偏好和习惯（主语是"我"，表达偏好）
entities     — 客户/商机/联系人相关的洞察
events       — 决策、里程碑、计划（含日期）
cases        — 问题 + 解决方案
patterns     — 从多次经验中归纳的可重复规律
tools        — 工具使用经验（系统自动统计）
skills       — 技能执行经验
```

| 用户输入 | 分类 | 判断依据 |
|:---|:---|:---|

| "你回复不超过100字" | soul | 主语是"你"，约束 Agent 行为 |

| "之前让你用表格，现在改成图表" | soul | 更新已有 soul 定义 |
| "我是销售总监" | profile | 主语是"我"，描述身份 |
| "我们公司是做企业软件的" | profile | 描述用户公司信息 |
| "我们的竞争对手是Salesforce" | profile | 描述用户公司竞品 |
| "我喜欢表格展示" | preferences | 主语是"我"，表达偏好 |
| "我习惯每天早上看数据" | preferences | 主语是"我"，表达习惯 |

## 第二章：L0-L1-L2 架构差异与合并设计

# L0/L1/L2 架构差异与合并设计

## 一、两种架构对比

### apps-agent（v2）：目录级三层

```
user/memory/entities/
  │
  ├── L0（1条，目录摘要）:
  │     "张磊磊，30岁，上海的软件开发人员，CRM销售，
  │      销售易CEO为史总，公司位于杭州滨江区，主营SaaS业务。"
  │
  ├── L1（1条，目录结构）:
  │     "## 个人信息
  │      - 姓名：张磊磊
  │      - 年龄：30岁
  │      ## 用户身份
  │      - 用户职业为CRM销售
  │      ## 实体信息
  │      - 企业：销售易
  │      - 人员：史总
  │      ## 公司信息
  │      - 地点：杭州滨江区"
  │
  └── L2（4条，独立记忆条目）:
        "用户的身份是CRM销售人员。"
        "销售易是一家企业，史总是该企业的CEO。"
        "用户表示其公司位于杭州滨江区，主要从事SaaS业务。"
        "张磊磊是一名30岁的软件开发人员，现居住在上海。"

关系:
  L2 是原子记忆单元（每次对话提取产生）
  L1 是从所有 L2 聚合生成的结构化目录
  L0 是从 L1 压缩生成的一句话摘要
  L0/L1 在 L2 变更时重新生成
```

### 当前 VikingMemoryEngine：单条记忆级三层

```
向量库中每条记忆:
  {
    abstract: "华为科技/ERP项目: 张总倾向方案B",     ← 这条记忆的 L0
    overview: "## 洞察\n- 倾向方案B\n## 建议...",    ← 这条记忆的 L1
    content:  "华为科技ERP项目关键决策人张总...",     ← 这条记忆的 L2
  }

每条记忆是独立的三层，没有目录级聚合。
```

### 核心差异

| 维度 | apps-agent | VikingMemoryEngine |
|:---|:---|:---|
| L0 是什么 | 整个类别/目录的聚合摘要（1条） | 单条记忆的摘要（每条各自有） |
| L1 是什么 | 整个类别/目录的结构化 Markdown（1条） | 单条记忆的结构化概览（每条各自有） |
| L2 是什么 | 独立的记忆条目（多条） | 单条记忆的完整内容（每条各自有） |
| L2 数量 | 一个目录下可以有多条 L2 | 每条记忆只有 1 个 L2 |
| 聚合关系 | L2 → 聚合生成 L1 → 压缩生成 L0 | L0/L1/L2 同时由 LLM 一次生成 |
| 更新时 | 新增 L2 后重新聚合 L0/L1 | 同 merge_key 的记忆整条替换 |

## 二、apps-agent 的合并逻辑

### 2.1 新记忆写入流程

```
新对话提取出候选记忆
  │
  ▼
去重判断（向量预筛 + LLM 精判）
  │
  ├── skip → 不存储
  ├── create → 新增一条 L2
  ├── merge → 合并到已有 L2（LLM 生成合并内容）
  └── delete → 删除已有 L2
  │
  ▼
L2 变更后，重新聚合 L0/L1
  │
  ├── L1 = 从该目录下所有 L2 聚合生成结构化 Markdown
  └── L0 = 从 L1 压缩生成一句话摘要
```

### 2.2 为什么 entities 下有 4 条 L2

```
对话 1: "我是张磊磊，30岁，在上海做软件开发"
  → 提取 L2: "张磊磊是一名30岁的软件开发人员，现居住在上海。"

对话 2: "我是CRM销售"
  → 去重: 和已有 L2 不重复（不同主题）
  → 新增 L2: "用户的身份是CRM销售人员。"

对话 3: "销售易CEO为史总"
  → 去重: 和已有 L2 不重复
  → 新增 L2: "销售易是一家企业，史总是该企业的CEO。"

对话 4: "我们公司在杭州滨江区，主要做 SaaS 业务"
  → 去重: 和已有 L2 不重复
  → 新增 L2: "用户表示其公司位于杭州滨江区，主要从事SaaS业务。"

每次新增 L2 后:
  L1 重新聚合 = "## 个人信息\n- 姓名：张磊磊\n## 用户身份\n- CRM销售\n..."
  L0 重新压缩 = "张磊磊，30岁，上海的软件开发人员，CRM销售，销售易CEO为史总..."
```

### 2.3 合并（merge）场景

```
已有 L2: "张磊磊是一名30岁的软件开发人员，现居住在北京。"

新对话: "我换到上海了"
  → 去重: 和已有 L2 高度相似（同一人的居住地）
  → LLM 判断: merge（部分更新，城市从北京→上海）
  → 合并后 L2: "张磊磊是一名30岁的软件开发人员，现居住在上海。"
  → 旧 L2 被替换

然后 L0/L1 重新聚合。
```

## 三、我们应该怎么做

### 3.1 方案对比

| 方案 | 描述 | 优点 | 缺点 |
|:---|:---|:---|:---|
| A: 保持现状 | 每条记忆独立的 L0/L1/L2 | 简单，检索精确 | 没有目录级聚合视图 |
| B: 完全对齐 v2 | 目录级 L0/L1 + 多条 L2 | 和 v2 一致 | 改动大，需要重构存储 |
| C: 混合方案 | 保持单条记忆的 L0/L1/L2，增加目录级聚合 | 兼容现有 + 获得聚合能力 | 多一层聚合逻辑 |

### 3.2 推荐方案 C：混合方案

```
保持现有的单条记忆结构不变:
  每条记忆仍然有自己的 abstract(L0) / overview(L1) / content(L2)
  向量检索仍然基于单条记忆的 L0 embedding

新增目录级聚合（按需生成，不持久化）:
  当需要展示某个目录的全貌时（如 VikingFS.tree / SOUL 蒸馏）:
    1. 查询该目录下所有 L2（如 parent_entity="华为科技" 的所有记忆）
    2. LLM 聚合生成目录级 L1（结构化 Markdown）
    3. LLM 压缩生成目录级 L0（一句话摘要）
    4. 缓存结果（TTL 或 L2 变更时失效）

优势:
  - 不改现有存储结构和检索逻辑
  - 单条记忆的 L0 仍然用于向量检索（精确匹配）
  - 目录级 L0/L1 用于浏览和 SOUL（全貌视图）
  - 和 v2 的效果等价，但实现更简单
```

### 3.3 具体实现

```
VikingMemoryEngine 新增方法:

  async def aggregate_directory(self, user_id, category, parent_entity=None):
      """聚合某个目录下所有 L2，生成目录级 L0/L1"""

      # 1. 查询该目录下所有记忆的 L2
      memories = query_by_filter(user_id, category, parent_entity)

      # 2. LLM 聚合生成 L1
      l2_texts = [m.content for m in memories]
      l1 = await llm.ainvoke(AGGREGATE_L1_PROMPT.format(l2_list=l2_texts))

      # 3. LLM 压缩生成 L0
      l0 = await llm.ainvoke(AGGREGATE_L0_PROMPT.format(l1=l1))

      return {"l0": l0, "l1": l1, "l2_count": len(memories)}

使用场景:
  - VikingFS.tree() 展示目录时，用聚合的 L0 作为目录摘要
  - SOUL 蒸馏时，用聚合的 L1 作为输入（比逐条 L0 更结构化）
  - 前端 /memory 页面展示类别概览时
```

## 四、合并逻辑总结

### 当前逻辑（已实现）

```
profile:     content 追加合并（旧 + "\n" + 新）
preferences: 同 merge_key → LLM 合并（保留旧记忆中仍有效的信息）
entities:    同 merge_key → LLM 合并（保留旧记忆中仍有效的信息）
events:      不合并，语义去重（>0.9 时 LLM 判断 skip/create/merge/delete）
cases:       不合并，语义去重
patterns:    同 merge_key → LLM 合并
tools:       同 merge_key → 直接替换（Python 统计）
skills:      同 merge_key → 直接替换
```

### v2 的逻辑

```
profile:     单文件累积（始终合并到 profile.md）
preferences: 向量预筛 + LLM 决策（skip/create/merge/delete）
entities:    向量预筛 + LLM 决策（skip/create/merge/delete）
events:      向量预筛 + LLM 决策（不支持 merge）
cases:       向量预筛 + LLM 决策（不支持 merge）
patterns:    向量预筛 + LLM 决策（支持 merge）
tools:       Python 统计累加
skills:      Python 统计累加

+ 每次 L2 变更后重新聚合 L0/L1
```

### 差异

```
1. v2 的 entities 可以有多条 L2（不同主题独立存储）
   我们的 entities 同 merge_key 只有 1 条（合并替换）
   → 效果等价: 我们用 merge_key 区分不同主题，每个主题 1 条
   → v2 用目录结构区分，每个主题也是 1 条 L2

2. v2 有目录级 L0/L1 聚合
   我们没有
   → 方案 C 可以补齐

3. v2 的 merge 是 LLM 生成合并内容
   我们已经对齐（刚改的 _merge_by_key）
```
