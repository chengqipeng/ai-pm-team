沙盒执行系统 — 架构设计¶

Agent V2 代码执行基础设施 · 双模式沙盒架构
支持 SSH 远程执行模式 + 腾讯云 Agent Runtime 沙盒模式
本文档为第一页：整体架构设计，聚焦系统全貌与双模式对比。

一、系统定位¶

沙盒执行系统是 Agent V2 框架「能力执行层」的核心基础设施，为 Agent 提供安全、隔离的代码执行环境。对应 Agent 整体设计方案中 Features.sandbox_enabled 特性开关和 AppConfig.sandbox: SandboxSettings 配置项。

Agent 在推理循环中通过 code_execution 工具调用沙盒，执行数据分析、文件处理、API 调用等操作。沙盒系统确保这些操作在受控环境中完成，不影响宿主系统安全。

核心价值

  • 安全隔离 — 代码在独立环境中执行，防止恶意代码或误操作影响生产环境
  • 双模式灵活切换 — SSH 模式适合自有基础设施，腾讯沙盒模式适合多租户生产环境
  • 统一抽象 — 上层 Agent 通过 SandboxProvider 接口调用，无需感知底层差异
  • 全链路可观测 — stdout/stderr 实时回传，执行耗时/结果纳入 Tracing 链路

六、实例生命周期¶

本节详细描述沙盒实例从创建到销毁的完整生命周期，包括状态流转、两种模式下的具体行为差异、典型场景时序，以及关键超时参数的配置说明。

6.1 状态机总览¶

♻️ 沙盒实例状态机
CREATING → READY ⇄ EXECUTING → READY → ... → DESTROYED
CREATING
触发：首次执行请求
行为：调用 Provider.create()
下一步：READY / FAILED
READY
触发：创建成功 / 执行完成
行为：等待下一次请求
下一步：EXECUTING / IDLE_TIMEOUT
EXECUTING
触发：收到执行请求
行为：Provider.execute()
下一步：READY / TIMEOUT / ERROR
TIMEOUT
触发：执行超时
行为：强制终止当前进程
下一步：READY（可恢复）/ DESTROYED
ERROR
触发：执行异常 / 连接断开
行为：记录错误，尝试恢复
下一步：READY / DESTROYED
DESTROYED
触发：空闲超时 / 主动销毁 / 会话结束
行为：释放所有资源
终态，不可恢复

6.3 两种模式的生命周期差异¶

生命周期阶段 SSH 模式（虚拟机） 腾讯沙盒模式（云容器）
CREATING 阶段
实例如何被创建		 耗时：200~500ms（连接复用时 <50ms）
具体动作：
1. 从连接池取一个空闲 asyncssh 连接（若无则新建）
2. 在远程主机创建会话目录：mkdir -p /home/agent/workspace/{thread_id}
3. 设置环境变量（PATH、PYTHONPATH 等）
4. 注册到 session_pool

1. 调用 Sandbox.create(template="code-interpreter-v1", timeout=300)
2. 腾讯云分配容器资源、拉取镜像、启动运行时
3. 返回 sandbox_id，SDK 建立 WebSocket 连接
4. 注册到 session_pool
失败场景：API 限流（429）、配额不足、网络超时 → 重试 1 次后抛出 SandboxCreationError
READY → EXECUTING
如何接收并执行代码		 复用优势：同一 SSH 连接、同一 shell 进程
状态保持：Python 进程不退出，变量/import 跨调用保留
文件持久化：上次执行生成的文件（如 output.csv）下次可直接读取
并发限制：单实例串行执行（一个 shell channel） 		复用优势：同一容器实例，无需重新创建
状态保持：run_code() 模式下变量持久化；commands.run() 模式下每次独立
文件持久化：容器内文件在实例存活期间保留，销毁即丢失
并发限制：单实例串行（E2B SDK 限制）
TIMEOUT 处理
超时后发生什么		 执行超时（600s）：
• Linux timeout 命令发送 SIGTERM → 等待 5s → SIGKILL
• SSH channel 收到 exit_code=124（timeout 退出码）
• 实例状态回到 READY（SSH 连接仍然存活）
• 下次执行不受影响

实例超时（idle_timeout=300s）：
• 定时器到期 → 清理工作目录 → 关闭连接 → DESTROYED 		执行超时（600s）：
• E2B SDK 内部中断执行，返回 timeout error
• 容器进程被 kill，但容器本身存活
• 实例状态回到 READY

实例超时（sandbox timeout=300s）：
• 腾讯云自动销毁容器（服务端 TTL 机制）
• 或 SandboxManager 主动调用 sandbox.kill()
• 容器及其所有文件立即消失 → DESTROYED
ERROR 恢复
出错后能否继续使用		 可恢复错误：
• 代码执行报错（exit_code≠0）→ 返回 stderr，实例仍 READY
• SSH 连接断开 → 自动重连（最多 3 次），重连成功 → READY

不可恢复错误：
• 主机宕机 / 磁盘满 → DESTROYED，下次请求重新创建
• 连续重连失败 → DESTROYED 		可恢复错误：
• 代码执行报错 → 返回 error 信息，容器仍 READY
• 网络抖动 → SDK 自动重连 WebSocket

不可恢复错误：
• 容器 OOM（内存超限）→ 容器被 kill → DESTROYED
• API 返回 404（容器已被云端回收）→ DESTROYED
DESTROYED 清理
销毁时具体做了什么		 1. 执行 rm -rf /home/agent/workspace/{thread_id}/
2. 关闭 SSH channel
3. 将 asyncssh 连接归还连接池（不关闭物理连接）
4. 从 session_pool 中删除映射
5. 记录 metrics：session_duration、total_executions、total_bytes 		1. 调用 sandbox.kill() 通知腾讯云销毁容器
2. 腾讯云释放 CPU/内存/存储资源
3. 容器内所有文件永久丢失（无持久化）
4. 从 session_pool 中删除映射
5. 记录 metrics：sandbox_id、alive_duration、api_calls_count

参数名 作用域 默认值 含义 超时后果
execution_timeout 单次代码执行 600s（10分钟） 单次 execute_code / terminal 调用的最大允许时长 强制终止当前进程，返回 SandboxTimeoutError，实例回到 READY
idle_timeout 实例空闲 300s（5分钟） 实例在 READY 状态无新请求的最大等待时长 触发 DESTROYED，释放所有资源
session_max_lifetime 实例总存活 3600s（1小时） 实例从 CREATING 到强制销毁的最大存活时间（防止资源泄漏） 无论是否在执行，强制 DESTROYED
connection_timeout SSH 连接建立 10s SSH 模式下建立连接的超时时间 抛出 SandboxCreationError，不创建实例
sandbox_create_timeout 容器创建 30s 腾讯沙盒模式下等待容器就绪的超时时间 重试 1 次，仍失败则抛出 SandboxCreationError

配置位置：所有超时参数在 AppConfig.sandbox: SandboxSettings 中配置，支持通过环境变量覆盖（如 SANDBOX_EXECUTION_TIMEOUT=600）。

6.5 边界场景与处理策略¶

🔀 场景 1：同一会话并发请求
触发条件：Agent 在同一轮推理中输出多个 tool_call（如同时调用 terminal + execute_code）
处理方式：SandboxManager 内部加锁（asyncio.Lock），串行执行，后到的请求排队等待
用户感知：第二个 tool_call 的响应延迟 = 第一个执行时长 + 自身执行时长
🔄 场景 2：用户中断后恢复对话
触发条件：用户 3 分钟后继续对话，实例仍在 READY（idle_timeout 未到期）
SSH 模式：直接复用，之前的文件和环境变量都在
腾讯沙盒：直接复用，容器内文件和变量仍在
若已 DESTROYED：透明重建新实例，用户无感知（但之前的文件/变量丢失）
♾️ 场景 3：用户代码死循环 / 内存泄漏
死循环：execution_timeout（600s）到期 → SIGTERM → SIGKILL → 返回超时错误
内存泄漏（SSH）：Linux OOM Killer 终止进程，SSH 连接存活，实例回到 READY
内存泄漏（腾讯）：容器 cgroup 内存限制触发 OOM → 容器被 kill → DESTROYED
Agent 行为：收到错误后 LLM 会尝试修改代码重新执行（最多重试 1 次）
🏢 场景 4：多租户同时使用
SSH 模式：不同 thread_id 使用不同工作目录，共享同一台主机资源（CPU/内存/磁盘）
腾讯沙盒：每个 thread_id 独立容器，完全隔离（网络/文件系统/进程空间）
资源竞争：SSH 模式下高并发可能导致主机资源不足；腾讯沙盒通过云端弹性扩缩解决
安全边界：PathGuard 确保 SSH 模式下租户只能访问自己的工作目录

6.6 Session Pool 管理机制¶

Session Pool 内部结构

# SandboxManager 内部数据结构
session_pool: Dict[str, SandboxSession] = {}

@dataclass
class SandboxSession:
    thread_id: str                    # 会话标识（对应一个用户对话）
    provider_instance: Provider       # SSH 连接 或 Sandbox 对象
    state: SessionState               # CREATING | READY | EXECUTING | DESTROYED
    created_at: datetime              # 创建时间
    last_active_at: datetime          # 最后一次执行完成的时间
    execution_count: int              # 累计执行次数
    total_execution_ms: int           # 累计执行耗时
    _lock: asyncio.Lock               # 串行执行锁

# 查找/创建逻辑（伪代码）
async def get_or_create(thread_id: str) -> SandboxSession:
    if thread_id in session_pool:
        session = session_pool[thread_id]
        if session.state != DESTROYED:
            session.last_active_at = now()   # 刷新空闲计时器
            return session
    # 创建新实例
    session = await _create_new_session(thread_id)
    session_pool[thread_id] = session
    return session
后台清理协程：每 60s 扫描一次 session_pool，将 now() - last_active_at > idle_timeout 的实例标记为 DESTROYED 并执行清理。
最大实例数：SSH 模式受连接池大小限制（默认 max_connections=10）；腾讯沙盒受 API 配额限制（默认 50 并发容器）。
驱逐策略：当达到最大实例数时，优先销毁 last_active_at 最早的 READY 实例（LRU）。
