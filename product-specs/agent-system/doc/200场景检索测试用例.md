## 混合搜索中向量递归搜索与 BM25 关键词搜索的优缺点

### 当前检索架构

```
用户查询
  │
  ▼
全局搜索（BM25 0.7 + 向量 0.3 混合）
  → 定位起始目录节点 + 直接命中的叶子节点
  │
  ▼
递归展开（纯向量搜索）
  → 在目录内按语义相似度找子节点
  → 分数传播: 子分数 = 0.5 × 自身 + 0.5 × 父目录分数
  → 收敛检测: Top-K 连续 3 轮不变停止
```

### 200 条查询实测数据（4 种方式对比）

| 方式 | 客户命中率 | Top-1 精确命中 | 关键词召回 | 平均耗时 |
|---|---|---|---|---|
| A: 纯向量扁平 | 138.5% | 70.8% | 76% | 21ms |
| B: 纯向量递归 | 138.5% | 70.8% | 76% | 26ms |
| C: BM25+向量扁平 | 138.5% | 70.0% | **83%** | 35ms |
| **D: BM25+向量递归** | **142.3%** | **76.2%** | 63% | 27ms |

### 向量递归搜索的优缺点

**优势：**

| 优势 | 说明 | 实测数据 |
|---|---|---|
| 目录隔离 | 递归进入"华为/"目录后，只在华为内搜索，不会返回腾讯的记忆 | 查询"腾讯POC"时，京东/POC(0.390)在全局搜索排第三，但递归展开后被腾讯记忆挤出 |
| 分数传播 | 父目录相关性高的子节点得到加成，即使自身语义匹配度不高也能被召回 | 华为/ERP项目自身分数0.775在全局排不进Top-6，但通过华为目录(0.389)加成后0.582排到第一 |
| Top-1 精确命中最高 | 76.2%，比扁平检索高 6.2% | 在"招行"和"百度"客户上提升最大（+4/+6） |
| 耗时可控 | 收敛检测避免无限递归，实测仅增加 8ms | 从 19ms 到 27ms |

**劣势：**

| 劣势 | 说明 | 实测数据 |
|---|---|---|
| 跨客户模糊查询弱 | "之前哪个客户说预算不够"没有明确目标客户，递归可能进入错误的目录 | 递归进了美团目录，错过了华为和比亚迪的预算记忆 |
| 通用经验被挤出 | 通用记忆（parent_entity=""）没有目录节点，递归优先展开有目录的客户 | "互联网客户特点"查询中，"互联网行业方案"被客户记忆挤出Top-3 |
| 关键词召回率下降 | 从 76% 降到 63%，但大部分是虚假命中的下降（见下方分析） | 25条下降中，"预算"10次、"性能"10次是跨客户查询的固有弱点 |

### BM25 关键词搜索的优缺点

**优势：**

| 优势 | 说明 | 实测数据 |
|---|---|---|
| 精确匹配客户名 | "华为"、"腾讯"等客户名精确匹配，不依赖语义相似度 | 查询"招行签合同"时，BM25精确匹配"招行"，Top-3全是招行记忆 |
| 关键词召回率高 | 83%（扁平hybrid），包含查询中的关键词的记忆更容易被召回 | 查询"给华为报价"时，"报价策略"通过"报价"关键词被召回 |
| 定位目录节点 | 在全局搜索阶段帮助快速定位到正确的客户目录 | 华为目录节点的abstract包含"华为"，BM25精确匹配后排到前面 |

**劣势：**

| 劣势 | 说明 | 实测数据 |
|---|---|---|
| 单独使用无额外收益 | 扁平场景下BM25对客户命中率和Top-1没有提升（A vs C） | 客户命中率都是138.5%，Top-1纯向量反而高0.8% |
| 可能引入噪声 | 关键词匹配可能把语义不相关但包含关键词的记忆拉上来 | "华为"查询中，"金融行业方案(含华为)"通过BM25被拉到Top-3 |
| 跨客户查询虚假命中 | 命中关键词但答案不对 | "哪个客户预算不够"命中"报价策略(含预算范围)"，但这不是答案 |

### BM25 + 向量递归的协同效果

```
BM25 单独用（扁平hybrid）: 对客户命中率无提升，只提升关键词召回
向量递归单独用（纯向量递归）: 对客户命中率无提升，Top-1 和扁平一样
BM25 + 向量递归组合: 客户命中率 +3.8%，Top-1 +5.4%

原因:
  BM25 在全局搜索阶段精确匹配客户名 → 定位到正确的目录节点
  向量递归在目录内按语义展开 → 找到最相关的子记忆
  两者互补: BM25 解决"找对目录"，向量解决"找对记忆"
```

### 关键词召回率下降的真实分析

```
方案 D 关键词召回从 76% 降到 63%，下降的 25 条查询分析:

  "预算"缺失 (10次): 全部是"之前哪个客户说预算不够"这类跨客户查询
    纯向量命中的是"报价策略(含预算范围)" — 虚假命中，答案是错的
    递归没命中 — 但纯向量命中的也不是正确答案
    → 两种方式都没找到正确答案，纯向量的"命中"是虚假的

  "性能"缺失 (10次): 全部是"互联网客户有什么特点"这类行业查询
    纯向量命中的是"互联网行业方案(含性能)" — 正确命中
    递归返回了阿里(真实互联网客户案例) — 也有价值，但缺少通用方案
    → 这是递归对通用经验查询的真实弱点

  其他 (5次): 报价、审批、合规等
    大部分是递归排序差异导致的，不是方向性错误

结论: 25 条下降中，10 条是虚假命中的下降（不算真正的损失），
     10 条是通用经验查询的弱点（真实问题），5 条是排序差异。
     真实的质量下降约 10 条 / 200 条 = 5%，而 Top-1 提升了 6.2%。
```

### 最终结论

```
当前方案（D: BM25 全局搜索 + 向量递归展开）是最优组合:
  ✅ Top-1 精确命中最高 (76.2%) — 用户体验最直接的指标
  ✅ 客户命中率最高 (142.3%) — 找对客户是 CRM 场景的核心需求
  ⚠️ 关键词召回率下降 — 大部分是虚假命中的下降，真实损失约 5%
  ✅ 耗时可控 (27ms) — 比扁平hybrid(35ms)还快

BM25 的价值不在于单独使用，而在于和递归检索配合:
  全局搜索阶段: BM25 精确匹配客户名 → 定位目录节点
  递归展开阶段: 纯向量语义匹配 → 找到最相关的记忆
  权重 0.7/0.3 合理: CRM 场景中客户名精确匹配比语义相似更重要
```

## 递归召回代码逻辑详细分析

### 整体流程

```
retrieve(query, user_id, top_k=5)
  │
  ├── Step 1: Embedding — 查询向量化（1 次 API 调用，复用于后续所有搜索）
  ├── Step 2: 全局搜索 — hybrid_search(BM25 0.7 + 向量 0.3)，返回 Top-10
  ├── Step 3: 分离 — 目录节点入优先队列，叶子节点直接收集
  ├── Step 4: 递归展开 — 按分数从高到低展开目录，纯向量搜索子节点
  │     └── 分数传播: final = 0.5 × 自身分数 + 0.5 × 父目录分数
  ├── Step 5: 收敛检测 — Top-K 连续 3 轮不变则停止
  └── Step 6: 返回 Top-K + 异步更新热度
```

### Step 2: 全局搜索（hybrid_search）

```python
global_results = self._vdb.hybrid_search(query_vec, query, GLOBAL_TOPK=10, filter_expr)
```

在整个向量库中搜索，不区分目录/叶子，返回 Top-10。BM25 精确匹配客户名定位目录节点，向量匹配语义相关的叶子。

示例（查询"明天要去华为开会"）:
```
[0.405] 📄 华为/报价: 先报标准价预留谈判空间          ← BM25 匹配"华为"
[0.389] 📁 华为目录节点: 华为/张伟说话直接...          ← BM25 匹配"华为"（目录节点）
[0.245] 📄 华为/安全审计: 即将closing                 ← BM25 匹配"华为"
[0.244] 📄 华为/李娜: 采购经理，做事谨慎              ← BM25 匹配"华为"
[0.243] 📄 华为/张伟: 说话直接，汇报用PPT             ← BM25 匹配"华为"
[0.230] 📄 腾讯/王强: CTO，技术导向                   ← 语义相关但不是华为
```

### Step 3: 分离目录节点和叶子节点

```python
for r in global_results:
    if r.get("is_leaf") == "false":
        heapq.heappush(dir_queue, (-score, dir_uri))  # 目录 → 入队
    else:
        r["_final_score"] = score
        collected.append(r)                            # 叶子 → 直接收集
```

`heapq` 是最小堆，存 `-score` 实现最大堆效果，`heappop` 取出分数最高的目录优先展开。

### Step 4: 递归展开 + 分数传播

```python
while dir_queue and unchanged_rounds < MAX_CONVERGENCE:
    neg_score, current_uri = heapq.heappop(dir_queue)  # 取分数最高的目录
    parent_score = -neg_score

    # 在该目录下搜索子节点（纯向量，不用 BM25）
    child_filter = f'user_id = "{uid}" and parent_uri = "{current_uri}"'
    children = self._vdb.search(query_vec, 10, child_filter)

    for child in children:
        child_score = float(child.get("score", 0))
        # 分数传播: α × 自身分数 + (1-α) × 父目录分数
        final_score = 0.5 * child_score + 0.5 * parent_score
```

分数传播示例:
```
华为目录节点分数 = 0.389

华为/ERP项目:
  自身分数 = 0.775（在华为目录内的向量相似度）
  传播后 = 0.5 × 0.775 + 0.5 × 0.389 = 0.582
  → 超过全局直接命中的华为/报价(0.405)，排到第一位

华为/ERP项目在全局搜索中排不进 Top-10（语义距离远），
但通过父目录的加成，传播后 0.582 排到了第一位。
这就是递归检索的核心价值 — 目录归属提升了相关记忆的排名。
```

### Step 5: 收敛检测

```python
current_topk_ids = [c.get("id") for c in sorted(collected, ...)[:top_k]]
if current_topk_ids == prev_topk_ids:
    unchanged_rounds += 1    # Top-K 没变，计数+1
else:
    unchanged_rounds = 0     # Top-K 变了，重置
# unchanged_rounds >= 3 时退出
```

先展开高分目录，如果高分目录展开后 Top-K 都没变，低分目录更不可能改变。实测 1-2 轮就收敛。

### 关键设计决策

| 决策 | 选择 | 原因 |
|---|---|---|
| 全局搜索用 hybrid | BM25 0.7 + 向量 0.3 | 客户名精确匹配定位目录节点 |
| 递归展开用纯向量 | 只用 cosine search | 已在正确目录内，语义匹配即可 |
| 分数传播 α=0.5 | 自身和父目录各占一半 | 平衡语义相关性和目录归属 |
| 收敛检测 3 轮 | Top-K 连续 3 轮不变停止 | 避免无限递归，实测 1-2 轮收敛 |
| 目录展开阈值 0.3 | 传播后分数 < 0.3 不展开 | 过滤低相关目录，节省搜索次数 |

### 完整执行示例

```
查询: "明天要去华为开会，有什么需要注意的"

Step 1: embed → 2560 维向量
Step 2: hybrid_search(全库) → 6 叶子 + 1 目录节点
Step 3: collected=[报价0.405, 安全审计0.245, 李娜0.244, ...]  dir_queue=[华为目录0.389]
Step 4: 展开华为目录 → ERP(0.775→0.582), 采购流程(0.750→0.570)
Step 5: Top-5 不再变化 → 收敛
Step 6: 返回 [ERP(0.582), 采购(0.570), 报价(0.405), 安全审计(0.245), 李娜(0.244)]

VDB 调用: 1 次 hybrid_search + 1 次 search = 2 次
耗时: ~27ms
```

## 为什么 BM25 和向量都只检索 L0

### 三层内容的检索角色

| 层级 | 字段 | BM25 检索 | 向量检索 | 角色 |
|---|---|---|---|---|
| **L0** | abstract | ✅ 生成稀疏向量 | ✅ 生成稠密向量 | **索引层** — 用于检索 |
| L1 | overview | ❌ | ❌ | 导航层 — 命中后按需加载 |
| L2 | content | ❌ | ❌ | 内容层 — 命中后返回给 Agent |

### 原因 1: Token 效率

```
L0: "华为科技/ERP项目: 张伟支持但李娜担心预算"     ← ~20 tokens
L2: "华为科技ERP项目中张伟和李娜意见不太一致，      ← ~80 tokens
     张伟想上ERP，但李娜觉得预算不够，
     建议分别沟通，先搞定张伟的技术认可..."

90 条记忆的 embedding 调用:
  用 L0: 90 × 20 = 1,800 tokens
  用 L2: 90 × 80 = 7,200 tokens（4 倍成本）
```

### 原因 2: 检索精度

```
L0: "华为科技/ERP项目: 张伟支持但李娜担心预算"
  → embedding 语义焦点: 华为 + ERP + 分歧 + 预算
  → 信息密度高，每个词都是关键信息

L2: "华为科技ERP项目中张伟和李娜意见不太一致，张伟想上ERP，
     但李娜觉得预算不够，建议分别沟通，先搞定张伟的技术认可，
     再解决李娜的预算顾虑。"
  → embedding 语义焦点: 华为 + ERP + 分歧 + 预算 + 沟通 + 技术 + 顾虑
  → 被非核心词稀释，"沟通""技术""顾虑"干扰了核心语义

查询 "华为ERP项目" 的匹配:
  vs L0 cosine: ~0.85（核心词高度匹配）
  vs L2 cosine: ~0.72（被非核心词稀释）
```

L0 是提炼后的摘要，信噪比高。L2 包含修饰词和细节，会稀释 embedding 的语义焦点。

### 原因 3: 索引和内容分离（对齐 OpenViking）

```
OpenViking 的架构:
  向量索引: 只存 URI + L0 embedding + 元数据（不存 L1/L2 内容）
  AGFS:     存完整内容（L0/L1/L2）

检索时: 向量索引搜 L0 → 命中后从 AGFS 加载 L1/L2

我们的架构:
  向量库: 存 L0 embedding + L0/L1/L2 文本（都在同一条记录中）
  检索时: 向量搜 L0 → 命中后直接从同一条记录读 L1/L2

区别: OpenViking 物理分离，我们逻辑分离。但检索入口都是 L0。
```

### 总结

**L0 是为检索设计的（短、精、信噪比高），L2 是为阅读设计的（完整、详细、给 Agent 用）。用 L0 检索、用 L2 回答，各司其职。**
