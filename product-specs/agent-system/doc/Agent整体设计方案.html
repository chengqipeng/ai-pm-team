NeoAgent2.0 整体设计方案¶

面向 2B CRM SaaS 的企业级 Agent 系统完整设计。
融合 Claude Code + NeoAgents + OpenViking/Hermes 四大体系精华。
本文档是系统全貌概览，各子系统详细设计见独立文档（记忆 / 上下文压缩 / 内容审查 / 协议 / 数据库表 等）。

1.2 Agent 框架内部架构¶

对应 1.3 完整链路结构图中涉及的各组件，展示 Agent 框架内部的层级关系与数据流向。

👤 用户请求（自然语言 / 语音 / 图片 / 文档）
▼
🚀 入口预处理层（server.py，LangGraph 之外）
标题生成
• 规则引擎同步生成（取前 20 字）
• 后台 LLM 异步优化标题
• 写入 ai_conversation.title
内容审查
• 敏感词词表快速匹配（< 5ms）
• LLM 语义审查（政治/色情/暴力）
• 命中 → 替换为拦截提示，终止流程
• 未命中 → 放行进入下一步
查询改写
• 首轮对话跳过（无历史上下文）
• 多轮对话：注入历史摘要 + 记忆
• LLM 改写为自包含完整查询
• 消歧 + 指代消解 + 意图补全
▼
📦 上下文准备层（before_agent 中间件，执行 1 次）
Tracing Middleware
• 创建 trace_id + root span
• 统计消息数 / token 预估
• 记录请求元数据（tenant/user/session）
• 写入 ai_trace 表
DanglingToolCall Middleware
• 检测上轮未闭合的 tool_call
• 补充空 ToolMessage 闭合
• 防止 LLM 因格式错误拒绝推理
• 断线恢复场景必需
FileProcess Middleware
• 从 configurable["files"] 读取上传文件
• 识别 MIME 类型（image/document）
• 解析为标准化 parsed_files 结构
• 写入 state.thread_data 供下游消费
• MultimodalInject + load_file_content 的数据源
InputTransform Middleware
• 敏感词 fallback（二次兜底）
• PII 脱敏：身份证/手机号/邮箱
• 替换为占位符，原文存 metadata
• 后处理时 OutputRender 还原
Memory Middleware
• 意图检测 → 决定检索策略
• 向量 + BM25 混合检索
• 命中记忆注入 SystemMessage
• profile/agent_rules 全量注入
• entities/preferences 按相关性 Top-K
▼
⚡ Agent Loop（LLM 推理循环，可执行 N 轮）
循环结构（每轮重复执行）
before_model → LLM 推理 → after_model → wrap_tool_call → 能力执行 → ↩ tool_result 回注，进入下一轮
终止条件：LLM 输出纯文本回复（无 tool_use）| 达到 max_llm_calls 上限 | 状态变为 PAUSED/FAILED
before_model（每轮 LLM 调用前执行）
Multimodal Inject Middleware
• 从 ToolMessage 提取多模态附件标记
• 从 parsed_files 提取图片/文档 URL
• 以 OpenAI 兼容格式注入 HumanMessage
• 控制单轮最多 5 张图片
• 历史图片 > 3 轮替换为文字占位符
• 幂等：已注入则跳过
Summarization Middleware
• 检测上下文是否超过 token 阈值
• 四层压缩策略：
  L0: 虚拟文件（原文不进上下文）
  L1: 工具结果摘要（> 阈值自动压缩）
  L2: 旧轮次裁剪（MD5去重+参数截断）
  L3: 回复摘要回写（sessionSummary）
• 保护区：最近 3 轮 + 当前轮不压缩
执行顺序: MultimodalInject → Summarization（按 build_middleware 注册顺序）
▼
🧠 LLM 推理
ModelRouter（按 TaskType 选模型）→ LLM API（豆包/DeepSeek/OpenAI/Claude/...）
输出: 纯文本回复（结束循环）| tool_use 调用指令（继续循环）
▼
after_model（每轮 LLM 输出后执行）
SubagentLimit Middleware
• 检查子 Agent 并发数
• 超过限制时排队等待
• 防止资源耗尽
LoopDetection Middleware
• 检测连续相同工具调用 ≥ 4 次
• 检测连续错误 ≥ 5 次
• 触发 → Router 转入 ReflectionNode
• stuck 自救机制
OutputValidation Middleware
• 输出内容敏感词校验
• 输出长度检查（防超长）
• 命中 → 替换为拦截提示
• 记录审查日志
▼ (仅当 LLM 输出 tool_use 时触发)
wrap_tool_call（工具调用前后拦截）
Guardrail Middleware
• 安全护栏 + 租户隔离校验
• is_destructive → 触发 HITL 审批
• 自动注入 tenant_id 到工具参数
• 权限不足 → 拒绝并返回错误
ToolErrorHandling Middleware
• 工具异常分级处理（L1-L4）
• 超时 → 返回超时错误给 LLM
• 网络异常 → 重试 1 次
• 未知异常 → 记录日志 + 降级响应
Clarification Middleware
• 检测 LLM 是否需要用户澄清
• ask_user 工具调用 → 暂停循环
• 等待用户输入后恢复
• 非 ask_user → 透传

1.4 Skill 两种调度模式¶

inline 模式
SOP prompt 注入当前对话，LLM 在主 Agent 上下文中按步骤执行
LLM 第 N 轮: 调用 skills_tool(analyze_pipeline)
↓
SkillsTool.call()
├─ SkillRegistry.get("analyze_pipeline")
├─ skill.format_prompt({account_id}) → 替换占位符
└─ context == "inline"
→ 返回 formatted_prompt 作为 ToolResult
↓
LLM 第 N+1 轮: 看到 SOP prompt，按步骤调用 Tool
├─ 步骤1: query_data(...)
├─ 步骤2: analyze_data(...)
└─ 步骤3: 生成结论
特点：
  • 零额外会话成本（不启动子 Agent）
  • 继承主 Agent 完整历史上下文
  • 适合轻量技能（verify_config / customer_360）
  • 执行耗时 < 50ms（仅格式化 prompt）
fork 模式
启动独立子 Agent 执行，工具集裁剪 + 深度限制 + 独立上下文
LLM 第 N 轮: 调用 skills_tool(generate_report)
↓
SkillsTool.call()
├─ SkillRegistry.get("generate_report")
├─ skill.format_prompt({...})
└─ context == "fork"
↓ 启动子 Agent
AgentFactory.build(
agent_name=skill.agent,
depth=current_depth+1,
tools=主Agent工具 ∩ skill.allowed_tools
)
↓
┌─ 子 Agent Loop ──────────────────────┐
│ thread_id: skill-generate_report-xxx │
│ 子循环 1: LLM → query_data(补充数据) │
│ 子循环 2: LLM → 生成完整报告 │
└──────────────────────────────────────┘
→ 提取最后 AIMessage 作为 ToolResult 返回
特点：
  • 独立上下文（不污染主 Agent 历史）
  • 工具集裁剪（最小必要集合）
  • 深度限制（max_depth=3，不可递归派生）
  • 适合复杂任务（diagnose / data_analysis / report）
  • 执行耗时 5-30s（含多轮 LLM 调用）
维度 inline 模式 fork 模式
执行方式 返回 SOP prompt 作为 ToolResult，LLM 在主上下文继续 启动独立子 Agent，独立 thread_id + 独立消息历史
上下文 继承主 Agent 完整历史 隔离（仅传入 formatted_prompt 作为 HumanMessage）
工具集 主 Agent 全部工具 主 Agent 工具 ∩ skill.allowed_tools（最小集合）
耗时 < 50ms（仅 prompt 格式化） 5-30s（含多轮子 Agent LLM 调用）
适用场景 轻量 SOP（verify_config / customer_360） 复杂任务（diagnose / report / batch_data）
继承 tenant_id / user_id / 记忆 / 全部中间件 tenant_id / user_id / 记忆 / 审计
隔离: messages / session_id / HITL 不弹

二、上下文压缩设计¶

详细设计见独立文档：上下文压缩设计.md
本节阐述上下文压缩的技术必要性与实现逻辑。

2.1 为什么需要上下文压缩

LLM 上下文窗口的物理约束

大语言模型的上下文窗口是有限的物理资源。当前主流模型的有效窗口在 64K-200K tokens 之间，但实际可用空间远小于标称值：

占用项典型大小说明
System Prompt + 工具定义5K-8K tokens固定开销，每次调用都存在
输出预留空间4K-8K tokensLLM 生成回复需要的空间
记忆注入1K-3K tokens长期记忆、用户画像、偏好
对话历史动态增长每轮对话累积 500-2000 tokens
工具执行结果动态增长单次工具返回 500-10K tokens

以 64K tokens 窗口为例，固定开销约 15K tokens，实际可用空间约 49K tokens。一个 5 轮对话 + 3 次工具调用就可能消耗 20K-30K tokens，留给后续推理的空间急剧缩小。

CRM 场景的数据量级远超编码场景

与编码辅助场景不同，CRM 业务场景的数据量级呈现以下特征：

数据源典型数据量业务不可裁剪的原因
商机列表查询（Pipeline）100-500 条记录，15K-75K 字符管理层需要全局视角，Top10 无法替代全量分析
大文本字段（需求描述/会议纪要）单字段 2K-20K 字符销售写的客户背景是核心业务信息
跨实体关联查询（客户画像）4-8 实体，20K-120K 字符拜访准备需要完整画像
搜索全文（竞品定价/案例）单页 10K-80K 字符snippet 拿不到定价表和功能对比矩阵
财报/工商数据单次 10K-30K 字符精确数字不能丢失
元数据 Schema 定义单实体 5K-20K 字符Agent 构建查询需要完整字段定义

一次"帮我调研华为并生成竞品分析报告"的任务，可能涉及 3 次搜索 + 2 次财报查询 + 1 次工商查询，工具结果总量轻松超过 50K 字符（约 12K tokens），单次任务就占满可用空间的 25%。

不压缩的三个后果

  1. 上下文溢出：超出窗口限制后 LLM 直接报错，任务中断
  2. 注意力稀释：即使未溢出，过长的上下文导致 LLM 对关键信息的注意力下降（"Lost in the Middle" 现象），推理质量显著降低
  3. 成本线性增长：LLM 按 token 计费，冗余内容直接增加每次调用的成本

核心矛盾

业务需要完整数据才能做出准确判断，但上下文窗口放不下所有数据，而压缩如果依赖 LLM 摘要又会引入 3-5 秒额外延迟。
三者不可能同时满足。解法不是"砍数据"，而是"分层存储 + 按需加载 + 渐进式压缩"。

2.3 上下文压缩的实现逻辑

整体思路：四层递进式压缩

压缩不是一次性动作，而是贯穿数据生命周期的四个阶段。每一层解决不同阶段的问题，层层递进：

Layer 1 · 源头隔离
时机：每次工具执行完毕时 · 覆盖 100% 对话
核心逻辑：在数据"进入"上下文之前就控制体积。
① 结构化数据通过前端 UI 组件直接渲染给用户，不进入 LLM 上下文
② 超过动态阈值的工具结果，先尝试代码规则提取摘要（零 LLM 成本），失败再调用快速模型生成摘要
③ 原文保留在虚拟文件中，后续推理如需细节可按需引用
典型效果：100 条商机 35K 字符 → 上下文中只有 80 字摘要，节省 99.5%
Layer 2 · 当前轮次裁剪
时机：reasoning 循环中调用 LLM 前 · 仅多步复杂任务触发（约 20-30%）
核心逻辑：清理已在上下文中但不再需要完整保留的旧消息。
① MD5 去重：LLM 重复调用同一工具时，只保留最新一份结果，旧副本替换为引用标记
② 信息摘要替换：保护区（最近 N 条）外的旧工具结果，用规则模板生成一行摘要替换
③ 参数截断：保护区外的 tool_call 大参数截断到固定长度
典型效果：10 轮竞品调研中，早期 6 轮工具结果 14,700 字符 → 400 字符摘要，节省 97%
Layer 3 · 回复摘要回写
时机：每轮回复结束时 · 回复 >500 字符时触发（约 60-70%）
核心逻辑：为下次对话加载历史做准备，将长回复浓缩为精简摘要。
① answerSummary：异步生成当轮回复的摘要，写入数据库，不阻塞前端响应
② sessionSummary：维护一份结构化的会话级摘要（包含已完成操作、关键数据、待处理事项），存入 Redis，每轮迭代更新而非重新生成
典型效果：2000 字竞品分析报告 → 75 字 answerSummary，下次加载历史时节省 96%
Layer 4 · 历史上下文构建
时机：每次新对话开始时 · 覆盖所有非首轮对话（100%）
核心逻辑：用最小的 token 开销重建完整的对话上下文。
① 双套视图：reasoning 节点使用 answerSummary 构建精简历史，意图识别节点使用虚拟文件按需引用完整内容
② sessionSummary 注入：作为 SystemMessage 注入推理循环，确保跨轮次的关键信息不丢失
③ Prompt Cache：利用前缀匹配缓存机制，减少重复 token 的计费
典型效果：8 轮对话完整消息链 25K tokens → 压缩后 3.1K tokens，节省 87%

主路径与辅助路径

大部分 CRM 交互是 3-5 步的短对话（查客户→查商机→回复），只走主路径：

主路径（所有对话）： Layer 1（源头隔离）→ Layer 3（回复摘要）→ Layer 4（历史构建）

只有多步复杂任务（报价谈判、竞品调研、客户交接等，约 20-30% 的对话）才会触发辅助路径：

辅助路径（多步复杂任务）： Layer 1 → Layer 2（当前轮次裁剪） → Layer 3 → Layer 4

Layer 1 源头隔离的实现逻辑

Layer 1 是最关键的一层，因为它在数据进入上下文之前就完成了体积控制，避免了后续压缩的被动局面。

处理环节逻辑说明适用场景
前端组件分流 工具返回的结构化数据（列表、图表、卡片）通过 AG-UI 协议推送给前端渲染为 UI 组件，用户直接在界面上看到完整数据。LLM 上下文中只注入一行统计摘要（如"100 条商机，总金额 $3.6M"）。 所有返回结构化数据的工具调用
动态摘要阈值 不同工具类型设置不同的摘要触发阈值。查询类工具阈值低（300 字符），因为列表数据信息密度低；报价/财务类工具阈值高（1500 字符），因为精确数字不能丢失。低于阈值的结果完整保留，高于阈值的触发摘要流程。 所有工具结果的入口判断
两层摘要策略 第一层：用代码规则从结构化数据中提取关键信息（如从 JSON 列表提取记录数和名称，从已知组件类型提取关键字段），零 LLM 成本，毫秒级完成。第二层：代码规则无法处理时（如非结构化文本），调用快速模型生成摘要。CRM 场景中代码规则能覆盖 60-70% 的情况。 超过阈值的工具结果
虚拟文件保留原文 摘要后的原文不丢弃，而是存入虚拟文件（FileInfo）。后续推理如果需要某个具体字段值或细节，可以从虚拟文件中按需引用，不需要重新调用工具。 所有被摘要的工具结果

Layer 2 当前轮次裁剪的实现逻辑

Layer 2 只在多步复杂任务中触发（ToolMessage 数量 ≥5 且总字符数 >3000）。它处理的是"已经在上下文中但价值衰减"的旧消息。

处理环节逻辑说明
保护区机制 从消息列表末尾向前累积，最近 ~20K tokens 范围内的消息属于"保护区"，不做任何裁剪。只有保护区之外的旧消息才会被处理。这确保 LLM 当前正在使用的信息不受影响。
Pass 1: MD5 去重 对所有 ToolMessage 内容计算哈希值，从末尾向前遍历。相同内容只保留最新一份（最靠近末尾的），旧副本替换为"[重复结果 — 与最近一次相同查询结果一致]"。解决 LLM 重复调用同一工具（如反复查询同一客户）导致的冗余。
Pass 2: 信息摘要替换 保护区外的旧 ToolMessage，用规则模板生成一行信息摘要替换。摘要保留工具名、关键参数、数据量等元信息（如"[query_data] 查询 opportunity，返回 8 条记录"），让 LLM 知道"之前做过什么"但不占用大量空间。
Pass 3: 参数截断 保护区外的 assistant 消息中，tool_call 的 arguments 如果超过 500 字符则截断到 200 字符。大参数（如 modify_data 写入的长文本字段）在执行完毕后不再需要完整保留。

Layer 3 回复摘要回写的实现逻辑

Layer 3 的核心目标是为 Layer 4（下次对话加载历史）做准备。它在当前轮次结束后异步执行，不影响用户体验。

处理环节逻辑说明
answerSummary 异步生成 当轮回复超过 500 字符时，后台异步调用快速模型生成摘要，写入数据库的 answerSummary 字段。前端响应不等待摘要完成。下次加载历史时，conversation_history 使用 answerSummary（~100 字）而非完整 answer（可能 2000+ 字）。
sessionSummary 迭代更新 维护一份结构化的会话级摘要，包含 7 个固定 section：Active Task / 客户上下文 / 已完成操作 / 关键数据 / 已回答问题 / 待处理 / 涉及实体。每轮结束后迭代更新（保留旧内容 + 追加新内容 + 移动状态变化），而非每次重新生成。存入 Redis，适配 SaaS 无状态架构。
容错与降级 摘要生成失败时不影响主流程：answerSummary 为空则 fallback 使用完整 answer；连续失败触发冷却机制（60s/600s），冷却期间跳过摘要生成；摘要模型不可用时自动降级到主模型重试。

Layer 4 历史上下文构建的实现逻辑

Layer 4 在每次新对话开始时执行，用最小的 token 开销重建完整的对话上下文。

处理环节逻辑说明
双套历史视图 从数据库加载最近 5 轮历史，构建两套视图：① conversation_history 使用 answerSummary 构建精简的 user/assistant 交替序列，传给 reasoning 节点；② file_list 虚拟文件保留完整 answer 在 content 字段中，传给意图识别节点按需引用。
sessionSummary 注入 从 Redis 加载 sessionSummary，作为 SystemMessage 注入推理循环。即使早期对话已超出 5 轮历史窗口，sessionSummary 中仍保留了关键数据（如第 1 轮查到的"Andi 8 个商机 $280K"在第 15 轮仍然可见）。这是长对话信息不丢失的关键机制。
Prompt Cache 对支持缓存的模型（如 Anthropic），在消息列表中设置 4 个 cache_control 断点。System prompt 跨轮稳定，前缀匹配命中率高，输入 token 计费降低约 75%。

2.4 压缩触发策略

压缩的触发遵循"永远不在用户等待的关键路径上调用 LLM 做摘要"的原则，通过三道防线实现：

防线触发条件处理方式延迟影响
第一道：事前控制 每次工具调用（100%） 每个工具的返回大小已被 max_result_size_chars 限制；搜索只返回摘要+snippet；查询默认分页（page_size=20）；Schema 分层返回概览 0ms（工具内部逻辑）
第二道：规则压缩 上下文占比超过阈值 纯内存操作：裁剪历史消息、清除旧工具结果、MD5 去重。按占比分级：50% 轻度裁剪 → 70% 中度裁剪 → 85% 极端裁剪 ~5ms（毫秒级，用户无感知）
第三道：异步摘要 上下文占比 >85% 先用极端裁剪立即降到安全线，同时后台启动 LLM 摘要任务。摘要完成后下一轮生效。摘要失败则保持裁剪状态。 ~10ms（极端裁剪）+ 后台异步

对比旧方案（同步 LLM 摘要阻塞 3-5 秒），新方案在任何情况下都不会让用户感知到压缩带来的延迟。

2.5 辅助机制

机制说明
辅助 LLM 路由 摘要类任务（answerSummary、sessionSummary、工具结果摘要）使用便宜快速模型（如 gemini-flash），与主推理模型分离。摘要质量要求低于推理，用低成本模型即可满足。
反抖动保护 连续 2 次压缩节省率 <10% 时，跳过后续压缩。避免在上下文中大部分是保护区内容时反复触发无效压缩。
Scratchpad 外部工作区 完整数据存储在 Agent 可访问的外部工作区（内存 SQLite），不占上下文空间。上下文中只放提取物/统计视图，Agent 需要细节时从 Scratchpad 按需读取。适用于百级商机列表、大文本字段等超大数据源。
语义提取层 大文本字段（需求描述、会议纪要）进入上下文前，先用专用提取 Prompt 做结构化提取（核心需求、决策链、预算信号、关键原话等）。提取物进上下文（原文体积的 15%），原文留在 Scratchpad 供按需回读。
