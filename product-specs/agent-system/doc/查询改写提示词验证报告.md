## 二、V1 提示词问题分析

当前 V1 提示词：

```
你是一个查询改写助手。根据多轮对话上下文，将用户的最新问题改写为
一句自包含的完整查询（不依赖上下文即可理解）。

要求：
1. 解析代词指代（'你'→具体对象，'那个'→具体实体）
2. 补全省略的主语和宾语
3. 只输出改写后的查询，不要输出任何分析、标注或解释
4. 如果原始查询已经足够清晰，直接输出原文
5. 输出不超过 80 字
```

### 问题 1：缺少"条件继承"规则

场景 #19「改成50万以上的」、#20「换成北京的看看」属于条件变更类型。
用户没有重复完整查询，只说了变化的部分。V1 prompt 没有明确指导 LLM 如何处理这类"替换式"改写。

**风险**：LLM 可能只输出"筛选金额大于50万的商机"而丢失原始查询的其他隐含条件，或者输出"50万以上"这样过于简短的结果。

### 问题 2：缺少"不添加"约束

场景 #17「能不能找个机会再聊聊，看看有没有二期」期望改写为包含"美团IT总监陈浩"和"美团外卖CRM项目"的完整查询。但如果 LLM 过度推理，可能添加上文未提及的信息（如具体时间、具体方式）。

**风险**：LLM 可能幻觉出"下周约美团IT总监陈浩喝咖啡"这样的内容。

### 问题 3：缺少"序数词"解析指导

场景 #4「后面那个」、#10「第一个单子」、#11「第4个」都涉及序数词/位置词到具体实体的映射。V1 prompt 只说了"代词指代"，没有覆盖序数词。

**风险**：LLM 可能保留"第4个"而不替换为"美团配送系统"。

### 问题 4：缺少"不改写"的判断标准

场景 #14、#15 是话题完全切换的新查询，不应该被改写。V1 prompt 说"如果原始查询已经足够清晰，直接输出原文"，但没有给出判断标准。

**风险**：LLM 可能错误地将上文信息混入新查询（如"帮我创建一个新的商机，客户是百度，金额200万，与华为联系人无关"）。

### 问题 5：缺少 CRM 领域锚定

通用的"查询改写助手"角色定义缺少 CRM 业务语境。LLM 可能不理解"Pipeline"、"漏斗转化率"、"KA客户"、"赢单/输单"等术语的上下文含义。

**风险**：改写时可能丢失业务语义（如把"输单的呢"改写为"失败的呢"而非"本季度输单的商机有哪些"）。

### 问题 6：偏好/规则类表达的改写边界不清

场景 #18「对，以后都这样」是用户在确认一个偏好设置。这类表达不是"查询"，而是"指令确认"。改写需要将隐含的指令内容补全。

**风险**：LLM 可能输出"对，以后都这样"原文（判断为"已经清晰"），或者过度改写为"请确认以后报告格式调整"。

## 三、V2 优化提示词

```
你是 CRM 系统的查询改写模块。将用户最新问题改写为一句自包含的完整查询。

## 规则
1. 代词替换：将"他/她/它/那个/这个/第N个/后面那个/最大的"替换为上文中对应的具体名称
2. 省略补全：补全被省略的主语、宾语、时间范围或筛选条件
3. 条件继承：当用户说"换成X"/"改成X"/"X呢"时，保留原查询结构，只替换变化的条件
4. 指令补全：当用户说"对"/"好的"/"以后都这样"确认某个设置时，将确认的完整内容补全
5. 不改写：如果最新问题已经自包含（不依赖上下文就能理解），原样输出
6. 不添加：禁止添加上文未提及的信息，禁止推测用户未表达的意图

## 输出格式
- 只输出一句改写后的查询
- 不输出分析过程、不标注实体、不解释代词
- 不超过 80 字

## 对话上下文
{context}

{query}
```

## 五、结论与建议

1. **V2 prompt 增加了 3 条关键规则**：条件继承、指令补全、序数词解析
2. **角色锚定为 CRM 系统**：帮助 LLM 理解业务术语
3. **格式改为 Markdown 分节**：结构更清晰，LLM 遵循度更高
4. **"不添加"约束独立成条**：防止幻觉

建议后续扩展到 100 个场景时，增加以下类别：
- 多实体对比后的单体追问（"第一个比第二个多多少"）
- 否定式改写（"不是那个，是另一个"）
- 时间范围切换（"看看上周的"/"这个月改成上个月"）
- 跨实体关联（"他负责的客户里最大的那个"）
- 模糊表达（"差不多的"/"类似的"/"同级别的"）
