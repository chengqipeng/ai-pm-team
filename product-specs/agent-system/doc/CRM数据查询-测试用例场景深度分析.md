## 一、查询能力的技术架构

### 1.1 Agent 工具链

```
用户自然语言
    │
    ▼
┌─ query-crm-data Agent ──────────────────────────────────────────┐
│                                                                   │
│  默认路径: crm_query_simple（一次 HTTP 调用完成全流程）             │
│      │                                                           │
│      ├─ status=success → answer_by_data（输出卡片/LLM回答）       │
│      ├─ status=interrupt → 返回中断卡片（实体选择/条件确认）       │
│      ├─ status=fallback → 降级到多步查询 ↓                       │
│      └─ status=error → 降级到多步查询 ↓                          │
│                                                                   │
│  降级路径: 多步工具链                                              │
│      extract_entity → generate_xoql → execute_xoql               │
│      → answer_by_data                                            │
│      （重试上限2次 → search_by_keyword 兜底1次）                   │
│                                                                   │
│  特殊路径:                                                        │
│      • 多实体串行: 逐实体 crm_query_simple → answer_by_data       │
│      • 跨实体关联: 先查前序实体 → 取前20条名称 → 作为目标条件       │
│      • 记录详情: get_record_detail                                │
│      • 元数据查询: get_entity_metadata                            │
└───────────────────────────────────────────────────────────────────┘
```

### 1.2 输出模式判断

| 用户意图 | mode | 输出形式 |
|---------|------|---------|
| 查数据列表 | search | 前端卡片组件（CrmRecordList/CrmRecordCard）|
| 查特定字段 | answer | LLM 自然语言回答 + 参考数据 |
| 汇总/统计 | answer | LLM 计算后输出（表格/数值）|
| 排名/TopN | answer | LLM 排序分析输出 |
| 对比/差异 | answer | LLM 对比表格输出 |

### 1.3 关键限制约束

| 约束 | 规则 |
|------|------|
| XOQL 执行上限 | 同一实体最多 2 次 |
| search_by_keyword | 最终兜底，最多 1 次，空结果不重试 |
| 多实体串行 | 禁止并行 answer_by_data |
| 跨实体关联 | 取前 20 条名称作关联条件，禁止多级穿透 |
| 结果截断 | 超 100 条展示前 100 条 |
| answer 模式 | 超 20 条展示前 10 条 |
| 不支持的查询 | 消息通知/未读消息/我的待办 → 直接拒绝 |

## 九、总结

### 现状

CRM 数据查询的 416 条用例在 **正向查询路径** 上覆盖扎实（各实体基本查询、聚合、跨实体关联都有），是整个 promptfoo-test 项目中用例数量最多、覆盖实体最广的 Skill。

### 核心问题

1. **错误恢复/降级路径几乎完全未测** — 这是 Agent 最重要的容错机制
2. **中断交互仅 2 条** — 这是用户日常高频遇到的交互模式
3. **相对时间表达缺失** — 用户最自然的时间描述方式
4. **多轮对话严重不足** — 现实中用户很少一次就满足

### 建议优先级

按 P0（必须）→ P1（应补）→ P2（锦上添花）分级，P0 共需补充约 **39 条** 用例，P1 约 **63 条**，P2 约 **50 条**。合计建议新增 **~150 条** 用例，将完善度从 52.5% 提升至 80%+。
