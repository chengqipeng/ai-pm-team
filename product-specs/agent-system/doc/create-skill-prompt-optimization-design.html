关键优势

🎯 轻量主控，按需深入
SKILL.md 仅包含路由摘要和流程编排，保持主文件精简。深度知识按需从域文件加载，避免 token 浪费。
📚 平级域知识，独立演进
7 个域文件平级独立，各自维护各自的专业深度。新增业务域只需添加新文件，不影响其他域。
🛡️ 无死角覆盖
6 个业务域覆盖 CRM 标准场景，generic.md 兜底非标场景（跨域/非CRM/新兴业务），确保任何需求都有对应指导。
🔧 灵活组合加载
跨域需求可同时加载多个域文件 + generic.md 的跨域组合指导，实现灵活的知识组合。

2. Step 0 — 前置检查（去重 + 能力边界）

在任何设计工作之前，必须先执行前置检查，避免重复创建和超出能力边界：

0-A: 去重检查
1. 调用 query_data(entity_api_key="ai_skill") 获取已发布技能
2. 语义匹配 name + description
3. 四维度加权判断（对象 40% / 目标 30% / 输出类型 20% / 参数 10%）
4. 完全匹配→建议使用 / 高度相似→建议优化 / 部分重叠→询问用户
0-B: 能力边界检查
快速判断（任一命中则拒绝）：
• 物理世界操作 • 外部系统非公开数据
• 实时/持续运行 • 专业资质判断
• 创意内容生产 • 跨系统写入
• 训练/修改 AI • 违规/有害内容
拒绝三要素：明确说不能做 + 原因 + 替代建议

3. Step 2.5 — 资源架构决策

根据技能的分析需求，判断是否需要附加资源文件。不是每个技能都需要，但需要时必须明确规划。

决策树：
需要"超出 CRM 数据"的领域知识？ → references/（方法论/评分模型）
需要"复杂计算"（统计/建模/可视化）？ → scripts/（Python 脚本）
需要"已有企业知识库文档"？ → knowledge_search（知识库检索）
需要"实时外部信息"？ → web_search（网络搜索）
references/ — HOW（怎么分析）
方法论和模型定义。如 MEDDIC 评分标准、健康度权重、行业基准数据。
通过 preload_resources 自动注入
knowledge/ — WHAT（需要知道什么）
行业知识和领域数据。如行业特征/竞品情报/基准数据/销售剧本。
通过 read_skill_resource 按需加载
scripts/ — COMPUTE（复杂计算）
超出简单聚合的计算。如时序预测/客户聚类/可视化报表/大数据量处理。
通过 terminal + execute_code 执行

## 一、toB CRM 技能体系

用户创建的技能必然落在以下业务域之一。根据用户意图快速定位所属业务域，然后应用该域的**专业分析体系**：

### 域 1: 客户分析（Account Intelligence）

**业务本质**：帮助销售理解客户的业务全貌，找到切入点和扩展路径。

**专业分析体系**：
```
客户画像构建
├── 基础画像: 行业/规模/区域/成立年限/融资阶段
├── 业务画像: 主营业务/商业模式/收入结构/增长引擎
├── 组织画像: 决策链/部门结构/IT 成熟度/数字化阶段
├── 关系画像: 历史合作/关键人关系/竞品渗透/合作满意度
└── 价值画像: LTV 预测/钱包份额/扩展潜力/战略匹配度

深度分析维度（每个维度必须有数据支撑+判断逻辑+行动指引）:
  1. 客户健康度 — 基于活动频次/商机进展/NPS/续约信号的加权评分
  2. 钱包份额 — 我方收入 / 客户该品类总预算，识别扩展空间
  3. 决策链路图 — 经济买家/技术买家/使用者/教练的角色识别
  4. 竞品渗透度 — 客户已采购的竞品产品/金额/满意度/替换难度
  5. 扩展路径 — 基于已购产品推导 Cross-sell/Up-sell 机会
```

**Prompt 中必须包含的分析逻辑**：
- 不是查一下客户名称和联系人就完了
- 必须交叉关联：客户的商机历史 × 活动记录 × 联系人角色 × 行业特征
- 必须有判断：这个客户值不值得投入？投入的最佳切入点是什么？
- 必须有预测：基于历史模式预判下一步最可能发生什么

### 域 2: 商机管理（Opportunity Management）

**业务本质**：帮助销售推进商机、识别风险、提高赢率。

**专业分析体系**：
```
商机健康度评估（基于 MEDDIC 框架）
├── Metrics: 客户的量化业务痛点是什么？ROI 如何计算？
├── Economic Buyer: 经济决策人是否已识别并接触？
├── Decision Criteria: 客户的评估标准是什么？我方是否匹配？
├── Decision Process: 决策流程/时间线/审批层级是否清晰？
├── Identify Pain: 痛点是否被客户自己承认（而非我方假设）？
└── Champion: 是否有内部支持者在推动？其影响力如何？

商机推进策略:
  1. 阶段转化分析 — 当前阶段的历史转化率/平均停留时间/关键动作
  2. 竞争态势 — 竞品是否参与？我方差异化优势是什么？
  3. 风险信号 — 活动断档/关键人变动/需求变更/预算冻结
  4. 赢单路径 — 基于相似商机的成功模式推荐下一步动作
  5. 预测置信度 — 基于多维信号的加权赢率计算
```

**Prompt 中必须包含的分析逻辑**：
- 不是列出商机字段就完了
- 必须评估：MEDDIC 每个维度的完成度（0-100%），给出整体赢率
- 必须对比：与同阶段已赢/已丢商机的特征对比，识别差距
- 必须建议：基于差距给出具体的推进动作（联系谁、做什么、什么时候）

### 域 3: 销售预测（Forecast & Pipeline）

**业务本质**：帮助销售经理准确预测收入、管理团队 Pipeline。

**专业分析体系**：
```
Pipeline 健康度模型
├── 覆盖率: Pipeline 金额 / 目标 ≥ 3x 为健康
├── 形态: 各阶段分布是否呈漏斗形（上宽下窄）
├── 流速: 新增速度 vs 关闭速度 vs 流失速度的平衡
├── 质量: 加权金额（金额 × 阶段赢率）vs 目标的差距
└── 时效: 超期商机占比 / 本季度可关闭金额的置信度

Forecast 准确度分析:
  1. Commit vs Actual 的历史偏差率
  2. 各销售的预测准确度排名（谁总是过于乐观/保守）
  3. 阶段赢率的实际值 vs 系统默认值的偏差
  4. 本季度 Upside/Commit/Best Case 三档预测
```

### 域 4: 销售行为分析（Activity Intelligence）

**业务本质**：通过活动数据洞察销售行为模式，识别最佳实践和改进点。

**专业分析体系**：
```
活动效能模型
├── 量: 活动总量/日均活动数/客户覆盖率
├── 质: 有效活动占比/推进商机的活动占比/高层拜访占比
├── 节奏: 活动间隔/跟进及时性/关键节点覆盖
├── 模式: 成功销售 vs 普通销售的活动模式差异
└── 转化: 活动→商机→签约的转化漏斗

行为洞察:
  1. 最佳实践提取 — Top Sales 的活动模式是什么？
  2. 风险预警 — 哪些客户/商机的活动出现断档？
  3. 辅导建议 — 基于行为差距给出具体改进建议
```

### 域 5: 客户成功（Customer Success）

**业务本质**：帮助 CSM 管理客户健康度、预防流失、驱动扩展。

**专业分析体系**：
```
客户健康度评分模型
├── 产品使用: 登录频次/功能覆盖度/使用深度/活跃用户占比
├── 关系健康: 联系频次/NPS/投诉率/关键人稳定性
├── 商业健康: 续约意向/扩展信号/付款及时性/合同剩余期限
├── 支持健康: 工单数量趋势/解决时效/升级频次
└── 价值实现: 客户 KPI 达成度/ROI 验证/成功案例产出

续约风险预测:
  1. 流失信号识别 — 使用下降/联系减少/竞品接触/关键人离职
  2. 风险等级判定 — 红/黄/绿三级 + 置信度
  3. 挽回策略 — 基于流失原因的差异化挽回方案
  4. 扩展机会 — 健康客户的 Up-sell/Cross-sell 时机识别
```

### 域 6: 团队管理（Sales Management）

**业务本质**：帮助销售经理管理团队绩效、辅导下属、优化资源分配。

**专业分析体系**：
```
团队绩效模型
├── 目标达成: 个人/团队的目标完成率 + 趋势
├── 效率指标: 人均产出/赢单周期/客单价/活动转化率
├── 能力矩阵: 各销售在不同维度（开拓/推进/关闭/维护）的能力评估
├── 资源分配: 客户分配合理性/区域覆盖度/大客户集中度

   │               建议"在现有技能基础上优化，而非重新创建"
   ├── 部分重叠（30-70%）→ 告知重叠部分，询问"A) 扩展现有技能 B) 创建独立新技能？"
   └── 无重叠 → 继续下一步
```

#### 0-B: 能力边界检查 — 需求是否可承载？

```
快速判断（任一命中则拒绝）：
├── 需要操作物理世界？（打电话/发邮件/制造实物）→ 拒绝
├── 数据不在 CRM 中？（外部系统内部数据）→ 拒绝（可降级为 web_search 公开信息）
├── 需要实时/持续运行？（监控/自动响应）→ 拒绝
├── 需要专业资质？（法律/医疗/审计意见）→ 拒绝（可做数据辅助，声明不替代专业判断）
├── 涉及跨系统写入？（同步飞书/发邮件/更新 ERP）→ 拒绝
├── 违反安全策略？（伪造数据/绕过权限）→ 拒绝
└── 全部通过 → 继续 Step 1

拒绝时必须包含三要素：
1. 明确说"不能做"
2. 一句话解释原因
3. 给出替代建议（如有）
```

详细的能力边界定义和灰色地带处理，参见 `knowledge/domains/generic.md` 第一-B节。

**需要 references 的场景：**

#### scripts（Python 脚本）— 何时需要

**需要 scripts 的场景：**

| 场景 | 需要的脚本 | 原因 |
|------|-----------|------|
| 趋势预测 | `scripts/forecast.py` | analyze_data 只能做简单聚合，无法做时序预测（ARIMA/指数平滑） |
| 客户聚类 | `scripts/clustering.py` | 需要 K-Means/DBSCAN 对客户分群，CRM 工具无此能力 |
| 可视化报表 | `scripts/visualize.py` | 需要生成图表（漏斗图/雷达图/趋势图），CRM 工具无此能力 |
| 大数据量处理 | `scripts/batch_process.py` | 数据量 > 1000 条时，需要 pandas 批量处理而非逐条查询 |
| 复杂评分模型 | `scripts/scoring.py` | 评分逻辑涉及多变量加权/归一化/非线性映射 |
| 数据清洗 | `scripts/clean.py` | 需要正则匹配/去重/格式标准化等 ETL 操作 |

**不需要 scripts 的场景：**
- analyze_data 的 count/sum/avg/min/max + group_by 能满足的统计需求
- 简单的百分比计算（如转化率 = 赢单数/总数）
- 简单的排序和筛选
- 数据量 < 200 条的分析

**scripts 文件规划规范：**
```

├── main.py              # 主入口（必须有）
├── utils.py             # 工具函数
├── models.py            # 评分/预测模型
├── visualize.py         # 可视化生成
└── requirements.txt     # 依赖声明（必须有）
```

#### knowledge（行业知识目录）— 何时需要

**knowledge/ 是 Skill 自带的行业知识文件目录**，存储在 `ai_skill_resource` 表中，通过 `read_skill_resource` 工具按需加载。它提供分析所需的**行业深度知识**，是让技能具备专业深度的关键。

**knowledge/ vs references/ 的区别：**

| 维度 | references/ | knowledge/ |
|------|------------|-----------|
| 存什么 | 方法论、评分模型、流程定义 | 行业知识、市场数据、领域专业内容 |
| 特点 | 通用的、跨行业的、结构化的 | 行业特定的、知识密集的、需要专业积累的 |
| 示例 | meddic-scoring.md、health-score-model.md | manufacturing.md、saas-metrics.md、new-energy-supply-chain.md |
| 加载时机 | preload_resources 自动注入（每次都需要） | 按行业/场景匹配后按需加载（不是每次都需要全部） |
| 更新频率 | 低（方法论不常变） | 中（行业数据定期更新） |

**需要 knowledge/ 的场景：**

| 场景 | 需要的 knowledge 文件 | 原因 |

| 客户业务模式理解 | `knowledge/business-models/{模式}.md` | 理解客户的商业模式（订阅/项目制/平台/制造）才能判断合作价值 |

### Step 3: 构建分析体系

根据业务域 + 数据可用性，构建技能的分析体系。

**专业性保障**：如果用户需求属于 ToB CRM 领域（数据分析/报告/业务建议），必须引用内置知识体系确保专业性：
- **方法论注入**：从 `generic.md §5B.1` 的方法论库中选择匹配的方法论注入 Prompt
- **基准数据注入**：从 `generic.md §5B.2` 的行业基准中选择对应指标作为判断标准
- **维度选择**：从 `generic.md §5B.3` 的维度池中选择分析维度（优先选有方法论支撑的）
- **深度保障**：每个维度必须达到 Level 2+（有对比有判断），专业技能要求 Level 3-4（有归因有建议）

**核心原则**：

**原则 1: 每个分析维度必须形成完整的"数据→指标→判断→行动"链路**
```
数据采集（调哪个工具、查什么字段）
    ↓
指标计算（如何从原始数据得出指标）
    ↓
基准对比（与什么对比？历史/同行/目标 — 优先用客户历史，无则用行业基准）
    ↓
判断逻辑（IF/ELIF/ELSE 的决策树）
    ↓
行动建议（具体做什么、优先级、预期效果）
```

**原则 2: 分析必须有"纵深"而非"广度"**

❌ 广度型（10 个维度各看一眼）：
```
查客户基本信息、查商机、查联系人、查活动、查合同...
```

✅ 纵深型（3-4 个核心维度深入分析）：
```
维度 1: 客户业务理解（深入到商业模式和增长引擎）
  → 不只是"制造业"，而是"精密零部件制造，服务于新能源汽车产业链，
     受益于电动化渗透率提升，但面临原材料价格波动风险"

维度 2: 合作关系评估（深入到决策链和竞争态势）
  → 不只是"有 3 个联系人"，而是"经济买家是 VP of IT，
     技术评估由架构师团队主导，内部 Champion 是数字化总监，
     但 CFO 对 ROI 要求严格，需要准备量化价值证明"

维度 3: 机会识别（深入到具体的切入点和时机）
  → 不只是"有扩展潜力"，而是"Q4 有 ERP 升级预算 500 万，
     当前用的是竞品 A 但满意度只有 60%，切入点是集成能力，
     最佳时机是 9 月预算审批前完成 POC"
```

**原则 3: 输出必须是"可直接行动的洞察"而非"信息汇总"**

❌ 信息汇总：
```
客户 A：制造业，500 人，年营收 3 亿，有 5 个商机共 200 万
```

✅ 可行动洞察：
```
## 核心判断
客户 A 正处于数字化转型加速期（证据：IT 预算同比增长 40%，
新任 CIO 上任 6 个月内已启动 3 个数字化项目）。
这是我方切入的最佳窗口期。

## 关键风险
但竞品 B 已在该客户有 2 个在用产品（CRM + BI），
客户对"一站式平台"有偏好，我方需要证明集成能力。

## 推荐行动
1. [本周] 通过 Champion（数字化总监）安排与新 CIO 的高层会面
2. [2 周内] 准备"平台集成能力"专题 Demo，重点展示与竞品 B 的数据互通
3. [1 个月内] 推动 POC 立项，锁定 Q4 预算窗口
```

**原则 4: 每个结论必须标注数据来源（Data Provenance）— 反幻觉核心机制**

这是最重要的原则。**任何结论、判断、数字都必须标注它来自哪个具体的数据查询结果。** 没有数据支撑的结论禁止输出。

技能 Prompt 中必须强制要求 Agent 在输出时使用**数据溯源标注格式**：

```
每个结论后面必须用 [来源:xxx] 标注数据出处：

[来源:query_data] — 来自 CRM 系统查询结果
[来源:analyze_data] — 来自聚合统计计算结果
[来源:web_search] — 来自网络搜索结果（标注 URL）
[来源:knowledge] — 来自知识库检索结果
[来源:推算] — 基于已有数据的逻辑推导（必须说明推导过程）
[来源:用户输入] — 用户在对话中提供的信息
```

**示例（正确 — 每个结论有数据支撑）：**
```
## 客户健康度评估

### 活跃度: 72/100
- 最近 30 天活动 8 次 [来源:query_data → activity, filters={account_id, last_30_days}]
- 月均活动 5.2 次，高于该行业客户均值 3.8 次 [来源:analyze_data → activity count group by account]
- 但较上月下降 23%（上月 10.4 次）[来源:query_data → activity, filters={last_60_days} 对比计算]

### 商机进展: 45/100
- 当前 3 个活跃商机，总金额 180 万 [来源:query_data → opportunity, filters={account_id, status=active}]
- 其中 2 个商机超过 45 天未推进阶段 [来源:query_data → opportunity.stage_updated_at 计算]
- ⚠️ 行业平均阶段停留时间为 28 天 [来源:analyze_data → opportunity avg(stage_duration) where industry=制造业]

### 综合判断
该客户活跃度尚可但呈下降趋势，商机推进明显滞后。
[来源:推算 — 活跃度下降 23% + 2 个商机超期 → 判断客户内部可能有优先级变化或决策阻塞]

建议: 48h 内联系 Champion 确认是否有内部变化 [来源:推算 — 基于活跃度下降+商机停滞的组合信号]
```

**示例（错误 — 无数据支撑的幻觉）：**
```
❌ "该客户年营收约 5 亿" — 没有标注来源，可能是编造的
❌ "客户对我方产品满意度很高" — 没有 NPS 数据支撑
❌ "预计 Q4 会签约" — 没有说明预测依据
❌ "竞品 A 的市场份额是 30%" — 没有标注信息来源
```

**技能 Prompt 中必须包含的反幻觉指令：**

```markdown
## ⚠️ 数据纪律（严格遵守）

1. **禁止编造数据** — 所有数字必须来自工具查询结果，不得凭空生成
2. **禁止无源结论** — 每个判断必须用 [来源:xxx] 标注数据出处
3. **区分事实与推断** — 事实标注 [来源:query_data/analyze_data]，推断标注 [来源:推算] 并说明推导逻辑
4. **数据缺失时明确声明** — 不要用模糊语言掩盖数据缺失，直接说"该维度无数据，无法评估"
5. **矛盾数据时标注冲突** — 如果不同来源的数据矛盾，列出两方数据并标注"数据冲突，需人工确认"
6. **外部数据标注时效** — web_search 结果标注搜索时间，知识库结果标注文档更新时间
```

**原则 5: 结果自校验 — 输出前必须执行核验步骤**

技能 Prompt 的最后一步必须是**自校验**，在输出最终结果前检查：

```markdown
## 步骤 N: 结果核验（输出前必须执行）

### 核验 1: 数据一致性
- 检查各维度引用的数据是否自洽（如：商机总金额 = 各商机金额之和）
- 检查同一指标在不同步骤中的引用是否一致

### 核验 2: 来源完整性
- 检查输出中每个数字/结论是否都有 [来源:xxx] 标注
- 如果发现无源结论 → 删除该结论或补充数据查询

### 核验 3: 逻辑合理性
- 检查结论是否与数据方向一致（如：活动增加但判断"客户不活跃"→ 矛盾）
- 检查建议是否与判断匹配（如：判断"低风险"但建议"紧急挽回"→ 矛盾）

### 核验 4: 置信度标注
对每个核心结论标注置信度：
- 🟢 高置信（多数据源交叉验证，数据充分）
- 🟡 中置信（单一数据源，或数据有限但逻辑合理）
- 🔴 低置信（数据不足，主要基于推断，需人工确认）
```

## 三、快速生成高质量 Skill 的模式库

当用户的需求匹配以下模式时，可以快速套用对应的分析体系骨架，然后根据具体需求细化：

### 模式 A: "分析某个客户"
→ 套用**客户 360 分析体系**
→ 核心维度：业务理解 + 关系评估 + 机会识别 + 风险预警
→ 输出：客户评分 + 关键洞察 + Top3 行动建议

### 模式 B: "分析某个商机 / 评估赢率"
→ 套用 **MEDDIC 评估体系**
→ 核心维度：6 个 MEDDIC 维度的完成度评估
→ 输出：赢率评分 + 薄弱环节 + 推进策略

### 模式 C: "看看我的 Pipeline / 预测本季度"
→ 套用 **Pipeline 健康度模型**
→ 核心维度：覆盖率 + 形态 + 流速 + 质量 + 时效
→ 输出：Pipeline 健康评分 + 风险商机清单 + Forecast 三档预测

### 模式 D: "分析团队表现 / 谁需要辅导"
→ 套用**团队绩效矩阵**
→ 核心维度：目标达成 + 效率指标 + 能力矩阵 + 辅导优先级
→ 输出：团队排名 + 能力雷达图 + 辅导建议

### 模式 E: "哪些客户有流失风险 / 续约分析"
→ 套用**客户健康度评分模型**
→ 核心维度：产品使用 + 关系健康 + 商业健康 + 价值实现
→ 输出：风险等级（红/黄/绿）+ 流失信号 + 挽回策略

### 模式 F: "找到扩展机会 / Cross-sell"
→ 套用**钱包份额 + 扩展路径模型**
→ 核心维度：当前渗透度 + 未覆盖需求 + 扩展时机 + 竞品空白
→ 输出：扩展机会清单 + 优先级排序 + 切入策略

### 模式 G: "分析销售活动 / 最佳实践"
→ 套用**活动效能模型**
→ 核心维度：量 + 质 + 节奏 + 模式 + 转化
→ 输出：活动效能评分 + Top Sales 模式对比 + 改进建议

### 模式 H: "竞品分析 / 如何打竞品"
→ 套用**竞争定位 + 攻防策略**
→ 核心维度：产品对比 + 客户重叠 + 赢/丢单归因 + 差异化话术
→ 输出：竞品攻防手册 + 场景化话术 + 成功案例参考

## 四、被创建 Skill 的可用工具清单

以下是系统中当前所有可用的工具。**你创建的技能只能从这个清单中选择 allowed_tools，禁止使用清单之外的工具。** 根据技能的实际需要精确选择，不要全选。

|------|------|----------|-------------|

|------|------|----------|-------------|

| read_file | 读取沙盒中的文件，支持按行范围 | path(必填), offset(起始行), limit(行数) | 读取脚本输出结果/生成的报告 |
| write_file | 在沙盒中创建或覆盖文件，自动创建父目录 | path(必填), content(必填) | 写入数据供脚本处理/保存中间结果 |

### 交互与外部工具
| 工具 | 用途 | 关键参数 | 适用技能类型 |
|------|------|----------|-------------|
| ask_user | 向用户发起确认/选择/输入请求（中断等待响应） | interrupt_type(confirm/select/multi_select/input), title, message, options | 涉及写操作或需要用户补充信息的技能 |
| ask_clarification | 信息不足或有歧义时中断追问 | question(必填), clarification_type, options | 参数可能不完整的技能 |
| web_search | 搜索互联网获取实时外部信息 | query(必填), max_results | 需要行业动态/公司信息/竞品新闻的技能 |
| file_upload | 上传文件到 COS 对象存储，返回 URL | file_path(必填), bucket, prefix | 需要导出报告/图表文件的技能 |

### 工具选择原则

```
1. 只读分析类技能 → query_data + analyze_data（基础）+ web_search（外部信息）
2. 需要行业知识 → 加 read_skill_resource（加载 knowledge/ 文件）
3. 需要复杂计算 → 加 terminal + execute_code + read_file + write_file
4. 涉及数据写入 → 加 modify_data + ask_user（必须配对，写前确认）
5. 需要产品文档 → 加 knowledge_search
6. 需要导出文件 → 加 file_upload

禁止：
- 不要把 manage_skill 加到普通技能中（那是 create_skill 专用的）
- 不要把 browse_metamodel/query_metadata 加到业务分析技能中（那是元数据管理专用的）
- 不要无脑全选，工具越少越精确，LLM 越不容易走偏
```

# 客户分析（Account Intelligence）— 行业知识指南

> 本文件为 create_skill 提供客户分析领域的专业知识，指导生成具备行业深度的客户分析类技能 Prompt。

---

## 一、业务本质与分析目标

客户分析的终极目标不是"展示客户信息"，而是回答三个核心问题：
1. **值不值得投入？** — 客户的战略价值和商业潜力
2. **从哪里切入？** — 最佳的业务切入点和时机
3. **下一步做什么？** — 具体可执行的行动建议

**关键区分**：新客户分析侧重"切入可行性"，存量客户分析侧重"扩展与留存"。

---

## 二、客户画像五维模型

### 2.1 维度定义与数据要求

| 维度 | 核心问题 | 关键数据点 | 判断输出 |
|:---|:---|:---|:---|
| 基础画像 | 这是一家什么样的公司？ | 行业/规模/区域/成立年限/融资阶段/经营状态 | 客户分级（S/A/B/C/D） |
| 业务画像 | 它靠什么赚钱？增长引擎是什么？ | 主营业务/商业模式/收入结构/增长率/数字化阶段 | 业务匹配度 + 成熟度判断 |
| 组织画像 | 谁说了算？采购怎么决策？ | 决策链/部门结构/审批流程/预算周期 | 销售策略选择 |
| 关系画像 | 我们和它的关系怎么样？ | 历史合作/关键人关系/竞品渗透/互动质量 | 关系健康度评分 |
| 价值画像 | 它能给我们带来多少价值？ | LTV/钱包份额/扩展潜力/战略匹配/标杆价值 | 投入优先级排序 |

### 2.2 客户分级模型（ABM 五级）

分级不仅看规模，更看**战略匹配度**和**增长潜力**：

```
S 级（标杆客户）：行业标杆 + 战略匹配度极高 + 有标杆效应（即使规模不大）
  → 策略：不计短期 ROI，追求标杆案例和行业影响力
A 级（战略客户）：规模大 + 预算充足 + 数字化成熟 + 多产品线需求
  → 策略：ABM 专属团队，高层对接，定制方案
B 级（重点客户）：中等规模 + 有明确需求 + 预算可支撑 + 决策链可触达
  → 策略：标准大客户销售流程，重点跟进
C 级（标准客户）：需求明确但预算有限，或规模小但行业有代表性
  → 策略：标准化方案，效率优先
D 级（观望客户）：需求不明确 / 预算不足 / 时机未到
  → 策略：低成本培育（内容营销/活动邀请），等待时机

分级权重：
├── 战略匹配度（30%）：我方产品与客户核心业务的契合程度
├── 商业潜力（25%）：预估 3 年 LTV
├── 增长动能（20%）：客户自身的增长速度和数字化投入趋势
├── 可触达性（15%）：决策链是否可接触，是否有 Champion
└── 标杆价值（10%）：行业影响力，能否带来同行业客户
```

### 2.3 客户数字化成熟度判断

成熟度直接决定销售策略（教育型 vs 方案型 vs 替换型）：

| 阶段 | 特征 | 销售策略 | 典型周期 |
|:---|:---|:---|:---|
| 觉醒期 | 知道需要数字化，但不知道怎么做 | 教育型：行业案例+方法论输出+免费诊断 | 6-12 月 |
| 探索期 | 在评估方案，可能有小规模试点 | 顾问型：POC+业务咨询+ROI 测算 | 3-6 月 |
| 实施期 | 已有系统，在扩展或优化 | 方案型：集成能力+扩展方案+迁移支持 | 2-4 月 |
| 深化期 | 系统成熟，追求更高价值 | 价值型：高级功能+数据智能+战略合作 | 1-3 月 |
| 替换期 | 对现有系统不满，考虑更换 | 替换型：差异化+迁移保障+快速见效 | 3-6 月 |

### 2.4 关系健康度评分

```
评分维度（各 20 分，满分 100）：
├── 互动频次（20分）：月均互动 ≥4次=20, 2-3次=12, 1次=6, 0次=0
├── 关系层级（20分）：有 C-level 关系=20, VP 级=15, 总监级=10, 仅执行层=5
├── 互动质量（20分）：有实质性业务讨论=20, 仅关系维护=12, 仅事务性=6
├── 响应速度（20分）：24h内回复=20, 3天内=12, 超过3天=6, 不回复=0
└── 主动度（20分）：客户主动联系 >30%=20, 10-30%=12, <10%=6, 从不主动=0
```

### 2.5 LTV 预测模型

```
标准公式：
LTV = 年合同金额 × 预期续约年数 × (1 + 年均增长率)
预期续约年数 = 1 / (1 - 历史续约率)

数据不足时的估算方法：
├── 无续约率数据 → 按行业基准估算（SaaS: 90%, 传统软件: 80%, 服务: 70%）
├── 无增长率数据 → 按客户分级估算（A级: 15%, B级: 10%, C级: 5%）
├── 新客户（无历史）→ 按同行业同规模客户的中位数估算
└── 快速估算法：LTV ≈ 首单金额 × 行业 LTV 系数
    SaaS 产品：系数 5-8x
    项目制服务：系数 2-3x
    平台型产品：系数 8-12x
```

## 三、深度分析维度（5 维）

每个维度必须形成完整的 **数据→指标→基准→判断→行动** 链路。

### 3.1 客户健康度

| 信号类别 | 正面信号（加分） | 负面信号（减分） |
|:---|:---|:---|
| 活动频次 | 月均互动 ≥4次，且呈上升趋势 | 互动频次下降 >30%，或连续 14天无互动 |
| 商机进展 | 有活跃商机且阶段在推进 | 商机停滞 >30天，或连续丢单 |
| NPS/满意度 | NPS ≥ 8，无投诉 | NPS < 6，或有升级投诉 |
| 续约信号 | 主动询问续约/扩展 | 询问合同终止条款，或接触竞品 |
| 使用深度 | 功能使用覆盖 >70%，活跃用户增长 | 使用率下降，核心功能停用 |

**健康度等级：**
- 🟢 健康（80-100）：可推动扩展，优先分配资源
- 🟡 关注（60-79）：需主动干预，安排深度沟通
- 🔴 预警（40-59）：流失风险高，启动挽回计划
- ⚫ 危险（<40）：极高风险，升级管理层介入

### 3.2 钱包份额与扩展空间

```
钱包份额 = 我方年收入 / 客户该品类年度总预算
扩展空间 = (1 - 钱包份额) × 客户总预算

判断标准：
├── > 60%：深度绑定，重点维护，防御竞品
├── 30-60%：有扩展空间，识别未覆盖需求，制定扩展计划
├── 10-30%：大量空间，分析竞品占位，寻找差异化切入
├── < 10%：刚起步，需要证明价值后再扩展
└── 无法计算：标注 [信息空白]，建议通过 QBR/客户访谈获取

预算获取方法（当 CRM 无数据时）：
├── 直接法：QBR 中直接询问年度 IT/数字化预算
├── 推算法：同行业同规模企业的平均 IT 支出占比（通常 3-8% 营收）
├── 信号法：客户招聘 IT 岗位数量 × 平均薪资 ≈ IT 投入规模
└── 竞品法：已知竞品合同金额 + 我方金额 ≈ 该品类总预算下限
```

### 3.3 决策链路图

| 角色 | 识别信号 | 影响力 | 销售策略 |
|:---|:---|:---|:---|
| 经济买家（EB） | C-level/VP + 预算审批权 + 参与合同谈判 | 最终决策 | 价值导向：ROI 量化 + 战略对齐 |
| 技术买家（TB） | 参与 POC/技术评估 + 架构师/IT 负责人 | 否决权 | 技术深度：方案演示 + 集成验证 |
| 使用者（User） | 日常使用 + 提需求 + 反馈问题 | 影响采纳 | 体验导向：易用性 + 培训支持 |
| 教练（Champion） | 主动推动 + 内部宣传 + 提供内部信息 | 推动力 | 赋能武装：提供内部汇报材料 |
| 阻碍者（Blocker） | 倾向竞品 / 抵制变化 / 利益冲突 | 阻碍力 | 中和策略：绕过或转化 |

**覆盖度判断：**
- 🟢 完整：EB + TB + Champion 均已识别并多次接触，无活跃 Blocker
- 🟡 部分：缺少 EB 或 Champion，或有未处理的 Blocker
- 🔴 薄弱：仅接触 User 层，或 EB 完全未触达

**多线程覆盖原则**：
- 每个活跃商机至少覆盖 3 个不同角色的联系人
- A/B 级客户至少有 2 条独立的关系线（避免单点依赖）

### 3.4 竞品渗透度

```
评估框架（5 维度）：
├── 竞品数量：客户已采购几家竞品产品？
├── 渗透深度：竞品覆盖了哪些业务场景？核心还是边缘？
├── 客户满意度：客户对竞品的满意度如何？
│   获取方式：NPS/投诉记录/续约行为/Champion 反馈
├── 合同锁定：竞品合同剩余期限？有无排他条款？
└── 替换成本：数据迁移量/集成复杂度/培训成本/业务中断风险

替换难度综合判断：
├── 低（可攻）：满意度 <6 + 合同 <6月到期 + 切换成本可控 + 有内部 Champion
├── 中（需策略）：满意度中等 + 有差异化切入点 + 可分步替换
├── 高（暂缓）：满意度高 + 合同锁定 >1年 + 深度集成 + 无内部支持
└── 策略选择：
    低 → 正面竞争，加速推进
    中 → 侧翼进攻，先切边缘场景再扩展
    高 → 长期培育，等待合同到期或满意度下降
```

### 3.5 扩展路径

```
扩展机会识别（按优先级排序）：

1. Up-sell（升级）— 最容易，已有信任基础
   信号：用户数接近许可上限 / 功能需求超出当前版本 / 使用深度持续增长
   策略：用数据证明当前版本的瓶颈，展示升级后的增量价值

2. Cross-sell（交叉）— 中等难度，需要新的业务理解
   信号：新部门开始使用 / 业务扩张到新领域 / 相关需求在沟通中提出
   策略：从已有成功案例切入，降低新产品的信任门槛

3. 增加用户/部门 — 低风险，量的扩展
   信号：活跃用户 >80% 许可 / 其他部门表达兴趣 / 集团化推广
   策略：提供部门级试用 + 内部推荐激励

时机判断矩阵：
├── 最佳时机：续约前 60天 / 年度 QBR / 客户融资后 / 新 CIO 上任
├── 次佳时机：新项目启动 / 组织架构调整 / 竞品合同到期
├── 避免时机：客户裁员/亏损 / 预算冻结期 / 关键人刚变动
└── 创造时机：主动发起 QBR / 分享行业洞察 / 邀请参加客户活动
```

## 四、客户风险因素评估

除了关系和使用维度，还需关注客户自身的经营风险：

| 风险类别 | 信号 | 对合作的影响 | 应对策略 |
|:---|:---|:---|:---|
| 经营下滑 | 裁员/营收下降/亏损公告 | 预算削减，可能降级或不续约 | 提前沟通降级方案，锁定核心模块 |
| 组织动荡 | 高管更替/架构重组/并购 | 决策链断裂，项目暂停 | 快速建立新关系，重新对齐价值 |
| 行业风险 | 政策变化/市场萎缩/技术颠覆 | 客户业务收缩，IT 投入减少 | 调整方案定位，强调降本增效价值 |
| 资金风险 | 付款延迟/融资失败/现金流紧张 | 可能拖欠或终止合同 | 缩短账期，考虑分期方案 |

## 五、交叉关联分析方法

客户分析的专业深度体现在**交叉关联**，而非单维度罗列：

```
必须交叉的维度组合（按价值排序）：
├── 健康度趋势 × 合同节点 → 预判续约风险和最佳干预时机
├── 决策链覆盖 × 商机阶段 → 判断当前推进是否有足够的关系支撑
├── 竞品渗透 × 客户满意度 → 识别竞品替换的机会窗口
├── 客户增长率 × 钱包份额 → 预测未来 3 年的收入潜力
├── 数字化成熟度 × 产品匹配 → 选择正确的销售策略（教育/方案/替换）
└── 经营风险 × 合同金额 → 评估坏账风险和应对优先级
```

## 八、Prompt 设计指导

生成客户分析类技能 Prompt 时，必须确保：

1. **不是信息罗列**：不能只查客户名称和联系人就结束
2. **必须有分级判断**：给出客户等级（S/A/B/C/D）和投入优先级
3. **必须有交叉关联**：至少 2 个维度的数据交叉分析
4. **必须有成熟度判断**：客户处于什么数字化阶段，决定销售策略
5. **必须有行动建议**：基于判断给出具体的下一步（联系谁/做什么/什么时候）
6. **必须有风险标注**：客户自身经营风险 + 关系风险
7. **必须有数据溯源**：每个结论标注 [来源:xxx]
8. **必须区分场景**：新客/续约/扩展/竞品攻防，侧重点不同

# 商机管理（Opportunity Management）— 行业知识指南

> 本文件为 create_skill 提供商机管理领域的专业知识，指导生成具备行业深度的商机分析类技能 Prompt。

---

## 一、业务本质与分析目标

商机分析的终极目标不是"展示商机字段"，而是回答三个核心问题：
1. **能不能赢？** — 基于多维信号的赢率判断
2. **卡在哪里？** — 识别推进障碍和薄弱环节
3. **下一步做什么？** — 具体的推进动作和优先级

---

## 二、MEDDIC 评估框架

### 2.1 六维度评分标准

每个维度独立评分 0-100%，整体赢率为加权综合。

| 维度 | 权重 | 核心问题 | 评分逻辑 |
|:---|:---|:---|:---|
| Metrics | 15% | 客户的量化业务痛点是什么？ | 有明确量化 ROI=80+，仅定性=40-60，未识别=0-20 |
| Economic Buyer | 20% | 经济决策人是否已接触？ | 多次深度接触=80+，已识别未接触=40-60，未识别=0-20 |
| Decision Criteria | 15% | 评估标准是什么？我方匹配度？ | 标准明确且匹配=80+，部分匹配=40-60，不匹配/不清楚=0-20 |
| Decision Process | 15% | 决策流程和时间线清晰吗？ | 完全清晰=80+，部分清晰=40-60，不清晰=0-20 |
| Identify Pain | 15% | 痛点是客户承认的还是我方假设？ | 客户主动表达=80+，引导后承认=40-60，我方假设=0-20 |
| Champion | 20% | 有内部支持者在推动吗？ | 有且有影响力=80+，有但弱=40-60，无=0-20 |

### 2.2 整体赢率计算

```
赢率 = Σ(维度得分 × 权重) × 阶段系数

阶段系数：
├── 初步接触：0.6
├── 需求确认：0.7
├── 方案演示：0.8
├── 商务谈判：0.9
└── 签约阶段：0.95

示例：MEDDIC 加权得分 72%，当前阶段"方案演示"
赢率 = 72% × 0.8 = 57.6%
```

### 2.3 等级判定

```
🟢 良好（≥70%）：推进顺利，保持节奏
🟡 关注（40-69%）：有薄弱环节，需针对性补强
🔴 风险（<40%）：多维度缺失，需重新评估是否继续投入
```

## 三、商机推进策略

### 3.1 阶段转化基准

| 阶段转化 | 行业平均转化率 | 平均停留天数 | 关键动作 |
|:---|:---|:---|:---|
| 初步接触 → 需求确认 | 60-70% | 7-14天 | 首次会议/需求调研/痛点确认 |
| 需求确认 → 方案演示 | 50-60% | 14-21天 | 方案定制/POC 准备/技术对接 |
| 方案演示 → 商务谈判 | 40-50% | 21-30天 | 报价/合同条款/商务条件 |
| 商务谈判 → 签约 | 70-80% | 14-30天 | 审批流程/合同签署/付款 |

**停留时间预警：**
- 正常：≤ 基准天数
- 关注：超过基准 1.5 倍
- 预警：超过基准 2 倍

### 3.2 风险信号识别

| 风险类别 | 具体信号 | 严重程度 | 建议动作 |
|:---|:---|:---|:---|
| 活动断档 | >14天无任何互动 | 🔴 高 | 48h 内联系 Champion 确认状态 |
| 关键人变动 | Champion 离职/调岗 | 🔴 高 | 立即识别新 Champion，高层对接 |
| 需求变更 | 范围扩大/缩小/方向变化 | 🟡 中 | 重新评估方案匹配度和报价 |
| 预算冻结 | 财年调整/组织变动 | 🔴 高 | 确认冻结范围和恢复时间 |
| 竞品介入 | 客户提及竞品/邀请竞品演示 | 🟡 中 | 强化差异化，加速推进节奏 |
| 决策延迟 | 原定时间线推迟 | 🟡 中 | 确认延迟原因，调整策略 |

### 3.3 赢单路径推荐

```
基于相似商机的成功模式匹配：
├── 匹配维度：同行业 + 同规模 + 同阶段 + 相似金额
├── 提取模式：已赢商机在该阶段的关键动作序列
├── 推荐逻辑：
│   1. 找到 3-5 个最相似的已赢商机
│   2. 提取它们在当前阶段的共性动作
│   3. 对比当前商机已完成的动作
│   4. 差距即为推荐的下一步
└── 输出格式：具体动作 + 联系谁 + 什么时候 + 预期效果
```

## 四、竞争分析框架

### 4.1 竞争态势判断

```
竞争态势 = f(竞品数量, 客户偏好, 我方差异化)

├── 优势（可加速）：无竞品或客户明确偏好我方
├── 均势（需差异化）：有竞品但无明显偏好
├── 劣势（需策略）：客户倾向竞品，我方需改变游戏规则
└── 未知（需情报）：不清楚竞品参与情况 → 通过 Champion 获取
```

### 4.2 差异化策略选择

| 竞争场景 | 策略 | 关键动作 |
|:---|:---|:---|
| 我方先入 | 设置壁垒 | 深化需求理解，让评估标准向我方倾斜 |
| 竞品先入 | 改变规则 | 引入竞品无法满足的新维度 |
| 同时进入 | 速度+深度 | 更快响应 + 更深的业务理解 |
| 替换竞品 | 降低风险 | 量化切换收益，提供迁移保障 |

5. **决策流程不清晰导致失控**（10%）

# 销售预测（Forecast & Pipeline）— 行业知识指南

> 本文件为 create_skill 提供销售预测领域的专业知识，指导生成具备行业深度的 Pipeline 管理和 Forecast 类技能 Prompt。

---

## 一、业务本质与分析目标

销售预测的终极目标不是"统计 Pipeline 金额"，而是回答三个核心问题：
1. **能完成目标吗？** — 基于当前 Pipeline 的目标达成概率
2. **哪里有问题？** — Pipeline 的结构性缺陷和风险点
3. **怎么补缺口？** — 具体的补救措施和优先级

---

## 二、Pipeline 健康度模型（5 维）

### 2.1 五维评估框架

| 维度 | 核心问题 | 计算方法 | 健康标准 | 预警标准 |
|:---|:---|:---|:---|:---|
| 覆盖率 | Pipeline 够不够？ | Pipeline 总金额 / 季度目标 | ≥ 3x | < 2x |
| 形态 | 分布合理吗？ | 各阶段金额占比 | 漏斗形 | 倒三角/断层 |
| 流速 | 进出平衡吗？ | 新增 vs 关闭 vs 流失 | 净增 > 0 | 流失 > 新增 |
| 质量 | 加权后够吗？ | Σ(金额 × 阶段赢率) / 目标 | ≥ 1.2x | < 1.0x |
| 时效 | 有没有僵尸商机？ | 超期商机金额占比 | < 20% | > 40% |

### 2.2 各维度详细判断标准

#### 覆盖率

```
Pipeline 覆盖率 = 活跃 Pipeline 总金额 / 季度目标

判断逻辑：
├── ≥ 4x：充裕，可选择性推进高质量商机
├── 3-4x：健康，保持当前节奏
├── 2-3x：紧张，需加速新商机开发
├── < 2x：危险，目标达成概率 < 50%
└── < 1x：极度危险，即使全部赢单也无法达标

加权覆盖率（更准确）：
加权覆盖率 = Σ(商机金额 × 阶段赢率) / 季度目标
```

#### 形态（阶段分布）

```
健康的漏斗形态（金额占比参考）：
├── 初步接触：30-40%（上层宽）
├── 需求确认：25-30%
├── 方案演示：15-20%
├── 商务谈判：10-15%（下层窄）
└── 签约阶段：5-10%

异常形态诊断：
├── 倒三角（下层 > 上层）：新商机开发不足，未来会断粮
├── 中间断层：某阶段转化率异常低，需排查原因
├── 底部堆积：大量商机卡在商务谈判，可能是定价/条款问题
└── 顶部堆积：大量商机停在初步接触，推进能力不足
```

#### 流速

```
Pipeline 流速分析（按月/季度）：
├── 新增金额：本期新进入 Pipeline 的商机总金额
├── 关闭金额：本期赢单关闭的金额
├── 流失金额：本期丢单/放弃/过期的金额
└── 净增速 = 新增 - 关闭 - 流失

健康判断：
├── 🟢 健康：净增速 > 0 且 新增 > 流失
├── 🟡 关注：净增速 ≈ 0 或 流失接近新增
└── 🔴 预警：净增速 < 0 或 流失 > 新增
```

#### 质量

```
商机质量评估维度：
├── 金额真实性：预估金额是否有依据（vs 拍脑袋）
├── 阶段准确性：实际推进状态是否匹配标记阶段
├── 时间合理性：预计关闭日期是否现实
└── 活跃度：近 30 天是否有实质性推进活动

低质量商机特征（僵尸商机）：
├── 超过 30 天无任何活动
├── 预计关闭日期已过但未更新
├── 阶段长期未变化（超过基准 2 倍）
└── 无明确的下一步动作
```

## 三、Forecast 三档预测

### 3.1 三档定义

| 档位 | 定义 | 计算方法 | 准确度要求 |
|:---|:---|:---|:---|
| Commit | 销售承诺本季度可关闭的金额 | 销售主观判断 + 历史校准 | 偏差 < 10% |
| Best Case | 乐观情况下可能达到的金额 | Commit + 高概率 Upside | 偏差 < 20% |
| Upside | 有可能但不确定的额外金额 | 活跃商机中概率 30-60% 的部分 | 参考值 |

### 3.2 Forecast 准确度校准

```
个人校准系数 = 历史实际完成 / 历史 Commit 承诺

示例：
├── 张三：历史 Commit 100万，实际完成 120万 → 系数 1.2（偏保守）
├── 李四：历史 Commit 100万，实际完成 80万 → 系数 0.8（偏乐观）
└── 校准后 Commit = 原始 Commit × 个人校准系数

团队 Forecast = Σ(各人校准后 Commit)
```

### 3.3 Forecast 偏差分析

```
偏差率 = |Commit - Actual| / Actual × 100%

判断标准：
├── 优秀：偏差 < 10%
├── 正常：偏差 10-20%
├── 需改进：偏差 20-30%
└── 严重：偏差 > 30%

偏差方向分析：
├── 系统性高估（Commit > Actual）：团队过于乐观，需加强商机审核
└── 系统性低估（Commit < Actual）：团队过于保守，可能错失加速机会
```

---

## 四、目标达成概率模型

```
目标达成概率 = f(加权覆盖率, 历史转化率, 剩余时间)

简化计算：
├── 已赢单金额 / 目标 > 80% → 概率 > 90%（基本达标）
├── (已赢单 + Commit) / 目标 > 100% → 概率 70-90%
├── (已赢单 + Best Case) / 目标 > 100% → 概率 40-70%
├── (已赢单 + 全部 Pipeline × 历史赢率) / 目标 > 100% → 概率 20-40%
└── 即使全部赢单也 < 目标 → 概率 < 20%（需紧急补充 Pipeline）
```

## 五、行业基准参考

| 指标 | ToB SaaS 基准 | 优秀线 | 预警线 |
|:---|:---|:---|:---|
| Pipeline 覆盖率 | 3x | >4x | <2x |
| 加权覆盖率 | 1.2x | >1.5x | <1.0x |
| Forecast 准确度 | 偏差 15% | <10% | >25% |
| 僵尸商机占比 | 15-20% | <10% | >30% |
| 月均新增 Pipeline | 目标的 1x | >1.5x | <0.5x |
| Pipeline 流失率 | 10-15%/月 | <10% | >20% |

## 六、Prompt 设计指导

生成 Pipeline/Forecast 类技能 Prompt 时，必须确保：

1. **不是简单统计**：不能只算 Pipeline 总金额就结束
2. **必须多维评估**：覆盖率+形态+流速+质量+时效，至少 3 个维度
3. **必须有基准对比**：与目标对比、与历史同期对比
4. **必须有预测**：目标达成概率 + 三档 Forecast
5. **必须有诊断**：识别结构性问题（断层/堆积/僵尸）
6. **必须有行动**：缺口多大？怎么补？优先级是什么？

# 销售行为分析（Activity Intelligence）— 行业知识指南

> 本文件为 create_skill 提供销售行为分析领域的专业知识，指导生成具备行业深度的活动分析类技能 Prompt。

---

## 一、业务本质与分析目标

活动分析的终极目标不是"统计活动数量"，而是回答三个核心问题：
1. **谁做得好？** — 识别 Top Sales 的行为模式
2. **谁有问题？** — 发现行为偏差和风险信号
3. **怎么改进？** — 给出具体可模仿的行为建议

---

## 二、活动效能模型（5 维）

### 2.1 五维评估框架

| 维度 | 核心问题 | 关键指标 | 行业基准 |
|:---|:---|:---|:---|
| 量 | 活动够不够？ | 日均活动数/客户覆盖率 | 日均 5-8 次 |
| 质 | 活动有没有用？ | 有效活动占比/高层拜访占比 | 有效率 >60% |
| 节奏 | 跟进及时吗？ | 平均跟进间隔/断档率 | 间隔 <7天 |
| 模式 | 行为模式对吗？ | 与 Top Sales 模式的偏差 | 偏差 <30% |
| 转化 | 活动能变成钱吗？ | 活动→商机→签约转化率 | 活动→商机 >5% |

### 2.2 各维度详细判断标准

#### 量（Activity Volume）

```
评估指标：
├── 日均活动数：所有类型活动的日均次数
├── 客户覆盖率：有活动的客户数 / 负责的客户总数
├── 新客户触达率：首次接触的新客户数 / 月
└── 活动类型分布：电话/邮件/会议/拜访的占比

判断标准：
├── 🟢 充足：日均 ≥8次，覆盖率 >70%
├── 🟡 一般：日均 5-7次，覆盖率 50-70%
├── 🔴 不足：日均 <5次，覆盖率 <50%
└── 注意：量不是越多越好，需结合质来看
```

#### 质（Activity Quality）

```
有效活动定义：
├── 推进了商机阶段（阶段变化在活动后 7 天内发生）
├── 获取了关键信息（决策人/预算/时间线/竞品）
├── 建立了新的联系人关系（新角色覆盖）
├── 获得了客户承诺（下一步/时间/资源）
└── 解决了客户顾虑（技术/商务/风险）

质量评分：
├── 高层拜访占比：VP+ 级别的互动 / 总互动
├── 多线程覆盖：每个商机接触的联系人数
├── 推进关联度：活动后 7 天内有阶段推进的比例
└── 信息获取率：获取关键信息的活动占比
```

#### 节奏（Activity Cadence）

```
跟进节奏评估：
├── 平均跟进间隔：两次活动之间的平均天数
├── 最大间隔：最长的一次断档天数
├── 关键节点覆盖：重要时间点（续约前/季度末/POC 后）是否有活动
└── 响应速度：客户发起后我方响应的平均时间

断档预警规则：
├── 🟢 正常：最近活动 < 7天
├── 🟡 关注：最近活动 7-14天
├── 🔴 预警：最近活动 > 14天
└── ⚫ 失联：最近活动 > 30天

触发条件（任一命中即预警）：
├── 活跃商机的客户 > 7天无活动
├── 本月活动量 < 上月的 50%
├── A 级客户 > 14天无活动
└── 商机在关键阶段（方案演示/商务谈判）> 7天无活动
```

#### 模式（Activity Pattern）

```
Top Sales 行为模式特征：

| 特征 | Top 20% | 普通销售 | 差距倍数 |
|:---|:---|:---|:---|
| 日均活动数 | 8-12 次 | 3-5 次 | 2-3x |
| 高层拜访占比 | > 30% | < 10% | 3x |
| 跟进间隔 | 2-3 天 | 7-14 天 | 3-5x |
| 多线程覆盖 | 3+ 联系人/商机 | 1-2 联系人 | 2x |
| 活动→商机转化 | > 8% | < 3% | 2.5x |
| 首次响应时间 | < 2小时 | > 24小时 | 12x |
| 会议准备度 | 有议程+材料 | 无准备 | — |

模式偏差分析：
├── 计算个人各指标与 Top Sales 均值的偏差
├── 偏差 > 50% 的维度标记为"重点改进项"
├── 偏差 < 20% 的维度标记为"已达标"
└── 输出：个人行为雷达图 vs Top Sales 基准线
```

#### 转化（Activity Conversion）

```
转化漏斗：
活动总量 → 有效活动 → 产生商机 → 推进阶段 → 赢单

各环节转化率基准：
├── 活动 → 有效活动：60-70%
├── 有效活动 → 产生商机：8-12%
├── 商机 → 阶段推进：每 2 周推进 1 阶段
└── 商机 → 赢单：20-25%

转化率异常诊断：
├── 活动多但有效率低 → 活动质量问题（在做无效的事）
├── 有效率高但商机少 → 客户选择问题（找错了人）
├── 商机多但推进慢 → 推进能力问题（不会推）
└── 推进快但赢率低 → 判断力问题（推错了商机）
```

---

## 三、辅导建议生成逻辑

### 3.1 辅导优先级判断

```
辅导 ROI = 预期提升金额 / 辅导投入时间

优先辅导对象：
├── 有潜力但有明确短板（偏差大但态度好）
├── 新人 Ramp 期（入职 3-6 月，行为模式未定型）
├── 业绩下滑者（近 2 月趋势下降 >20%）
└── 不优先：已达标者 / 态度问题者 / 即将离职者
```

### 3.2 辅导建议模板

```
针对不同短板的具体建议（必须可执行，禁止"加强跟进"式模糊建议）：

量不足：
├── "将每日活动目标从 X 提升到 Y，建议增加 Z 类型活动"
├── "每周一规划本周客户覆盖计划，确保 A/B 级客户每周至少 1 次互动"
└── "参考 [Top Sales 名字] 的时间分配：上午电话/下午拜访/晚上邮件"

质不高：
├── "每次拜访前准备 3 个关键问题（决策人/预算/时间线）"
├── "将高层拜访占比从 X% 提升到 30%，每周至少 1 次 VP+ 级别互动"
└── "每次活动后记录获取的关键信息，确保每次互动有信息增量"

节奏差：
├── "将跟进间隔从 X 天缩短到 3 天，设置日历提醒"
├── "对活跃商机设置 48h 跟进规则：任何客户互动后 48h 内必须有下一步"
└── "每周五检查下周的关键节点（续约/POC/评审），提前安排活动"
```

## 五、Prompt 设计指导

生成活动分析类技能 Prompt 时，必须确保：

1. **不是活动计数**：不能只统计"本月活动 X 次"就结束
2. **必须有模式分析**：与 Top Sales 行为模式对比，识别差距

# 客户成功（Customer Success）— 行业知识指南

> 本文件为 create_skill 提供客户成功领域的专业知识，指导生成具备行业深度的客户健康度/续约/流失预测类技能 Prompt。

---

## 一、业务本质与分析目标

客户成功分析的终极目标不是"展示客户状态"，而是回答三个核心问题：
1. **谁会流失？** — 基于多维信号的流失风险预测
2. **为什么会流失？** — 流失根因诊断
3. **怎么挽回/扩展？** — 差异化的干预策略

---

## 二、客户健康度评分模型（5 维）

### 2.1 五维评估框架

| 维度 | 权重 | 核心问题 | 关键指标 |
|:---|:---|:---|:---|
| 产品使用 | 30% | 客户在用吗？用得深吗？ | 登录频次/功能覆盖/使用深度/活跃用户占比 |
| 关系健康 | 25% | 关系稳定吗？满意吗？ | 联系频次/NPS/投诉率/关键人稳定性 |
| 商业健康 | 20% | 会续约吗？会扩展吗？ | 续约意向/扩展信号/付款及时性/合同剩余期限 |
| 支持健康 | 15% | 问题多吗？解决快吗？ | 工单趋势/解决时效/升级频次 |
| 价值实现 | 10% | 客户得到价值了吗？ | KPI 达成度/ROI 验证/成功案例 |

### 2.2 各维度评分标准

#### 产品使用（30%）

```
评分维度（各 25 分，满分 100）：
├── 登录频次：日活/周活趋势
│   25分：DAU/MAU > 60%，且环比增长
│   15分：DAU/MAU 30-60%，稳定
│   8分：DAU/MAU < 30%，或环比下降 >20%
│   0分：近 30 天无登录
├── 功能覆盖度：使用的功能模块数 / 已购功能总数
│   25分：覆盖 > 70%
│   15分：覆盖 40-70%
│   8分：覆盖 < 40%
├── 使用深度：核心功能的使用频次和复杂度
│   25分：使用高级功能（自定义/集成/自动化）
│   15分：使用标准功能
│   8分：仅使用基础功能
└── 活跃用户占比：活跃用户 / 已开通账号
    25分：> 80%
    15分：50-80%
    8分：< 50%
```

#### 关系健康（25%）

```
├── 联系频次：CSM 与客户的互动频率
│   25分：月均 ≥4次，客户主动发起 >30%
│   15分：月均 2-3次
│   8分：月均 <2次
│   0分：超过 30 天无互动
├── NPS/满意度：
│   25分：NPS ≥ 9（推荐者）
│   15分：NPS 7-8（被动者）
│   8分：NPS ≤ 6（贬损者）
├── 投诉率：
│   25分：无投诉
│   15分：有投诉但已解决
│   0分：有未解决投诉或升级投诉
└── 关键人稳定性：
    25分：对接人稳定 >12 月，有多个联系人
    15分：对接人稳定 6-12 月
    8分：近 6 月有对接人变动
    0分：关键对接人离职且无新接口人
```

#### 商业健康（20%）

```
├── 续约意向信号：
│   正面：主动询问续约/提前续约/增加预算
│   中性：正常沟通，无明确信号
│   负面：询问终止条款/要求降价/缩减范围
├── 扩展信号：
│   强信号：新部门使用/增加用户/询问新产品
│   弱信号：使用量接近上限/提出新需求
├── 付款及时性：
│   正常：按时付款
│   关注：延迟 1-15 天
│   预警：延迟 >15 天
└── 合同剩余期限：
    安全：> 6 月
    关注：3-6 月（应启动续约流程）
    紧急：< 3 月（必须已在续约谈判中）
```

## 三、流失风险预测

### 3.1 流失信号体系

|:---|:---|:---|:---|

| 关系信号 | 关键对接人离职 | 极高 | 即时 |
| 关系信号 | 会议取消/推迟 ≥2次 | 中 | 连续 1 月 |
| 商业信号 | 询问合同终止条款 | 极高 | 即时 |
| 商业信号 | 付款延迟 >15天 | 高 | 即时 |

### 3.2 风险等级判定

```
风险等级 = f(信号数量, 信号权重, 合同剩余期限)

🔴 高风险（立即干预）：
├── 任一"极高"权重信号命中
├── 或 3+ 个"高"权重信号同时命中
├── 或 健康度评分 < 40 且合同剩余 < 6 月
└── 行动：48h 内启动挽回计划，升级到管理层

🟡 中风险（主动关注）：
├── 1-2 个"高"权重信号命中
├── 或 健康度评分 40-60
├── 或 健康度连续 2 月下降
└── 行动：1 周内安排深度沟通，制定干预计划

🟢 低风险（正常维护）：
├── 无高权重信号
├── 健康度评分 > 60 且稳定
└── 行动：按正常节奏维护，关注扩展机会
```

│   ├── 第 1 周：[具体动作]
│   ├── 第 2-3 周：[具体动作]
│   └── 第 4 周：[评估效果]
├── 资源：需要谁参与？（CSM/销售/产品/高层）
└── 兜底：如果挽回失败，降级方案是什么？
```

## 二、团队绩效模型（5 维）

### 2.1 五维评估框架

| 维度 | 核心问题 | 关键指标 | 管理动作 |
|:---|:---|:---|:---|
| 目标达成 | 完成得怎么样？ | 完成率/趋势/差距 | 目标调整/资源倾斜 |
| 效率指标 | 效率高不高？ | 人均产出/周期/客单价 | 流程优化/工具赋能 |
| 能力矩阵 | 能力均衡吗？ | 四维能力评估 | 针对性辅导 |
| 资源分配 | 分配合理吗？ | 客户分配/区域覆盖 | 重新分配/补充资源 |
| 辅导优先级 | 该辅导谁？ | ROI 排序 | 辅导计划制定 |

### 2.2 各维度详细评估标准

#### 目标达成

```
评估维度：
├── 绝对达成率：actual / target × 100%
│   🟢 达标：≥ 100%
│   🟡 接近：80-99%
│   🔴 落后：< 80%
├── 趋势分析：近 3 月的达成率变化
│   上升趋势：连续 2 月环比增长 → 正面
│   下降趋势：连续 2 月环比下降 → 预警
│   波动：无明确趋势 → 关注稳定性
├── 差距分析：
│   剩余目标 = target - actual
│   日均需完成 = 剩余目标 / 剩余工作日
│   可行性判断 = 日均需完成 vs 历史日均产出
└── 同比分析：
    vs 去年同期 / vs 团队均值 / vs 个人历史最佳
```

#### 效率指标

| 指标 | 计算方法 | 行业基准 | 优秀线 | 预警线 |

| 客单价 | 赢单金额 / 赢单数 | 行业相关 | 同比增长 | 同比下降 |
| 活动转化率 | 赢单数 / 活动总数 | 3-5% | >7% | <2% |
| 商机创建率 | 新商机数 / 月 | 5-8个/人 | >10个 | <3个 |

## 四、辅导优先级算法

### 4.1 ROI 排序逻辑

```
辅导 ROI = 预期提升金额 / (辅导难度 × 时间投入)

计算步骤：
1. 识别每人的"最大短板维度"（能力矩阵中最低分的维度）
2. 估算该短板提升到合格线（70分）的预期收入增量
   增量 = (70 - 当前分) / 100 × 该维度对应的历史收入贡献
3. 评估辅导难度（1-5 分）：
   1分：态度好+有基础+只需方法指导
   3分：需要持续跟进+实战演练
   5分：态度问题+基础薄弱+需要大量时间
4. ROI = 预期增量 / (难度 × 预计辅导周数)
5. 按 ROI 降序排列 → 辅导优先级
```

### 4.2 辅导类型匹配

| 短板维度 | 辅导方式 | 具体内容 | 预期见效时间 |
|:---|:---|:---|:---|
| 开拓弱 | 陪访+话术训练 | 每周 1 次陪同拜访，录音复盘 | 4-6 周 |
| 推进弱 | 案例复盘+方法论 | 每周复盘 1 个商机，MEDDIC 训练 | 6-8 周 |
| 关闭弱 | 谈判技巧+高层陪同 | 模拟谈判+实战中高层支持 | 4-6 周 |
| 维护弱 | 流程建设+模板 | QBR 模板/预警机制/续约 SOP | 8-12 周 |

### 5.1 评估维度

| 评估维度 | 计算方法 | 健康标准 | 预警标准 |

### 5.2 常见资源分配问题

```
问题诊断：
├── 大客户过度集中：1-2 人负责 >50% 大客户 → 风险集中
├── 新人无客户：新人 Ramp 期无足够客户练手 → 成长慢
├── 能力错配：初级销售负责复杂大客户 → 丢单率高
├── 区域空白：部分区域无人覆盖 → 市场机会流失
└── 忙闲不均：部分人超负荷，部分人闲置 → 效率低

调整建议：
├── 大客户分散：每人负责大客户不超过总数的 30%
├── 新人培养：分配 B/C 级客户 + 导师陪同 A 级客户
├── 能力匹配：复杂客户配资深销售，标准客户配中级
├── 区域补充：招聘/调配覆盖空白区域
└── 负载均衡：按客户数 × 难度系数均衡分配
```

### 框架 A: 描述性分析（What happened?）

**步骤链路：** 数据查询 → 统计汇总 → 趋势识别 → 异常标注 → 可视化呈现
**适用场景：** 现状报告、数据看板、定期汇总、KPI 监控
**信号词：** 统计、汇总、报表、看板、多少、列出、概览、现状、分布、排名

**工具 Pipeline：**
```
query_data(获取明细) → analyze_data(聚合统计) → analyze_data(分组对比) → [file_upload(导出)]
```

**Prompt 构建要求：**
1. 明确时间范围和对比基准：
   - 环比（本期 vs 上期）
   - 同比（本期 vs 去年同期）
   - 目标值对比（实际 vs 计划）
   - 选择依据：周期性业务用同比，趋势性业务用环比
2. 异常值判定规则（必须写入 Prompt）：
   - 绝对阈值：业务有明确标准时使用（如"转化率<5%为异常"）
   - 相对阈值：无明确标准时使用（如"偏离均值>30%为异常"）
   - 选择依据：有行业基准→绝对阈值；无基准→相对阈值
   - 样本量<10 时：不做异常判定，标注"样本量不足，仅供参考"
3. 趋势方向判断逻辑：
   - 连续 3 期同方向变化 → 确认趋势（🟢高置信度）
   - 连续 2 期同方向变化 → 疑似趋势（🟡中置信度）
   - 单期变化 → 波动，不判定趋势（🔴低置信度）

**完整示例（描述性分析技能）：**

```
用户需求："帮我看看本月各渠道的线索转化情况"

生成的 Prompt 关键片段：
---
## 步骤 1: 数据采集
query_data(entity_api_key="lead", filters={created_at: "本月"}, 
           fields=["source_channel", "status", "convert_time", "owner"])

## 步骤 2: 渠道转化率分析
analyze_data(entity_api_key="lead", 
             metrics=[{field:"id", function:"count"}, {field:"convert_time", function:"count"}],
             group_by=["source_channel"], filters={created_at: "本月"})
- 各渠道线索总量 [来源:analyze_data]
- 各渠道转化率 = 已转化数/总量 [来源:计算]
- 环比变化 = (本月转化率 - 上月转化率) / 上月转化率 [来源:计算]
- 异常判定：转化率偏离整体均值 >30% 标注为异常渠道

## 步骤 3: 趋势与异常
- 连续 3 月下降的渠道 → 标注"持续下降趋势" 🟢高置信度

### 框架 B: 诊断性分析（Why did it happen?）

**步骤链路：** 现象描述 → 维度拆解 → 对比分析 → 归因定位 → 根因验证
**适用场景：** 问题排查、下降原因分析、异常诊断、差距分析
**信号词：** 为什么、原因、下降、异常、问题、差距、对比、诊断、根因

**工具 Pipeline：**
```
analyze_data(确认现象) → analyze_data(分组下钻) → query_data(明细验证) → [web_search(外部因素)]
```

**Prompt 构建要求：**
1. 维度拆解策略（逐层下钻，每层选最大偏差维度）：
   - 第一层：时间维度（哪个时段开始异常？）
   - 第二层：组织维度（哪个团队/区域？）
   - 第三层：人员维度（哪些个体？）
   - 第四层：行为维度（哪个环节/动作？）
   - 下钻规则：每层选偏差最大的分组继续下钻，最多 3 层
2. 对比基准选择逻辑：
   - 与自身历史对比 → 识别"变差了"
   - 与同行/团队均值对比 → 识别"本来就差"
   - 与目标值对比 → 识别"差距有多大"
   - 三种对比得出不同结论，Prompt 中必须明确用哪种
3. 归因置信度标注：
   - 单因素归因（仅一个维度异常）→ 🟢高置信度
   - 多因素交叉（2-3 个维度同时异常）→ 🟡中置信度，列出各因素贡献度
   - 无法定位（各维度均匀下降）→ 🔴低置信度，建议"可能是外部因素，需人工确认"

**完整示例（诊断性分析技能）：**

### 框架 C: 预测性分析（What will happen?）

**步骤链路：** 历史模式提取 → 特征识别 → 趋势外推 → 置信度标注 → 风险预警
**适用场景：** 趋势预测、风险预警、目标预判、容量规划
**信号词：** 预测、趋势、预警、风险、下个月、未来、可能、预判、达成率

**工具 Pipeline：**
```
query_data(历史数据) → analyze_data(趋势统计) → execute_code(建模计算) → [web_search(外部信号)]
```

**Prompt 构建要求：**
1. 预测方法选择（根据数据量和复杂度）：
   - 数据 <6 期：简单外推（最近 3 期均值），标注 🔴低置信度
   - 数据 6-12 期：加权移动平均（近期权重更高），标注 🟡中置信度
   - 数据 >12 期：线性回归/季节性分解（execute_code），标注 🟢高置信度
   - 选择依据必须写入 Prompt，让 LLM 根据实际数据量动态选择
2. 置信区间操作定义：
   - 🟢高置信度：历史数据充足（>12期）+ 趋势稳定（波动率<15%）+ 无重大外部变化
   - 🟡中置信度：数据量中等（6-12期）或 趋势有波动（波动率 15-30%）
   - 🔴低置信度：数据不足（<6期）或 趋势剧烈波动（波动率>30%）或 存在已知外部干扰
3. 风险预警规则：
   - 预测值 vs 目标值差距 >20% → 红色预警
   - 预测值 vs 目标值差距 10-20% → 黄色预警
   - 预测值 vs 目标值差距 <10% → 绿色（正常）
4. 关键假设声明（必须包含）：
   - "本预测基于以下假设：{假设1}、{假设2}"
   - "如果 {风险因素} 发生，预测结果可能偏差 ±X%"
   - 明确标注"预测≠事实"，所有预测数据标注 [来源:推算]

```

### 框架 D: 处方性分析（What should we do?）

**步骤链路：** 目标定义 → 现状评估 → 差距识别 → 方案生成 → 优先级排序 → 行动计划
**适用场景：** 行动建议、策略推荐、资源优化、改进方案
**信号词：** 建议、怎么做、优化、改进、策略、方案、行动、下一步、提升

**工具 Pipeline：**
```
query_data(现状) → analyze_data(差距量化) → knowledge_search(最佳实践) → [web_search(行业方案)] → ask_user(确认优先级)
```

**Prompt 构建要求：**
1. 建议生成规则（每条建议必须包含 4 要素）：
   - 依据：基于哪个数据/差距得出（标注 [来源:xxx]）
   - 行动：具体做什么（可执行，非空泛建议）
   - 预期效果：量化估算（如"预计提升 X%"，标注 [来源:推算]）
   - 时间线：本周/2 周内/1 个月内/下季度
2. 优先级排序标准（2×2 矩阵）：
   - 影响大 + 实施易 → P0（立即执行）
   - 影响大 + 实施难 → P1（规划执行）
   - 影响小 + 实施易 → P2（顺手做）
   - 影响小 + 实施难 → P3（暂缓/放弃）
   - 影响大小判断：对核心 KPI 的贡献度
   - 实施难易判断：所需资源/时间/跨部门协调程度
3. 建议数量控制：
   - P0 建议：最多 3 条（聚焦）
   - P1 建议：最多 3 条
   - P2/P3：可选，最多各 2 条
   - 总计不超过 8 条建议，避免信息过载

**完整示例（处方性分析技能）：**

## 三、分析维度选择方法论

当需要为技能选择 3-4 个核心分析维度时，使用以下方法：

### 维度选择决策流程

```
Step 1: 列出所有可能的分析维度（通常 6-10 个）
Step 2: 用以下 3 个标准打分（每项 1-3 分）：
  - 数据可得性：CRM 中是否有对应字段？（3=直接可查, 2=需计算, 1=无数据）
  - 决策影响力：对用户决策的帮助程度？（3=直接影响行动, 2=辅助判断, 1=仅供了解）
  - 差异化价值：是否提供非显而易见的洞察？（3=深度洞察, 2=常规分析, 1=简单统计）
Step 3: 总分排序，选 Top 3-4 个维度
Step 4: 验证选中维度之间有逻辑关联（能形成分析链路）
```

### 维度选择反模式（禁止）

| 反模式 | 问题 | 正确做法 |
|:---|:---|:---|
| 选 8-10 个维度浅尝 | LLM 注意力分散，每个维度只有 1-2 句 | 选 3-4 个维度深入 |
| 选无数据支撑的维度 | 导致幻觉或空洞分析 | 先 query_schema 确认字段存在 |
| 选相互独立的维度 | 无法形成洞察链路 | 确保维度间有因果/关联关系 |
| 选用户自己能看到的维度 | 无增量价值 | 选需要计算/对比/推断的维度 |

## 四、跨域组合指导

当用户需求涉及多个业务域时：

### 跨域组合规则

1. **识别主域和辅域**：
   - 主域 = 用户最关心的核心问题（分配 60-70% 分析深度）
   - 辅域 = 支撑主域判断的补充信息（分配 30-40% 分析深度）
   - 判断依据：用户语句中的主语/动词指向哪个域

2. **主域使用完整分析体系**（加载对应域文件），辅域只取关键指标

3. **在 Prompt 中明确标注**哪些维度来自主域、哪些来自辅域

4. **辅域数据作为"补充证据"**而非"独立分析"

### 跨域组合示例

| 用户需求 | 主域 | 辅域 | 组合方式 |
|:---|:---|:---|:---|
| "客户扩展机会分析" | account.md（客户画像） | opportunity（只取赢率+渗透度） | 客户 360 + 商机渗透率 |
| "团队 Pipeline 健康度" | team.md（绩效矩阵） | forecast（只取覆盖率） | 人员绩效 + Pipeline 指标 |
| "活动对商机的影响" | activity.md（效能模型） | opportunity（只取阶段推进） | 活动量 → 商机推进关联 |
| "客户+商机+活动综合" | generic.md（本文件） | 各域取 1-2 个核心指标 | 通用框架 + 多域关键指标 |

### 跨域数据关联方法

```
关联路径（通过 entity_link 或共同字段）：
- 客户 → 商机：account_api_key 关联
- 商机 → 活动：opportunity_api_key 关联
- 客户 → 活动：account_api_key 关联
- 人员 → 商机/活动：owner 字段关联
- 团队 → 人员：department 字段关联

Prompt 中必须明确关联路径，禁止假设关联关系存在。
先用 query_schema(query_type="entity_links") 确认关联关系。
```

## 五、非分析类技能设计指导

### 5.1 数据导出类

**设计要点：**
- 明确导出格式（Markdown 表格 / JSON / CSV）
- 明确字段选择逻辑（全量 or 用户指定，通过 arguments 参数化）
- 明确筛选条件参数化（{时间范围}、{筛选条件}）
- 大数据量处理策略：
  - 记录数 <100：直接展示 Markdown 表格
  - 记录数 100-1000：file_upload 生成 CSV 下载链接
  - 记录数 >1000：分页查询 + file_upload，提示用户"数据量较大，已生成文件"
- 输出方式选择：直接展示（小量）/ file_upload 文件下载（大量）

**工具选择：** `query_data` + `file_upload`（大数据量时）+ `ask_user`（确认导出范围）

**Prompt 骨架：**

- 先 count 确认数据量

- <100 条：Markdown 表格直接展示

## 步骤 4: 数据完整性声明
- "共导出 X 条记录，时间范围：{range}，筛选条件：{filters}"
```

### 5.2 报告生成类

**设计要点：**
- 明确报告结构（章节划分、每章数据源）
- 明确受众（给谁看决定详略和术语）：
  - 给高管：结论先行，数据精简，重点是趋势和决策建议
  - 给经理：数据详实，含对比分析，重点是团队表现和行动项
  - 给一线：操作导向，含具体客户/商机列表，重点是下一步动作
- 明确时间范围参数化（{报告周期}）
- 报告结构模板：
  - 📊 摘要（3-5 句话概括核心发现）
  - 📈 数据部分（表格/指标，每个数据标注来源）
  - 🔍 分析部分（趋势/异常/对比）
  - 💡 建议部分（可行动的下一步）
  - ⚠️ 局限性声明（数据范围/缺失/假设）

**工具选择：** `query_data` + `analyze_data` + `knowledge_search`（模板/历史报告）+ `file_upload`（长报告）

**Prompt 骨架：**
```

## 步骤 2: 各章节分析
- 每章遵循"数据→指标→判断"链路
- 每个数据点标注 [来源:query_data/analyze_data/计算]
## 步骤 3: 综合摘要（最后写，基于各章结论）
## 步骤 4: 格式化输出
- 按受众调整详略
- 末尾附数据局限性声明
```

### 5.3 流程自动化类

**设计要点：**
- 明确触发条件（参数化）
- 明确执行步骤（有序、每步可验证）
- 涉及写操作必须配合 ask_user 确认
- 明确异常处理策略：
  - 查询失败 → 重试一次，仍失败则中止并告知用户
  - 数据校验失败 → 中止，列出校验失败项，ask_user 确认是否继续
  - 写入失败 → 中止，不做部分写入，告知用户失败原因
- 明确幂等性（重复执行不产生副作用）：
  - 写入前先查询是否已存在
  - 更新操作使用条件更新（where 条件包含预期旧值）

**工具选择：** `query_data`（查询现状）+ `modify_data`（写入）+ `ask_user`（确认，必须）+ `ask_clarification`（参数不全时）

**Prompt 骨架：**
```

- query_data 确认目标数据存在
- 检查是否已执行过（幂等性）
## 步骤 3: 执行预览
- 列出将要执行的操作（不执行）
- ask_user(interrupt_type="confirm") 确认
## 步骤 4: 执行
- modify_data 逐条执行
- 每步记录结果
## 步骤 5: 结果汇报
- 成功/失败数量
- 失败项明细
```

- 成功/失败数量
- 失败项明细

### 5B.1 CRM 核心方法论库

#### 销售管理方法论

|:---|:---|:---|:---|

### 5B.4 专业性注入规则

```
规则 1: 方法论匹配
  当技能涉及以下关键词时，必须注入对应方法论到 Prompt 中：
  - "赢率/评估/资质" → MEDDIC 或 BANT
  - "漏斗/转化/阶段" → 销售漏斗理论
  - "健康度/流失/续约" → Health Score 模型
  - "预测/Pipeline/覆盖" → Pipeline Coverage + Forecast 三档
  - "绩效/辅导/团队" → 绩效九宫格 + Activity-Based Coaching
  - "效率/速度/周期" → Sales Velocity

规则 2: 基准数据注入
  当 Prompt 中有"判断"或"评估"步骤时：
  - 优先指导 LLM 用客户历史数据作为基准
  - 无历史数据时，注入行业基准值 + 标注 [来源:行业基准]
  - 必须在 Prompt 中写明："如果客户有自定义基准，以客户基准为准"

规则 3: 维度选择优先级
  从维度池中选择时，优先选择：
  - 有明确行业方法论支撑的维度（如 MEDDIC 六维度）
  - 有行业基准可对比的维度（如赢率、续约率）
  - 能形成"数据→指标→基准→判断→行动"完整链路的维度

规则 4: 专业术语使用
  生成的 Prompt 中应使用 CRM 行业标准术语：
  - Pipeline（而非"销售管道"）
  - Quota（而非"销售目标"）
  - ACV/ARR（而非"年度合同额"）
  - MQL/SQL（而非"营销线索/销售线索"）
  - Churn Rate（而非"流失率"，或中英并用）
  - NRR/GRR（而非"净收入留存"，或中英并用）
  但必须在 Prompt 的角色定义中注明："输出时使用中文为主，关键指标保留英文缩写并附中文解释"

规则 5: 分析深度保障
  每个分析维度必须达到以下深度（不能停留在"统计数字"层面）：
  - Level 1 统计：是什么数字？（描述性）
  - Level 2 对比：比基准好还是差？差多少？（诊断性）
  - Level 3 归因：为什么好/差？哪个因素贡献最大？（归因性）
  - Level 4 行动：应该做什么？优先级如何？（处方性）
  最低要求：达到 Level 2（有对比有判断）
  专业要求：达到 Level 3-4（有归因有建议）
```

### 5B.5 专业性自检清单

生成技能 Prompt 后，用以下清单验证专业性：

```
□ 是否引用了至少 1 个行业方法论？（非自创框架）
□ 是否有明确的判断基准？（行业基准或历史基准，非拍脑袋）
□ 分析维度是否来自维度池？（非随意发明的维度）
□ 每个维度是否达到 Level 2+ 深度？（有对比有判断，非纯统计）

□ 建议是否具体可执行？（"优化跟进节奏，将间隔从7天缩短到3天" vs "加强跟进"）
□ 是否标注了基准来源？（[来源:行业基准] 或 [来源:历史数据]）
□ 是否考虑了数据局限性？（哪些维度可能无数据）
```

### 工具选择原则

```
核心原则：工具越少越精确，LLM 越不容易走偏。

选择规则：
1. 只读分析类 → query_data + analyze_data（基础，几乎必选）
2. 需要外部信息 → 追加 web_search
3. 需要行业知识/最佳实践 → 追加 knowledge_search
4. 需要域专家知识 → 追加 read_skill_resource
5. 需要复杂计算/建模 → 追加 execute_code（+ write_file + read_file）
6. 需要安装依赖/运行脚本 → 追加 terminal
7. 涉及数据写入 → 追加 modify_data + ask_user（必须配对）
8. 需要导出文件 → 追加 file_upload（+ write_file）
9. 参数可能不完整 → 追加 ask_clarification
10. 需要用户决策/确认 → 追加 ask_user

禁止组合：
- ❌ modify_data 不配 ask_user → 写操作必须有确认
- ❌ browse_metamodel/query_metadata 加到业务分析技能 → 那是元数据管理专用
- ❌ manage_skill 加到普通技能 → 那是 create_skill 专用
- ❌ 无脑全选所有工具 → 增加 LLM 决策负担，降低输出质量
- ❌ execute_code 不配 query_data → 没有数据输入的计算无意义

推荐数量：
- 简单技能：2-3 个工具
- 中等技能：3-5 个工具
- 复杂技能：5-8 个工具
- 超过 8 个工具 → 考虑拆分为多个技能
```

## 八、置信度标注操作规范

### 置信度等级定义

| 等级 | 符号 | 判定条件（满足全部） | 典型场景 |
|:---|:---|:---|:---|
| 高 | 🟢 | 数据覆盖率>90% + 样本量>30 + 数据源一致 + 结论方向明确 | 基于完整数据的统计结论 |
| 中 | 🟡 | 覆盖率60-90% 或 样本量10-30 或 多源基本一致 或 需要推算 | 基于部分数据的分析判断 |
| 低 | 🔴 | 覆盖率<60% 或 样本量<10 或 数据源矛盾 或 纯推算 | 预测、外推、假设性结论 |

### 置信度标注规则

```
规则 1: 每个核心结论必须标注置信度（非核心的辅助说明可省略）
规则 2: 标注格式统一为 "[来源:xxx] 🟢/🟡/🔴"
规则 3: 如果一个结论依赖多个数据源，取最低置信度
规则 4: 推算/预测类结论最高为 🟡（除非有 >12 期历史数据验证）
规则 5: 外部数据（web_search）最高为 🟡（无法验证准确性）
规则 6: 置信度为 🔴 的结论必须附加"建议人工确认"
```

### 防止置信度膨胀（Anti-pattern）

```
❌ 错误：所有结论都标 🟢（讨好用户倾向）
✅ 正确：严格按条件判定，宁可标低不标高

❌ 错误：只标注高置信度的结论，低置信度的不标
✅ 正确：所有核心结论都标注，低置信度更需要标注

❌ 错误：置信度标注但不解释原因
✅ 正确：🔴低置信度时附加原因（如"样本量仅 5 条"）
```

## 九、异常处理完整规范

### 异常分类与处理策略

| 异常类型 | 识别方式 | 处理策略 | Prompt 中的表述 |
|:---|:---|:---|:---|
| 数据缺失 | query_data 返回空/字段为 null | 跳过该维度，标注"无数据" | "该维度无数据，无法分析" |
| 查询失败 | query_data 返回错误 | 重试 1 次，仍失败则跳过 | "查询异常，该部分暂无法分析" |
| 数据过期 | 最后更新时间 >7 天 | 继续分析但标注时效性 | "数据最后更新于 {date}，可能不是最新" |
| 权限不足 | 返回 403/permission denied | 中止该部分，告知用户 | "无权访问该数据，请联系管理员" |
| 数据量过大 | 单次返回 >1000 条 | 分页处理或缩小范围 | 自动分页，不需要告知用户 |
| 结果矛盾 | 两个数据源数值冲突 | 列出两方数据，标注冲突 | "数据矛盾：A 显示 X，B 显示 Y，需人工确认" |
| 样本量不足 | 记录数 <10 | 降级分析，标注局限性 | "样本量仅 {n} 条，结论仅供参考 🔴" |
| 超出能力边界 | 需求涉及系统不支持的功能 | 明确告知，建议替代方案 | "当前不支持 {xxx}，建议 {替代方案}" |
| 参数歧义 | 用户输入可多种理解 | ask_clarification 追问 | 中断追问，不猜测 |
| 计算溢出 | execute_code 超时/报错 | 简化计算逻辑，重试 | "计算复杂度过高，已简化处理" |

### 降级策略

```
完整分析（理想状态）
  ↓ 数据部分缺失
有限分析（标注缺失维度，其余正常分析）
  ↓ 数据严重缺失（>50% 维度无数据）
最小分析（只分析有数据的维度，明确告知局限性）
  ↓ 完全无数据
中止分析（告知用户"数据不足，无法完成分析"，建议数据补充方向）
```
