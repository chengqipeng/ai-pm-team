NeoAgent2.0 与 AgentOS 对接架构设计

NeoAgent2.0（企业级 CRM Agent 大脑）× AgentOS / CloudAgent（云端沙箱运行时）对接方案

一、两系统架构对比

NeoAgent2.0（企业级 CRM Agent 系统）
面向 2B CRM SaaS 的智能中台：Agent 框架（Tool/Skill/Middleware/MCP/记忆/反思）+ 知识库 + 提示词模板。
底层由大模型网关 + 基础原子能力平台支撑，通过 AG-UI/A2UI 协议与前端交互。

本质：智能决策层 — 决定做什么、怎么做
AgentOS / CloudAgent（云端沙箱运行时）
腾讯云提供的企业级 Agent 运行时平台：Runtime 沙箱（容器级隔离）+ ACP 通信 + Checkpoint/Version 快照 + Manifest 配置注入。
通过 API 创建和管理 AI Agent 沙箱，支持 Session 幂等、断线重连、Webhook 事件。

本质：运行时基础设施 — 保证安全运行、可管理、可恢复
关键关系：NeoAgent2.0 是 AgentOS 的"被托管者"，AgentOS 是 NeoAgent2.0 的"运行时底座"。NeoAgent 提供 Agent 智能内核（推理/记忆/编排），AgentOS 提供沙箱隔离、状态持久化、生命周期管理。两者通过 ACP 协议 + REST API + Webhook 解耦协作。

2.1 关键问题分析

问题分析结论
NeoAgent 的 Skill 如何放到 AgentOS？ 通过 Manifest skills[] 声明注入。NeoAgent 将 Skill 的 prompt（SOP 指令）+ allowed_tools 列表转换为 AgentOS Manifest 格式，在创建 Runtime 时注入。Skill 的执行逻辑由沙箱内 Agent 根据 prompt 驱动。 Manifest skills[] 注入
Skill prompt 即 SOP，沙箱 Agent 按 prompt 执行
Skill 中涉及 NeoAgent 内部 Tool（如 query_data），AgentOS 如何执行？ AgentOS 沙箱无法直接调用 NeoAgent 内网 Tool。解决方式：NeoAgent 将这些 Tool 暴露为 MCP Server，在 Manifest mcp{} 中配置指向该 Server。沙箱内 Agent 执行 Skill 时，通过 MCP 协议回调 NeoAgent 侧执行。 MCP 回调
NeoAgent 暴露 MCP Server，沙箱通过 mcp{} 调用
Skill 中的基础 Tool 在两侧都存在（如 web_search），Skill 应该调用哪侧的？ 这是核心设计问题。当 Skill 被放到 AgentOS 沙箱执行时，Skill 内引用的 Tool（如 web_search）在 NeoAgent 和 AgentOS 中都有相同实现。需要明确一个原则：Skill 在哪里执行，就调用哪里的 Tool。

• Skill 放到 AgentOS 执行 → 沙箱内 Agent 调用沙箱本地的 web_search
• 如果沙箱内没有该 Tool 的实现 → 通过 MCP 回调 NeoAgent 侧的

设计疑问：同一个 Skill 在 NeoAgent 本地执行和在 AgentOS 沙箱执行时，调用的 Tool 实例不同（虽然能力相同），可能导致行为差异（如网络环境不同、权限不同、返回格式差异）。这要求 Skill 设计时必须明确其执行环境归属，不能"两边都能跑"。		 需要明确设计
原则：Skill 绑定执行环境，不做跨平台复用；基础 Tool 各自实现，Skill 只调用所在环境的 Tool
总结：Skill 通过 Manifest 注入沙箱；NeoAgent 专属 Tool 通过 MCP 回调解决；基础 Tool 两侧各有实现，Skill 必须绑定执行环境（放在哪侧就调用哪侧的 Tool），不做跨平台复用设计。
