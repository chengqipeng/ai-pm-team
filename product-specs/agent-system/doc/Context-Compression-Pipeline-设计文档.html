一、管线总览

ContentRouter 根据输入内容类型自动路由到最适合的压缩引擎，每种引擎针对特定数据结构采用最优策略：

JSON 数组/对象 → SmartCrusher 结构感知压缩，保留异常+统计摘要
代码文件 → CodeCompressor tree-sitter AST 解析，保留签名/类型
日志/终端输出 → LogCompressor 模式识别去重，保留错误行+统计
搜索结果 → SearchCompressor BM25 相关性评分裁剪
HTML 页面 → HTMLExtractor 去 boilerplate，提取正文内容
自然语言文本 → LightKompress TF-IDF + 多维评分 + 实体保护

二、各引擎详细规格

引擎输入类型核心算法压缩率延迟依赖
SmartCrusher JSON 数组/对象 保留异常记录 + 统计摘要 + 首尾采样 70-92% <5ms 无
CodeCompressor Python/JS/Go/Rust/Java/C++ tree-sitter AST → 保留 import + 签名 + 类型，删函数体 50-80% 5-15ms tree-sitter
LogCompressor 日志/终端输出 重复模式折叠(×N) + 保留 ERROR/异常行 + 统计摘要 60-90% <3ms 无
SearchCompressor 搜索/RAG 结果列表 BM25 + embedding 相关性评分 → 保留 TOP-K 高相关结果 40-70% <5ms 无
HTMLExtractor HTML 页面/富文本 去 nav/footer/ads/script → 提取正文 + 标题 + 表格 60-90% <10ms 无
LightKompress 自然语言文本（中/英/混合） 六维评分(TF-IDF+位置+实体+上下文+密度+技术) + 实体保护 + 句内精简 15-62% 4-20ms jieba

三、各引擎工作原理

📦 SmartCrusher
  • 检测 JSON 数组长度，若 > 阈值则裁剪
  • 保留策略：错误记录(100%) + 统计异常 + 匹配用户查询的记录(BM25)
  • 首尾各保留 N 条 + 中间统计摘要
  • 输出保证 JSON 结构有效
  • 例：500条记录 → "返回20条(含3条异常)，统计：总金额¥2.3M"
💻 CodeCompressor
  • 用 tree-sitter 解析为 AST
  • 保留：import/require + class/function 签名 + 类型注解
  • 删除：函数体实现 + 注释 + 空行
  • 输出保证语法有效（AST 重建）
  • 支持 Python/JS/TS/Go/Rust/Java/C++
📋 LogCompressor
  • 模式识别：相似日志行归组(Levenshtein)
  • 折叠重复："[×200] INFO: health check passed"
  • 优先保留：ERROR/FATAL/Exception 行
  • 尾部保留最近 N 行（通常含最终结果）
  • 输出统计："500行→12行(8 ERROR, 4 关键)"
🔍 SearchCompressor
  • 对搜索结果列表按与用户 query 的相关性排序
  • BM25 词频匹配 + 位置权重
  • 保留 TOP-K 最相关结果
  • 长结果片段做摘要截取(保留匹配上下文)
  • 去除重复/近似结果
🌐 HTMLExtractor
  • DOM 解析 → 识别正文区域(content heuristic)
  • 去除：导航栏/侧边栏/页脚/广告/脚本/样式
  • 保留：标题(h1-h3) + 正文段落 + 表格 + 列表
  • 提取 meta 信息(title/description)
  • 输出纯文本(可选 markdown 格式)
✂️ LightKompress
  • 三层分句(标点→逗号→窗口)处理任意文本
  • 六维度评分：TF-IDF + 位置 + 实体 + 上下文 + 信息密度 + 技术标识符
  • 13条正则硬保护关键数据(数字/金额/日期/URL...)
  • 动态保留比例(根据实体密度自适应)
  • 句内精简(子句切分+填充短语删除)

四、阶段 2: 智能分句（三级降级策略）

Level 1: 标准标点分句

按 。！？；\n 和英文 .!? 后空格分割，过滤 <5 字符的碎片

正则: ([。！？；\n]|(?<=[.!?])\s+)

退出条件：分句结果 > 2 句 → 使用此结果

Level 2: 逗号降级分句

按 ，,、 分割，合并分隔符到前一个片段

触发: Level 1 结果 ≤ 2 句 且 平均句长 > 80 字符

退出条件：分句结果 > 2 句 → 使用此结果

Level 3: 固定窗口分句

在 jieba 词边界处按 ~60 字符窗口切割，最后片段 <15 字符则合并到上一段

触发: Level 2 后仍 ≤ 2 句 且 文本长度 > 150 字符

退出：切割后 > 2 段 → 使用；否则返回整个文本作为单句

设计意图：L1 处理标准文本，L2 处理逗号分隔的无句号长段落，L3 兜底处理 OCR/API 返回的无标点纯文本块。

LightKompress — 阶段 3: 六维度评分体系

对每个句子计算加权重要性分数，决定保留优先级

评分总览

维度权重计算方式设计目的
1. TF-IDF 关键词×3.0Σ(词TF-IDF权重) / √(词数+1)识别主题核心句
2. 位置加权+2.5/1.8/1.5/1.0首句/次句/末句/前4句 固定加分保留开头结论和总结
3. 实体密度×4.0 + base 3.013条正则命中数 × 4 + 3保护关键数据不被删除
4. 上下文相关×3.0句子与用户问题的内容词交集大小保留与当前问题相关的内容
5. 信息密度×2.0实词占比 = 非停用词/总词数过滤废话/过渡句
6. 技术标识符×2.0 + base 2.0技术模式命中数 × 2 + 2保护代码/配置/协议等技术细节

维度 1: TF-IDF 关键词密度

算法步骤

# 1. 对全文提取 TOP50 关键词及其 TF-IDF 权重
keywords = jieba.analyse.extract_tags(full_text, topK=50, withWeight=True)
keyword_weights = {word: weight for word, weight in keywords}

# 2. 对每个句子计算关键词得分
for i, sent in enumerate(sentences):
    words = jieba.cut(sent)
    kw_score = sum(keyword_weights.get(w, 0) for w in words)
    scores[i] += (kw_score / math.sqrt(len(words) + 1)) * 3.0
公式: score_tfidf[i] = ( Σ TF-IDF(word) for word in sentence ) / √(|words| + 1) × 3.0

除以 √(词数+1) 的目的：归一化，避免长句因词多而占优

维度 2: 位置加权

固定加分规则

位置加分理由
首句 (i=0)+2.5通常包含核心结论或主题句
次句 (i=1)+1.8对首句的补充说明，常含关键数据
末句 (i=n-1)+1.5结论/建议/总结句
前4句 (i≤3)+1.0前置信息通常较重要

维度 4: 上下文相关性

算法：句子与用户问题的词交集

# 用户问题分词 → 去停用词 → 取长度>1的词
context_words = set(jieba.cut(context)) - STOP_WORDS
context_words = {w for w in context_words if len(w) > 1}

# 计算每个句子与问题的词重叠数
for i, sent in enumerate(sentences):
    sent_words = set(jieba.cut(sent))
    overlap = len(context_words & sent_words)
    if overlap:
        scores[i] += overlap * 3.0
score_context[i] = |context_words ∩ sent_words| × 3.0

当 context="" 时此维度不生效。当用户问"为什么超时"时，含"超时""错误"的句子获得加分。

维度 5: 信息密度

算法：实词占比

# 实词 = 非停用词 且 长度>1 的词
content_words = [w for w in words
                 if w.strip() and len(w.strip()) > 1
                 and w not in STOP_WORDS]
density = len(content_words) / (len(words) + 1)
scores[i] += density * 2.0
score_density[i] = |content_words| / (|words| + 1) × 2.0

废话/过渡句中停用词占比高、实词密度低，得分自然低于信息密集句。

LightKompress — 阶段 4: 动态选句

四条路径协同：硬约束保护 + 冗余检测 + 自适应target + 贪心选句

路径 A: 硬约束保护（不可删句子）

路径 A — 实体保护前置

规则：含任意正则实体命中的句子，标记为 protected，无条件保留

for i, sent in enumerate(sentences):
    if any(pattern.search(sent) for pattern in MUST_KEEP_PATTERNS):
        protected_indices.add(i)
与维度 3 的区别：维度 3 是"加分"（让含实体句更可能被选中），路径 A 是"硬约束"（即使分数不够也必须保留）。双重保障确保关键数据零丢失。

路径 B: 冗余句检测

路径 B — Jaccard 相似度去重

规则：相邻 3 句范围内，Jaccard > 0.5 标记后面的为冗余

for i in range(len(sentences) - 1):
    words_i = set(jieba.cut(sentences[i])) - STOP_WORDS
    words_i = {w for w in words_i if len(w) > 1}
    for j in range(i+1, min(i+3, len(sentences))):
        words_j = set(jieba.cut(sentences[j])) - STOP_WORDS
        words_j = {w for w in words_j if len(w) > 1}
        jaccard = len(words_i & words_j) / len(words_i | words_j)
        if jaccard > 0.5:
            redundant.add(j)  # 删后面的，保前面的
Jaccard(i, j) = |words_i ∩ words_j| / |words_i ∪ words_j| > 0.5 → 冗余

路径 D: 自适应 target_ratio

路径 D — 根据信息密度动态调整压缩目标

# 计算全文信息密度
all_words = jieba.cut(cleaned_text)
content_words = [w for w in all_words if len(w)>1 and w not in STOP_WORDS]
info_density = len(content_words) / (len(all_words) + 1)

# 映射到 [0.35, 0.85]：密度高→保留多，密度低→压缩多
adaptive_ratio = 0.35 + info_density * 0.5

# 取 adaptive 和 user_target 中更激进（更小）的那个
effective_target = min(target_ratio * bias, adaptive_ratio)
effective_target = max(0.30, min(0.85, effective_target))
target_chars = int(len(cleaned_text) * effective_target)

贪心选句主逻辑

选句算法伪代码

# Step 1: 保护句必选（路径 A）
kept_indices = protected_indices.copy()
kept_chars = sum(len(sentences[i]) for i in protected_indices)

# Step 2: 非保护句按分数降序排列
deletable = [(i, scores[i]) for i if i not in protected_indices]
deletable.sort(key=score, reverse=True)  # 高分优先保留

# Step 3: 贪心填充到目标字符数
for idx, _ in deletable:
    if kept_chars >= target_chars: break
    if idx in redundant_indices: continue  # 路径B: 跳过冗余句
    kept_indices.add(idx)
    kept_chars += len(sentences[idx])

# Step 4: 保底 — 确保 TOP2 高分句被保留
top2 = sorted(range(n), key=lambda i: scores[i], reverse=True)[:2]
for idx in top2: kept_indices.add(idx)

# Step 5: 按原始顺序拼接保留句
compressed = "".join(sentences[i] for i in sorted(kept_indices))
顺序保持原则：选句后按原始位置索引排序拼接，不打乱文本逻辑顺序，确保输出可读性。

完整数据流（端到端）

compress(text, context, bias=1.0, target_ratio=0.5)
│
├─ [Guard] len(text) < 100 → return strategy="too_short"
├─ [阶段1] 填充短语预删除 → cleaned_text (60+条中英文)
├─ [阶段2] 智能分句 → sentences[] (L1标点→L2逗号→L3窗口)
├─ [Guard] len(sentences) ≤ 3 → return "too_few_sentences"
├─ [阶段3] 六维度评分 → scores[]
│   ├─ 维度1: TF-IDF(×3) + 维度2: 位置(+2.5/1.8/1.5)
│   ├─ 维度3: 实体(hits×4+3) + 维度4: 上下文(overlap×3)
│   └─ 维度5: 密度(×2) + 维度6: 技术标识符(hits×2+2)
├─ [阶段4] 动态选句
│   ├─ 路径A: protected (含实体必留)
│   ├─ 路径B: redundant (Jaccard>0.5标记)
│   ├─ 路径D: effective_target (自适应密度)
│   └─ 贪心: protected→高分优先→跳冗余→TOP2保底→原序拼接
├─ [阶段5] 句内精简 (ratio>target×0.85时触发)
│   ├─ 长句(>100字符): 子句分割→评分→贪心选择
│   └─ 激进(ratio<0.4): 词级填充短语删除
└─ return CompressResult(strategy="tfidf_textrank")

五大核心设计决策

#设计决策原因Trade-off
1确定性正则保护 > 概率性模型预测关键数据 100% 不丢失可能过度保护，降低压缩率
2提取式 > 生成式输出是原文子集，忠实度 100%压缩率上限不如 LLM 摘要
3三级降级分句兼容标准/无标点/超长复合句L3 可能在不恰当位置断开
4自适应 target_ratio密度高少压缩、废话多多压缩增加 ~1ms 计算
5零模型零 GPU部署成本为零，延迟确定性 <20ms无法做语义理解/同义判断

维度LLMLingua-2 (mBERT-base)
模型bert-base-multilingual-cased (110M params, 709MB)
论文ACL 2024 (Pan et al.) — Data Distillation for Task-Agnostic Prompt Compression
GitHubmicrosoft/LLMLingua — 5.5k stars，持续维护
中文支持原生覆盖 104 种语言（含中文），预训练数据含中文 Wikipedia
部署CPU 可运行（~145ms/条），MPS/CUDA 更快（~15ms）

四、精度安全性分析

✅ 为什么 FP16 不影响结果
  • LLMLingua-2 决策是离散的：按概率排序 → 取 top-K token 保留
  • FP16 误差 ~1e-3 级别，不改变 token 概率排序
  • 只有两 token 概率差 <1e-3 时才可能翻转（极罕见）
  • 即使翻转，也是边界 token（"可保留可不保留"），语义无损
🔬 验证方法
  • ONNX FP32 推理 → logits 转 float16 → 转回 float32
  • 模拟 TensorRT FP16 Tensor Core 的精度行为
  • 12 组用例 × 逐字对比 → 100% 一致
  • token 数完全相同（无边界翻转发生）

五、CPU 环境说明

CPU 上 ONNX 比 PyTorch 慢约 43%（813ms vs 1439ms），原因：
• numpy ↔ torch tensor 数据拷贝开销
• ONNX Runtime CPU provider 对大模型无算子融合优势
• CPU 无 Tensor Core，FP16 无加速意义

ONNX 的价值仅在 GPU 上体现（CUDA/TensorRT provider：去 Python 调度 + 算子融合 + FP16 硬件加速）。
