产品概述

AG-UI Chat 是 aPaaS 平台的智能对话交互层，基于 AG-UI（Agent-User Interface）协议构建。它将企业级 AI Agent 的复杂推理能力封装为自然语言对话体验，让业务用户无需理解底层技术即可完成数据分析、流程操作和知识获取。

产品价值

对终端用户：从"等待黑盒"到"透明协作"

传统 AI 对话产品中，用户发出请求后只能面对空白等待，不知道系统在做什么、还要多久、是否出了问题。AG-UI Chat 通过实时推理链路可视化，让用户全程看到 Agent 的思考过程——正在查询哪些数据、调用了什么工具、子任务进展如何。这种透明度将用户从被动等待者转变为知情协作者，显著提升信任感和使用意愿。

对业务团队：从"手动多步操作"到"一句话完成"

业务人员过去需要在多个系统间切换、手动拼接数据才能完成一次分析。AG-UI Chat 通过 Skill 编排和多轮推理循环，将"分析华东区商机 Pipeline 并给出客户画像"这样的复合需求自动拆解为数据查询、聚合分析、画像生成等步骤，一次对话即可交付完整结果。

对运维与研发：从"出了问题找不到原因"到"全链路秒级定位"

每次请求生成完整的 Trace 链路，覆盖从入口审查到后处理的全部节点。异常节点自动红色标记、超时自动告警、成本精确归因到每个 Skill 和 LLM 调用。运维团队无需翻日志，直接在链路面板中定位问题根因。

对平台：从"不可控的 AI 输出"到"安全合规闭环"

全链路嵌入安全机制——入口内容审查拦截违规输入、PII 脱敏保护隐私数据、工具护栏防止越权操作、输出校验过滤敏感内容。每一层防护都有对应的埋点记录，满足企业级合规审计要求。

一、AG-UI Chat 完整推理链路结构图

1.1 产品价值

AG-UI Chat 推理链路是连接用户自然语言输入与 Agent 智能执行的核心管道。通过将复杂的多步推理过程结构化、可观测化，它为产品带来以下核心价值：

  • 端到端透明度 — 将 Agent 的"黑盒"推理过程转化为可追踪、可回放的事件流，让运营和研发团队能够精确定位每一步的耗时、成本与异常，大幅降低排障成本。
  • 用户体验可控 — 通过 AG-UI 事件协议将推理进度实时映射到前端 UI（思考中 → 工具调用中 → 生成中），消除用户等待焦虑，提升交互信任感。
  • 质量与安全保障 — 在链路关键节点嵌入内容审查、护栏校验、循环检测等中间件，确保 Agent 输出合规、可控、不失控。
  • 成本可归因 — 每次 LLM 调用和子 Agent 执行均记录资源消耗，支持按租户、按 Skill、按请求维度的精细化成本核算。
  • 架构可扩展 — 中间件 + 事件流的分层设计使得新增能力（如新的 Skill、新的审查策略）无需改动核心链路，即插即用。

1.2 产品目标

本推理链路设计需达成以下可量化的产品目标：

目标维度具体目标
响应体验首 token 延迟（TTFT）≤ 3s；用户感知等待时间通过进度事件降低 50%（对比无推理链路展示的方案）
全链路可观测100% 请求生成完整 Trace；关键节点（LLM 调用、工具执行、子 Agent）埋点覆盖率 100%
异常检测循环调用、超时、护栏拦截等异常在 ≤ 1s 内被识别并触发告警或自动降级
成本透明每次请求的 token 消耗和资源点成本可精确归因到具体 Skill / 子 Agent，误差 ≤ 1%
安全合规所有用户输入经过内容审查 + PII 脱敏；所有工具调用经过护栏校验；敏感操作触发人工确认
扩展性新增 Middleware 或 Skill 不需要修改核心 Agent Loop 代码；子 Agent 支持最大 3 层嵌套深度

1.4 知识预加载与引用追踪

fork 模式子 Agent 的知识文件加载优化方案。
解决问题：子 Agent 需要多轮 LLM 推理才能逐个加载知识文件（read_skill_resource），导致不必要的延迟和 token 消耗。
核心思路：在子 Agent 启动前批量预加载全部知识文件，并在每轮推理中追踪模型引用了哪些知识。

1.4.1 预加载机制

环节说明实现
触发条件Skill 的 allowed_tools 包含 read_skill_resourceSkillExecutor._preload_resources() 前置检查
配置来源ai_skill_definition.ext_info.preload_resourcesPreloadConfig: always[] + scene_map{} + max_preload
降级策略无配置时自动发现 _index.md 文件_auto_discover_preload() 查询 path LIKE '%/_index.md'
加载方式一次 SQL 批量查询 ai_skill_resource 表ResourcePreloader.preload() → ~2ms
注入位置task_instruction 末尾，子 Agent 的 HumanMessage 中format_preloaded_context() → Markdown 文本块
链路记录写入子 Agent 的 sub_thread_id，type=resource_preload_record_preload_span() → _add_to_thread()

1.4.2 引用追踪机制

预加载的知识文件作为上下文注入后，模型在推理时"引用"它们不会产生工具调用事件。为了在链路中体现模型每轮引用了哪些知识文件，采用标记解析方案：

环节说明
Prompt 指令Skill prompt 要求模型每轮回复开头输出 <!-- REF: file1.md, file2.md --> 标注本轮引用的知识文件
后端解析AGUIConverter.on_chat_model_end 中调用 _parse_knowledge_refs() 从 LLM 输出提取引用列表
Span 记录knowledge_refs 写入 llm_call span 的 metadata 和 output_data
文本剥离_emit_text() 中用正则剥离 REF 标记，不显示给用户
前端展示在"🧠 模型推理"行下方显示 📚 引用: file1.md, file2.md

2.1 埋点分层模型

层级 Span 类型 覆盖节点 粒度 关键指标
L0 · 请求 request 整个用户请求生命周期（SSE 连接建立 → RUN_FINISHED → 后处理完成） 1 次/请求 总耗时、总 token、总成本(cost_credits)、循环总数
L1 · 阶段 phase 入口预处理(entry) / 上下文准备(context) / Agent Loop(reasoning) / 回复输出(output) / 后处理(post) 5 次/请求 阶段耗时、阶段状态、阶段内节点数
L2 · 循环 loop_iteration Agent Loop 每一轮（Summarization → LLM 推理 → after_model 中间件 → Guardrail → 工具/Skill 执行） N 次/请求 轮次号、LLM 耗时、工具耗时、是否 FINAL
L3 · 操作 operation 单次 LLM 调用 / 单次工具执行 / 单次 Middleware / 单次 Skill 执行 M 次/轮 操作耗时、输入/输出大小、错误码、cost_credits
L4 · 子Agent sub_agent fork 模式 Skill 的子 Agent 完整生命周期（独立 thread_id，内含子循环 L2 + 子操作 L3） K 次/请求 子循环数、子LLM调用数、子工具调用数、depth、总耗时、cost_credits

2.4 埋点触发规则

规则 描述 适用节点
全量记录每次触发都记录，无采样所有 L0-L3 节点；RUN_STARTED/FINISHED；STEP_*；STATE_*；ACTIVITY_*
采样记录 (10%)高频事件按 trace_id hash 取模采样TEXT_MESSAGE_CONTENT；REASONING_MESSAGE_CONTENT；TOOL_CALL_ARGS
异常全量升级当请求出现异常时，该 trace 下所有事件升级为全量记录RUN_ERROR 触发后回填该 trace 的采样事件
耗时阈值告警超过阈值时自动标记 alert=true 并推送监控见各节点"异常判定规则"列
成本归因每个 LLM_CALL 和 SUB_AGENT span 记录 cost_credits，汇总到 L0llm_call, sub_agent_*
链路关联所有 span 通过 trace_id + parent_span_id 形成树状结构全部节点；子Agent span 的 parent = skill span
AG-UI 事件关联每个 AG-UI 事件记录 related_span_id 指向产出它的 L3 span所有 agui_* 节点
