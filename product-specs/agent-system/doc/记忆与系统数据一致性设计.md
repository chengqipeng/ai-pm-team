# 记忆与系统数据一致性设计

## 一、问题定义

### 1.1 当前数据流

```
用户: "查一下华为的商机"
  │
  ▼
Agent 调用 query_data(entity="opportunity", filters={"account_name":"华为科技"})
  │
  ▼
ToolMessage 返回:
  {"records": [
    {"id":"opp_001", "name":"ERP升级", "amount":5000000, "stage":"谈判", "account_name":"华为科技"},
    {"id":"opp_002", "name":"云迁移", "amount":2000000, "stage":"方案", "account_name":"华为科技"}
  ]}
  │
  ▼
Agent 回复: "华为科技有2个商机：ERP升级500万谈判阶段，云迁移200万方案阶段"
  │
  ▼
MemoryMiddleware.aafter_agent() → extract_and_update()
  │
  ▼
LLM 提取记忆:
  记忆1: merge_key="华为科技/ERP升级", abstract="华为科技/ERP升级: 金额500万，谈判阶段"
  记忆2: merge_key="华为科技/云迁移", abstract="华为科技/云迁移: 金额200万，方案阶段"
```

### 1.2 三个问题场景

**场景 A：系统数据字段变更**

```
T1: 记忆写入 → "华为科技/ERP升级: 金额500万，谈判阶段"
T2: 销售在 CRM 中修改商机金额 → 800万，阶段 → closing
T3: 用户问 "华为ERP项目多少钱"
    → Agent 检索记忆 → 回答 "500万，谈判阶段"（错误！系统中已经是800万closing）
```

**场景 B：实体名称变更**

```
T1: 记忆中有 5 条 parent_entity="华为科技" 的记忆
T2: 管理员在 CRM 中把客户名改为 "深圳华为科技有限公司"
T3: 用户问 "深圳华为科技的商机"
    → 向量库 filter parent_entity="深圳华为科技有限公司" → 0 条命中
    → 向量语义搜索可能命中（因为"华为"语义相近），但 parent_entity 不匹配
```

**场景 C：实体被删除/合并**

```
T1: 记忆中有 "华为科技/ERP升级" 和 "华为技术/ERP升级" 两条（重复客户）
T2: 管理员在 CRM 中合并客户 → 只保留 "华为科技"
T3: 记忆中 "华为技术/ERP升级" 变成孤儿记忆，指向不存在的客户
```

### 1.3 根因分析

```
根因: 记忆系统把"工具返回的结构化数据"和"对话中的增量认知"混在一起存储

  工具返回的结构化数据（系统中已有）:
    "ERP升级项目金额500万，谈判阶段"
    "张总，CTO，电话139-0001-0001"
    → 这些数据在 CRM 系统中有权威来源
    → 存成记忆 = 存了一份会过时的快照
    → Agent 应该实时查询系统，而不是依赖记忆

  对话中的增量认知（系统中没有）:
    "张总倾向方案B，对价格敏感，建议不要主动提折扣"
    "华为内部审批流程复杂，至少需要3周"
    "上次和张总开会，他提到Q3有预算压力"
    → 这些信息 CRM 系统中没有对应字段
    → 只有记忆系统能存
    → 不会因为系统数据变更而失效
```

## 二、记忆应该记什么

### 2.1 核心原则

```
原则: 记忆系统只记录 CRM 系统中不存在的增量认知，
      不做系统数据的镜像。

判断标准:
  这条信息能通过 query_data 工具实时查到吗？
    能 → 不需要存记忆（Agent 直接查系统）
    不能 → 需要存记忆（只有记忆系统能存）
```

### 2.2 各类别的记忆边界

| 类别 | 应该记的（增量认知） | 不应该记的（系统数据） |
|:---|:---|:---|
| entities | 客户决策风格、沟通技巧、内部关系、审批流程特点 | 客户名称、行业、商机金额、阶段、联系人电话 |
| events | 会议中的口头承诺、非正式决策、用户的主观判断 | 系统中已记录的活动（activity 实体） |
| profile | 用户角色、团队、技术水平、工作习惯 | — （系统中没有这些字段） |
| preferences | 展示偏好、回复风格、数据范围偏好 | — （系统中没有这些字段） |
| cases | 问题排查经验、解决方案 | — （系统中没有这些字段） |
| patterns | 工作流程、分析习惯 | — （系统中没有这些字段） |
| tools | 工具使用统计 | — （纯 Python 统计） |
| skills | 技能执行策略 | — （系统中没有这些字段） |

### 2.3 entities 类的具体拆分

```
当前（混在一起）:
  "华为科技/ERP升级: 金额500万，谈判阶段"              ← 系统数据快照
  "华为科技/ERP升级: 张总倾向方案B，对价格敏感"          ← 增量认知
  "华为科技/张总: 职位CTO，电话139-0001-0001"           ← 系统数据快照
  "华为科技/张总: 喜欢先看数据再讨论，不喜欢PPT"         ← 增量认知

改进后（只记增量认知）:
  "华为科技/ERP升级: 张总倾向方案B，对价格敏感，建议先展示ROI"
  "华为科技/张总: 喜欢先看数据再讨论，不喜欢PPT，会议控制30分钟"
  "华为科技: 内部审批流程复杂，至少3周，需要同时搞定技术和采购"
  "华为科技: 和腾讯是竞争关系，报价时注意不要提腾讯的案例"
```

## 三、场景 A 处理方案：系统数据字段变更

### 3.1 方案对比

| 方案 | 思路 | 优点 | 缺点 |
|:---|:---|:---|:---|
| A1: 不记系统数据 | 提取时过滤掉系统数据 | 根治问题，零维护成本 | 丢失"上次查到的快照"上下文 |
| A2: 短 TTL 标记 | 系统数据记忆设 24h TTL，过期标记 stale | 兼容现有逻辑 | 24h 内仍可能返回过时数据 |
| A3: 检索时实时校验 | 检索到记忆后，调 query_data 校验是否过时 | 最准确 | 每次检索多一次工具调用，延迟高 |
| A4: Webhook 同步 | CRM 数据变更时推送到记忆系统更新 | 实时一致 | 架构复杂，需要 CRM 侧配合 |

### 3.2 推荐方案：A1 + A2 组合

```
核心策略:
  1. 提取时: LLM 优先提取增量认知，系统数据只在有增量认知附着时才提取
  2. 存储时: 系统数据类记忆标记 source_type="system_data"
  3. 检索时: system_data 类记忆附加提示 "[数据可能已变更，建议用工具实时查询确认]"

示例:

  对话:
    [用户] 查一下华为的商机
    [工具] 返回 ERP升级500万谈判阶段
    [助手] 华为ERP升级项目500万，谈判阶段。张总说他倾向方案B，但对价格比较敏感。

  提取结果:
    ✅ 提取: "华为科技/ERP升级: 张总倾向方案B，对价格敏感"  (source_type=insight)
    ❌ 不提取: "华为科技/ERP升级: 金额500万，谈判阶段"      (系统数据，不记)

  如果对话中没有增量认知:
    [用户] 查一下华为的商机
    [工具] 返回 ERP升级500万谈判阶段
    [助手] 华为ERP升级项目500万，谈判阶段。

    提取结果: 空（纯系统数据查询，无增量认知，不提取）
```

### 3.3 提取提示词改进要点

```
当前问题:
  EXTRACTION_PROMPT 没有区分系统数据和增量认知
  LLM 会把工具返回的金额、阶段、电话等原样提取

改进方向:
  不是列举"应该提取什么"（会过拟合），
  而是告诉 LLM 一个判断原则 + 列举"不提取什么"（系统已有的字段是确定的）。
```

#### 原则：排除法而非枚举法

```
❌ 过拟合的写法（枚举应该提取的内容）:
  "提取客户决策风格、沟通策略、价格敏感度、内部关系、审批流程、竞争情报..."
  问题:
    1. 列表永远不完整 — 用户可能说"华为的食堂不错，下次约张总吃饭"，这不在列表里但有价值
    2. LLM 会过度匹配 — 看到"价格"就提取，即使只是工具返回的金额字段
    3. 限制了 LLM 的判断力 — 变成了模式匹配而不是理解

✅ 正确的写法（排除系统已有的 + 给判断原则）:
  "不提取 CRM 系统中已有的结构化字段（以下字段可通过工具实时查询）:
     account: name, industry, city, employeeCount, annualRevenue, rating
     opportunity: name, amount, stage, probability, closeDate, source
     contact: name, title, phone, email
     activity: type, subject, dueDate, status
     lead: name, company, phone, email, source, status, score

   提取原则: 对话中出现的、上述字段之外的信息，都值得记录。
   判断标准: 这条信息能通过 query_data/query_schema 查到吗？
     能查到 → 不提取
     查不到 → 提取"
```

#### 为什么排除法更好

```
排除法的优势:
  1. 系统字段是确定的、有限的（5个实体 × 5-10个字段 = 30-50个字段）
  2. 增量认知是开放的、无限的（用户可能说任何事）
  3. 排除确定的，保留不确定的 — 不会遗漏

示例 — 排除法能覆盖但枚举法遗漏的:
  "华为的食堂不错，下次约张总在公司吃饭比较方便"
    → 枚举法: 不在"决策风格/沟通策略/价格敏感度"列表里 → 可能不提取
    → 排除法: 不是系统字段 → 提取（社交偏好，有价值）

  "张总最近在忙集团的数字化转型战略，可能没时间看我们的方案"
    → 枚举法: 不在列表里 → 可能不提取
    → 排除法: 不是系统字段 → 提取（时间窗口判断，很有价值）

  "华为今年IT预算砍了30%，所有项目都在压价"
    → 枚举法: 勉强算"价格敏感度" → 可能提取
    → 排除法: 不是系统字段 → 提取（预算背景，比"价格敏感"更有信息量）

  "上次给华为做的POC效果很好，张总在内部会议上表扬了我们"
    → 枚举法: 不在列表里 → 可能不提取
    → 排除法: 不是系统字段 → 提取（客户认可度，影响后续策略）
```

#### 提示词改进方案

```
改进后的 EXTRACTION_PROMPT 中关于 entities 的规则:

  ## entities 类提取规则

  以下字段值不要作为记忆的主体内容（CRM 系统已有，可实时查询）:
  - 客户: 行业、城市、员工数、营收、评分
  - 商机: 金额、阶段、概率、关闭日期、来源
  - 联系人: 职位、电话、邮箱
  - 活动: 类型、主题、日期、状态
  - 线索: 公司、电话、来源、状态、评分

  但客户名和人名必须保留在 merge_key / parent_entity / abstract 中作为定位锚点。
  区别:
    ❌ "华为科技/张伟: 职位IT总监，电话138xxx"（记忆系统字段值 → 会过时）
    ✅ "华为科技/张伟: 喜欢PPT汇报，开会不要绕弯子"（用人名定位增量认知）

  提取原则: 对话中出现的、上述字段之外的信息，都值得记录。
  判断标准: 这条信息能通过 query_data 查到吗？查不到就提取。
```

## 四、场景 B 处理方案：实体名称变更

### 4.1 方案对比

| 方案 | 思路 | 优点 | 缺点 |
|:---|:---|:---|:---|
| B1: biz_id 锚定 | 记忆绑定 record_id，不依赖名称 | 根治问题 | 需要从 ToolMessage 中解析 id |
| B2: 级联更新 API | 提供 rename_entity() 方法批量更新 | 可控 | 需要外部触发，不自动 |
| B3: 语义 fallback | 名称不匹配时用向量语义搜索兜底 | 无需改存储 | 可能误匹配其他客户 |
| B4: 别名表 | 维护 old_name → new_name 映射 | 简单 | 映射表需要维护 |

### 4.2 推荐方案：B1 + B2 组合

```
Phase 1 — biz_id 锚定（从 ToolMessage 中提取）:

  当前 ToolMessage 内容:
    {"records": [{"id":"opp_001", "name":"ERP升级", "amount":5000000, ...}]}

  提取时:
    LLM 或后处理从 ToolMessage 中解析出 record_id
    存储时写入 biz_id 字段

  记忆存储:
    merge_key:     "华为科技/ERP升级"      ← 人类可读（用于目录展示）
    parent_entity: "华为科技"              ← 人类可读（用于目录展示）
    biz_id:        "opp_001"              ← 系统锚点（不变）
    biz_parent_id: "acc_001"              ← 父实体锚点（不变）

  检索时:
    优先用 biz_id / biz_parent_id filter（精确，不受改名影响）
    fallback 到 parent_entity 字符串 filter（兼容无 biz_id 的旧记忆）

  客户改名后:
    biz_parent_id="acc_001" 不变 → 记忆仍然能检索到
    merge_key / parent_entity 中的旧名称只影响展示，不影响检索


Phase 2 — rename_entity() 级联更新:

  用途: 更新记忆中的展示名称（非必须，但提升体验）

  触发方式:
    方式 1: CRM Webhook → 自动触发
    方式 2: Agent 检测到名称不一致时主动调用
    方式 3: 管理员手动触发

  逻辑:
    1. 查询所有 biz_parent_id = target_id 的记忆
    2. 批量替换 merge_key / parent_entity / abstract 中的旧名称
    3. 重新 embed(abstract) 更新向量
    4. 记录一条 events: "客户华为科技更名为深圳华为科技"
```

### 4.3 biz_id 的来源

```
来源 1: ToolMessage 中的 record_id（最可靠）

  Agent 调用 query_data → ToolMessage 返回 {"records": [{"id":"opp_001", ...}]}
  提取时从对话上下文中解析出 id

  实现方式:
    在 _convert_messages() 中，对 ToolMessage 保留 id 字段
    在 EXTRACTION_PROMPT 中要求 LLM 输出 biz_id（如果对话中有）
    后处理: 从 ToolMessage 中正则提取 "id":"xxx" 作为 biz_id

来源 2: Agent 主动查询（补充）

  如果记忆中没有 biz_id，Agent 在检索到记忆后可以:
    1. 用 merge_key 中的实体名调 query_data 查询
    2. 拿到 record_id 后回填到记忆中

来源 3: 不可用时的降级

  如果无法获取 biz_id（比如用户口头提到的客户，没有调工具查询）:
    biz_id 为空，退化为当前的名称字符串匹配
    这种情况下改名问题仍然存在，但这类记忆通常是 insight 类
    insight 类记忆即使客户改名，内容本身仍然有价值
    （"张总对价格敏感" 不会因为客户改名而失效）
```

## 五、场景 C 处理方案：实体删除/合并

### 5.1 实体删除

```
场景: 客户 "测试客户A" 在 CRM 中被删除

处理:
  1. 如果有 Webhook: 收到删除事件 → 标记相关记忆为 archived
  2. 如果没有 Webhook: 依赖遗忘策略自然过期（entities 180天）
  3. Agent 检索到已删除客户的记忆时:
     如果是 system_data 类 → 不返回
     如果是 insight 类 → 返回但标记 "[客户可能已不存在]"
```

### 5.2 实体合并

```
场景: "华为科技" 和 "华为技术" 合并为 "华为科技"

处理:
  1. 调用 rename_entity("华为技术", "华为科技")
  2. 合并后的记忆可能有重复 → 触发 reflect_global() 碎片合并
  3. 合并后记录 events: "客户华为技术合并到华为科技"
```

## 六、向量库 Schema 变更

### 6.1 新增字段

```
当前 Schema:
  id, vector, text, abstract, overview, content,
  category, merge_key, parent_entity, user_id,
  thread_id, created_at, updated_at

新增字段:
  source_type:    String  ← "insight" / "system_data"
  biz_id:         String  ← CRM 系统的 record_id（如 "opp_001"）
  biz_parent_id:  String  ← 父实体的 record_id（如 "acc_001"）
  biz_type:       String  ← 业务实体类型（如 "opportunity"）

注意:
  source_type 不需要 filter index（不用于检索过滤，只用于后处理标记）
  biz_id 需要 filter index（用于精确检索）
  biz_parent_id 需要 filter index（用于级联查询）
  biz_type 不需要 filter index
```

### 6.2 PG 表变更

```
agent_memory 表新增:
  source_type     VARCHAR(32)  DEFAULT 'insight'
  biz_id          VARCHAR(128) DEFAULT ''
  biz_parent_id   VARCHAR(128) DEFAULT ''
  biz_type        VARCHAR(64)  DEFAULT ''

索引:
  CREATE INDEX idx_agent_memory_biz_id ON agent_memory (biz_id) WHERE biz_id != '';
  CREATE INDEX idx_agent_memory_biz_parent ON agent_memory (biz_parent_id) WHERE biz_parent_id != '';
```

## 七、检索逻辑变更

### 7.1 当前检索流程

```
查询 → 意图分析 → embed → hybrid_search(filter: user_id + category) → 返回 Top-K
```

### 7.2 改进后检索流程

```
查询 → 意图分析 → embed → hybrid_search → 后处理 → 返回 Top-K

后处理新增:
  对每条检索结果:
    1. 检查 source_type
       insight → 正常返回
       system_data → 附加提示 "[建议用工具实时查询确认最新数据]"

    2. 如果意图分析识别出 biz_id（如用户说"查 opp_001 的情况"）
       优先用 biz_id filter 精确匹配
       fallback 到语义搜索
```

### 7.3 _format_memory 注入格式变更

```
当前:
  <memory_context>
  【customer_context】
    - 华为科技/ERP升级: 金额500万，谈判阶段
  </memory_context>

改进后:
  <memory_context>
  【customer_context】
    - 华为科技/ERP升级: 张总倾向方案B，对价格敏感（洞察）
    - 华为科技: 内部审批流程复杂，至少3周（洞察）
  </memory_context>

  注: system_data 类记忆不注入（Agent 应该用工具实时查询）
  或: system_data 类记忆降低优先级，排在 insight 后面
```

## 八、实施路径

### Phase 1: 改提取逻辑（不改存储）

```
改动范围: EXTRACTION_PROMPT + _llm_extract 后处理
工作量: 1-2 天
效果: 新提取的记忆不再包含系统数据快照

具体改动:
  1. EXTRACTION_PROMPT 增加"不提取系统数据"规则
  2. _llm_extract 后处理: 自动推断 source_type
  3. 检索时: source_type="system_data" 的记忆降低优先级或附加提示
  4. 不改存储 schema（source_type 存在 metadata_json 中）
```

### Phase 2: 加 biz_id 锚定

```
改动范围: 存储 schema + 提取逻辑 + 检索逻辑
工作量: 3-5 天
效果: 实体改名不影响记忆检索

具体改动:
  1. 向量库 collection 增加 biz_id / biz_parent_id 字段和 filter index
  2. PG 表增加 biz_id / biz_parent_id 列
  3. _convert_messages 中保留 ToolMessage 的 id 字段
  4. _llm_extract 或后处理中解析 biz_id
  5. 检索时优先用 biz_id filter
  6. 实现 rename_entity() 级联更新方法
```

### Phase 3: Webhook 自动同步

```
改动范围: 新增 Webhook 接收端点
工作量: 5-7 天
效果: CRM 数据变更自动同步到记忆系统

具体改动:
  1. 新增 /api/memory/webhook 端点
  2. 接收 CRM 的 entity.updated / entity.deleted / entity.merged 事件
  3. entity.updated: 如果是名称变更 → 调 rename_entity()
  4. entity.deleted: 标记相关记忆为 archived
  5. entity.merged: 调 rename_entity() + reflect_global()
```

## 九、风险和权衡

### 9.1 不记系统数据的风险

```
风险 1: Agent 失去"上次查到什么"的上下文

  场景:
    第一轮: 用户查了华为的商机 → Agent 回答了 ERP 500万
    第二轮: 用户说"刚才那个商机能不能打折"
    → 如果不记系统数据，Agent 不知道"刚才那个商机"是什么

  缓解:
    1. 同一会话内: 上下文在 messages 列表中，不需要记忆
    2. 跨会话时: Agent 可以重新调 query_data 查询
    3. events 类记忆可以记录"发生了什么事":
       "2026-04-28 查询了华为商机，讨论了ERP项目的折扣方案"
       → 记的是事件，不是数据快照

风险 2: 纯查询对话提取不到任何记忆

  场景:
    用户: "查一下华为的商机"
    助手: "华为有3个商机：ERP 500万谈判阶段..."
    → 纯系统数据查询，没有增量认知，提取结果为空

  这不是问题:
    1. 这种对话确实没有值得长期记忆的内容
    2. 数据在系统中，下次查还是一样的结果
    3. 如果用户在查询后发表了看法（"这个项目有戏"），那就有增量认知了

风险 3: 混合对话中增量认知和系统数据交织

  场景:
    用户: "查一下华为ERP项目"
    助手: "ERP项目500万谈判阶段。张总说他倾向方案B。"
    → "500万谈判阶段"是系统数据，"张总倾向方案B"是增量认知
    → LLM 可能把两者混在一条记忆里

  处理:
    1. 提示词要求: 如果一条记忆同时包含系统数据和增量认知，只保留增量认知部分
    2. 可以接受: "华为科技/ERP升级: 张总倾向方案B，对价格敏感"
       （merge_key 中包含商机名是可以的，因为这是定位用的，不是数据快照）
    3. 不可以接受: "华为科技/ERP升级: 金额500万，谈判阶段，张总倾向方案B"
       （金额和阶段是系统数据，会过时）
```

### 9.2 biz_id 不可用的降级

```
场景: 用户口头提到客户，没有调工具查询

  用户: "华为那个项目张总说可以签了"
  → 没有 ToolMessage，无法获取 biz_id
  → 退化为名称字符串匹配

处理:
  biz_id 为空时，仍然用 merge_key / parent_entity 匹配
  这种记忆通常是 insight 类（"张总说可以签了"）
  insight 类记忆即使客户改名，内容本身仍然有价值
```

### 9.3 提取质量的依赖

```
风险: LLM 可能仍然提取系统数据

缓解:
  1. EXTRACTION_PROMPT 中明确列出"不提取"的字段类型
  2. 后处理中自动检测: 如果 content 中只有金额/阶段/电话等结构化字段
     且没有主观判断词 → 标记为 system_data 或直接丢弃
  3. 定期 reflect_global() 清理纯系统数据类记忆

系统提示词的角色:
  CRM_SYSTEM_PROMPT 不负责约束记忆提取行为（那是 EXTRACTION_PROMPT 的职责）。
  但增加了一条 Agent 使用记忆时的行为约束:
    "记忆是参考不是数据源: 记忆中的客户/商机信息可能已过时，
     涉及具体数据（金额、阶段、电话等）时必须用工具实时查询确认"
  这条规则解决的是: 即使记忆中存了过时的系统数据，Agent 也不会直接引用，
  而是会调工具查最新数据。这是防御性设计，和提取侧的排除法互补。
```
