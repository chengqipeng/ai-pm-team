# 字段类型不匹配全量扫描报告

> 日期：2026-04-28
> 触发事件：客户（account）保存报错 `column "dbc_bigint27" is of type bigint but expression is of type character varying`
> 扫描范围：account、lead、opportunity、user、role、department 全部实体字段

---

## 一、问题本质

PostgreSQL 不做隐式类型转换。当 MyBatis-Plus 的 `UpdateWrapper.set("dbc_bigint27", value)` 中 `value` 是 `String` 类型时，PG 直接报错。

根因有两个层面：

1. **元数据配置层**：字段的 `itemType`（决定前端组件和值格式）与 `dbColumn`（决定物理列类型）不匹配
2. **代码层**：写入链路缺少基于 `dbColumn` 前缀或 `dataType` 的值类型转换

---

## 二、权威类型映射规则

根据 `ItemTypeEnum` 完整映射（元模型设计体系.md §4.2）：

| itemType | 名称 | 默认 dataType | 默认 dbc 前缀 | Java 类型 |
|---|---|---|---|---|
| 1 TEXT | 文本 | VARCHAR(1) | dbc_varchar | String |
| 2 SELECT | 单选 | VARCHAR(1) | dbc_varchar | String |
| 3 MULTI_SELECT | 多选 | VARCHAR(300)[] | dbc_array | List\<String\> |
| 5 NUMBER | 整数 | BIGINT(3) | dbc_bigint | Long |
| 6 CURRENCY | 实数 | DECIMAL(4) | dbc_decimal | BigDecimal |
| 7 DATE | 日期 | BIGINT(3) | dbc_bigint | Long |
| 10 RELATION_SHIP | 关联 | BIGINT(3) | dbc_bigint | Long |
| 22 PHONE | 电话 | VARCHAR(1) | dbc_varchar | String |
| 31 BOOLEAN | 布尔 | SMALLINT(6) | dbc_smallint | Integer |
| 33 PERCENT | 百分比 | DECIMAL(4) | dbc_decimal | BigDecimal |
| 38 DATETIME | 时间 | BIGINT(3) | dbc_bigint | Long |

**核心规则**：`dbColumn` 前缀决定物理列类型，Java 层传入的值类型必须与之匹配：
- `dbc_bigint*` → 必须传 `Long`
- `dbc_decimal*` → 必须传 `BigDecimal`
- `dbc_smallint*` → 必须传 `Integer`/`Short`
- `dbc_varchar*` / `dbc_textarea*` → 传 `String`
- `dbc_array*` → 传 `List<String>`（PG 原生数组）

## 三、全量扫描结果

### 分类说明

- **A 类（必炸）**：itemType 的默认 dataType 是 VARCHAR/TEXT，但 dbColumn 是 dbc_bigint/dbc_decimal/dbc_smallint。前端按 itemType 提交字符串值，写入 bigint 列必然报错。
- **B 类（反向不匹配）**：itemType 的默认 dataType 是 BIGINT/DECIMAL，但 dbColumn 是 dbc_varchar/dbc_int。前端提交数字值写入 varchar 列不会报错（PG 允许数字→字符串隐式转换），但语义错误，查询排序会出问题。
- **C 类（跨类型混用）**：dbColumn 前缀与 itemType 的默认 dataType 不同，但在特定业务场景下可能是有意为之（如 RELATION_SHIP + VARCHAR 存 api_key）。需要确认 dataType 是否已显式覆盖。

## 五、根因分析

### 5.1 老系统迁移遗留

老系统（CRM）的字段定义使用老 itemType 编码，迁移到新系统时：
- `itemType` 编码已转换为新编码（ItemTypeEnum）
- 但 `dbColumn` 保持了老系统的物理列名不变
- 老系统中部分字段的 itemType 和 dbColumn 本身就不匹配（老系统可能在应用层做了类型转换，或者 MySQL 做了隐式转换）

### 5.2 MySQL → PostgreSQL 迁移

老系统使用 MySQL，MySQL 会自动做隐式类型转换（`'12345'` 写入 BIGINT 列会自动转为 `12345`）。迁移到 PostgreSQL 后，这些隐式转换不再生效。

### 5.3 sync/config.py 的 ITEM_TYPE_TO_BIZ_PREFIX 注释错误

`config.py` 中 `ITEM_TYPE_TO_BIZ_PREFIX` 的注释写的是"新 itemType"，但实际使用的是**老 itemType 编码**：

```python
# 注释说"新 itemType"，但实际是老编码：
ITEM_TYPE_TO_BIZ_PREFIX = {
    1: 'dbc_varchar',   # 老1=文本 → varchar ✓
    2: 'dbc_bigint',    # 老2=数字 → bigint ✓（新2=SELECT → 应该是 varchar）
    3: 'dbc_bigint',    # 老3=日期 → bigint ✓（新3=MULTI_SELECT → 应该是 array）
    4: 'dbc_varchar',   # 老4=单选 → varchar ✓（新4=TEXTAREA → 应该是 textarea）
    5: 'dbc_bigint',    # 老5=查找关联 → bigint ✓（新5=NUMBER → bigint ✓ 巧合一致）
    10: 'dbc_decimal',  # 老10=货币 → decimal ✓（新10=RELATION_SHIP → 应该是 bigint）
    ...
}
```

这个映射表如果被用于新系统的类型校验或转换，会产生严重的类型错误。

## 六、修复方案

### 6.1 紧急修复（P0）：写入链路加类型转换

在 `EntityDataService.update()` / `TenantDataServiceImpl` 构建 UpdateWrapper 时，根据 `dbColumn` 前缀强制转换值类型：

```java
/**
 * 根据 dbColumn 前缀将值转换为正确的 Java 类型。
 * 这是防御性措施，确保即使元数据配置有历史遗留问题，也不会导致 SQL 类型错误。
 */
private Object castToColumnType(String dbColumn, Object value) {
    if (value == null) return null;
    String str = value.toString().trim();
    if (str.isEmpty()) return null;

    try {
        if (dbColumn.startsWith("dbc_bigint")) {
            return Long.parseLong(str);
        } else if (dbColumn.startsWith("dbc_decimal")) {
            return new BigDecimal(str);
        } else if (dbColumn.startsWith("dbc_smallint")) {
            return Integer.parseInt(str);
        }
        // dbc_varchar, dbc_textarea → String，无需转换
        // dbc_array → List<String>，需要单独处理
    } catch (NumberFormatException e) {
        log.warn("字段值类型转换失败: dbColumn={}, value={}, error={}",
                 dbColumn, value, e.getMessage());
        return null;  // 或抛业务异常
    }
    return value;
}
```

在 UpdateWrapper 构建处调用：
```java
updateWrapper.set(dbColumn, castToColumnType(dbColumn, fieldValue));
```

同样需要在 `insert` 链路中加入相同的转换逻辑。

### 6.2 元数据修正（P1）：修复 A 类字段配置

对 15 个 A 类字段，有两种修正策略：

**策略一：修正 dbColumn（推荐，不改物理表）**

将字段的 `dbColumn` 改为与 `itemType` 匹配的列前缀，同时迁移存量数据：

```sql
-- 以 account.employeeNumber 为例：单选(2) 应该存 dbc_varchar
-- 1. 找一个空闲的 dbc_varchar 列号
-- 2. 迁移数据
UPDATE paas_entity_data.p_tenant_data_0
SET dbc_varchar_NEW = dbc_bigint4::VARCHAR
WHERE entity_api_key = 'account' AND dbc_bigint4 IS NOT NULL;
-- 3. 更新元数据
UPDATE paas_metarepo_common.p_common_metadata
SET dbc_varchar3 = 'dbc_varchar_NEW'  -- dbColumn
WHERE metamodel_api_key = 'item' AND entity_api_key = 'account'
  AND api_key = 'employeeNumber';
```

**策略二：修正 itemType（如果业务语义本身就是数字）**

部分字段的 `itemType` 标错了，实际业务语义是数字而非单选：

| apiKey | 当前 itemType | 应改为 | 理由 |
|---|---|---|---|
| score | 单选(2) | 整数(5) | 客户分值是数字 |
| visitUnvisitDay | 单选(2) | 整数(5) | 未拜访天数是数字 |
