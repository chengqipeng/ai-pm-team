# 字段类型修正对比表

> 日期：2026-04-28
> 范围：account、opportunity、lead 全部类型不匹配字段
> 判定规则：dbColumn 前缀决定物理列类型，itemType 的 defaultDataType 决定值的 Java 类型，两者必须一致

---

## 判定标准

| dbColumn 前缀 | 物理列类型 | 要求的 Java 类型 | 兼容的 itemType |
|---|---|---|---|
| dbc_varchar | VARCHAR(300) | String | 1(文本), 2(单选), 9(自动编号), 13/22(电话), 16(多选标签), 23(邮箱), 24(网址), 29(图片), 32(地理), 39(文件) |
| dbc_bigint | BIGINT | Long | 5(整数), 7(日期), 10(关联), 11(整数旧), 15(日期时间旧), 34(多态关联), 38(时间), 41(多值关联) |
| dbc_decimal | DECIMAL(20,4) | BigDecimal | 6(实数/货币), 33(百分比) |
| dbc_smallint | SMALLINT | Integer | 31(布尔) |
| dbc_textarea | TEXT | String | 4(文本域), 40(富文本) |
| dbc_array | VARCHAR(300)[] | List\<String\> | 3(多选) |
| dbc_int | **不存在** | — | 大宽表无此列类型 |

## 五、执行计划

### 阶段 0：防御性修复（P0，0.5 天）

在写入链路加 `castToColumnType()`，根据 dbColumn 前缀强制转换值类型。**一劳永逸解决所有 A 类问题**，不依赖元数据修正。

### 阶段 1：元数据修正 — 只改 itemType/dataType（P1，1 天）

执行动作一（20 个字段改 itemType）+ 动作二（7 个字段改 dataType）。

**无需数据迁移，只需更新 p_common_metadata 中的 dbc_int1/dbc_int2 值。**

```sql
-- 示例：修正 account.score 的 itemType 从 单选(2) 改为 整数(5)
UPDATE p_common_metadata
SET dbc_int1 = 5  -- itemType = NUMBER
WHERE metamodel_api_key = 'item'
  AND entity_api_key = 'account'
  AND api_key = 'score'
  AND delete_flg = 0;
```

### 阶段 2：数据迁移 — 改 dbColumn（P1，2 天）

执行动作三（5 个字段）+ 动作四（8 个字段）。

每个字段需要：
1. 查询目标实体当前已用的 dbc 列号，找空闲列号
2. 编写数据迁移 SQL（类型转换 + 复制数据）
3. 更新 p_common_metadata 的 dbColumn（dbc_varchar3）
4. 验证迁移后数据一致性
5. 清空旧列数据（可选，保留一段时间作为回退）

### 阶段 3：清理废弃字段（P2，1 天）

执行动作五，软删除 12 个 V2 已删除的字段。

### 阶段 4：config.py 修正（P1，0.5 天）

修正 `ITEM_TYPE_TO_BIZ_PREFIX` 的注释（实际是老编码不是新编码），或新增 `NEW_ITEM_TYPE_TO_BIZ_PREFIX` 映射表。
