# 智能客户洞察 V2 — 角色化深度洞察体系

> 版本：v1.0 | 日期：2026-04-24
> 定位：基于 toB CRM 平台能力，构建面向不同角色的深度客户洞察体系
> 前置文档：智能客户洞察-产品设计全集.md（V1 设计汇总）

---

## 一、V1 设计问题诊断

### 1.1 核心问题

现有设计本质上是"通用企业画像生成器"——用网络搜索+工商数据拼出一份企业背景报告。在 toB CRM 场景下存在三个根本性缺陷：

| 问题 | 表现 | 影响 |
|------|------|------|
| 角色定位模糊 | 一份洞察报告试图服务销售和CSM两个角色 | 两边都觉得不够深，使用率低 |
| CRM内部数据利用不足 | 偏重外部数据（工商/网络搜索），对商机、订单、联系人等内部数据缺乏深度分析 | 洞察结论与销售实际脱节 |
| 缺少行为数据维度 | 完全没有产品使用行为数据 | CSM无法判断客户健康度 |

### 1.2 V2 核心改变

从"一个通用洞察"升级为"角色化洞察体系"：

```
V1：客户洞察 = 一个通用模板 x 外部数据为主

V2：客户洞察体系
    ├── 销售洞察（Sales Insight）
    │   ├── 行业深度定位（三级行业 + 行业排名 + 增长态势）
    │   ├── 客户关系网络（集团树 + 上下游 + 同行业客户网络）
    │   ├── 商机深度分析（Pipeline全景 + 赢单/丢单模式 + 交叉销售）
    │   ├── 竞对关系分析（竞争对手识别 + 竞品对比 + 差异化策略）
    │   └── 决策链分析（关键人覆盖度 + 活跃度 + 变动风险）
    │
    └── 客户成功洞察（CS Insight）
        ├── 产品使用健康度（活跃度趋势 + License使用率 + 使用集中度）
        ├── 功能采纳分析（模块级采纳率 + 功能深度 + 同行业对标）
        ├── 流失预警与增购信号（多维信号矩阵 + 综合健康度评分）
        └── 价值实现追踪（购买目标回溯 + 达成评估 + 改进建议）
```

## 二、角色与场景定义

### 2.1 销售洞察的目标用户与场景

| 角色 | 场景 | 频率 | 核心诉求 |
|------|------|------|---------|
| AE/销售代表 | 首次拜访前准备 | 每次拜访前 | 10分钟内掌握客户全貌，制定切入策略 |
| AE/销售代表 | 商机推进中 | 每周 | 了解商机停滞原因，找到突破口 |

| 销售VP | 大客户战略规划 | 每月 | 评估大客户的增长潜力和竞争态势 |

| 角色 | 场景 | 频率 | 核心诉求 |
|------|------|------|---------|

## 三、销售洞察 — 详细设计

### 3.1 维度一：行业深度定位

#### 3.1.0 产品价值

**销售视角**：

| 价值点 | 没有行业定位时 | 有了行业定位后 |
|--------|--------------|--------------|
| 话术准备 | "我们服务很多制造业客户" | "我们服务了3家UPS电源行业客户，包括XX和YY" |
| 案例匹配 | 只能按一级行业模糊匹配，案例说服力弱 | 按三级行业精准匹配，客户认为"你懂我的行业" |
| 策略选择 | 凭经验猜客户关注什么 | 行业快速增长期→强调可扩展性；成熟期→强调降本增效 |

**CSM视角**：

| 价值点 | 没有行业定位时 | 有了行业定位后 |
|--------|--------------|--------------|
| 同行业使用对标 | "你们使用率偏低"（客户不服气） | "同行业标杆客户使用率85%，你们33%"（有数据支撑） |
| 续约风险评估 | 无法判断行业因素对续约的影响 | 行业下行+使用率下降=高流失风险，提前介入 |
| 最佳实践推荐 | 通用建议，客户觉得不贴合 | "体外诊断行业客户通常启用审批流管理合规，建议你们也开启" |

#### 3.1.1 三级行业分类

**数据来源**：统一通过网络检索 + AI 推断获取，不依赖工商数据，不改 CRM 字段结构。

| 层级 | 示例 | 数据来源 | 洞察价值 |
|------|------|---------|---------|
| 一级行业 | 制造业 | CRM `industryId` 字段（如有）；无则由网络检索推断 | 粗分类，用于筛选和分组 |
| 二级行业 | 电气设备制造 | 网络检索 + AI 推断 | 同行业对标的基础粒度 |
| 三级行业 | UPS电源及配电系统 | 网络检索 + AI 推断 | 精确定位客户在产业链中的位置 |

**分析逻辑**：

```
Step 1: 构造搜索查询
  输入：客户名称 + CRM中的一级行业（如有）
  搜索关键词："[客户名称] 行业 主营业务 产业链 细分领域"

Step 2: AI 从搜索结果中提取行业信息
  提取内容：
  - 二级行业归属（如"电气设备制造"）
  - 三级行业归属（如"UPS电源及配电系统"）
  - 在产业链中的位置（上游原材料/中游制造/下游渠道）
  - 核心业务描述（1-2句话）

Step 3: 置信度评估
  - 高：多个搜索结果一致指向同一细分行业
  - 中：搜索结果有一定指向但不完全一致
  - 低：搜索结果模糊或客户业务跨多个行业

Step 4: 输出
  格式："该客户属于[一级]-[二级]-[三级]，主要从事[核心业务描述]，
        在产业链中处于[位置]环节。"
  置信度低时追加："（基于有限公开信息推断，建议销售确认）"
```

**存储方式**：行业定位结果存储在洞察结果 JSON 中，不回写到客户实体的 `industryId` 字段。每次洞察时重新检索，确保信息时效性。

**输出 JSON 结构**：
```json
{
  "industryLevel1": "制造业",
  "industryLevel2": "电气设备制造",
  "industryLevel3": "UPS电源及配电系统",
  "positionInChain": "中游制造",
  "coreBusinessDesc": "专注于不间断电源系统及配电解决方案的研发与制造，服务于数据中心、工业制造等领域",
  "confidence": "high"
}
```

#### 3.1.2 行业排名评估

**数据来源**：CRM 内部字段 + 网络检索补充。

| 数据 | 来源 | 可用性 |
|------|------|--------|
| 年销售额 | CRM `annualRevenue` | 可能为空，填充率不确定 |
| 员工规模 | CRM `employeeNumber` | 单选字段，有区间值 |
| 上市公司财报 | 网络检索 | 仅上市公司可获取 |
| 行业排名报告 | 网络检索 | 部分行业有公开排名 |

**分析逻辑**：

```
Step 1: 优先使用 CRM 数据
  - annualRevenue 有值 → 直接使用
  - annualRevenue 为空 → 进入 Step 2

Step 2: 网络检索补充
  搜索关键词："[客户名称] 营收 规模 排名"
  AI 从搜索结果中提取：年营收数据、员工规模、行业排名信息

Step 3: 排名区间判定
  基于营收 + 员工规模，结合网络检索到的行业排名信息，
  输出排名区间（不输出精确排名）：
  - 头部企业（行业领军）
  - 中上企业（行业主力）
  - 腰部企业（行业中等）
  - 尾部企业（行业小型）

Step 4: 输出
  格式："该客户年营收约¥XX亿，员工规模XX人，
        在[三级行业]中属于[排名区间]企业。"
  数据不足时："（营收数据基于公开信息估算，仅供参考）"
```

#### 3.1.3 行业增长态势

**数据来源**：完全依赖网络检索。

**分析逻辑**：

```
Step 1: 构造搜索查询
  搜索关键词："[二级行业] 行业趋势 市场规模 增长率 2025/2026"

Step 2: AI 提取并结构化
  输出结构：
  {
    "industryPhase": "快速增长期",
    "growthRate": "15-20%",
    "keyDrivers": ["政策利好：新能源补贴延续", "技术驱动：AI+制造"],
    "keyRisks": ["原材料价格波动", "国际贸易摩擦"],
    "salesImplication": "客户处于扩张期，更愿意投入新系统，建议以'支撑业务快速扩张'为切入点",
    "csmImplication": "行业上行期客户预算充足，是推动深度采纳和增购的好时机"
  }

Step 3: 行业阶段对销售和CSM策略的影响

  | 行业阶段 | 销售策略建议 | CSM策略建议 |
  |---------|------------|------------|
  | 快速增长期 | 强调可扩展性、快速部署、支撑业务增长 | 推动深度采纳，抓住增购窗口 |
  | 成熟期 | 强调ROI、自动化、数据驱动决策 | 强化价值证明，用数据说话 |
  | 衰退期 | 强调性价比、替换旧系统迁移成本低 | 提前预警续约风险，准备保续方案 |
```

**风险说明**：AI 基于网络搜索的行业判断可能不准确，特别是非常细分的行业。输出中统一标注"基于公开信息分析，仅供参考"。

### 3.2 维度二：客户关系网络分析

#### 3.2.0 产品价值

**销售视角**：

| 子项 | 核心价值 | 没有这个能力时 | 有了这个能力后 |
|------|---------|--------------|--------------|
| 集团内关联 | 集团拓展 + 避免撞车 | 不知道集团下有哪些子公司，也不知道哪些已被同事覆盖 | 一眼看到集团树，哪些已成交、哪些未覆盖、谁在负责 |
| 上下游关系 | 转介绍获客 + 产业链打法 | 不知道客户的供应商恰好是我们的客户，错过转介绍机会 | 直接提示"供应商XX是我们的客户，负责人张三，可请求转介绍" |
| 同行业网络 | 案例说服 + 定价参考 + 赢单复制 | "我们有制造业客户"说服力弱 | "同行业12家客户，平均客单价¥80万"——用数据说话 |

**CSM视角**：

| 子项 | 核心价值 | 没有这个能力时 | 有了这个能力后 |
|------|---------|--------------|--------------|
| 集团内关联 | 集团推广 + 连锁预警 | 不知道集团下还有哪些分公司可以推广 | 集团树标注健康度，一家预警时提示"同集团其他N家需关注" |
| 上下游关系 | 生态价值故事 + 增购场景 | 续约时只能讲功能层面的价值 | "你的供应商和下游客户都在用我们的系统，启用协同模块可以提升对接效率" |
| 同行业网络 | 使用对标 + 功能推荐 + 健康度基准 | CSM说"使用率偏低"，客户不服气 | "同行业标杆使用率85%，你们33%"——用同行数据施压 |

#### 3.2.1 集团内关联分析

**数据来源**：CRM `account.parentAccountId`（自关联）+ 客户名称模糊匹配补充。

**分析逻辑**：

```
Step 1: 构建集团树
  - 从当前客户出发，向上递归查 parentAccountId，找到集团顶层
  - 再从顶层向下递归，找到所有子公司
  - 如果 parentAccountId 为空，进入 Step 2

Step 2: 名称模糊匹配补充（当 parentAccountId 为空时）
  - 提取客户名称中的集团关键词（如"伊顿"）
  - 在 CRM 客户库中模糊搜索包含该关键词的其他客户
  - AI 判断是否属于同一集团（排除同名不同集团的情况）
  - 标注为"疑似关联"，与确认的 parentAccountId 关联区分

Step 3: 统计集团内业务数据
  对集团树中每个节点，查询：
  - 商机数量和金额（按阶段分）
  - 已成交订单金额
  - 最近活动记录时间
  - 负责人

Step 4: 识别拓展机会
  - 有客户记录但无商机 → "未开发"
  - 有商机但长期无进展 → "停滞"
  - 名称匹配但无客户记录 → "待录入"
```

**输出格式**：
```
集团结构：伊顿集团（共5家关联公司）
├── 伊顿（中国）投资有限公司 [总部]
│   负责人：罗奇 | 已成交 ¥500万 | 3个在跟商机（¥687万）
├── 伊顿电气（常州）有限公司
│   负责人：罗奇 | 已成交 ¥40万 | 1个在跟商机
├── 伊顿电气（平顶山）有限公司
│   负责人：无 | 无商机 ★ 建议拓展（年营收约¥XX亿）
├── 山特电子（深圳）有限公司 [疑似关联]
│   负责人：官治昊 | 已成交 ¥3万
└── 伊顿液压（上海）有限公司
    无客户记录 ★ 建议录入
```

#### 3.2.2 供应商/客户关系挖掘

**数据来源**：网络检索 + CRM 客户库交叉匹配。

**分析逻辑**：

```
Step 1: 网络检索客户的上下游关系
  搜索关键词："[客户名称] 供应商 客户 合作伙伴 产业链"
  AI 从搜索结果中提取：
  - 主要供应商列表
  - 主要客户/下游列表
  - 合作伙伴列表

Step 2: 与 CRM 客户库交叉匹配
  将提取出的企业名称，在 CRM 客户库中精确+模糊匹配
  匹配结果分三类：
  - 已在 CRM 中且有商机/订单 → "已合作"
  - 已在 CRM 中但无商机 → "已录入未开发"
  - 不在 CRM 中 → "潜在客户"

Step 3: 识别商业机会
  - 转介绍机会：上下游企业是我们的已成交客户 → 请其引荐
  - 生态拓展：上下游企业不在CRM中 → 标记为潜在客户
  - 产业链打法：上下游中多家是我们的客户 → 打"产业链协同"牌
```

**输出格式**：
```
客户上下游关系：伊顿（中国）

供应商（上游）：
├── 国轩高科 → CRM中已有，已成交客户（负责人：张三）★ 可请求转介绍
├── 施耐德电气 → CRM中已有，2个在跟商机
└── 台达电子 → 不在CRM中 ★ 潜在客户

客户（下游）：
├── 中国移动数据中心 → CRM中已有，已成交客户
├── 阿里云 → CRM中已有，无商机 ★ 建议拓展
└── 华为数据中心 → 不在CRM中 ★ 潜在客户
```

**风险说明**：上下游关系完全依赖网络检索+AI推断，准确性有限。输出中标注"基于公开信息推断，仅供参考"。

#### 3.2.3 同行业客户网络

**数据来源**：CRM 内部数据（account + opportunity + order），结合 3.1 的二级行业定位结果。

> 同行业对标在销售洞察和CSM洞察中都会用到，设计为共享的"同行业对标引擎"。

**分析逻辑**：

```
Step 1: 确定对标池
  - 优先用二级行业（来自 3.1 的洞察结果）筛选同行业客户
  - 如果二级行业匹配的客户 < 5 家，降级到一级行业
  - 排除当前客户自身

Step 2: 统计同行业客户的成交模式
  对对标池中的客户，聚合计算：
  - 平均客单价（totalWonOpportunityAmount / totalWonOpportunities）
  - 最常购买的产品线（order→orderProduct→product 聚合）
  - 平均销售周期（opportunity 的创建到结单天数）
  - 平均商机赢率

Step 3: 与当前客户对比
  - 当前客户的客单价 vs 同行业均值
  - 当前客户已购产品线 vs 同行业最常购买的产品线
  - 当前客户的销售周期 vs 同行业均值

Step 4: 输出机会和建议
  - 产品线差距："同行业68%客户使用了服务云，该客户未购买"
  - 客单价差距："同行业平均客单价¥80万，该客户仅¥30万，存在增购空间"
  - 赢单经验："同行业赢单商机的共性是XX，建议参考"
```

**输出格式**：
```
同行业对标：电气设备制造（共12家客户）

| 指标 | 该客户 | 同行业均值 | 差距 |
|------|--------|-----------|------|
| 客单价 | ¥30万 | ¥80万 | -62% ★ 增购空间大 |
| 已购产品线 | 销售云 | 销售云+服务云 | 缺服务云 ★ |
| 销售周期 | 90天 | 75天 | +20% 偏慢 |
```

#### 3.3.2 商机停滞预警

**数据来源**：`opportunity.stageUpdatedAt`（阶段更新时间）、`opportunity.standardPeriod`（标准周期）、`activityrecord`（活动记录）。

**分析逻辑**：

```
Step 1: 筛选在跟商机
  status = 进行中

Step 2: 计算停留天数
  停留天数 = 当前日期 - stageUpdatedAt

Step 3: 判定停滞等级
  - 正常：停留天数 ≤ standardPeriod
  - 停滞：停留天数 > standardPeriod × 1.5
  - 严重停滞：停留天数 > standardPeriod × 2
  - standardPeriod 为空时，用同行业该阶段的平均停留天数作为基准

Step 4: 按风险排序
  先按停滞等级降序，再按金额降序

Step 5: AI 分析停滞原因（结合活动记录）
  查询该商机最近的活动记录，AI推断可能的停滞原因：
  - 最近30天无活动 → "跟进中断"
  - 有活动但阶段未推进 → "客户内部决策卡点"
  - 活动记录中提到竞对 → "竞争对手介入"
```

**输出格式**：

**关键前提**：CSM洞察的核心数据依赖是 **用户行为日志**，CRM当前不具备。需要平台侧提供以下能力：

```
  人均日操作数 = SUM(operation_count) / COUNT(DISTINCT active_user)

  - 平稳：波动在 ±10% 以内

  - 骤降：任意一周 WAU < 前一周 × 0.7（单周暴跌30%+）

  | 任意 | <40% | 🔴 预警 |
```

#### 4.1.2 使用集中度分析

```

  按 total_operations 降序排列

  - 姓名、部门、职务（从 user/contact 关联）

  - 最近登录时间
  - 主要使用的模块
```

**分析逻辑**：

```

  如果无 License 粒度数据，默认按产品线（销售云/服务云/营销云）推导

  从 user_activity_daily.modules_used 中提取

  模块采纳率 = 模块MAU / 该模块License数 × 100%
  如果无模块级License数据，用总License数作为分母
```

#### 4.2.2 功能深度分析

**数据来源**：`user_activity_daily`（操作级别统计）+ 功能启用配置。

> 在已采纳的模块内，进一步分析核心功能的使用深度。不是所有功能都分析，只分析每个模块的 **Top 5 核心功能**。

**分析逻辑**：

```
Step 1: 定义每个模块的核心功能清单
  由产品侧预定义，例如：
  商机管理模块的核心功能：
  - 商机创建/编辑
  - 阶段推进
  - 赢单/丢单关闭
  - 商机预测
  - 商机评分

  每个功能的周均使用次数

Step 3: 与同行业对标（复用 3.2.3 同行业对标引擎）
  计算同行业客户中该功能的平均使用频次
  差距 = (客户频次 - 同行业均值) / 同行业均值

Step 4: 功能深度评分
  每个功能按使用频次与同行业均值的比值打分：
  - ≥100% 同行业均值 → 10分

  - 1%-49% → 3分
  - 0%（未使用）→ 0分
  模块深度评分 = 各功能评分之和 / 满分 × 100

Step 5: 识别"已启用但未深度使用"的功能
  功能已有操作记录但频次远低于同行业均值（<30%）→ 标记为"浅层使用"
```

#### 4.4.2 目标达成评估

```sql
  INDEX idx_tenant_user_date (tenant_id, user_id, stat_date)
);
```

**数据写入方式**：
- 方案A（推荐）：平台侧在用户操作时异步写入，按天聚合
- 方案B：从平台操作日志中定时ETL，每日凌晨聚合前一天数据

**存储估算**：
- 假设平均每租户50个活跃用户，1000个租户
- 每日数据量：50 × 1000 = 5万行
- 每年数据量：5万 × 365 ≈ 1800万行
- 建议保留2年数据，超过2年归档

## 七、产品设计 — 递归分析引擎与交互体系

> 前六章定义了"分析什么"和"怎么分析"，本章从产品视角定义"怎么呈现"和"怎么用"。
> 核心设计理念：洞察不是报告，而是**行动驱动器**——每一层分析的输出都指向下一步行动。

### 7.1 产品形态总览

#### 7.1.1 入口与载体

| 载体 | 说明 | 交付期次 |
|------|------|---------|
| 客户详情页-洞察Tab | 主入口，销售/CSM在客户详情页内查看洞察 | 第一期 |
| CSM工作台 | 独立页面，按健康度排序批量管理客户 | 第三期 |
| 消息推送 | 关键信号变化时推送通知（流失预警/增购信号） | 第三期 |
| 移动端卡片 | 拜访前快速查看洞察摘要 | 第四期（可选） |

#### 7.1.2 角色自动切换

```
用户打开客户洞察Tab时：
├── 系统判断当前用户角色
│   ├── 角色=销售/AE/销售经理 → 默认展示"销售洞察"视图
│   └── 角色=CSM/客户成功经理 → 默认展示"CSM洞察"视图

```

#### 7.1.3 生成策略

| 数据类型 | 生成方式 | 缓存策略 | 刷新方式 |
|---------|---------|---------|---------|
| CRM内部数据维度（商机/决策链/合同/活动） | 定时预生成（每日凌晨）+ 事件触发增量更新 | 24小时 | 商机变更/活动新增时自动刷新 |
| 网络检索维度（行业/上下游/竞对） | 用户触发 + 结果缓存 | 7天 | 用户点击"刷新"按钮 |
| 使用行为数据（WAU/采纳率） | 定时预生成（每日凌晨） | 24小时 | 每日自动刷新 |
| 综合策略/行动计划 | 依赖数据更新后自动重新生成 | 跟随数据层 | 任一数据层刷新后重新生成 |

**首次无数据时**：页面显示"生成洞察"按钮，用户点击后触发全量生成，渐进式加载各卡片。

### 7.2 销售洞察 — 递归分析链产品设计

#### 7.2.1 递归推导链

销售的分析逻辑是**由外向内**——从不了解客户到制定精准策略：

```
第一层：客户身份识别（输入：客户名称）
  "这个客户是干什么的"
       │
       ├──→ 第二层：行业环境扫描（输入：第一层的三级行业）
       │    "这个行业现在怎么样"
       │
       ├──→ 第三层：客户定位评估（输入：第一层+第二层+CRM数据）
       │    "这个客户在行业里什么位置"
       │
       └──→ 第四层：CRM同行业数据关联（输入：第一层的行业定位）
            "同行业客户在我们这里买了什么"
                 │
                 └──→ 第五层：销售策略生成（输入：前四层全部输出）
```

#### 7.2.3 销售洞察DAG编排

```
                    第一层：客户身份识别
                   ╱          │          ╲
                 ╱            │            ╲
    第二层：行业环境扫描   第三层：客户定位   第四层：CRM同行业数据
         （依赖行业）     （依赖行业+CRM）   （依赖行业）
                 ╲            │            ╱
                   ╲          │          ╱
                    第五层：销售策略生成
                   （依赖前四层全部输出）
```

| 规则 | 说明 |
|------|------|
| 第一层必须先完成 | 后续所有层依赖行业定位结果 |
| 第二、三、四层可并行 | 三者互不依赖，可同时执行 |
| 第五层等待全部完成 | 需要前四层的全部输出作为输入 |
| 部分失败不阻塞 | 如网络检索失败，跳过该层，用已有数据生成策略 |
| 渐进式呈现 | 每层完成后立即展示，不等全部完成 |

**渐进式加载时序**：

```
T+0s:  显示骨架屏，提示"正在分析..."
T+3s:  第一层完成 → 客户身份卡片渲染
T+5s:  第四层完成 → 同行业客户网络卡片渲染（纯CRM数据，最快）
T+8s:  第二层完成 → 行业环境卡片渲染
T+10s: 第三层完成 → 客户定位卡片渲染
T+12s: 第五层完成 → 销售策略卡片渲染（最后出现）

整体耗时：首次约12-15秒 | 缓存命中<2秒
```


### 7.3 CSM洞察 — 递归分析链产品设计

#### 7.3.1 递归推导链

CSM的分析逻辑与销售相反，是**由内向外**——从合同出发，逐层深入到使用细节，最终生成行动计划：

```
第一层：合同与续约基线（输入：accountId）
  "这个客户的合同什么状态"
       │
       ├──→ 第二层：使用健康度扫描（输入：第一层的已购产品范围）
       │    "客户在用我们的产品吗"
       │         │
       │         └──→ 第三层：功能采纳差距定位（输入：第二层使用数据+同行业对标）
       │              "用了哪些功能、哪些没用"
       │                   │
       │                   └──→ 第四层：归因分析（输入：第三层低采纳功能列表）
       │                        "为什么没用好"
       │
       ├──→ 第五层：价值达成评估（输入：赢单记录+使用数据）  ← 与第二/三层并行
       │    "当初买的时候想解决什么，解决了吗"
       │
       └──→ 流失预警信号检测（输入：合同到期+活动记录）      ← 与第二/五层并行
            "有没有流失风险信号"
                 │
                 └──→ 第六层：CSM行动计划生成（输入：前五层+流失预警全部输出）
                      "所以我现在应该做什么"
```

**第四层：归因分析**

> CSM递归链中最关键的一层——不只告诉"哪里没用好"，而是分析"为什么没用好"。

```
输入：第三层的低采纳功能列表 + CRM活动记录 + 功能配置状态
执行：对每个低采纳功能，按决策树归因：

  功能采纳率低
  ├── 功能是否已配置？
  │   ├── 未配置 → 原因A：功能未上线
  │   │   可能：实施时未包含 / 客户不知道有此功能
  │   │   建议：安排功能配置+培训
  │   └── 已配置 →
  │       ├── 有用户使用过但频次极低？
  │       │   ├── 是 → 原因B：体验不佳/流程不匹配
  │       │   │   建议：1对1辅导，了解使用障碍
  │       │   └── 否（从未使用）→ 原因C：用户不知道
  │       │       建议：安排功能演示
  │       └── 使用量曾经高但近期下降？
  │           └── 是 → 原因D：替代方案/需求变化
  │               建议：了解客户是否在用其他工具替代

  同时：AI从活动记录文本中搜索与该功能相关的客户反馈
  关键词："不好用""太复杂""Excel""其他系统"
  如果找到 → 补充归因证据

输出：
  每个低采纳功能的：
  ├── 归因类型（A/B/C/D）
  ├── 证据（配置状态/使用记录/活动记录文本）
  ├── 可能原因
  ├── 建议行动
  └── 预期效果
```

#### 7.3.3 CSM洞察DAG编排

```
              第一层：合同与续约基线
             ╱          │          ╲
           ╱            │            ╲
第二层：使用健康度   第五层：价值达成    流失预警信号检测
   （依赖已购产品）  （依赖赢单记录）   （依赖合同+活动）
         │
         ▼
第三层：功能采纳差距
   （依赖使用数据+同行业）
         │
         ▼
第四层：归因分析
   （依赖低采纳功能列表）
         ╲               │            ╱
           ╲             │          ╱
            第六层：CSM行动计划生成
           （依赖前五层+流失预警全部输出）
```

| 层 | 依赖 | 可并行 |
|---|------|--------|
| 第一层 | 无 | 最先执行 |
| 第二层 | 第一层（已购产品范围） | 与第五层、流失预警并行 |
| 第五层 | 第一层（赢单商机） | 与第二层、流失预警并行 |
| 流失预警 | 第一层（合同到期） | 与第二层、第五层并行 |
| 第三层 | 第二层（使用数据） | 第二层完成后立即执行 |
| 第四层 | 第三层（低采纳列表） | 第三层完成后立即执行 |
| 第六层 | 全部 | 最后执行 |

**渐进式加载时序**：

```
T+0s:   骨架屏
T+1s:   第一层完成 → 合同基线卡片渲染
T+3s:   流失预警完成 → 健康度评分渲染（纯CRM数据，快）
T+5s:   第五层完成 → 价值达成卡片渲染
T+6s:   第二层完成 → 使用健康度卡片渲染
T+8s:   第三层完成 → 功能采纳差距卡片渲染
T+10s:  第四层完成 → 归因分析卡片渲染
T+12s:  第六层完成 → CSM行动计划渲染（最后，最重要）

整体耗时：首次约10-12秒 | 缓存命中<2秒
（CSM洞察比销售洞察快，因为不依赖网络检索）
```

### 7.5 行动可操作化设计

> 洞察的最终价值不是"看"，而是"做"。每个行动建议都可一键转化为CRM操作。

#### 7.5.1 一键操作映射

| 行动建议 | 一键操作 | 预填内容 |
|---------|---------|---------|
| 安排拜访XX | → 创建活动记录 | 类型=拜访，联系人=XX，备注=洞察建议内容 |
| 创建续约商机 | → 创建商机 | 客户=当前客户，类型=续约，金额=合同金额，关闭日期=合同到期日 |
| 准备增购方案 | → 创建商机 | 客户=当前客户，产品=推荐产品，金额=预估客单价 |
| 安排培训 | → 创建活动记录 | 类型=培训，备注=培训内容和目标 |
| 安排演示 | → 创建活动记录 | 类型=演示，备注=演示功能和预期效果 |
| 创建任务 | → 创建任务 | 标题=行动描述，截止日期=建议时间，负责人=当前用户 |

#### 7.5.2 行动执行追踪

```
行动建议创建CRM记录后：
├── 洞察页面标记该行动为"已创建"（✅ 替代 □）
├── 关联的CRM记录ID存储在洞察结果中
├── 下次打开洞察时，检查关联记录的状态：
│   ├── 活动已完成 → 标记"已执行"
│   ├── 商机已推进 → 标记"进行中"
│   └── 超过建议时间未执行 → 标记"逾期"⚠️
└── CSM工作台可按"行动执行率"排序客户
```

### 7.9 权限与数据安全

| 场景 | 权限规则 |
|------|---------|
| 查看自己负责客户的洞察 | 遵循account的数据权限（ownerId + 共享规则） |
| 同行业对标数据 | 只展示聚合统计值（均值/百分比），不暴露具体客户名称和金额 |
| 集团树中其他子公司 | 展示公司名称和负责人，金额数据遵循各子公司的数据权限 |
| CSM洞察中的用户行为数据 | 只展示聚合指标（WAU/采纳率），不暴露具体用户操作明细 |
| 洞察结果导出 | 需要额外权限控制，防止批量导出客户数据 |
| 竞品对比信息 | 标注"基于公开信息，仅供参考"，不暴露内部定价策略 |
