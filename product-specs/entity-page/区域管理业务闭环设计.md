# 区域管理业务闭环设计

> 日期：2026-04-29
> 目标：基于老系统区域管理的完整业务流程，设计新系统的最小闭环实现
> 原则：保证业务流程完整可用，不追求老系统的全部功能（343 个文件），聚焦核心链路

---

## 一、老系统区域管理的完整业务流程

```
管理员配置阶段：
  1. 创建区域模型（TerritoryModel）— 定义一套区域管理方案
  2. 在模型下创建区域树（Territory）— 华北→北京→朝阳
  3. 配置区域覆盖维度（Coverage）— 华北覆盖：省份=北京/天津/河北
  4. 配置区域成员 — 管理员 + 普通成员
  5. 配置区域规则（TerritoryRule）— 省份=北京 → 分配到华北区域
  6. 配置区域关联实体（WorkObject）— 该模型管理 account + lead
  7. 配置区域公海规则 — 回收天数/领取模式/限额
  8. 配置区域实体权限（SourceObject）— 成员对 account 只读/读写

数据运行阶段：
  9.  数据创建 → 规则引擎自动匹配区域 → 分配到对应区域
  10. 数据进入区域公海 → 等待领取
  11. 成员领取/管理员分配 → 数据归属销售
  12. 销售跟进 → 超时回收 → 回到区域公海
  13. 销售退回 → 回到区域公海
  14. 管理员换组 → 数据从一个区域移到另一个区域
  15. 管理员废弃 → 数据标记为废弃
  16. 管理员恢复 → 废弃数据恢复
  17. 分配日志记录 → 所有操作留痕
```

## 二、新系统最小闭环范围

从老系统的 17 个环节中，筛选出业务闭环必须的：

```
必须实现（没有就不能用）：
  ✅ 1. 区域树管理（创建/编辑/层级/状态）
  ✅ 2. 区域成员管理（管理员/成员）— 已有 poolMember
  ✅ 3. 区域覆盖维度（按什么维度划分区域）
  ✅ 4. 区域规则匹配（数据自动分配到区域）
  ✅ 5. 区域公海配置（回收天数/领取模式/限额）
  ✅ 6. 区域公海操作（领取/退回/分配/转移）— 已有 PoolOperationService
  ✅ 7. 区域公海回收 — 已有 autoRecycle
  ✅ 8. 通用区域（未匹配数据的兜底）
  ✅ 9. 换组（数据从一个区域移到另一个区域）
  ✅ 10. 前端区域树管理页

可以后做：
  · 区域模型（多套方案）— 大多数客户只用一套，P2
  · 审批流 — 接入工作流引擎，P2
  · 废弃/恢复 — 低频操作，P2
  · 分配日志 — 审计需要但不阻断业务，P1
  · 规则预演 — 高级功能，P2
  · 缓存体系 — 数据量小时不需要，P2
```

### 3.2 territoryCoverage（区域覆盖）— 新增实体

定义区域覆盖哪些维度值。如"华北区域覆盖省份=北京/天津/河北"。

```
territoryCoverage
┌──────────────────────────────────────────────────────────────┐
│ # │ apiKey           │ label      │ itemType │ dbColumn      │
│───┼──────────────────┼────────────┼──────────┼───────────────│
│ 1 │ territoryId      │ 所属区域    │ 10(REFER)│ dbc_bigint1   │
│ 2 │ dimensionField   │ 维度字段    │ 1(TEXT)  │ dbc_varchar1  │
│   │                  │ 如 fState   │          │               │
│ 3 │ dimensionValue   │ 维度值      │ 1(TEXT)  │ dbc_varchar2  │
│   │                  │ 如 北京     │          │               │
│ 4 │ dimensionEntity  │ 适用实体    │ 1(TEXT)  │ dbc_varchar3  │
│   │                  │ account/lead│          │               │
└──────────────────────────────────────────────────────────────┘

示例数据：
  华北区域(id=100):
    { territoryId=100, dimensionField='fState', dimensionValue='北京', dimensionEntity='account' }
    { territoryId=100, dimensionField='fState', dimensionValue='天津', dimensionEntity='account' }
    { territoryId=100, dimensionField='fState', dimensionValue='河北', dimensionEntity='account' }
    { territoryId=100, dimensionField='fState', dimensionValue='北京', dimensionEntity='lead' }
    ...
```

### 3.3 实体关系

```
territory（区域）
  ├── parentTerritoryId → territory.id（树形层级）
  ├── poolMember（成员）— poolEntity='territory', poolId=territory.id
  ├── poolDepart（部门范围）— poolEntity='territory', poolId=territory.id
  └── territoryCoverage（覆盖维度）— territoryId=territory.id

account（客户）
  ├── territoryHighSeaId → territory.id（所属区域公海）
  └── highSeaId → highSea.id（所属普通公海，与区域互斥）

lead（线索）
  ├── territoryLeadHighSeaId → territory.id（所属区域线索公海）
  └── leadHighSeaId → leadHighSea.id（所属普通线索公海，与区域互斥）
```

```java
    void move(long id, Long newParentId)

    Long getDefaultTerritoryId()
}
```

### 4.2 TerritoryRuleEngine — 区域规则匹配

```java
@Service
public class TerritoryRuleEngine {

    /**
     * 匹配数据到区域。
     * 按覆盖维度匹配：遍历所有区域的 territoryCoverage，
     * 检查数据的维度字段值是否在覆盖范围内。
     *
     * @param entityApiKey "account" / "lead"
     * @param data 数据字段 Map
     * @return 匹配到的 territoryId，未匹配返回 defaultTerritoryId
     */
    Long match(String entityApiKey, Map<String, Object> data) {
        // 1. 查所有启用的区域 + 覆盖维度
        // 2. 遍历区域，检查数据的维度字段值
        //    如：data.fState='北京' → 匹配到华北区域
        // 3. 第一个匹配成功的区域生效（按 territoryRank 排序）
        // 4. 都不匹配 → 返回通用区域（type=1）
        // 5. 无通用区域 → 返回 null
    }
}
```

## 五、API 设计

```
区域管理 API：
  GET    /territory/tree                    查询区域树
  POST   /territory                         创建区域
  PUT    /territory/{id}                    更新区域
  DELETE /territory/{id}                    删除区域
  PUT    /territory/{id}/move               移动区域（改变父节点）

区域覆盖 API：
  GET    /territory/{id}/coverage           查询区域覆盖维度
  POST   /territory/{id}/coverage           添加覆盖维度值
  DELETE /territory/{id}/coverage/{covId}   删除覆盖维度值

区域公海配置 API：
  GET    /territory/{id}/highsea-config     查询区域公海配置
  PUT    /territory/{id}/highsea-config     更新区域公海配置

区域公海操作 API（复用已有）：
  PUT    /entity/data/{entity}/{id}/claim   领取（已有）
  PUT    /entity/data/{entity}/{id}/release 退回（已有）
  PUT    /entity/data/{entity}/{id}/assign  分配（已有）

换组 API：
  PUT    /entity/data/{entity}/{id}/change-territory
  Body: { toTerritoryId: 123 }

区域成员 API（复用已有）：
  GET    /pool/territory/{id}/members       查询成员（已有）
  POST   /pool/territory/{id}/members       添加成员（已有）
  DELETE /pool/territory/{id}/members/{mid}  删除成员（已有）
```

## 七、业务流程闭环验证

```
场景 1：管理员配置区域
  1. 管理员进入区域管理页 → 看到区域树
  2. 点击"新建区域" → 输入名称，选择父区域 → 创建成功
  3. 选中区域 → 配置覆盖维度 → 添加"省份=北京/天津/河北"
  4. 配置成员 → 添加张三(管理员)、李四(成员)
  5. 配置公海 → 开启客户区域公海 → 设置回收天数 30 天
  → ✅ 闭环

场景 2：数据自动进入区域
  1. 销售创建客户 → 省份=北京
  2. DataRoutingService.routeOnCreate → TerritoryRuleEngine.match
  3. 匹配到华北区域 → 华北开启了客户公海
  4. 客户进入华北区域公海 → status=inHighSea
  → ✅ 闭环

场景 3：成员领取区域公海数据
  1. 李四打开华北区域公海数据列表
  2. 看到 status=inHighSea 的客户
  3. 点击"领取" → PoolOperationService.claim
  4. 权限校验：李四是华北区域成员 → 允许
  5. 限额校验：李四持有数 < 50 → 允许
  6. 执行领取 → ownerId=李四, status=claimed
  → ✅ 闭环

场景 4：超时自动回收
  1. 李四领取了客户但 30 天没跟进
  2. HighSeaRecycleTask 扫描 → expireTime < now
  3. 自动回收 → ownerId=null, status=inHighSea
  4. 客户回到华北区域公海
  → ✅ 闭环

场景 5：管理员换组
  1. 张三（华北管理员）发现一个客户应该归华东
  2. 点击"换组" → 选择华东区域
  3. TerritoryChangeService.changeTerritory
  4. 客户的 territoryHighSeaId 改为华东区域 ID
  5. 如果华东开启了公海 → 客户进入华东公海
  → ✅ 闭环

场景 6：未匹配数据进入通用区域
  1. 销售创建客户 → 省份=西藏（没有区域覆盖西藏）
  2. TerritoryRuleEngine.match → 所有区域都不匹配
  3. 返回通用区域（type=1）
  4. 如果通用区域开启了公海 → 进入通用区域公海
  5. 如果通用区域未开启公海 → 走普通公海匹配
  → ✅ 闭环
```
